# High-Performance Computer Architecture (HPCA): Course Overview

## Introduction
The evolution of computer architecture is a continuous battle against physical limits—power dissipation, the speed of light, and the immense latency gap between processors and memory. As the free lunch of Moore's Law and Dennard Scaling ended, architects could no longer simply increase clock speeds. Instead, they had to rely on radical architectural innovations to extract hidden parallelism and mask memory latency.

This course explores **High-Performance Computer Architecture (HPCA)** by walking through the mechanisms that transform a simple sequential processor into a chaotic, highly parallel, and aggressively speculative dataflow engine—all while maintaining the strict illusion of sequential execution for the programmer. By the end of this course, you will understand the hardware-software contracts and the brilliant tradeoffs that power modern CPUs.

---

## Core Themes and Conceptual Framework

### 1. Pipelining, Prediction, and the Quest for Steady State (Modules 1-4)
The foundation of processor performance is governed by the **Iron Law**: `Time/Program = Instructions × Cycles/Instruction (CPI) × Time/Cycle`. However, pushing limits is constrained by **Amdahl's Law**, which dictates that overall speedup is bottlenecked by the strictly sequential parts of a program, leading to diminishing returns on parallelization.

To drive CPI down to 1, processors use **Pipelining**—overlapping instruction execution much like a factory assembly line. However, pipelines are constantly threatened by structural, data, and control hazards.
* **Branch Prediction & Function Returns:** Because pipelines are so deep, waiting to resolve a branch condition introduces massive stalls. Processors act like a fast conveyor belt, aggressively guessing the path using history-based predictors (like PShare, GShare, and Tournament predictors) and executing speculatively. To handle dynamic function returns, architectures use a **Return Address Stack (RAS)** with a "wraparound" policy, sacrificing deep call history to accurately predict frequent leaf-function returns. Furthermore, **Pre-decoding** tags instructions in the L1 cache, trading cache capacity (cache bloat) for pipeline decode speed.
* **Predication:** When prediction isn't enough for short, hard-to-predict branches, architectures employ Predication (if-conversion), executing both paths and discarding the wrong one. This trades ALU power and fetch bandwidth for a guaranteed zero-flush penalty. **Tradeoff:** Conditional moves increase register pressure, while Full Predication (e.g., Intel Itanium) causes ISA bloat, increasing code size to save branch penalties.

### 2. Instruction-Level Parallelism (ILP) and Out-of-Order Execution (Modules 5-8)
To push CPI below 1, processors must execute multiple instructions simultaneously (Superscalar). You will learn how the hardware extracts **Instruction-Level Parallelism (ILP)** from seemingly sequential code using **Tomasulo's Algorithm**. 
* **Register Renaming & The Dataflow Engine:** Hardware eliminates "false" dependencies (WAW, WAR) by dynamically mapping architectural registers to a vast pool of hidden physical registers. Instructions wait asynchronously in Reservation Stations and fire out-of-order the exact moment their true dependencies (RAW) arrive via the Common Data Bus (CDB).
* **The Reorder Buffer (ROB) & Memory Disambiguation:** Because out-of-order execution is chaotic, the ROB serves as an "event horizon." Instructions execute speculatively but commit to permanent architectural state in strict, sequential order, guaranteeing precise recovery for exceptions or mispredictions. Memory operations rely on a **Load/Store Queue (LSQ)** to perform memory disambiguation and store-to-load forwarding, ensuring memory dependencies are respected even out of order.
* **Compiler ILP (VLIW):** You will contrast this hardware-heavy approach with **Static Scheduling (VLIW)**. Here, the compiler does the heavy lifting via techniques like Loop Unrolling, Software Pipelining, and Trace Scheduling to bundle independent operations. **Tradeoff:** VLIW trades hardware complexity for compiler complexity and energy efficiency. While perfect for deterministic workloads (DSPs), it suffers from massive code bloat (NOP insertion) and a lack of binary compatibility across hardware generations, ultimately failing for unpredictable, general-purpose computing.

### 3. The Memory Wall: Caches, Translation, and Storage (Modules 9-13)
A fast processor is useless if it is starved for data. Architectures combat the "Memory Wall" using the **Principle of Locality** to build deep memory hierarchies.
* **Cache Dynamics & The 3 C's:** You will study how caches mitigate Compulsory, Capacity, and Conflict misses. You will explore the delicate balancing act of optimizing Average Memory Access Time (AMAT) through Direct-Mapped vs. Set-Associative caches. Advanced techniques like **Prefetching**, **Way Prediction**, and **Non-Blocking Caches** (using MSHRs) are employed to hide cache miss latency.
* **Virtual Memory:** By decoupling the programmer's view of memory from the hardware's fragmented reality, Virtual Memory enables process isolation. You will learn how Multi-Level Page Tables save massive amounts of RAM, and how the **Translation Lookaside Buffer (TLB)** acts as an ultra-fast cache. Concepts like **VIPT (Virtually Indexed, Physically Tagged)** caches are discussed as a crucial mechanism to overlap translation with cache access.
* **Storage & Fault Tolerance:** The course scales out to the physics of DRAM and storage media. As systems scale, hardware failure becomes a mathematical certainty. Architectures design resilient systems using SECDED ECC memory (often utilizing separate parity chips to physically isolate failure domains) and RAID storage. **RAID Tradeoffs:** You will explore the balance between RAID 0's fragility (decreased MTTF for pure performance), RAID 1's cost (50% capacity waste for mirroring), RAID 4's read-modify-write parity bottleneck, RAID 5's distributed parity, and RAID 6's necessity in combating correlated failures and human error during multi-day drive rebuilds.

### 4. The Multi-Core Era: Coherence, Consistency, and Concurrency (Modules 14-18)
Hitting the "Power Wall" forced the industry to pivot from faster single cores to Multi-Processing, Simultaneous Multithreading (SMT), and Many-Core architectures. **Tradeoff:** Due to Pollack's Rule and thermal limits, powering many cores forces a frequency drop across the chip, exacerbating the serial bottlenecks of Amdahl's Law (the Multi-Core Penalty) and creating "Dark Silicon." This is mitigated by **Turbo Boost (DVFS)**, which smartly redirects power from idle cores to active ones while carefully managing localized thermal density hotspots. Furthermore, OSes employ **Topology-Aware Scheduling** to intelligently map threads, balancing the tradeoff between maximizing L3 cache capacity (spreading across sockets) and minimizing communication latency (packing threads), while treating SMT as a fallback for latency hiding rather than true cores.
* **Cache Coherence & False Sharing:** When multiple cores have private L1 caches, sharing data becomes dangerous, introducing a 4th "C" of cache misses (Coherence misses). You will study how hardware implements strict Coherence protocols (like MESI/MOSI/MOESI) using snooping buses or scalable Network-on-Chip (NoC) directory-based systems. To avoid tracking all of main memory, architectures utilize **Partial On-Chip Directories** that scale only with private cache capacity, minimizing hardware cost while introducing directory eviction complexities. Additionally, **Last Level Cache (LLC) Mapping** tradeoffs are explored, contrasting round-robin distribution (perfect capacity balance) against page-based mapping (maximized physical locality).
* **Memory Consistency:** While Coherence governs *one* memory location, Consistency governs the ordering of accesses across *multiple* locations. You will explore how strict Sequential Consistency crushes performance, and how Relaxed Consistency models require programmers to use explicit Memory Barriers (Fences) to prevent out-of-order networks from breaking synchronization logic.
* **Synchronization:** You will dive into the hardware primitives (like Atomic Test-and-Set and Load-Linked/Store-Conditional) required to build software locks and barriers, ensuring safe access to shared resources without destroying performance.

### Conclusion
High-Performance Computer Architecture is a masterclass in indirection, speculation, and managing tradeoffs. By studying how processors guess the future, rename reality, and maintain the illusion of sequential shared memory across chaotic distributed cores, you will gain the fundamental "hardware sympathy" required to write code that truly pushes the limits of modern computing.
