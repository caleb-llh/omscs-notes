## Lesson 1: GPU Compiler Flow

### General Compiler Flow
[![image](https://lowyx.com/assets/posts/gatech/gpu/m10l1_compileflow.png)](https://lowyx.com/assets/posts/gatech/gpu/m10l1_compileflow.png)

A typical compilation process involves:
1. **Frontend:** Converts source code into an Intermediate Representation (IR).
2. **Optimizer:** Performs various hardware-independent optimizations using the IR.
3. **Backend:** Executes machine-specific optimizations and generates the target executable program.

> **Mental Model:** Think of the frontend as a translator converting English to a universal language (Esperanto), the optimizer as an editor refining the universal language, and the backend as a translator converting it into the specific dialect of the target audience (e.g., French or Japanese).

### GPU Compilation Flow
[![image](https://lowyx.com/assets/posts/gatech/gpu/m10l1_compileflowgpu.png)](https://lowyx.com/assets/posts/gatech/gpu/m10l1_compileflowgpu.png)

The GPU compilation process is similar to the standard flow but handles a split codebase: **host code** (CPU) and **device code** (GPU). 
* Both codebases go through parallel compilation processes. 
* For NVIDIA GPUs, device code is compiled into **NV PTX** (Parallel Thread Execution) code. 
* This PTX assembly is then combined with the compiled host code to create a **fat binary**.

[![image](https://lowyx.com/assets/posts/gatech/gpu/m10l1_compileflowgpunvidia.png)](https://lowyx.com/assets/posts/gatech/gpu/m10l1_compileflowgpunvidia.png)

The NVIDIA compiler pipeline involves complex linking steps because NVIDIA utilizes a runtime library on the host alongside numerous other libraries. Since PTX is a virtual Instruction Set Architecture (ISA), it targets a "virtual architecture" rather than a specific physical GPU.

> **Background Context:** The use of PTX allows NVIDIA to maintain forward compatibility. When they release a new GPU architecture, old PTX code can be JIT (Just-In-Time) compiled by the new driver into the new architecture's specific machine code (SASS).

### GPU Compiler Passes
[![image](https://lowyx.com/assets/posts/gatech/gpu/m10l1_compileflowgpunvidiahost.png)](https://lowyx.com/assets/posts/gatech/gpu/m10l1_compileflowgpunvidiahost.png)

In the first open-source full CUDA compilation toolchain (which mirrors NVIDIA's proprietary process), device code generation utilizes **Clang**, performs IR optimization, and concludes with NVPTX code generation.

### Key Tools and Concepts

#### Roles of Clang
[![image](https://lowyx.com/assets/posts/gatech/gpu/m10l1_clang.png)](https://lowyx.com/assets/posts/gatech/gpu/m10l1_clang.png)
Clang acts as the **frontend parser**. Originally designed for C-family languages, it has been extended to support others. Its primary output is the **Abstract Syntax Tree (AST)**. Even a simple function (like computing a delta) can generate a complex AST, where the structure of nodes depends on the AST's specific usage.

#### C++ Preprocessor
[![image](https://lowyx.com/assets/posts/gatech/gpu/m10l1_cpp.png)](https://lowyx.com/assets/posts/gatech/gpu/m10l1_cpp.png)
The preprocessor performs text substitution prior to compilation (e.g., replacing a `#define COURSE_NUMBER 8803` macro directly with `8803`).

#### IR Optimizations
Intermediate Representation (IR) is utilized in the backend compiler process. IR provides a shared abstraction layer across different programming languages and architectures, making it ideal for performing general compiler optimizations. It also carries essential metadata to aid the compiler.

> **Intuition:** Why use IR instead of compiling directly to machine code? If you have $M$ source languages and $N$ target architectures, direct compilation requires $M \times N$ compilers. With an IR, you only need $M$ frontends and $N$ backends, reducing the complexity to $M + N$.

#### PTX vs. SASS
* **PTX (Parallel Thread Execution):** A virtual, architecture-independent ISA. It is eventually translated into machine code. Because it lacks target machine specifics, PTX **does not allocate hardware registers**. Code written in PTX remains identical across different GPU architectures.
* **SASS (Shader Assembly):** A low-level, real, architecture-dependent assembly language. It possesses specific target hardware information, meaning **registers are allocated**. SASS code will change when migrating from one GPU architecture version to a newer one.

> **Common Confusion:** Developers often think PTX is the final machine code that runs on the hardware. It is not! PTX is still a virtual ISA. SASS is the actual binary instructions executed by the streaming multiprocessors (SMs).

#### Fat Binaries
Fat binaries contain executable code for multiple architectures. For GPUs, a fat binary supports multiple GPU hardware versions and includes the host code. At runtime, the fat binary is split:
* The host executes the CPU code.
* The device component is sent to the GPU device driver.
* The device driver often dynamically recompiles the virtual device code (like PTX) into machine-specific instructions (SASS) before execution.

> **Tradeoff:** Fat binaries increase the size of the final executable file significantly because they package multiple versions of the compiled code and PTX. However, this cost is usually worth it for the seamless portability and forward compatibility across different GPU generations.

## Lesson 2: PTX (Parallel Thread Execution)

### PTX Instruction Format
[![image](https://lowyx.com/assets/posts/gatech/gpu/m10l2_ptx.png)](https://lowyx.com/assets/posts/gatech/gpu/m10l2_ptx.png)

PTX instructions take zero to four operands and may include optional predicate information prefixed by an `@` symbol. 
* **Format Example:** `@p opcode d, a, b, c` where `d` is the destination operand and `a, b, c` are source operands.
* **`setp` Instruction:** This is a crucial PTX instruction that writes to two destination predicate registers simultaneously, separated by a vertical bar `|`.
  * *Example:* `setp.lt.s32 p | q, a, b` sets predicate `p` to `True` if `a < b`, and sets `q` to the inverse (NOT `p`).

### Predicated Execution
[![image](https://lowyx.com/assets/posts/gatech/gpu/m10l2_ptx2.png)](https://lowyx.com/assets/posts/gatech/gpu/m10l2_ptx2.png)

GPUs heavily rely on predicated execution to eliminate divergent control-flow branches. Predication is optional.
* Predicate registers must be explicitly declared (e.g., `.reg .pred p, q, r;`), because all PTX registers are virtual and require type specifiers.
* *Example:* An `if (i < n) { j = j + 1; }` block compiles to:
  1. A `setp` instruction evaluating `i < n` and storing the result in predicate `p`.
  2. A predicated addition: `@p add.s32 j, j, 1;`

> **Hypothetical:** If GPUs did not use predicated execution for small branches, every thread in a warp taking a different path would force the hardware to manage complex instruction pointers and heavily serialize execution, destroying SIMT efficiency. Predication lets all threads execute the same instruction, but only those with a `True` predicate actually commit the result.

### Example of PTX Code
[![image](https://lowyx.com/assets/posts/gatech/gpu/m10l2_ptx3.png)](https://lowyx.com/assets/posts/gatech/gpu/m10l2_ptx3.png)

PTX code consists of **directives** and **instructions**. 
* **Directives:** Specify metadata, variables, and setup (e.g., `.target`, `.address_size`, `.func`, or declaring `.reg` and global memory).
* **Statements:** Begin with an optional label and end with a semicolon. Examples include data movement (`mov`), arithmetic (`add`), and memory operations (`ld`). Note that every PTX instruction specifies its data type (e.g., `.f32`, `.s32`).

### Other PTX Instructions
[![image](https://lowyx.com/assets/posts/gatech/gpu/m10l2_ptx4.png)](https://lowyx.com/assets/posts/gatech/gpu/m10l2_ptx4.png)

* **Control Flow:** `bra targ1` (branch to label `targ1`), `call func` (call function `func`), `ret` (return).
* **Synchronization:** `membar`, `fence` (memory barriers/fences operations).
* **Atomics:** Indicated by the `atom` prefix (e.g., `atom.add.f16`). CUDA supports both integer and floating-point atomics, so specifying the data type is critical.
* **Special Registers:** 
  * `%ntid`: Number of threads in a Cooperative Thread Array (CTA).
  * `%tid`: Thread ID.
  * `%sp`: Stack pointer.

*(Note: Refer to the official PTX manual for a complete instruction set).*

## Lesson 3: IR and Basic Blocks

### Intermediate Representation (IR)
[![image](https://lowyx.com/assets/posts/gatech/gpu/m10l3_ir.png)](https://lowyx.com/assets/posts/gatech/gpu/m10l3_ir.png)

IR typically uses "three-address code" formatting (e.g., `A = B op C`). 
* **LLVM IR Example:** `%result = add i32 %a, %b`
  * `%result`: Destination register.
  * `add`: Operation.
  * `i32`: 32-bit integer data type.
  * `%a`, `%b`: Source operands.
* **PTX IR Equivalent:** `add.u32 r1, r2, r3` or `add.s32 r1, r2, r3` (PTX explicitly separates unsigned and signed operations).

### Basic Blocks
A **basic block** is a maximal sequence of instructions with exactly **one entry point** and **one exit point**.
* Because there is only one entry, only the first instruction can be reached from outside the block.
* Because there is only one exit, once the program enters the block, all instructions inside are guaranteed to execute consecutively.
* The final instruction is typically a control-flow instruction (e.g., branch or return).
* Optimizations performed within a basic block are considered **local code optimizations** because the compiler only considers the limited scope inside the block.

> **Mental Model:** A basic block is like a single straight tube of a waterslide. Once you enter at the top, you have no choice but to go all the way down and exit at the bottom. You can't enter from the side, and you can't jump out early.

### Flow Graphs and Basic Block Identification
[![image](https://lowyx.com/assets/posts/gatech/gpu/m10l3_flowgraph.png)](https://lowyx.com/assets/posts/gatech/gpu/m10l3_flowgraph.png)

In a **Control Flow Graph (CFG)**, each node represents a basic block, and the directed edges represent possible execution paths. The graph starts with an entry node (the first program statement).

#### Algorithm to Find Basic Blocks
[![image](https://lowyx.com/assets/posts/gatech/gpu/m10l3_bb.png)](https://lowyx.com/assets/posts/gatech/gpu/m10l3_bb.png)

1. **Identify Leaders:** A "leader" is the first instruction of a basic block. An instruction is a leader if it is:
   * The first instruction in the program.
   * The target of a conditional or unconditional jump/branch.
   * The instruction immediately following a conditional or unconditional jump/branch.
2. **Form Blocks:** A basic block consists of a leader and all subsequent instructions up to (but not including) the next leader.

#### Example of if-else PTX Code
[![image](https://lowyx.com/assets/posts/gatech/gpu/m10l3_egptx.png)](https://lowyx.com/assets/posts/gatech/gpu/m10l3_egptx.png)
[![image](https://lowyx.com/assets/posts/gatech/gpu/m10l3_egptx2.png)](https://lowyx.com/assets/posts/gatech/gpu/m10l3_egptx2.png)

Using the algorithm on a sample PTX `if-else` construct:
* **Basic Block 1:** Evaluates the condition and branches conditionally to Block 2 or Block 3.
* **Basic Block 2 & 3:** The `if` and `else` branches, both ending with an unconditional jump to the end of the statement.
* **Basic Block 4 & 5:** The convergence point (`end_if`) where paths merge. 
By linking the exits of each block to the entries of their targets, we construct the CFG.

## Lesson 4: Data Flow Analysis

### Global Code Optimizations
[![image](https://lowyx.com/assets/posts/gatech/gpu/m10l4_codeopt.png)](https://lowyx.com/assets/posts/gatech/gpu/m10l4_codeopt.png)

While local optimizations happen *within* a basic block, **global code optimization** occurs *across* multiple basic blocks. 
* To perform global optimization, the compiler must track how program properties change across blocks using **data flow analysis**.
* **Crucial Rule:** Any optimization must strictly preserve the original semantics and functionality of the program.

> **Example:** If you have `x = 5` in Block 1, and `y = x + 2` in Block 2, a global optimizer using data flow analysis can figure out that `x` is always 5 when reaching Block 2, and rewrite the second block as `y = 7`.

**Examples of Code Optimizations:**
* **Removing redundant instructions:** Eliminating duplicate computations.
* **Copy propagation:** Identifying and propagating constant values, which often reveals further redundant instructions.
* **Dead code elimination:** Removing code that is proven to never execute.
* **Code motion and induction variable detection:** Moving loop-invariant code or applying strength reduction (e.g., replacing multiplication with addition) to loop indices.

### Data-Flow Analysis Abstraction
Data-flow analysis evaluates the execution of a program by observing state transformations:
* **Input State (`IN`):** The program state immediately before a statement or basic block.
* **Output State (`OUT`):** The program state immediately after a statement or basic block.

### Transfer Functions
[![image](https://lowyx.com/assets/posts/gatech/gpu/m10l4_trans.png)](https://lowyx.com/assets/posts/gatech/gpu/m10l4_trans.png)

Transfer functions mathematically model these state changes. For a basic block $B$:
$$ OUT[B] = f_B(IN[B]) $$
* $IN[B]$ is the union of the $OUT$ states of all predecessor blocks (blocks that execute *before* $B$).
* $OUT[B]$ can also determine the $IN$ state for all successor blocks (blocks that execute *after* $B$).
* The transfer function $f_B$ concatenates the effects of all individual statements within the basic block.

### Reaching Definitions
[![image](https://lowyx.com/assets/posts/gatech/gpu/m10l4_reachdefn.png)](https://lowyx.com/assets/posts/gatech/gpu/m10l4_reachdefn.png)

**Reaching definitions** analyze whether a variable's assignment reaches a specific point in the code. A definition $d$ reaches a point $p$ if there is an execution path from $d$ to $p$ where the variable is not "killed" (overwritten).
* **Definition:** When a variable is assigned a value.
* **Use:** When a variable's value is read.

#### Gen and Kill Sets
[![image](https://lowyx.com/assets/posts/gatech/gpu/m10l4_gnk.png)](https://lowyx.com/assets/posts/gatech/gpu/m10l4_gnk.png)
[![image](https://lowyx.com/assets/posts/gatech/gpu/m10l4_gnk2.png)](https://lowyx.com/assets/posts/gatech/gpu/m10l4_gnk2.png)

Every statement $d$ generating a new definition creates a **Gen** set and simultaneously overwrites older definitions of that variable, forming a **Kill** set.
* **Gen ($gen_B$):** Definitions created within block $B$.
* **Kill ($kill_B$):** Definitions outside or prior to block $B$ that are overwritten by $B$'s generations.

For example, if Block 1 defines variables $i, j, a$ (definitions $d_1, d_2, d_3$), it *generates* those definitions and *kills* any other definitions of $i, j, a$ found elsewhere in the program.

#### Generalized Transfer Functions
[![image](https://lowyx.com/assets/posts/gatech/gpu/m10l4_gnk_general.png)](https://lowyx.com/assets/posts/gatech/gpu/m10l4_gnk_general.png)

The reaching definitions transfer function for a basic block $B$ is expressed as:
$$ f_B(x) = gen_B \cup (x - kill_B) $$
Where $x$ is the $IN[B]$ state. The $OUT[B]$ is essentially the new definitions generated by the block, combined with the incoming definitions that were *not* killed.

> **Intuition:** The transfer function is just formalizing common sense: "What comes out of this block is whatever new stuff I created here ($gen$), plus whatever came into the block ($x$) that I didn't overwrite or destroy ($kill$)."

## Lesson 5: Example of Reaching Definitions

[![image](https://lowyx.com/assets/posts/gatech/gpu/m10l5_gnk_eg.png)](https://lowyx.com/assets/posts/gatech/gpu/m10l5_gnk_eg.png)

Applying the principles from Lesson 4, we use an iterative algorithm to compute reaching definitions across a CFG. First, we define the `Gen` and `Kill` sets for every basic block.

### Control Flow Equations
[![image](https://lowyx.com/assets/posts/gatech/gpu/m10l5_cfe.png)](https://lowyx.com/assets/posts/gatech/gpu/m10l5_cfe.png)

The state computations are defined by two equations:
1. **$IN[B] = \bigcup_{P \in pred(B)} OUT[P]$** (The input is the union of outputs from all predecessor blocks).
2. **$OUT[B] = gen_B \cup (IN[B] - kill_B)$** (The output is the block's generated definitions plus the surviving input definitions).

### The Iterative Algorithm
[![image](https://lowyx.com/assets/posts/gatech/gpu/m10l5_algo.png)](https://lowyx.com/assets/posts/gatech/gpu/m10l5_algo.png)

1. Initialize $OUT[ENTRY]$ as an empty set.
2. Initialize $OUT[B]$ as empty for all other basic blocks.
3. Iterate through all basic blocks, updating $IN[B]$ and $OUT[B]$ using the equations above.
4. Repeat the iteration until no $OUT[B]$ values change (the system reaches a steady state).

### Illustration of the Algorithm
[![image](https://lowyx.com/assets/posts/gatech/gpu/m10l5_algo_vis.png)](https://lowyx.com/assets/posts/gatech/gpu/m10l5_algo_vis.png)

Representing definitions $d_1$ through $d_7$ as a 7-bit vector (e.g., `0000000` means no definitions reach), the algorithm updates the bit vectors block by block:

* **Initialization:** All $OUT$ vectors are `0000000`.
* **Iteration 1:** 
  * $B_1$ processes its Gen/Kill, outputting its definitions.
  * $B_2$ takes $B_1$ and $B_4$'s output (which is initially 0 for $B_4$), applies its own Gen/Kill.
  * The process continues sequentially down the graph to the `EXIT` block.
* **Iteration 2:**
  * Because $B_4$ now has a non-zero $OUT$ from Iteration 1, the $IN$ for $B_2$ changes (since $B_4$ is a predecessor looping back to $B_2$).
  * The bit vectors are recalculated. 
* **Termination:**
  * By Iteration 3, the calculations will yield the exact same bit vectors as Iteration 2. Because there are no further changes, the iterative process terminates, leaving us with the final set of reaching definitions at every point in the program.
