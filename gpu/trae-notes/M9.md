## Lesson 1: Multi-GPU Hardware

### 1.1 Introduction to Multi-GPUs
Multi-GPU configurations are the backbone of modern data centers. As computing demands grow, GPUs must scale up. Initially, performance scaling was achieved by simply increasing the number of cores on a single monolithic GPU. However, this approach eventually hit a wall due to manufacturing costs and reliability concerns.

> **Background Context:** Making a monolithic chip larger significantly decreases manufacturing yield. A single defect on a massive die ruins the entire chip, making large monolithic GPUs extremely expensive to produce compared to connecting multiple smaller, high-yield chiplets.

To overcome these physical limitations, the industry shifted to alternative scaling methods:
1. **Packaging-level Integration**: Connecting multiple GPU chips using a silicon interposer or multi-sockets to build larger "logical" GPUs.
2. **Board-level Integration**: Connecting multiple GPU boards via PCI Express (PCIe) or specialized interconnects.

> **Intuition:** Instead of trying to build one giant city (monolithic GPU), we build several smaller, highly efficient towns (chiplets/boards) and connect them with massive, ultra-fast superhighways (interconnects) so they function as a single metropolis.

These innovations allow for continuous performance scaling beyond Moore's law.

[![Multi-GPUs](https://lowyx.com/assets/posts/gatech/gpu/m9l1_multigpu.png)](https://lowyx.com/assets/posts/gatech/gpu/m9l1_multigpu.png)

### 1.2 Multi-GPU Connections
To support the massive bandwidth requirements of these scaled systems, 3D stacked memory (like HBM) is heavily utilized. However, sharing I/O bandwidth across the entire system poses a challenge.

In NVIDIA systems, this interconnection is typically handled by **NVLink**. Despite physically comprising multiple GPUs, the system appears as a single unified device from the programmer's perspective—many Streaming Multiprocessors (SMs) sharing a global memory space. 

The primary challenge in this unified view is that the memory is **NUMA (Non-Uniform Memory Access)**. This means memory access latency and bandwidth vary depending on whether the memory is "near" (local to the GPU) or "far" (on another GPU). This raises two critical questions:
- How should thread blocks be scheduled?
- How should memory pages be allocated? 

> **Common Confusion:** It's easy to assume that "Unified Memory" means all memory accesses take the same amount of time. In reality, it just means you have a single address space; the underlying hardware still dictates that fetching data from another GPU's HBM takes much longer than fetching from the local HBM.

> **Mental Model:** Think of NUMA like working in a large office: getting a file from your own desk (local memory) is fast, but walking over to a colleague's desk in another room (far memory) takes much longer, even though you both work for the same company (unified address space).

A straightforward solution is to allocate memory pages in the "near memory" of the GPU where the thread block is scheduled.

[![Multi-GPU Connections](https://lowyx.com/assets/posts/gatech/gpu/m9l1_nvlink.png)](https://lowyx.com/assets/posts/gatech/gpu/m9l1_nvlink.png)

### 1.3 Thread Block Scheduling and Memory Mapping
Consider a scenario with several thread blocks, each requiring different memory areas.

[![Thread Block Scheduling 1](https://lowyx.com/assets/posts/gatech/gpu/m9l1_tb_s0.png)](https://lowyx.com/assets/posts/gatech/gpu/m9l1_tb_s0.png)

Using a simple round-robin scheduling approach, each GPU is assigned a different thread block. When a thread block requests access to a page, that page is allocated to the local DRAM of the corresponding GPU. This is known as **first-touch-based allocation**.

> **Tradeoff:** First-touch allocation is extremely fast and simple for initial setup, but if subsequent thread blocks on different GPUs need that same data, it leads to expensive remote accesses. The system must balance the cost of migrating the page against the penalty of repeated remote accesses.

[![Thread Block Scheduling 2](https://lowyx.com/assets/posts/gatech/gpu/m9l1_tb_s1.png)](https://lowyx.com/assets/posts/gatech/gpu/m9l1_tb_s1.png)

As execution continues, additional thread blocks are scheduled. For instance, Thread Block 5 might be scheduled on the same GPU that previously ran Thread Block 1. 

[![Thread Block Scheduling 3](https://lowyx.com/assets/posts/gatech/gpu/m9l1_tb_s2.png)](https://lowyx.com/assets/posts/gatech/gpu/m9l1_tb_s2.png)

This new thread block might request a new page (e.g., Page 10, allocated locally) but may also need an existing page (e.g., Page 8, which resides on a different GPU). Accessing Page 8 becomes a **far memory access**. 

> **Hypothetical:** What if Thread Block 5 constantly reads and writes to Page 8? If Page 8 stays on the remote GPU, the NVLink interconnect will be flooded with traffic, significantly degrading overall application performance due to the bandwidth bottleneck and latency.

[![Thread Block Scheduling 4](https://lowyx.com/assets/posts/gatech/gpu/m9l1_tb_s3.png)](https://lowyx.com/assets/posts/gatech/gpu/m9l1_tb_s3.png)

To optimize performance, scheduling should leverage **memory locality**. If Thread Block 5 is instead scheduled on the GPU where Page 8 is already located, it benefits from near memory accesses. Alternatively, if far memory accesses become too frequent, the memory pages themselves can be migrated to the GPU where they are most heavily used.

### 1.4 NVLink and NVSwitch
**NVLink** is NVIDIA's proprietary high-speed communication protocol, designed as a superior alternative to the PCIe bus for GPU-to-GPU data transfers. For context, the fourth generation of NVLink delivers 900 GB/s per GPU across 18 links. While a modern GPU like the H100 boasts 3 TB/s of HBM3 memory bandwidth, NVLink still provides an impressive one-fourth of that bandwidth for inter-GPU communication.

As cluster sizes grow, point-to-point connections become insufficient. To ensure scalability, NVIDIA introduced the **NVSwitch**. Multi-GPU systems connected via NVSwitch and NVLink achieve significantly higher bandwidth and lower latency compared to traditional architectures.

> **Example:** In a DGX H100 system, 8 GPUs are fully connected via NVSwitches. This all-to-all non-blocking topology allows any GPU to talk to any other GPU at the full 900 GB/s NVLink bandwidth, acting as a massive crossbar switch.

[![NVLink/NVSwitch](https://lowyx.com/assets/posts/gatech/gpu/m9l1_nvlink1.png)](https://lowyx.com/assets/posts/gatech/gpu/m9l1_nvlink1.png)

### 1.5 Memory Space and Communication
When GPUs are connected to CPUs via PCIe, they occupy different memory spaces. The PCIe bus lacks the bandwidth required for efficient communication between the memory spaces of multiple GPUs across a board. 

To resolve this, multi-GPU environments utilize **RDMA (Remote Direct Memory Access)**. This approach mirrors distributed memory systems, enabling point-to-point connections that bridge all memory spaces directly.

> **Intuition:** Think of the PCIe bus as a slow, crowded bridge between two islands (GPUs). Instead of forcing all traffic across this bridge through the mainland (CPU), RDMA builds direct high-speed ferries between the islands, bypassing the mainland entirely.

[![Memory Space](https://lowyx.com/assets/posts/gatech/gpu/m9l1_mem_space.png)](https://lowyx.com/assets/posts/gatech/gpu/m9l1_mem_space.png)

### 1.6 Background: RDMA Technology
In **traditional communication**, data transfers (e.g., from Buffer 1 to Buffer 2) rely on TCP/IP-like networks. This requires the data to traverse the network software stack and consume CPU resources (CPU 1 and CPU 2). Performance is therefore bottlenecked by the CPU's availability and processing speed.

[![Traditional Communication](https://lowyx.com/assets/posts/gatech/gpu/m9l1_rdma.png)](https://lowyx.com/assets/posts/gatech/gpu/m9l1_rdma.png)

**RDMA** functions similarly to standard DMA (Direct Memory Access) but across a network. It enables memory-to-memory communication (e.g., from Buffer 4 directly to Buffer 2) while entirely bypassing the host CPUs. This host-bypass technology frees up CPU resources and accelerates data transfer.

> **Tradeoff:** While RDMA provides ultra-low latency and zero-copy transfers, it often requires specialized network hardware (like InfiniBand or RoCE-capable NICs) and bypasses traditional OS security and routing layers, which can complicate cluster network management.

[![RDMA](https://lowyx.com/assets/posts/gatech/gpu/m9l1_rdma1.png)](https://lowyx.com/assets/posts/gatech/gpu/m9l1_rdma1.png)

### 1.7 GPUDirect RDMA
For GPUs, **GPUDirect RDMA** allows direct buffer-to-buffer communication via network interfaces, leveraging NVLink and NVSwitch. This technology bypasses the PCIe bottleneck, enabling seamless communication not only between GPUs but also with third-party network devices. Given the massive communication demands of modern multi-GPU setups, GPUDirect RDMA is essential for maintaining system performance.

> **Example:** When training a large language model across multiple nodes, GPUDirect RDMA allows a GPU on Node A to send gradients directly from its local HBM, out through the InfiniBand network card, and straight into the HBM of a GPU on Node B, completely ignoring the CPUs and host memory on both nodes.

[![GPUDirect RDMA](https://lowyx.com/assets/posts/gatech/gpu/m9l1_rdma2.png)](https://lowyx.com/assets/posts/gatech/gpu/m9l1_rdma2.png)

## Lesson 2: Concurrency on GPUs

### 2.1 Increasing GPU Utilization
While multi-GPUs offer immense computational power, achieving high utilization is a challenge. In traditional data centers, GPUs handle multiple tenant jobs simultaneously. Conversely, massive AI workloads (like LLM training) might consume an entire GPU cluster for a single tenant, where the overall speed is often bottlenecked by the slowest task. Maximizing GPU efficiency is critical in both scenarios.

> **Background Context:** GPUs are massively parallel and rely on huge amounts of work to hide latency. If a workload doesn't have enough parallel threads to keep all SMs busy, a large portion of the GPU's compute capability sits idle, burning power without doing useful work.

### 2.2 GPU Concurrency Mechanisms
To efficiently manage multiple jobs, GPUs employ several concurrency mechanisms:
- **Streams**: Independent command queues executed concurrently on the GPU, typically from a single client.
- **MPS (Multi-Process Service)**: Multiple clients share a GPU; clients are assigned different SMs, but other resources (like memory and caches) remain shared.
- **MIG (Multi-Instance GPU)**: Physically partitions a single GPU into isolated instances, ensuring strict separation of resources for multiple clients.

> **Mental Model:** Streams are like multiple lanes on a highway managed by one company. MPS is like a shared workspace where different companies use different desks but share the same breakroom and Wi-Fi. MIG is like subdividing a large office building into completely separate, locked suites with their own dedicated utilities.

[![GPU Concurrency Mechanisms](https://lowyx.com/assets/posts/gatech/gpu/m9l2_gpucon.png)](https://lowyx.com/assets/posts/gatech/gpu/m9l2_gpucon.png)

### 2.3 Multi-Instance GPU (MIG)
MIG allows a single large GPU to be carved into multiple independent instances. It provides strict hardware-level isolation for both memory and GPU cores (SMs). Furthermore, MIG partitions the L2 cache, DRAM bandwidth, and on-chip crossbar ports. 

This strict isolation guarantees **Quality of Service (QoS)**, ensuring that one workload does not interfere with another. For example, an NVIDIA A100 can host up to 7 isolated MIG instances, making it highly valuable for cloud providers offering multi-tenant services.

> **Common Confusion:** While MIG provides strict hardware isolation, it doesn't support dynamic resizing on the fly without disruption. The partitioning is relatively static, meaning you can't instantly give an idle instance's resources to a busy instance.

[![MIG](https://lowyx.com/assets/posts/gatech/gpu/m9l2_gpumulti.png)](https://lowyx.com/assets/posts/gatech/gpu/m9l2_gpumulti.png)

### 2.4 Multi-Process Service (MPS)
Introduced with spatial partitioning capabilities in the Volta (V100) architecture (prior to this, it only supported time-slicing), MPS allows multiple processes to run concurrently on the same GPU. 

Unlike MIG, MPS does not strictly partition all hardware resources. While this can lead to unpredictable performance due to resource contention, MPS often yields **higher overall utilization** than MIG by allowing dynamic sharing of idle resources. MPS is particularly useful for porting MPI (Message Passing Interface) jobs to CUDA in environments where strict QoS is not mandatory.

> **Tradeoff:** MPS maximizes overall throughput by dynamically filling idle execution slots across the entire GPU, but it sacrifices strict predictability. A sudden burst in memory bandwidth usage by one process can severely slow down another process sharing the same GPU.

### 2.5 Stream-Based Programming
CUDA Streams enable the concurrent execution of multiple kernels. By using streams, developers can submit operations from multiple CPU threads and overlap computation with memory transfers (e.g., using `cudaMemcpyAsync`). 

This model makes it relatively easy to port OpenMP programs to the GPU. However, managing dependencies between multiple streams can introduce scheduling overhead. To mitigate this, **CUDA Graphs** can be used to define and optimize the entire dependency chain prior to launching the kernels.

> **Example:** In a data processing pipeline, you can use streams to concurrently copy batch 2 from CPU to GPU, execute the neural network on batch 1, and copy the results of batch 0 from GPU back to CPU—keeping all hardware engines simultaneously active.

[![Stream-Based Programming](https://lowyx.com/assets/posts/gatech/gpu/m9l2_stream.png)](https://lowyx.com/assets/posts/gatech/gpu/m9l2_stream.png)

### 2.6 Programming for Multi-GPUs
When programming for multiple GPUs, explicit management is required:
1. Memory must be allocated separately for each GPU.
2. The host must explicitly set the active device using `cudaSetDevice()`.
3. Kernels (e.g., `gaussian_pdf`) are launched independently on their respective GPUs.
4. The host must synchronize and wait for all devices to complete their tasks.

> **Intuition:** By default, CUDA commands implicitly target the "current" device (usually Device 0). `cudaSetDevice()` acts like a context switch for the CPU thread, changing the target GPU for all subsequent CUDA calls until it is changed again.

Note that multiple CUDA streams can be utilized simultaneously across multiple GPUs to further boost concurrency.
