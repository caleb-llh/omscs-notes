## Lesson 1: Multi-threaded Architecture

### Learning Objectives
* Explain the difference between multithreading and context switching.
* Describe the resource requirements for GPU multithreading.

### 1.1 Recap: Fundamentals of GPU Architecture
> **Mental Model:** Think of a GPU core not as a single traditional CPU core, but as a mini-processor itself that can manage and execute hundreds of threads simultaneously. If a CPU core is an agile sports car, a GPU core is a massive transit bus optimized for throughput.

[![image](https://lowyx.com/assets/posts/gatech/gpu/m4l1_gpu_architecture.png)](https://lowyx.com/assets/posts/gatech/gpu/m4l1_gpu_architecture.png)
* GPUs are equipped with numerous cores.
* Each core features **multithreading**, which facilitates the execution of a warp or wavefront within the core.
* Each core contains shared memory and hardware caches.

### 1.2 Multithreading vs. Out-of-Order Execution
[![image](https://lowyx.com/assets/posts/gatech/gpu/m4l1_multithreading.png)](https://lowyx.com/assets/posts/gatech/gpu/m4l1_multithreading.png)

Consider a GPU with a five-stage pipeline executing four instructions. 
* **In-order Processor:** If an instruction experiences a cache miss, subsequent instructions must wait until the first completes. 
* **Out-of-Order Processor:** If Instruction 2 is independent of Instruction 1, it doesn't have to wait. It begins executing Instructions 2 and 3 before Instruction 1 completes. Once Instruction 1 receives its memory request, Instruction 4 can proceed.

[![image](https://lowyx.com/assets/posts/gatech/gpu/m4l1_multithreading_2.png)](https://lowyx.com/assets/posts/gatech/gpu/m4l1_multithreading_2.png)
[![image](https://lowyx.com/assets/posts/gatech/gpu/m4l1_multithreading_3.png)](https://lowyx.com/assets/posts/gatech/gpu/m4l1_multithreading_3.png)

* **Multithreading in GPUs:** Instead of dealing with complex out-of-order logic, a multithreaded processor simply switches to another thread regardless of whether a previous instruction stalls (e.g., from a cache miss). Since instructions come from different threads, they are entirely independent. In this scenario, the processor executes four instructions from four different threads and concurrently generates four memory requests.

> **Intuition:** Out-of-Order execution is like a single highly intelligent worker dynamically rearranging their own tasks to stay busy. GPU multithreading is like a manager with thousands of workers; if one worker gets stuck waiting for parts, the manager instantly points to another worker who is ready to go.

### 1.3 The Benefits of Multithreading
GPUs utilize multithreading to generate multiple concurrent memory requests and hide latency. Instead of waiting for stalled instructions, the GPU executes instructions from another thread.

* **Hiding Stall Time:** Multithreading masks processor stall time caused by cache misses, branch instructions, or long-latency ALU operations.
* **CPU vs. GPU Approaches:** While CPUs rely on out-of-order execution, complex cache hierarchies, and instruction-level parallelism (ILP) to tackle latency, GPUs leverage massive multithreading.
* **Thread Scaling:** Longer memory latencies require a greater number of threads to effectively hide the delay.

> **Common Confusion:** It's easy to confuse GPU multithreading with CPU multithreading (like Intel's Hyper-Threading). A CPU might support 2 threads per core to hide short stalls. A GPU supports *hundreds* of threads per core, designed specifically to hide massive memory latencies (hundreds of clock cycles) without relying on huge data caches.

### 1.4 Hardware Support for Multithreading
To support multithreading, GPUs require specific architectural extensions:

#### Front-End Extensions
[![image](https://lowyx.com/assets/posts/gatech/gpu/m4l1_fe_extension.png)](https://lowyx.com/assets/posts/gatech/gpu/m4l1_fe_extension.png)
* The front-end must maintain multiple **Program Counter (PC) registers**. (Assuming one PC per warp, supporting four warps requires four PC registers).
* It requires multiple sets of register files. 
* Context switching on a GPU is instantaneous: it simply switches the active pointer among the multiple PC registers and register files.

#### Comparison: CPU Context Switching
> **Background Context:** Context switching on a CPU usually involves the OS kernel. The OS must trap into kernel mode, save the thread state (registers, flags, PC) into a Process Control Block (PCB) in main memory, and load the state of the next thread. This software-managed process takes thousands of cycles, making it orders of magnitude slower than a GPU's zero-cycle hardware switch.

[![image](https://lowyx.com/assets/posts/gatech/gpu/m4l1_cpu_context.png)](https://lowyx.com/assets/posts/gatech/gpu/m4l1_cpu_context.png)
[![image](https://lowyx.com/assets/posts/gatech/gpu/m4l1_cpu_context_1.png)](https://lowyx.com/assets/posts/gatech/gpu/m4l1_cpu_context_1.png)
[![image](https://lowyx.com/assets/posts/gatech/gpu/m4l1_cpu_context_2.png)](https://lowyx.com/assets/posts/gatech/gpu/m4l1_cpu_context_2.png)
* In a CPU, the instruction pipeline, PC, and registers are dedicated to a specific thread.
* To switch from Thread 2 to Thread 3, the CPU must save Thread 2's context (registers, PC) to memory and load Thread 3's context from memory.
* This incurs substantial performance overhead, making CPU context switching expensive compared to GPUs.

#### Register and PC Resource Requirements
* **PCs:** One PC is needed for each warp (since all threads in a warp share the same PC).
* **Register Files:** A massive register file is required. If each thread needs `K` architectural registers, the total register file size equals `K` × number of threads. The value of `K` varies by application.

#### Occupancy Calculation Example
Recall that occupancy is bounded by available resources (threads, registers, shared memory).
* **Scenario:** An SM can execute 256 threads, has 64 × 1024 registers, and 32 KB of shared memory. Assume 32 threads per warp.
* **How many PCs are needed?** 256 threads / 32 threads per warp = 8 PCs.
* **Instruction Fetching:** If a program has 10 instructions, the SM must fetch instructions 10 instructions × 8 warps = 80 times.

## Lesson 2: Bank Conflicts

### Learning Objectives
* Explain the SIMT behavior of register file and shared memory accesses.
* Describe techniques to enhance bandwidth for register and shared memory accesses.

### 2.1 CUDA Blocks, Threads, and Warps
[![image](https://lowyx.com/assets/posts/gatech/gpu/m4l2_warp.png)](https://lowyx.com/assets/posts/gatech/gpu/m4l2_warp.png)
* Multiple CUDA blocks run on one streaming multiprocessor (SM).
* Each block consists of multiple threads, grouped into **warps** for execution. 
* Registers are allocated **per thread**. If an instruction reads two source operands and writes one, and the execution width is 8, the hardware must supply 24 values simultaneously (8 × 2 reads + 8 × 1 write).

### 2.2 Ports vs. Banks
**Ports:** A port is a hardware interface for data access. Providing dedicated read/write ports for every simultaneous access (e.g., 8 read ports and 4 write ports per register element) consumes a massive amount of physical space and wiring.
[![image](https://lowyx.com/assets/posts/gatech/gpu/m4l2_port_vs_bank.png)](https://lowyx.com/assets/posts/gatech/gpu/m4l2_port_vs_bank.png)

**Banks:** To save space, register files are partitioned into **banks**. A bank is a subset of the register file. By splitting the register file into multiple banks (e.g., a 4-bank setup), each bank requires fewer ports (e.g., only 2 read ports and 1 write port per element). Multiple banks can be accessed simultaneously, drastically reducing hardware wiring while maintaining high bandwidth.

> **Tradeoff:** The transition from ports to banks is a classic area-versus-bandwidth tradeoff. Dedicated ports guarantee peak bandwidth regardless of access patterns but consume excessive die area and power. Banks save die area and power but introduce the risk of performance bottlenecks (bank conflicts) if memory access patterns are poorly optimized.

[![image](https://lowyx.com/assets/posts/gatech/gpu/m4l2_port_vs_bank_1.png)](https://lowyx.com/assets/posts/gatech/gpu/m4l2_port_vs_bank_1.png)

### 2.3 Bank Conflicts
A **bank conflict** occurs when multiple threads in a warp simultaneously attempt to access different registers located in the *same* bank, exceeding the bank's port capacity.

[![image](https://lowyx.com/assets/posts/gatech/gpu/m4l2_bank_conflict.png)](https://lowyx.com/assets/posts/gatech/gpu/m4l2_bank_conflict.png)
[![image](https://lowyx.com/assets/posts/gatech/gpu/m4l2_bank_conflict2.png)](https://lowyx.com/assets/posts/gatech/gpu/m4l2_bank_conflict2.png)
* **Scenario 1 (No Conflict):** Reading `R1` from Threads 1, 2, 3, and 4. If each thread's registers map to different banks, a 4-bank system can easily provide all four values simultaneously.

[![image](https://lowyx.com/assets/posts/gatech/gpu/m4l2_bank_conflict3.png)](https://lowyx.com/assets/posts/gatech/gpu/m4l2_bank_conflict3.png)
* **Scenario 2 (Conflict):** Reading `R1, R2, R3, R4` from Thread 1. Since all these registers belong to the same thread, they may reside in the same bank. An 8-port system handles this fine, but a 4-bank system with limited ports can only read a subset at a time, forcing the operation to take multiple clock cycles.

### 2.4 Register Allocation and Bank Conflicts
[![image](https://lowyx.com/assets/posts/gatech/gpu/m4l2_variable.png)](https://lowyx.com/assets/posts/gatech/gpu/m4l2_variable.png)
Different CUDA programs require a varying number of registers per thread.
* **Case 1 (4 registers per thread):** Reading operands across threads avoids conflicts because each thread's register file sits in a different bank.
* **Case 2 (2 registers per thread):** Threads 1 and 2 might map to the same bank. Reading `R1` and `R2` across multiple threads causes conflicts because the hardware must access the same bank for different threads simultaneously.

**Solutions to Register Bank Conflicts:**
1. **Compile-Time Optimization:** The compiler knows register IDs at static time and can optimize code layout to minimize conflicts.
2. **Scoreboarding & Buffering:** Not all conflicts can be avoided statically. Modern GPUs use a more complex pipeline with buffers and scoreboarding to manage dynamic execution.

> **Side Bar: Static vs. Dynamic Analysis**
> * **Static:** Properties determined before runtime, independent of input (e.g., compile-time).
> * **Dynamic:** Properties dependent on runtime execution and input.
> * *Example:* A loop with 2 instructions (`ADD`, `BREQ`) running 10 times has a static instruction count of 2, but a dynamic instruction count of 20.

### 2.5 Scoreboarding in GPUs
> **Background Context:** The term "scoreboard" originates from the CDC 6600 supercomputer in 1964, which used a centralized control logic (a physical "scoreboard") to track register dependencies and allow instructions to execute out of order safely. GPUs adapt this concept to manage dependencies across massive numbers of threads rather than just single-thread instruction-level parallelism.

[![image](https://lowyx.com/assets/posts/gatech/gpu/m4l2_solution.png)](https://lowyx.com/assets/posts/gatech/gpu/m4l2_solution.png)
In CPUs, scoreboards enable out-of-order execution. In GPUs, a **scoreboard** is used to check if all source operands for a warp are ready. 
* Reading register files may take multiple cycles (due to limited ports or bank conflicts).
* As values are read, they are stored in a **buffer**.
* The scoreboard sets a "ready" bit for each operand as it arrives in the buffer.

[![image](https://lowyx.com/assets/posts/gatech/gpu/m4l2_scoreboarding.png)](https://lowyx.com/assets/posts/gatech/gpu/m4l2_scoreboarding.png)
[![image](https://lowyx.com/assets/posts/gatech/gpu/m4l2_scoreboarding2.png)](https://lowyx.com/assets/posts/gatech/gpu/m4l2_scoreboarding2.png)
[![image](https://lowyx.com/assets/posts/gatech/gpu/m4l2_scoreboard3.png)](https://lowyx.com/assets/posts/gatech/gpu/m4l2_scoreboard3.png)
[![image](https://lowyx.com/assets/posts/gatech/gpu/m4l2_scoreboard4.png)](https://lowyx.com/assets/posts/gatech/gpu/m4l2_scoreboard4.png)
[![image](https://lowyx.com/assets/posts/gatech/gpu/m4l2_scoreboard5.png)](https://lowyx.com/assets/posts/gatech/gpu/m4l2_scoreboard5.png)
[![image](https://lowyx.com/assets/posts/gatech/gpu/m4l2_scoreboard_ready.png)](https://lowyx.com/assets/posts/gatech/gpu/m4l2_scoreboard_ready.png) 
[![image](https://lowyx.com/assets/posts/gatech/gpu/m4l2_scoreboard_ready_execution.png)](https://lowyx.com/assets/posts/gatech/gpu/m4l2_scoreboard_ready_execution.png)

Once all source operands for a warp are marked ready, the scoreboard selects that warp and sends it to the execution unit. Scheduling policies (e.g., oldest first) determine which ready warp goes next.

### 2.6 Shared Memory Bank Conflicts
[![image](https://lowyx.com/assets/posts/gatech/gpu/m4l2_shared_mem.png)](https://lowyx.com/assets/posts/gatech/gpu/m4l2_shared_mem.png)
Shared memory (on-chip scratchpad memory) is also partitioned into banks to provide high bandwidth.
Consider this code snippet:
```cpp
__shared__ float sharedInput[index1];  
Index1 = threadIdX.x * 4;
```
Here, Thread 1 accesses address 4, Thread 2 accesses address 8, Thread 3 accesses address 12, etc. If the shared memory has 4 banks, addresses 4, 8, and 12 might all map to the exact same bank. This forces sequential access, severely degrading performance. Resolving this typically requires software-level restructuring (e.g., padding).

> **Example:** To resolve the conflict in the code snippet, developers often use **padding**. By changing the allocation to `__shared__ float sharedInput[index1 + 1];` or modifying the index calculation, the stride changes. This shifts the mapping so that Thread 1 accesses Bank 0, Thread 2 accesses Bank 1, etc., eliminating the bank conflict at the cost of a small amount of wasted shared memory.

## Lesson 3: GPU Architecture Pipeline

### Learning Objectives
* Describe GPU pipeline behavior with multithreading and register file access.
* Explain the use of mask bits.

### 3.1 Pipeline Execution Flow
[![image](https://lowyx.com/assets/posts/gatech/gpu/m4l3_gpu_pipeline.png)](https://lowyx.com/assets/posts/gatech/gpu/m4l3_gpu_pipeline.png)

Let's trace instructions through the GPU pipeline using four active warps:
* **Warp 1:** Block 1, Threads 1–4
* **Warp 2:** Block 1, Threads 5–8
* **Warp 3:** Block 2, Threads 1–4
* **Warp 4:** Block 2, Threads 5–8

[![image](https://lowyx.com/assets/posts/gatech/gpu/m4l3_pc_values.png)](https://lowyx.com/assets/posts/gatech/gpu/m4l3_pc_values.png)
[![image](https://lowyx.com/assets/posts/gatech/gpu/m4l3_register_values.png)](https://lowyx.com/assets/posts/gatech/gpu/m4l3_register_values.png)
[![image](https://lowyx.com/assets/posts/gatech/gpu/m4l3_i_cache.png)](https://lowyx.com/assets/posts/gatech/gpu/m4l3_i_cache.png)
[![image](https://lowyx.com/assets/posts/gatech/gpu/m4l3_scoreboard.png)](https://lowyx.com/assets/posts/gatech/gpu/m4l3_scoreboard.png)

**Step 1: Fetch and Decode**
> **Hypothetical:** What happens if the instruction cache misses during the Fetch step? Because the GPU uses multithreading, it won't stall the entire pipeline. The scheduler will simply pick another ready warp (whose instructions are already fetched and operands are ready) to execute in the next cycle while the missing instruction is fetched from memory.

* The front-end fetches one instruction for an entire warp (e.g., `ADD r1, r1, 1` from address `0x8000` for Warp 1).
[![image](https://lowyx.com/assets/posts/gatech/gpu/m4l3_scoreboard1.png)](https://lowyx.com/assets/posts/gatech/gpu/m4l3_scoreboard1.png)
* The instruction is decoded. Immediate/constant values (like the `1` in the ADD instruction) are broadcasted directly to the scoreboard, marking that operand as ready.

**Step 2: Register File Access**
[![image](https://lowyx.com/assets/posts/gatech/gpu/m4l3_scoreboard2.png)](https://lowyx.com/assets/posts/gatech/gpu/m4l3_scoreboard2.png)
* The hardware accesses the register file to read the remaining source operands (e.g., `r1` for Threads 1–4). These values are sent to the scoreboard buffer.

**Step 3: Execution and Write-Back**
[![image](https://lowyx.com/assets/posts/gatech/gpu/m4l3_scoreboard3.png)](https://lowyx.com/assets/posts/gatech/gpu/m4l3_scoreboard3.png)
* Once the scoreboard confirms all source operands are ready, the warp is scheduled for execution. The ALU performs the addition, and results are written back to the register file in the write-back stage.

[![image](https://lowyx.com/assets/posts/gatech/gpu/m4l3_scoreboard4.png)](https://lowyx.com/assets/posts/gatech/gpu/m4l3_scoreboard4.png)
[![image](https://lowyx.com/assets/posts/gatech/gpu/m4l3_scoreboard5.png)](https://lowyx.com/assets/posts/gatech/gpu/m4l3_scoreboard5.png)
[![image](https://lowyx.com/assets/posts/gatech/gpu/m4l3_scoreboard6.png)](https://lowyx.com/assets/posts/gatech/gpu/m4l3_scoreboard6.png)
* This identical process applies seamlessly to subsequent warps (e.g., Warp 2 executing subtraction).

### 3.2 Special Registers: `tid.x` and `ctaid.x`
GPUs utilize special registers to identify threads and blocks:
* `tid.x`: Stores the Thread ID within a block.
* `ctaid.x`: Stores the Block ID within a grid.

[![image](https://lowyx.com/assets/posts/gatech/gpu/m4l3_scoreboard7.png)](https://lowyx.com/assets/posts/gatech/gpu/m4l3_scoreboard7.png)
If Warp 4 (Block 2) executes an instruction to move `ctaid.x` to `r2`, the hardware reads the Block ID (`2`) and stores it in the scoreboard buffer. It is then written to `r2` during write-back.

[![image](https://lowyx.com/assets/posts/gatech/gpu/m4l3_scoreboard8.png)](https://lowyx.com/assets/posts/gatech/gpu/m4l3_scoreboard8.png)
Similarly, if Warp 4 (Threads 5–8) reads `tid.x`, the hardware populates the buffer with values `5, 6, 7, 8`, which are then written back to the target register.

### 3.3 Mask Bits and Active Lanes
> **Mental Model:** Think of mask bits as a set of on/off switches for each lane in a wide assembly line. Even if a particular lane's switch is "off" (inactive), the assembly line keeps moving at the same speed. The inactive lane just ignores the operation and doesn't write any results.

[![image](https://lowyx.com/assets/posts/gatech/gpu/m4l3_scoreboard9.png)](https://lowyx.com/assets/posts/gatech/gpu/m4l3_scoreboard9.png)
In SIMT (Single Instruction, Multiple Threads) architecture, one ALU execution path is called a **lane**. Not all threads in a warp necessarily need to execute every instruction (e.g., due to branch divergence).
* **Mask Bits:** The GPU maintains a bitmask indicating which threads (lanes) are currently active.
* **Active vs. Inactive:** Active threads perform the computation and update state; inactive threads idle.
* *Example:* If Warp 1's mask is `1111`, all 4 lanes compute. If Warp 2's mask is `1110`, only the first three lanes compute; the fourth is masked off.

## Lesson 4: Global Memory Coalescing

### Learning Objectives
* Explore global memory accesses.
* Explain memory address coalescing.
* Describe how one warp can generate multiple memory requests.

### 4.1 Global Memory Access and Bandwidth Constraints
[![image](https://lowyx.com/assets/posts/gatech/gpu/m4l4_dram.png)](https://lowyx.com/assets/posts/gatech/gpu/m4l4_dram.png)
A single memory instruction in a warp can generate up to 32 memory requests (assuming a warp size of 32). 
* **Bandwidth Saturation:** If a GPU has 32 SMs, each firing 32 requests per cycle, that’s 1024 requests/cycle. At 64 bytes per request on a 1 GHz GPU, this would demand a theoretical **64 TB/s** of memory bandwidth. Because GPU caches are relatively small, it is extremely easy to saturate available memory bandwidth.

> **Side Bar: DRAM vs. SRAM & HBM**
> [![image](https://lowyx.com/assets/posts/gatech/gpu/m4l4_sram.png)](https://lowyx.com/assets/posts/gatech/gpu/m4l4_sram.png)
> * **SRAM (Static RAM):** Uses 6 transistors per bit. Fast but space-intensive; used primarily for caches.
> * **DRAM (Dynamic RAM):** Uses 1 transistor per bit. High density/capacity, but limited by physical pin communication speeds.
> * **HBM (High Bandwidth Memory):** Overcomes DRAM bandwidth limits by vertically stacking DRAM dies and connecting them directly to the GPU via a silicon interposer, eliminating slow off-chip communication.

### 4.2 Memory Coalescing
To prevent bandwidth saturation, reducing the total number of memory transactions is critical. 

[![image](https://lowyx.com/assets/posts/gatech/gpu/m4l4_coalesce.png)](https://lowyx.com/assets/posts/gatech/gpu/m4l4_coalesce.png)
* **Coalesced Access:** If the threads in a warp access consecutive, contiguous memory addresses, the hardware can combine (coalesce) these multiple requests into a single, large memory transaction (e.g., fetching a 64-byte or 128-byte chunk all at once). This drastically reduces the number of requests sent to DRAM.

[![image](https://lowyx.com/assets/posts/gatech/gpu/m4l4_coalesce2.png)](https://lowyx.com/assets/posts/gatech/gpu/m4l4_coalesce2.png)
* **Uncoalesced Access:** If threads access scattered addresses (e.g., strided by 128 bytes), the hardware cannot combine them. Each thread generates a separate, individual memory request. This causes massive performance degradation and bottlenecks the memory system. 

> **Tradeoff:** To achieve coalesced accesses, GPU programmers often must convert data structures from an Array of Structures (AoS) to a Structure of Arrays (SoA). While AoS is more intuitive for object-oriented CPU programming (e.g., an array of `Point` objects with `x, y, z`), SoA allows Thread 0 to access `x[0]`, Thread 1 to access `x[1]`, etc., perfectly coalescing the memory access at the cost of less intuitive code readability.

**Summary:** Coalescing memory requests is one of the most vital software optimization techniques in CUDA programming, as uncoalesced accesses can cripple GPU performance.
