## Lesson 1: Handling Divergent Branches

### 1. What are Divergent Branches?
A **warp** is a group of threads executed together. In the Single Program Multiple Data (SPMD) model, we typically assume all threads in a warp execute the same instructions. However, threads may occasionally need to execute different program paths (e.g., due to an `if-else` statement dependent on thread IDs).

> **Intuition:** Think of a warp as a tour group with a single tour guide. If half the group wants to go to a museum and the other half wants to go to a park, the guide can't split in two. They must take the whole group to the museum (while the park-goers wait), and then take the whole group to the park (while the museum-goers wait).

[![image](https://lowyx.com/assets/posts/gatech/gpu/m6l1_divb.png)](https://lowyx.com/assets/posts/gatech/gpu/m6l1_divb.png)

When threads within a single warp fetch different parts of a program, it creates a **divergent branch**, and the warp is termed a **divergent warp**. 
* **Active Masks:** Divergent warps use an active mask (e.g., `1, 1, 1, 0`) to indicate which threads are active for a given basic block (BB).
* **Reconvergence Point:** The point where split paths meet again (e.g., after the `if-else` blocks finish). At this point, all threads in the warp resume executing together. In compiler terminology, this is known as the *immediate post-dominator*.

> **Background Context:** The immediate post-dominator of a node `n` is the first node that must be reached on every path from `n` to the end of the control flow graph. It perfectly serves as the earliest point where we can guarantee all divergent paths have naturally merged back.

### 2. If-Else Conversion: Predicated Execution
Divergent branches can sometimes be eliminated using **if-else conversion** (or **predicated execution**).

[![image](https://lowyx.com/assets/posts/gatech/gpu/m6l1_divb2.png)](https://lowyx.com/assets/posts/gatech/gpu/m6l1_divb2.png)

In this approach, instructions are executed based on a boolean predicate value. Both the `if` (Work 1) and `else` (Work 2) paths are fetched, but instructions are only committed if their associated predicate is true.
* **Pros:** Commonly used in vector processors and modern CPUs for small branch workloads.
* **Cons:** The processor must fetch instructions for paths that ultimately won't be executed. Therefore, predicated execution is inefficient if the workload inside the branches is large.

> **Tradeoff:** Predication trades instruction fetch/execution efficiency for control flow simplicity. You avoid branch penalties and complex reconvergence tracking, but you waste execution units performing dummy work for the false predicates.

### 3. GPU Execution Flow & The SIMT Stack
Because predicated execution is inefficient for large branches, most complex sub-branches remain as standard branch instructions and must be handled as divergent branches.

[![image](https://lowyx.com/assets/posts/gatech/gpu/m6l1_gpuflow1.png)](https://lowyx.com/assets/posts/gatech/gpu/m6l1_gpuflow1.png)

When a processor computes the next instruction address, it checks if the Program Counter (PC) values for all threads in the warp are identical. If they differ, divergence has occurred. 

[![image](https://lowyx.com/assets/posts/gatech/gpu/m6l1_gpuflow2.png)](https://lowyx.com/assets/posts/gatech/gpu/m6l1_gpuflow2.png)

**The Challenge:** If the processor fetches and executes Path A (e.g., BB2) first, it eventually moves on to the reconvergence point (BB4), completely skipping Path B (BB3). How does the processor remember to go back and execute BB3?

> **Mental Model:** Imagine navigating a maze and coming to a fork. You must drop a breadcrumb (the alternate path's address) so you know where to return after exploring the first branch.

[![image](https://lowyx.com/assets/posts/gatech/gpu/m6l1_gpuflow3.png)](https://lowyx.com/assets/posts/gatech/gpu/m6l1_gpuflow3.png)
[![image](https://lowyx.com/assets/posts/gatech/gpu/m6l1_gpuflow4.png)](https://lowyx.com/assets/posts/gatech/gpu/m6l1_gpuflow4.png)

**The Solution: SIMT Stack**
If we only store a single alternative PC value, nested branches (branches within branches) will overwrite that value, causing the processor to lose track of unexecuted paths. To solve this, GPUs use a hardware stack known as the **SIMT (Single Instruction, Multiple Thread) Stack**, which operates similarly to nested function calls.

[![image](https://lowyx.com/assets/posts/gatech/gpu/m6l1_gpuflow5.png)](https://lowyx.com/assets/posts/gatech/gpu/m6l1_gpuflow5.png)
[![image](https://lowyx.com/assets/posts/gatech/gpu/m6l1_gpuflow6.png)](https://lowyx.com/assets/posts/gatech/gpu/m6l1_gpuflow6.png)

1. Upon hitting a divergent branch, the processor pushes the **alternative PC value** and the **reconvergence point** onto the SIMT stack.
2. It proceeds to execute the current path. If it hits another divergence, it pushes the new alternative PC and reconvergence point onto the stack.
3. When the processor computes the next PC and finds that it matches the reconvergence point at the top of the stack, it **pops** the stack.
4. Instead of continuing past the reconvergence point, it fetches the alternative PC it just popped. 
5. This process repeats until all alternative paths are executed and the stack is empty for that branch, allowing all threads to finally reconverge.

> **Example:** For an `if-else` branch, the stack pushes the `else` path and the reconvergence point, then starts executing the `if` path. At the reconvergence point, it pops the `else` path, executes it, and at the next reconvergence point, the stack is empty so it proceeds normally.

### 4. Identifying the Reconvergence Point
How does the hardware know where the reconvergence point is?
* **Static/Compile Time:** The compiler uses control flow graph analysis to insert a marker or a special instruction indicating the reconvergence point. Some compilers insert explicit stack operations specifying when to push and pop.
* **Hardware Preference:** Hardware generally prefers to manage the stack autonomously, detecting divergence and storing reconvergence points based purely on hardware information.
* **Compiler Drawbacks:** Determining divergent branches at compile time is difficult, often leading compilers to over-classify branches as divergent. Thus, runtime hardware management is preferred.

> **Common Confusion:** Why can't the compiler just look at the `if` condition? Because the condition often depends on runtime values, like data loaded from memory or thread IDs interacting with dynamic data. The compiler can't always prove whether threads in the same warp will take the same path.

### 5. Large Warps & Dynamic Warp Formation
**Large Warps:**
The width of a warp (e.g., 32, 64, 120 threads) is a microarchitecture feature.
* **Pros:** A wider warp acts as a wide vector processor; fetching a single instruction generates many execution operations, improving throughput.
* **Cons:** Larger warps have a much higher chance of encountering divergence, forcing the processor through complex SIMT stack operations.
* **Application Dependency:** Optimal warp size is highly application-specific. Uniform execution paths benefit from large warps, while highly divergent paths suffer.

> **Hypothetical:** If a GPU had a warp size of 1, there would be no divergence penalty ever, because each thread manages its own PC. But the hardware cost of fetching and decoding instructions independently for thousands of threads would be astronomically high!

**Dynamic Warp Formation:**
[![image](https://lowyx.com/assets/posts/gatech/gpu/m6l1_dynamicwarp.png)](https://lowyx.com/assets/posts/gatech/gpu/m6l1_dynamicwarp.png)

When a warp diverges, execution unit utilization plummets (e.g., dropping to 50% if half the threads take a different path). To solve this, **Dynamic Warp Formation** regroups active threads from different warps that are executing the same PC into a new, temporary warp.
* This dramatically increases execution width utilization.
* **Challenge:** Thread placement within a warp is usually optimized to minimize register file read/write conflicts. Regrouping threads dynamically risks breaking this optimization and causing severe register file conflicts.

> **Tradeoff:** Dynamic Warp Formation sacrifices register access efficiency (and increases crossbar complexity) to win back ALU utilization during highly divergent control flow.

## Lesson 2: Register Optimizations

### 1. Register File Challenges
* **Size & Scalability:** Each Streaming Multiprocessor (SM) manages a massive number of threads, each requiring multiple registers. The total register file size per SM can easily reach 64KB, 128KB, or even 256KB.
* **Bandwidth & Latency:** Providing high bandwidth and low latency for such large structures is challenging. In GPUs, register file read bandwidth must match execution bandwidth.
* **Solutions borrowed from CPUs:** We can apply traditional computer architecture optimizations, such as hierarchical structures (to reduce latency) and resource sharing (to reduce size).

### 2. Key Observations on GPU Register Usage

**Observation 1: Not All Threads are Active**
GPUs execute asynchronously. While the SPMD model gives all threads identical register file requirements on paper, threads finish at different times. Once a thread finishes, its allocated registers are **no longer needed**. Furthermore, divergent branches cause varying runtime register usage across threads.

**Observation 2: Not All Registers are Live**
[![image](https://lowyx.com/assets/posts/gatech/gpu/m6l2_o2.png)](https://lowyx.com/assets/posts/gatech/gpu/m6l2_o2.png)
A register is "live" if its stored value will be read again; it is "dead" if it will be overwritten before the next read. In CPUs, an instruction writing to a register is often immediately followed by the instruction reading it. In GPUs, due to heavy warp-interleaving (executing warp 1, then warp 2, etc., to hide latency), the time between a register becoming "dead" and becoming "live" again can be extremely long.

> **Intuition:** CPU threads sprint through their instructions, so registers are hot. GPU threads take turns taking single steps, meaning a value written to a register might sit there for hundreds of cycles while other warps take their turns, doing nothing but occupying space.

**Observation 3: Short Distances Between Instructions**
[![image](https://lowyx.com/assets/posts/gatech/gpu/m6l2_o3.png)](https://lowyx.com/assets/posts/gatech/gpu/m6l2_o3.png)
Conversely, there are instances where a value is computed and immediately consumed by the very next instruction within the same thread. If the scheduler groups these instructions tightly, the value doesn't necessarily need to be written to the main register file at all; it could be bypassed.

**Observation 4: Most Register Values are Read Only Once**
[![image](https://lowyx.com/assets/posts/gatech/gpu/m6l2_o4.png)](https://lowyx.com/assets/posts/gatech/gpu/m6l2_o4.png)
Studies show that almost 70% of GPU register values are read only once before being overwritten. This begs the question: is it necessary to store these transient values in a massive, power-hungry register file?

> **Background Context:** This high "read-once" rate is due to the nature of graphics and compute shaders, which often involve long sequences of independent math operations (e.g., `A = B * C`, `D = A + E`, where `A` is never used again).

### 3. Register Optimization Techniques

**Optimization 1: Hierarchical Register Files**
[![image](https://lowyx.com/assets/posts/gatech/gpu/m6l2_opt1.png)](https://lowyx.com/assets/posts/gatech/gpu/m6l2_opt1.png)
To improve access latency and reduce power consumption, register files can be split into a hierarchy:
* **Register File Cache:** A smaller, faster L0/L1 register cache stores actively used values, while the main register file acts as a slower backing store.
* **Partitioned Register Files:** Different storage technologies can be used. For instance, slow, large register files could be implemented using non-volatile memory to save energy, while active registers are kept in fast SRAM.

**Optimization 2: Register File Virtualization**
[![image](https://lowyx.com/assets/posts/gatech/gpu/m6l2_opt2.png)](https://lowyx.com/assets/posts/gatech/gpu/m6l2_opt2.png)
Since not all allocated registers are actively storing useful data at the same time, we can decouple the register namespace from physical storage.
* By using a small pool of physical registers mapped to a larger virtual namespace, we facilitate resource sharing. This maintains program compatibility while significantly reducing the physical hardware footprint.

> **Mental Model:** Similar to virtual memory where pages are mapped to physical RAM on demand, Register File Virtualization maps "virtual" registers to a smaller set of physical registers only when they actually hold live data.

## Lesson 3: Unified Register File and Shared Memory

### 1. Reviewing Occupancy
In CUDA programming, the maximum number of blocks an SM can run (its **occupancy**) is constrained by its hardware resources—specifically, register file size and shared memory. 
* *Example SM Resources:* 64KB registers, 32KB shared memory.
* *Scenario A:* A program requires 64 registers per block but no shared memory. Shared memory is underutilized, but register exhaustion limits occupancy.
* *Scenario B:* A program requires 4 registers per block but 2KB of shared memory. Register files are heavily underutilized, but shared memory limits occupancy.
* **The Goal:** Can we increase occupancy by sharing resources between the register file and shared memory?

> **Example:** If we have a single pool of 96KB memory, Scenario A could allocate 64KB for registers and 0KB for shared memory, while Scenario B could allocate 4KB for registers and 2KB for shared memory. Both would achieve maximum occupancy without hitting artificial partition limits.

### 2. Cache Types: Hardware vs. Software Managed
* **Hardware-Managed Cache:** The hardware decides what to cache (e.g., via LRU policies). It requires address tag bits to verify if requested data is present in the cache.
* **Software-Managed Cache:** The programmer explicitly manages memory placement (e.g., GPU shared memory). No tag bits are required because the software guarantees the data's location. 

### 3. Register Files vs. Software-Managed Cache
A register file and a software-managed cache (like GPU shared memory) share many similarities:
* Both store raw data.
* Both omit address tags (the location *is* the address).
* **Differences:** Register files require multiple read/write ports (often reading two operands simultaneously per instruction), whereas standard memory typically accesses one address per cycle. However, register access patterns are known statically at compile time, providing unique optimization opportunities.

### 4. Proposed Solution: Unified Structures
By creating a unified structure that serves as both shared memory and the register file, hardware can dynamically allocate resources based on the specific needs of a program.
* **Benefits:** Flexible resource sharing eliminates hard boundary constraints. Occupancy is now limited by the *sum* of register and shared memory requirements, rather than whichever hits its individual limit first.
* **Challenges:** Unified structures require exceptionally high memory bandwidth. They must support the heavy multi-port demands of register accesses, often necessitating highly complex, heavily banked memory architectures to prevent conflicts between different access patterns.

> **Tradeoff:** Unifying the structures maximizes capacity utilization (better occupancy), but severely complicates the memory banking and routing logic to satisfy both the predictable, wide accesses of registers and the dynamic accesses of shared memory.
