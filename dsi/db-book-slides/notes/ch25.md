## Hardware Tuning: Choice of RAID Level
- **RAID 1 vs. RAID 5**: The choice depends on the ratio of reads to writes.
- RAID 5 requires 2 block reads and 2 block writes to write out one data block.
- For an application requiring $r$ reads and $w$ writes per second:
  - RAID 1 requires $r + 2w$ I/O operations per second.
  - RAID 5 requires $r + 4w$ I/O operations per second.
- For reasonably large $r$ and $w$, this requires lots of disks to handle the workload.
- RAID 5 may actually require more disks than RAID 1 to handle the load. The apparent saving of the number of disks by RAID 5 (by using parity, as opposed to mirroring done by RAID 1) may be illusory!
- **Thumb Rule**: RAID 5 is fine when writes are rare and data is very large, but RAID 1 is preferable otherwise. If you need more disks to handle the I/O load, just mirror them since disk capacities these days are enormous.

## Tuning the Database Design
### Materialized Views
- Materialized views can help speed up certain queries, particularly aggregate queries.
- **Overheads**:
  - Space requirements.
  - Time for view maintenance.
- **Immediate View Maintenance**: Done as part of the update transaction. The time overhead is paid by the update transaction.
- **Deferred View Maintenance**: Done only when required. The update transaction is not affected, but system time is spent on view maintenance. Until updated, the view may be out-of-date.
- Preferable to a denormalized schema since view maintenance is the system's responsibility, not the programmer's. This avoids inconsistencies caused by errors in update programs.

### Choosing Materialized Views
- Helping one transaction type by introducing a materialized view may hurt others.
- The choice of materialized views depends on costs. Users often have no idea of the actual cost of operations.
- Overall, manual selection of materialized views is tedious.
- Some database systems provide tools to help the DBA choose views to materialize (e.g., "Materialized view selection wizards").

## Tuning of Transactions
### Reducing Lock Contention
- Long transactions (typically read-only) that examine large parts of a relation result in lock contention with update transactions.
  - *Example*: Large query to compute bank statistics vs. regular bank transactions.
- **To Reduce Contention**:
  - Use multi-version concurrency control.
    - *Example*: Oracle "snapshots" which support multi-version 2PL.
  - Use degree-two consistency (cursor-stability) for long transactions.
    - *Drawback*: The result may be approximate.

### Handling Long Update Transactions
- Long update transactions cause several problems:
  - Exhaust lock space.
  - Exhaust log space, greatly increase recovery time after a crash, and may even exhaust log space during recovery if the recovery algorithm is badly designed.
- **Mini-batch Transactions**: Use them to limit the number of updates that a single transaction can carry out.
  - *Example*: If a single large transaction updates every record of a very large relation, the log may grow too big.
  - Split large transaction into a batch of "mini-transactions", each performing part of the updates.
  - Hold locks across transactions in a mini-batch to ensure serializability.
  - If lock table size is a problem, locks can be released, but at the cost of serializability.
  - In case of failure during a mini-batch, the remaining portion must be completed on recovery to ensure atomicity.

## Performance Simulation
- Performance simulation using a queuing model is useful to predict bottlenecks as well as the effects of tuning changes, even without access to a real system.
- **Queuing Model**: Models activities that go on in parallel.
- **Simulation Model**: Quite detailed, but usually omits some low-level details.
  - Models service time, but disregards details of service.
  - *Example*: Approximate disk read time by using an average disk read time.
- Experiments can be run on the model to provide an estimate of measures such as average throughput and response time.
- Parameters can be tuned in the model and then replicated in the real system (e.g., number of disks, memory, algorithms).

## Database Application Classes
- **Online Transaction Processing (OLTP)**: Requires high concurrency and clever techniques to speed up commit processing to support a high rate of update transactions.
- **Decision Support Applications**: Includes Online Analytical Processing (OLAP) applications. Requires good query evaluation algorithms and query optimization.
- **Architecture Tuning**:
  - Some database systems are tuned to one of the two classes (e.g., Teradata is tuned to decision support).
  - Others try to balance the two requirements (e.g., Oracle, with snapshot support for long read-only transactions).

## Benchmarks Suites
### TPC Benchmarks
- **TPC-D**: Complex decision support application. Superceded by TPC-H and TPC-R.
- **TPC-H (Ad Hoc)**: Based on TPC-D with some extra queries.
  - Models ad hoc queries which are not known beforehand.
  - Total of 22 queries with emphasis on aggregation.
  - Prohibits materialized views.
  - Permits indices only on primary and foreign keys.
- **TPC-R (Reporting)**: Same as TPC-H, but without any restrictions on materialized views and indices.
- **TPC-W (Web)**: End-to-end Web service benchmark modeling a Web bookstore, with a combination of static and dynamically generated pages.

### TPC Performance Measures
- **Two types of tests for TPC-H and TPC-R**:
  - **Power Test**: Runs queries and updates sequentially, then takes the mean to find queries per hour.
  - **Throughput Test**: Runs queries and updates concurrently. Multiple streams running in parallel each generate queries, with one parallel update stream.
- **Composite Query per Hour Metric**: Square root of the product of power and throughput metrics.
- **Composite Price/Performance Metric**.

### Other Benchmarks
- **OODB Transactions**: Require a different set of benchmarks.
  - **OO7 Benchmark**: Has several different operations and provides a separate benchmark number for each kind of operation. Reason: it is hard to define what a typical OODB application is.
- Benchmarks for XML are being discussed.

## SQL Standards History
- **SQL:1999**: Adds a variety of new features (extended data types, object orientation, procedures, triggers, etc.). Broken into several parts:
  - **SQL/Framework (Part 1)**: Overview.
  - **SQL/Foundation (Part 2)**: Types, schemas, tables, query/update statements, security, etc.
  - **SQL/CLI (Part 3)**: Call Level Interface (API interface).
  - **SQL/PSM (Part 4)**: Persistent Stored Modules (procedural extensions).
  - **SQL/Bindings (Part 5)**: Embedded SQL for different embedding languages.
- **More parts undergoing standardization process**:
  - **Part 7 (SQL/Temporal)**: Temporal data.
  - **Part 9 (SQL/MED - Management of External Data)**: Interfacing of the database to external data sources. Allows other databases or files to be viewed as part of the database.
  - **Part 10 (SQL/OLB - Object Language Bindings)**: Embedding SQL in Java.
  - Missing part numbers 6 and 8 cover features that are not near standardization yet.

## XML-Based Standards
- Several XML-based standards exist for E-commerce (e.g., RosettaNet for supply chains, BizTalk).
  - Define catalogs, service descriptions, invoices, purchase orders, etc.
- XML wrappers are used to export information from relational databases to XML.
- **Simple Object Access Protocol (SOAP)**: XML-based remote procedure call standard.
  - Uses XML to encode data, HTTP as the transport protocol.
  - Standards based on SOAP for specific applications (e.g., OLAP and Data Mining standards from Microsoft).

## E-Commerce
- **Definition**: The process of carrying out various activities related to commerce through electronic means.
- **Activities include**:
  - **Presale activities**: Catalogs, advertisements, etc.
  - **Sale process**: Negotiations on price and quality of service.
  - **Marketplace**: Stock exchange, auctions, reverse auctions.
  - **Payment for sale**.
  - **Delivery related activities**: Electronic shipping or electronic tracking of order processing/shipping.
  - **Customer support and post-sale service**.

### E-Catalogs
- Product catalogs must provide searching and browsing facilities:
  - Organize products into an intuitive hierarchy.
  - Keyword search.
  - Help customers with the comparison of products.
- **Customization of catalog**:
  - Negotiated pricing for specific organizations.
  - Special discounts for customers based on past history (e.g., loyalty discounts).
  - Legal restrictions on sales (e.g., certain items not exposed to under-age customers).
  - Customization requires extensive customer-specific information.

### Marketplaces
- Help in negotiating the price of a product when there are multiple sellers and buyers. Real-world marketplaces can be quite complicated due to product differentiation.
- **Database issues**:
  - Authenticate bidders.
  - Record buy/sell bids securely.
  - Communicate bids quickly to participants (delays can lead to financial loss).
  - Need to handle very large volumes of trade at times (e.g., at the end of an auction).
- **Types of Marketplaces**:
  - **Reverse Auction System**: Single buyer, multiple sellers. Buyer states requirements, sellers bid for supplying items. Lowest bidder wins (tender system). Open bidding vs. closed bidding.
  - **Auction**: Multiple buyers, single seller. Simplest case: only one instance of each item is being sold, and the highest bidder wins. More complicated with multiple copies where buyers bid for a specific number of copies.
  - **Exchange**: Multiple buyers, multiple sellers (e.g., stock exchange). Buyers specify a maximum price, sellers specify a minimum price. The exchange matches buy and sell bids, deciding on a price for the trade (e.g., average of buy/sell bids).

### Order Settlement and Payment
- **Order Settlement**: Payment for goods and delivery.
- **Insecure means for electronic payment** (e.g., sending credit card numbers):
  - Buyers may present someone else's credit card numbers.
  - Seller has to be trusted to bill only for the agreed-on item and not pass the number to unauthorized people.
- **Need for Secure Payment Systems**:
  - Avoid the above problems and provide a greater degree of privacy (e.g., not reveal the buyer's identity to the seller).
  - Ensure that anyone monitoring electronic transmissions cannot access critical information.

### Secure Payment Systems
- All information must be encrypted to prevent eavesdropping (Public/private key encryption widely used).
- Must prevent **person-in-the-middle attacks** (e.g., someone impersonates the seller or bank and fools the buyer into revealing information). Encrypting messages alone doesn't solve this.
- Three-way communication between seller, buyer, and credit-card company:
  - Credit card company credits the amount to the seller.
  - Consolidates all payments from a buyer and collects them together (e.g., via buyer's bank).
- **Digital Certificates**: Used to prevent impersonation/man-in-the-middle attacks.
  - Certification agency creates a digital certificate by encrypting the seller's public key using its own private key (verifies seller's identity by external means first).
  - Seller sends certificate to the buyer.
  - Customer uses the public key of the certification agency to decrypt the certificate and find the seller's public key. A man-in-the-middle cannot send a fake public key.
  - Seller's public key is used for setting up secure communication.
  - Example of secure payment protocol: **Secure Electronic Transaction (SET)**.

### Digital Cash
- Credit-card payment does not provide anonymity. Even with the SET protocol (which hides the buyer's identity from the seller), the buyer can be traced with the help of the credit card company.
- **Digital Cash Systems**: Provide anonymity similar to physical cash (e.g., Digicash).
  - Based on encryption techniques that make it impossible to find out who purchased digital cash from the bank.
  - Digital cash can be spent by the purchaser in parts (much like writing a check on an account whose owner is anonymous).

## Legacy Systems
- **Definition**: Older-generation systems that are incompatible with current generation standards and systems but still in production use (e.g., Cobol applications on mainframes). Today's hot new system is tomorrow's legacy system.
- Porting legacy applications to a more modern environment is problematic:
  - Very expensive; involves millions of lines of code written over decades.
  - Original programmers are usually no longer available.
- **Wrapper Approach**: Build a wrapper layer on top of a legacy application to allow interoperation between newer systems and the legacy application (e.g., using ODBC or OLE-DB).
- **Rewriting Legacy Applications**:
  - Requires understanding what it does (often has no/outdated documentation).
  - **Reverse Engineering**: Going over legacy code to come up with schema designs (ER or OO model) and find out what procedures are implemented to get a high-level view.
  - **Re-engineering**: Reverse engineering followed by the design of a new system (improvements are made).
- **Switching Over (Old to New System)**:
  - Production systems are used every day, generating new data. Stopping them may cause enormous losses.
  - **Big-bang Approach**:
    1. Implement a completely new system.
    2. Populate it with data from the old system (no transactions during this step; scripts used to do this quickly).
    3. Shut down the old system and start using the new system.
    - *Danger*: Bugs, performance problems, or missing features can bring the company to a halt.
  - **Chicken-little Approach**:
    - Replace legacy system one piece at a time.
    - Use wrappers to interoperate between legacy and new code (e.g., replace front end first, with wrappers on the legacy backend).
    - Old front end can continue working in case of problems.
    - Replace back end one functional unit at a time.
    - *Drawback*: Significant extra development effort to build wrappers and ensure smooth interoperation. Still worth it if the company's life depends on the system.
