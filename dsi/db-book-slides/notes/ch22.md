## Parallel Query Processing
Different queries/transactions can be run in parallel with each other.
- **Interquery parallelism:** Concurrency control takes care of conflicts in case of updates. The focus here is on read-only queries (more on parallel transaction processing in Chapter 23).
- Individual relational operations (e.g., sort, join, aggregation) can be executed in parallel. Data can be partitioned and each processor can work independently on its own partition.
- Queries are expressed in a high-level language (SQL, translated to relational algebra), which makes parallelization easier.

### Intraquery Parallelism
Execution of a single query in parallel on multiple processors/disks. It is important for speeding up long-running queries. 
Two complementary forms:
- **Intraoperation Parallelism:** Parallelize the execution of each individual operation in the query. Supports a high degree of parallelism.
- **Interoperation Parallelism:** Execute the different operations in a query expression in parallel. Limited degree of parallelism.

### Parallel Processing of Relational Operations
Assumptions for parallel algorithms:
- Read-only queries
- Shared-nothing architecture with $n$ nodes, $N_1, \dots, N_n$
- Each node has its own disks and processors.

Shared-nothing architectures can be efficiently simulated on shared-memory and shared-disk systems. Algorithms for shared-nothing systems can thus be run on shared-memory and shared-disk systems. However, some optimizations may be possible.

## Intraoperation Parallelism

### Range-Partitioning Parallel Sort
![Parallel Sort](../images/ch22_slides/slide_009.png)
1. **Redistribute:** Choose nodes $N_1, \dots, N_m$, where $m \le n -1$ to do sorting. Create a range-partition vector with $m-1$ entries on the sorting attributes. Redistribute the relation using range partitioning.
2. **Local Sort:** Each node $N_i$ sorts its partition of the relation locally. This is an example of data parallelism: each node executes the same operation in parallel without interaction with the others.
3. **Merge:** The final merge operation is trivial: range-partitioning ensures that if $i < j$, all key values in node $N_i$ are less than all key values in $N_j$.

### Parallel External Sort-Merge
- Assume the relation has already been partitioned among nodes $N_1, \dots, N_n$.
- Each node $N_i$ locally sorts the data (using local disk as required).
- The sorted runs on each node are then merged in parallel:
  - The sorted partitions at each node $N_i$ are range-partitioned across the processors $N_1, \dots, N_m$.
  - Each node $N_i$ performs a merge on the streams as they are received to get a single sorted run.
  - The sorted runs on nodes $N_1, \dots, N_m$ are concatenated to get the final result.
- **Execution Skew:** The described algorithm is vulnerable to execution skew (e.g., all nodes send to node 1, then to node 2). It can be modified so each node sends data to all other nodes in parallel (block at a time).

### Partitioned Parallel Join
![Partitioned Parallel Join](../images/ch22_slides/slide_012.png)
For equi-joins and natural joins, the two input relations can be partitioned across processors to compute the join locally.
- Use either range partitioning or hash partitioning.
- Relations $r$ and $s$ must be partitioned on their join attributes ($r.A$ and $s.B$) using the same range-partitioning vector or hash function.
- The join can be computed locally using hash join, merge join, or nested-loops join (leading to partitioned parallel variants of these algorithms).

#### Partitioned Parallel Hash-Join
- A hash function $h_1$ maps the join attribute value of each tuple in $s$ to one of the $n$ nodes.
- As tuples are received at destination nodes, they are further partitioned using another hash function $h_2$, which is used to compute the hash-join locally.
- Repeat for each tuple in $r$.
- Each node $N_i$ executes the build and probe phases of the hash-join on local partitions $r_i$ and $s_i$.
- Hash-join optimizations (like hybrid hash-join to cache incoming tuples in memory) can be applied.

### Fragment-and-Replicate Joins
![Fragment-and-Replicate Joins](../images/ch22_slides/slide_015.png)
When partitioning is not possible (e.g., non-equijoin conditions like $r.A > s.B$), use the fragment-and-replicate technique.
- **Asymmetric Fragment-and-Replicate (Broadcast Join):**
  - One relation, say $r$, is partitioned (using any technique).
  - The other relation, $s$, is replicated across all processors.
  - Node $N_i$ computes the join of $r_i$ with all of $s$.
- Both asymmetric and symmetric fragment-and-replicate work with any join condition, since every tuple in $r$ can be tested with every tuple in $s$.
- This typically has a higher cost than partitioning because of replication.
- Sometimes preferable if $s$ is small, $r$ is large, and $r$ is already partitioned. Replicating $s$ may be cheaper than repartitioning both on join attributes.

### Handling Skew
Skew can significantly slow down parallel joins.
- **Avoidance:** Balanced partitioning vector, Virtual node partitioning.
- **Dynamic handling:** Detect overloaded physical nodes. If a physical node has no remaining work, it can take on a waiting task (virtual node) currently assigned to a different physical node that is overloaded (**work stealing**). Cheaper in shared memory but usable in shared-nothing/shared-disk systems.

### Other Relational Operations
- **Selection $\sigma_\theta(r)$:**
  - If $\theta$ is $a_i = v$ and $r$ is partitioned on $a_i$, perform at a single node.
  - If $\theta$ is a range selection and $r$ is range-partitioned on $a_i$, perform at nodes overlapping the range.
  - Otherwise, perform in parallel at all nodes.
- **Duplicate Elimination:**
  - Perform using parallel sort techniques and eliminate duplicates as they are found.
  - Alternatively, partition tuples (range/hash) and perform locally at each node.
- **Projection:**
  - Projection without duplicate elimination can be performed as tuples are read from disk in parallel.
  - If duplicate elimination is required, use the above techniques.

### Grouping/Aggregation
1. **Partition** the relation on the grouping attributes.
2. **Compute** aggregate values locally at each node.
- **Optimization (Partial Aggregation):** Reduce tuple transfer cost by aggregating before partitioning (for distributive aggregates). 
  - Perform aggregation locally on tuples, resulting in partial sums.
  - The result is then partitioned on grouping attributes and aggregated again at destination nodes to get final results.

### Map and Reduce Operations
![Map and Reduce Operations](../images/ch22_slides/slide_022.png)
- **Workers:** Threads/processes that execute map and reduce functions.
- **Tasks:** Units of work. There are many more tasks than workers (similar to virtual node partitioning).
- **Skew Handling:**
  - **Straggler tasks:** Handled by initiating an extra copy of the task at another node.
  - **Combiners (Partial Aggregation):** Helps reduce skew at reduce nodes.

## Parallel Evaluation of Query Plans
![Parallel Plans](../images/ch22_slides/slide_032.png)

### Interoperator Parallelism
#### Pipelined Parallelism
- Example: $r_1 \bowtie r_2 \bowtie r_3 \bowtie r_4$. Set up a pipeline computing the joins in parallel.
- Each operation sends result tuples to the next even as it computes further results (requires pipelineable algorithms like indexed nested loops join).
- **Push model:** Appropriate for pipelining. Buffers sit between consumers and producers. Tuples can be batched before sending to reduce messages and shared buffer contention.
- **Limitations:** Pipeline chains are not very long (low degree of parallelism). Cannot pipeline operators that need all inputs before outputting (e.g., sort, aggregate). Little speedup if there is skew (one operator costs much more).
- **Utility:** Still very useful as it avoids writing intermediate results to disk.

#### Independent Parallelism
- Example: Let $N_1$ compute $temp_1 = r_1 \bowtie r_2$ and $N_2$ compute $temp_2 = r_3 \bowtie r_4$.
- $N_1$ and $N_2$ work independently in parallel.
- $N_3$ computes $temp_1 \bowtie temp_2$ and waits for input from $N_1$ and $N_2$.
- Less useful in highly parallel systems due to limited degree of parallelism.

### Exchange Operator Model
- Movement of data is encapsulated in the **exchange operator** (partition and merge steps).
- **Partitioning:** Hash, Range, Broadcasting (replication), or sending all data to a single node.
- **Merging:** Random merge or Ordered merge.
- Other operators can be unaware of parallelism (Data parallelism: each works on local data).

**Parallel Plans Using Exchange Operator:**
- **Range partitioning sort:** Exchange operator (range) $\rightarrow$ Local sort.
- **Parallel external sort merge:** Local sort $\rightarrow$ Exchange operator (ordered merge).
- **Partitioned join:** Exchange operator (hash/range) $\rightarrow$ Local join.
- **Asymmetric fragment and replicate:** Exchange operator (broadcast) $\rightarrow$ Local join.

### Fault Tolerance in Query Plans
![Fault Tolerance in Map-Reduce](../images/ch22_slides/slide_036.png)
- **Alternative 1: Re-execute query on failure.** Good for medium-scale (100s of machines) if mean time to failure $\gg$ execution time. Bad for massively parallel long queries.
- **Alternative 2: Re-execute work of only failed nodes.** Good if consumers process data only after it is completely generated (e.g., map-reduce). Discard partial data. Harder with pipelined execution (must generate tuples in exact same order to determine which are new).
- **Map-Reduce Fault Tolerance:** Map workers write to local disk. Reducers use data only after fully received. On map failure, re-execute map task and reducers discard partial data. On reduce failure, re-execute and re-fetch from map nodes. Results are safely replicated on a distributed file system.
- **Fault Tolerant Query Execution Overheads:** Materialization cost and waiting for previous steps. Apache Spark uses **Resilient Distributed Datasets (RDDs)**: Data is replicated in memory/disk, but intermediate results are not materialized. Query nodes can be re-executed to regenerate results.

## Query Processing in Shared Memory Systems
- Shared memory parallel processing is usually thread-based.
- **Optimized Algorithms:**
  - Asymmetric fragment-and-replicate: smaller relation can be in shared memory instead of being replicated.
  - Hash join: Build relation partitioned or shared in memory with a single index. Probe relation partitioned into "morsels".
  - Shared index construction requires atomic instructions (test-and-set/compare-and-swap).
- **Skew Handling:** Work stealing is cheap.
- **NUMA (Non-Uniform Memory Access):** Threads should be scheduled on the same core. Data structures used by 1 thread should be allocated in memory local to that core.
- **SIMD Parallelism:** Single Instruction Multiple Data (GPUs, Intel Xeon Phi, vector processing) is increasingly used for relational operations.

## Query Optimization for Parallel Execution
Significantly more complex than sequential databases due to partitioning options, complex cost models, skew, and resource contention.

### Parallel Query Plan Space
A parallel plan specifies:
- How to parallelize operations (algorithm, exchange operators).
- Scheduling (nodes per operation, pipelining, independent/sequential execution).
- Example: Partitioning $r$ and $s$ on $(A, B)$ for join requires repartitioning for aggregation on $A$, but partitioning on $A$ avoids this.

### Cost of Parallel Query Execution
- **Resource consumption cost model:** CPU + I/O cost (used for centralized DBs).
- **Response time cost model:** $T = \max(\text{CPU cost}, \text{I/O cost})$.
  - For parallel operators: $T = \max(T_1, \dots, T_n)$.
  - Must account for startup costs and skew. Better suited for parallel DBs but increases optimization cost.
- **Cost Estimation:** $T_{part} + T_{asm} + \max(T_1, \dots, T_n)$.

### Choosing Query Plans
1. **Heuristic:** Choose the best sequential plan, then parallelize. (Best sequential might not lead to the best parallel plan).
2. **Extended Cost Model:** Parallelize every operation across all nodes, use exchange operators, and use a standard optimizer with an extended cost model.

### Physical Schema
- **Colocation:** Store data accessed together on the same nodes (e.g., student records with their `takes` records).
- Store multiple copies partitioned on different attributes.
- **Materialized Views:** Avoid joins at query time; partitioned across nodes. Speeds up queries but increases update costs.

## Streaming Data
- Real-time analytics with online processing of incoming data.
- **Lambda architecture:** Send a copy to a real-time stream system and another to data storage. Modern systems often combine both.

### Parallel Processing of Streaming Data
![Logical Routing of Streams](../images/ch22_slides/slide_052.png)
- **Logical Routing:** Handled via a Directed Acyclic Graph (DAG), configured statically (Apache Storm topology) or dynamically via publish-subscribe (Apache Kafka).
- **Physical DAG:** Multiple instances of operators run in parallel. Each topic/stream is partitioned.
- Operators often store state locally (cheaper) or in parallel data-stores (fault tolerance).

### Fault Tolerance
- Semantics: At-least once, At-most once, Exactly once.
- **Checkpoints:** Lower overhead by checkpointing operator state and replaying from the checkpoint instead of persisting all output. Must remove duplicates.
- **Replication:** Running a hot-spare copy concurrently allows instant recovery.

## Distributed Query Processing

### Data Integration From Multiple Sources
- **Federated Database System:** A software layer on top of heterogeneous databases, creating an illusion of logical integration. Has global schema integrating local schemas.
- **Mediator Systems / Virtual Database:** Support common schema and queries, but not updates.
- **Data Virtualization:** Allows access without a common schema.
- **External Data:** SQL Management of External Data (SQL MED). Wrappers translate local data to global schema and vice versa for updates.

### Data Warehouses and Data Lakes
- **Data Warehouse:** Migrates data to a common schema. Avoids run-time overhead but incurs translation cost.
- **Data Lake:** Data is stored in multiple storage systems/formats but can be queried from a single system.

### Schema and Data Integration
- **Global-as-view:** At each site, create a view of local data mapping to the global schema. Good for queries, hard for updates.
- **Local-as-view:** Create a view defining contents of local data as a view of global data. View is for update processing.
- **Unified View of Data:** Requires agreement on common data model, conceptual schema, representation (data types, character sets), units of measure, and names (globally unique naming or name equivalences like Linked Data).

### Query Processing Across Data Sources
- Address limited query capabilities of sources (e.g., web forms). Break up queries.
- Remove duplicate information.
- Global query optimization to decide execution sites.

### Join Locations and Join Ordering
Consider $r_1 \bowtie r_2 \bowtie r_3$ stored at $S_1, S_2, S_3$, with result needed at $S_I$.
- **Options:** Ship all to $S_I$; or ship $r_1$ to $S_2$, compute $r_1 \bowtie r_2$, ship result to $S_3$, compute final join, and ship to $S_I$.
- Must consider data volume, transmission cost, and processing speeds.
- Can exploit parallelism (e.g., compute $r_1 \bowtie r_2$ at $S_2$ and $r_3 \bowtie r_4$ at $S_4$ simultaneously).

### Semijoin Strategy
To compute $r_1 \bowtie r_2$ (at $S_1, S_2$):
1. Compute $temp_1 = \Pi_{R1 \cap R2}(r_1)$ at $S_1$.
2. Ship $temp_1$ to $S_2$.
3. Compute $temp_2 = r_2 \bowtie temp_1$ at $S_2$ (This is the semijoin $r_2 \ltimes r_1$).
4. Ship $temp_2$ back to $S_1$.
5. Compute $r_1 \bowtie temp_2$ at $S_1$.
- Reduces network transmission if the semijoin heavily filters $r_2$.
- **Bloom Filters:** Used to approximately compute semijoins efficiently using bitmaps.

### Distributed Query Optimization
- New physical property: Data location.
- Operators annotated with execution sites.
- Optimizer finds the best plan considering data location and operator execution location.

### Query Transformation
- Translating algebraic queries on fragmented relations.
- Example: $account$ horizontally fragmented into $account_1$ ("Hillside") and $account_2$ ("Valleyview"). A query for "Hillside" becomes $\sigma_{branch\_name = "Hillside"}(account_1 \cup account_2)$, optimized to just reading $account_1$.

### Distributed Directory Systems
- Used to store organizational data (DNS, LDAP).
- Stored and controlled hierarchically.
- Queried uniformly, with queries forwarded to the correct storage site.

### Advantages of Distributed/Federated Systems
- Preserves investment in hardware, software, and applications.
- Retains local autonomy and administrative control.
- Avoids the technical/political cost of converting everything into a unified homogeneous DBMS.
