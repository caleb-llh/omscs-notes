# Chapter 24: Advanced Indexing

## 1. Bloom Filters
- A **bloom filter** is a probabilistic data structure used to check the membership of a value in a set.
  - It may return true (with low probability) even if an element is not present (false positive).
  - It never returns false if an element is present.
  - Useful to filter out irrelevant sets.
- **Data Structure**: The key structure is a single bitmap. For a set with *n* elements, a typical bitmap size is *10n*.
- **Hash Functions**: It uses multiple independent hash functions.
  - **Single Hash Function**: With a single hash function $h()$ whose range is the number of bits in the bitmap:
    - For each element $s \in S$, compute $h(s)$ and set the bit $h(s)$.
    - To query an element $v$, compute $h(v)$ and check if the bit $h(v)$ is set.
    - **Problem**: There is a significant chance of a false positive due to hash collisions (e.g., a 10% chance with $10n$ bits).
  - **Multiple Hash Functions**: The key idea is to reduce false positives by using multiple hash functions $h_i()$ for $i = 1 \dots k$.
    - For each element $s \in S$, for each $i$, compute $h_i(s)$ and set the bit $h_i(s)$.
    - To query an element $v$, for each $i$, compute $h_i(v)$ and check if the bit $h_i(v)$ is set.
    - If the bit $h_i(v)$ is set for every $i$, report $v$ as present. Otherwise, report $v$ as absent.
    - **Performance**: With $10n$ bits and $k=7$, the false positive rate is reduced to 1% (compared to 10% with $k=1$).

## 2. Write Optimized Indices
- The performance of $B^+$-trees can be poor for write-intensive workloads:
  - There is one I/O per leaf (assuming all internal nodes are in memory).
  - With magnetic disks, $<100$ inserts per second per disk.
  - With flash memory, one page overwrite per insert.
- **Two approaches to reduce the cost of writes:**
  1. Log-structured merge tree
  2. Buffer tree

### Log Structured Merge (LSM) Tree
- Records are first inserted into an in-memory tree (L0 tree).
- When the in-memory tree is full, records are moved to disk (L1 tree).
  - A $B^+$-tree is constructed using a bottom-up build by merging the existing L1 tree with records from the L0 tree.
- When the L1 tree exceeds a threshold, it merges into an L2 tree, and so on for more levels.
- The size threshold for the $L_{i+1}$ tree is $k$ times the size threshold for the $L_i$ tree.
- Merging creates a new $B^+$-tree using a bottom-up build.

#### Benefits and Drawbacks of LSM
- **Benefits**:
  - Inserts are done using only sequential I/O operations.
  - Leaves are full, avoiding space wastage.
  - Reduced number of I/O operations per inserted record compared to normal $B^+$-trees.
  - **I/O Math**: If each leaf has $m$ entries, $m/k$ entries are merged in using 1 I/O. Total I/O operations: $(k/m) \log_k(I/M)$ where $I$ = total number of entries and $M$ is the size of the L0 tree.
- **Drawbacks**:
  - Queries have to search multiple trees.
  - The entire content of each level is copied multiple times.

#### Optimizations of LSM
- **Rolling merge**: Used to spread merging costs.
- **Partitioning**: LSM/Stepped Merge is often implemented on a partitioned relation. Each partition has a max size and is split if it becomes oversized. Partitions are spread over multiple machines.

#### Stepped Merge Index
- A variant of the LSM tree with $k$ trees at each level on disk.
- When all $k$ indices exist at a level, merge them into one index of the next level.
- **Advantages**: Reduces write cost compared to an LSM tree.
- **Disadvantages**: Queries are even more expensive since many trees need to be queried.
- **Optimization for Point Lookups**:
  - Compute a Bloom filter for each tree and store it in memory.
  - Query a tree only if the Bloom filter returns a positive result.

#### Deletion and Updates in LSM Trees
- **Deletion**: Handled by adding special "delete" entries. Lookups find both the original and delete entries and return only entries without a matching delete entry. When trees merge, matching original and delete entries are dropped.
- **Updates**: Handled using insert + delete.
- **Usage**: Initially for disk-based indices, but useful to minimize erases with flash-based indices. The stepped-merge variant is used in many BigData storage systems (Google BigTable, Apache Cassandra, MongoDB) and storage engines (SQLite4, LevelDB, MyRocks for MySQL).

### Buffer Tree
- An alternative to the LSM tree.
- **Key Idea**: Each internal node of a $B^+$-tree has a buffer to store inserts.
  - Inserts move to lower levels when the buffer is full.
  - A large buffer means many records move to lower levels at once, decreasing per-record I/O.
- **Benefits**: Less overhead on queries. Can be used with any tree index structure (e.g., PostgreSQL Generalized Search Tree (GiST) indices).
- **Drawback**: More random I/O than LSM trees.

## 3. Bitmap Indices
- A special type of index designed for efficient querying on multiple keys (not particularly useful for single attribute queries).
- Records are numbered sequentially (e.g., from 0).
- Applicable to attributes that have a relatively small number of distinct values (e.g., gender, country, income-level intervals).
- A **bitmap** is simply an array of bits.
- **Structure**: A bitmap index has a bitmap for each value of the attribute.
  - The bitmap has as many bits as records.
  - For value $v$, the bit for a record is 1 if the record has value $v$, and 0 otherwise.

### Operations and Efficiency
- Queries are answered using fast bitwise operations: Intersection (AND), Union (OR), Complementation (NOT).
  - Example: `Males with income level L1: 10010 AND 10100 = 10000`
- **Size**: Bitmap indices are very small. If there are 8 distinct values, the bitmap index is only 1% of the relation size.
- **Deletion**: Managed via an *Existence Bitmap* to note if there is a valid record at a location (used for complementation).
- **Null Values**: Bitmaps should be kept for all values, including `null`, to correctly handle SQL null semantics.
- **Implementation**:
  - Bitmaps are packed into words (e.g., computing AND of 32 or 64 bits at once).
  - Counting 1s can be done fast using precomputed arrays (byte by byte) or hardware instructions.
- Bitmaps can be used instead of Tuple-ID lists at leaf levels of $B^+$-trees for values with a large number of matching records (merging benefits of bitmaps and $B^+$-trees).

## 4. Spatial and Temporal Indices

### Spatial Data
- Databases can store spatial data types (lines, polygons, raster images).
- Queries can mix spatial and nonspatial conditions (e.g., contains, overlaps).
- Query types: Nearest neighbor queries, Range queries, Intersection/Union queries, Spatial joins.

### Indexing of Spatial Data
- **k-d tree**: Early structure for multiple dimensions.
  - Each level partitions space into two, cycling through dimensions at each level.
  - Partitioning stops when a node has fewer than a given number of points.
- **k-d-B tree**: Extends k-d tree to allow multiple child nodes for each internal node; suited for secondary storage.

### Division of Space by Quadtrees
![Division of Space by Quadtrees](../images/ch24_slides/slide_019.png)
- Each node is associated with a rectangular region. The top node is the entire target space.
- Non-leaf nodes divide their region into four equal-sized quadrants.
- Leaf nodes have between zero and a fixed maximum number of points.
- **PR quadtree**: Stores points; division is based on regions, not the actual set of points.
- **Region quadtree**: Stores array (raster) information. Leaves correspond to regions where all array values are the same.

### R-Trees
![Example R-Tree](../images/ch24_slides/slide_022.png)
- N-dimensional extensions of $B^+$-trees, useful for indexing rectangles and polygons.
- Generalizes the one-dimensional interval of a $B^+$-tree to an N-dimensional rectangle (bounding box).
- A polygon is stored only in one node, and the node's bounding box must contain the polygon (better storage efficiency than k-d trees/quadtrees).
- Bounding boxes of a node's children are allowed to overlap.

#### Search in R-Trees
- Starting from the root:
  - Leaf node: Output items whose keys intersect the query region.
  - Internal node: Recursively search each child whose bounding box intersects the query region.
- Can be inefficient in the worst case (searching multiple paths) but works well in practice.

#### Insertion in R-Trees
- Find a leaf by following a child whose bounding box contains the data item's bounding box, or whose overlap is maximum.
- **Splits**: Required when nodes overflow. Goal is to divide entries into two nodes so that their bounding boxes have minimum total area.
  - **Quadratic split (heuristic)**: Find the pair of entries with maximum separation, place them in two new nodes, and repeatedly assign the remaining entries based on "maximum preference" (increase in bounding box area).
  - **Linear split**: Cheaper heuristic running in linear time, but generates slightly worse splits.

#### Deleting in R-Trees
- Similar to $B^+$-tree deletion. Underfull nodes borrow from siblings or merge. Alternatively, remove all entries, delete the node, and reinsert.

### Indexing Temporal Data
- Temporal data has an associated time period (start and end time).
- End time is set to infinity if currently valid.
- **Temporal Index Creation**:
  - Use a spatial index (like an R-tree) with the attribute as one dimension and time as another.
  - **Problem**: Currently valid tuples have infinite intervals.
  - **Solution**: Store all current tuples in a separate index keyed on `(attribute, start-time)`. To find tuples valid at time $t$, search this index in the range `(attribute, 0)` to `(attribute, t)`.

## 5. Hashing

### Static Hashing
![Example of Hash File Organization](../images/ch24_slides/slide_033.png)
- A **bucket** is a unit of storage (typically a disk block).
- A **hash function** maps search-key values to bucket addresses.
- Used to locate entries for access, insertion, and deletion.
- In a hash index, buckets store entries with pointers to records. In a hash file-organization, buckets store the actual records.
- **Ideal Hash Function**: Uniform and random, assigning the same number of records to each bucket regardless of key distribution.

### Handling Bucket Overflows
- Overflows occur due to insufficient buckets or skew in data (duplicate keys or non-uniform hash function).
- **Overflow chaining (Closed Addressing)**: Overflow buckets are chained together in a linked list. (Open addressing is not suitable for databases).
- **Deficiencies of Static Hashing**: As databases grow, performance degrades due to overflows. If space is pre-allocated, space is wasted. Periodic reorganization is expensive. Dynamic hashing is a better solution.

### Dynamic Hashing
- **Periodic rehashing**: When the hash table gets too full, create a new larger table and rehash all entries.
- **Linear Hashing**: Rehashing is done in an incremental manner.
- **Extendable Hashing**: Tailored to disk-based hashing.
![General Extendable Hash Structure](../images/ch24_slides/slide_039.png)
  - Uses a hash function generating a $b$-bit integer (e.g., $b=32$).
  - At any time, uses only a prefix of $i$ bits ($0 \le i \le 32$) to index a bucket address table of size $2^i$.
  - Multiple entries in the table may point to the same bucket.
  - **Insertion**: If a bucket $j$ is full:
    - If $i > i_j$ (more than one pointer to bucket $j$): allocate a new bucket, split the records, and update the address table.
    - If $i = i_j$ (only one pointer to bucket $j$): increment $i$, double the address table size, and then split.
  - **Deletion**: Reverse process (coalescing buddy buckets, optionally decreasing table size).

#### Extendable Hashing vs. Other Schemes
- **Benefits**: Performance does not degrade with file growth; minimal space overhead.
- **Disadvantages**: Extra level of indirection; the address table might become larger than memory. Changing table size is expensive.
- **Linear Hashing**: An alternative that allows incremental growth of the directory without full doubling, at the cost of more bucket overflows.

### Partitioned Hashing
- Hash values are split into segments that depend on each attribute of a multi-attribute search-key.
- To answer an equality query on a single attribute, multiple buckets must be looked up (similar to grid files).

## 6. Comparison of Ordered Indexing and Hashing
- **Hashing**: Generally better for point queries (retrieving records with a specific key value).
- **Ordered Indices**: Preferred if range queries are common.
- **In Practice**:
  - Hash indices are extensively used in-memory but rarely used on disk.
  - Oracle supports static hash file organization but not hash indices.
  - SQL Server and PostgreSQL do not support hashing on disk.
