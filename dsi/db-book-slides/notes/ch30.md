## 1. Introduction
- **XML (Extensible Markup Language)**: Defined by the WWW Consortium (W3C). It is derived from SGML (Standard Generalized Markup Language) but is simpler to use.
- **Purpose**: Documents have tags giving extra information about sections of the document (e.g., `<title> XML </title>`).
- **Extensibility**: Unlike HTML, XML is extensible. Users can add new tags and separately specify how the tags should be handled for display.
- **Data Exchange**: The ability to specify new tags and create nested tag structures makes XML a great way to exchange data, not just documents. It has largely become the basis for new generation data interchange formats rather than just a replacement for HTML.
- **Self-Documenting**: Tags make data relatively self-documenting.

## 2. Motivation for XML
- **Critical for Data Interchange**: Crucial in today's networked world for banking (funds transfer), order processing, and scientific data (ChemML, BSML).
- **Electronic Flow**: Replaces the paper flow of information between organizations.
- **Overcoming Earlier Formats**: Earlier formats were based on plain text with line headers. They didn't allow for nested structures, lacked a standard "type" language, and were tied too closely to low-level document structure.
- **Standardization**: Each XML-based standard defines valid elements using XML type specification languages (like DTD or XML Schema) plus textual semantics. Tools are widely available for parsing, browsing, and querying XML.

## 3. Comparison with Relational Data
- **Inefficiency**: Tags act as schema information but are repeated, which is inefficient.
- **Advantages as Data-Exchange Format**:
  - Self-documenting due to tags.
  - Non-rigid format (tags can be added easily).
  - Allows nested structures.
  - Wide acceptance in databases, browsers, tools, and applications.

## 4. Structure of XML Data
- **Tags and Elements**: A tag is a label for a section of data. An element is a section of data beginning with `<tagname>` and ending with `</tagname>`.
- **Proper Nesting**: Elements must be properly nested. Every start tag must have a unique matching end tag in the context of the same parent element.
- **Top-Level Element**: Every document must have a single top-level root element.
- **Motivation for Nesting**: Very useful in data transfer. External applications often don't have direct access to data referenced by a foreign key, making nested structures (like items within an itemlist) ideal for transmission. (Note: Relational DBs discourage nesting via normalization, while Object-Relational DBs support it).
- **Mixed Content**: Mixture of text with sub-elements is legal (useful for document markup, but discouraged for pure data representation).

## 5. Attributes vs. Subelements
- **Attributes**: Specified by `name="value"` pairs inside the starting tag of an element. An element may have several attributes, but each attribute name can occur only once.
- **Distinction**:
  - In documents: Attributes are part of markup; subelement contents are part of the basic document.
  - In data representation: The difference is unclear. Both can represent the same information.
- **Suggestion**: Use attributes for identifiers of elements, and use subelements for actual contents.

## 6. Namespaces
- **Avoiding Name Clashes**: XML data exchanged between organizations might use the same tag name for different meanings.
- **XML Namespaces**: Provides a way to use unique names by attaching a namespace prefix to the element name (e.g., `unique-name:element-name`).
  - Example: `<university xmlns:yale="http://www.yale.edu"> ... <yale:course> ... </yale:course>`

## 7. More on XML Syntax
- **Empty Elements**: Elements without subelements or text content can be abbreviated by ending the start tag with `/>` (e.g., `<course course_id="CS-101" />`).
- **CDATA**: Used to store string data that may contain tags without those tags being interpreted as subelements.
  - Example: `<![CDATA[<course> ... </course>]]>`

## 8. XML Document Schema
Schemas constrain what information can be stored and the data types of stored values, which is vital for automated data exchange.

### Document Type Definition (DTD)
- **Features**: Constrains the structure of XML data (what elements can occur, what attributes are required, subelement occurrences).
- **Limitations**: Does not constrain data types (all values are strings). Difficult to specify unordered sets. IDs and IDREFs are untyped.
- **Syntax**:
  - `<!ELEMENT element (subelements-specification)>`
  - `<!ATTLIST element (attributes)>`
- **Subelement Specification**: Can be `#PCDATA` (parsed character data), `EMPTY`, `ANY`, or use regular expressions (`|` for alternatives, `+` for 1 or more, `*` for 0 or more).
- **IDs and IDREFs**:
  - `ID`: An element can have at most one ID attribute. The value must be distinct across the document (acts as an object identifier).
  - `IDREF` / `IDREFS`: Contains the ID value(s) of elements in the same document.

### XML Schema
- **Features**: A more sophisticated schema language addressing DTD drawbacks. Supports typing of values (integer, string, min/max constraints), user-defined complex types, uniqueness constraints, foreign key constraints, and inheritance.
- **Format**: Specified in XML syntax (unlike DTDs) and integrated with namespaces.
- **Drawback**: Significantly more complicated than DTDs.
- **Key Constraints**: Can define keys (`xs:key`) and foreign keys (`xs:keyref`) using XPath selectors.

## 9. Querying and Transforming XML Data
Languages based on a tree model of XML data (nodes correspond to elements, attributes, text).

### XPath
- **Purpose**: Address and select parts of documents using path expressions.
- **Syntax**: Sequence of steps separated by `/`. Evaluated left to right.
- **Features**:
  - `[ ]` for selection predicates (e.g., `[credits >= 4]`).
  - `@` for accessing attributes.
  - `//` to skip multiple levels of nodes (all descendants).
  - `..` to specify the parent.
  - `|` to implement union.
- **Functions**: `count()`, `not()`, `id()` (dereferences IDREFs), `doc(name)`.

### XQuery
- **Purpose**: General-purpose query language for XML data (W3C standard), derived from Quilt.
- **FLWOR Syntax**:
  - `for` (like SQL `from`): Ranges over values returned by XPath.
  - `let`: Temporary variables.
  - `where` (like SQL `where`): Selection conditions.
  - `order by` (like SQL `order by`): Sorting.
  - `return` (like SQL `select`): Constructs the XML result.
- **Features**: Supports joins, nested queries (used for grouping), aggregation (`fn:sum()`), sorting, user-defined functions, universal/existential quantification (`some`, `every`), and if-then-else clauses.

### XSLT
- **Purpose**: General-purpose transformation language (XML to XML, or XML to HTML).
- **Mechanism**: Expressed using rules called templates, which combine XPath selection with result construction.

## 10. Application Program Interfaces to XML
- **SAX (Simple API for XML)**: Event-driven parser model. Users provide event handlers for parsing events (e.g., start of element, end of element).
- **DOM (Document Object Model)**: Parses XML data into a tree representation. Provides functions for traversing and updating the tree (e.g., `getParentNode()`, `getElementsByTagName()`).

## 11. Storage of XML Data
### Non-Relational Data Stores
- **Flat Files**: Natural for XML, but lacks database features (concurrency, recovery).
- **XML Databases**: Built specifically for XML (DOM model, declarative querying), but commercial-grade systems are rare.

### Relational Databases
Requires translating XML into relational form. Benefits from mature database systems, but suffers from translation/query overhead.
- **String Representation**: Store each top-level element as a string field. Fast access, can use function indices, but parsing strings to access inner values is slow.
![Tree Representation](../images/ch30_slides/slide_048.png)

- **Tree Representation**: Model XML as a tree and store in relations (e.g., `nodes(id, parent_id, type, label, value)`). Can store any XML without a DTD, but breaks data into too many pieces, causing slow queries due to numerous joins.
- **Map to Relations**: Create a relation for each element type. Attributes represent simple subelements; `parent_id` tracks hierarchy. Subelements occurring multiple times are put in separate tables.
- **Publishing & Shredding**: Publishing is converting relational data to XML. Shredding is converting XML into tuples for insertion. Native `xml` data types are often supported for efficiency.

### SQL/XML
Standard SQL extension allowing creation of nested XML output.
- **Functions**: `xmlelement` (creates elements), `xmlattributes` (creates attributes), `xmlagg` (creates a forest of elements, often used with `group by`), `xmlforest`.

## 12. XML Applications
- **Data Exchange**: Open Document Format (ODF), Office Open XML (OOXML), ChemML, MathML.
- **Data Mediation**: Common data representation bridging different systems.
- **Web Services**: 
  - **SOAP (Simple Object Access Protocol)**: Remote procedure calls over HTTP using XML.
  - **WSDL (Web Services Description Language)**: Describes web services.
  - **UDDI**: Standard for directories of web services.
