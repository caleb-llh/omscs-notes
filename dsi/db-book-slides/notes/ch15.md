# Chapter 15: Query Processing

## Overview
- Basic Steps in Query Processing
  - Parsing and translation
  - Optimization
  - Evaluation

## Basic Steps in Query Processing
1. **Parsing and Translation**: 
   - Translates the query into its internal form, which is then translated into relational algebra.
   - The parser checks syntax and verifies relations.
2. **Optimization**: 
   - A relational algebra expression may have many equivalent expressions. 
     - *Example*: $\sigma_{salary<75000}(\Pi_{salary}(instructor))$ is equivalent to $\Pi_{salary}(\sigma_{salary<75000}(instructor))$.
   - Each relational algebra operation can be evaluated using one of several different algorithms. Correspondingly, a relational-algebra expression can be evaluated in many ways.
   - An annotated expression specifying a detailed evaluation strategy is called an **evaluation-plan**. 
     - *Example*: Use an index on `salary` to find instructors with `salary < 75000`, or perform a complete relation scan and discard instructors with `salary \geq 75000`.
   - **Query Optimization**: Amongst all equivalent evaluation plans, choose the one with the lowest cost.
     - Cost is estimated using statistical information from the database catalog (e.g., number of tuples in each relation, size of tuples, etc.).
3. **Evaluation**: 
   - The query-execution engine takes a query-evaluation plan, executes that plan, and returns the answers to the query.

## Measures of Query Cost
- Many factors contribute to time cost: disk access, CPU, and network communication.
- Cost can be measured based on:
  - **Response time**: Total elapsed time for answering the query.
  - **Total resource consumption**.
- Total resource consumption is typically used as a cost metric since response time is harder to estimate, and minimizing resource consumption is beneficial in a shared database.
- CPU costs are ignored for simplicity in basic models (though real systems take them into account).
- Network costs must be considered for parallel systems.
- We do not include the cost of writing output to disk in intermediate cost estimates.
- Disk cost can be estimated as:
  - Number of seeks $\times$ average-seek-cost
  - Number of blocks read $\times$ average-block-read-cost
  - Number of blocks written $\times$ average-block-write-cost
- For simplicity, we use the **number of block transfers from disk ($b$)** and the **number of seeks ($S$)** as the cost measures.
  - $t_T$: Time to transfer one block.
  - $t_S$: Time for one seek.
  - Assuming write cost is the same as read cost.
  - Cost for $b$ block transfers plus $S$ seeks: $b \times t_T + S \times t_S$
  - *Example values for 4 KB blocks*:
    - High-end magnetic disk: $t_S = 4$ ms, $t_T = 0.1$ ms
    - SSD: $t_S = 20-90$ $\mu$s, $t_T = 2-10$ $\mu$s
- Required data may already be buffer resident, avoiding disk I/O, but this is hard to account for in cost estimation.
- Several algorithms reduce disk I/O by using extra buffer space. The amount of available real memory depends on other concurrent queries and OS processes (known only during execution).
- Worst-case estimates assume no data is initially in the buffer and only the minimum amount of memory needed for the operation is available. In practice, more optimistic estimates are used.

## Selection Operation

### File Scan
- **Algorithm A1 (Linear Search)**: Scan each file block and test all records to see whether they satisfy the selection condition.
  - **Cost estimate** = $b_r$ block transfers + 1 seek ($b_r$ denotes the number of blocks containing records from relation $r$).
  - If selection is on a key attribute, it can stop upon finding the record: cost = $(b_r / 2)$ block transfers + 1 seek.
  - Linear search can be applied regardless of the selection condition, ordering of records, or availability of indices.
  - *Note*: Binary search generally does not make sense since data is not stored consecutively, except when there is an index available (and binary search requires more seeks than index search).

### Selections Using Indices (Index Scan)
- Search algorithms that use an index. The selection condition must be on the search-key of the index.
- **A2 (Clustering index, equality on key)**: Retrieve a single record that satisfies the corresponding equality condition.
  - **Cost** = $(h_i + 1) \times (t_T + t_S)$ where $h_i$ is the height of the index.
- **A3 (Clustering index, equality on nonkey)**: Retrieve multiple records.
  - Records will be on consecutive blocks.
  - **Cost** = $h_i \times (t_T + t_S) + t_S + t_T \times b$ (where $b$ is the number of blocks containing matching records).
- **A4 (Secondary index, equality on key/non-key)**:
  - Retrieve a single record if the search-key is a candidate key.
    - **Cost** = $(h_i + 1) \times (t_T + t_S)$
  - Retrieve multiple records if the search-key is not a candidate key.
    - Each of the $n$ matching records may be on a different block.
    - **Cost** = $(h_i + n) \times (t_T + t_S)$
    - Can be very expensive!

### Selections Involving Comparisons
- Can implement selections like $\sigma_{A \leq V}(r)$ or $\sigma_{A \geq V}(r)$ using a linear file scan or indices.
- **A5 (Clustering index, comparison)**: (Relation is sorted on A)
  - For $\sigma_{A \geq V}(r)$, use the index to find the first tuple $\geq V$ and scan the relation sequentially from there.
  - For $\sigma_{A \leq V}(r)$, just scan the relation sequentially till the first tuple $> V$; do not use the index.
- **A6 (Secondary index, comparison)**:
  - For $\sigma_{A \geq V}(r)$, use the index to find the first index entry $\geq V$ and scan the index sequentially from there to find pointers to records.
  - For $\sigma_{A \leq V}(r)$, just scan leaf pages of the index finding pointers to records, till the first entry $> V$.
  - In either case, retrieve records that are pointed to. This requires one I/O per record, meaning a linear file scan might be cheaper!

### Implementation of Complex Selections
- **Conjunction**: $\sigma_{\theta_1 \wedge \theta_2 \wedge ... \wedge \theta_n}(r)$
  - **A7 (Conjunctive selection using one index)**: Select a combination of $\theta_i$ and algorithms A1 through A7 that results in the least cost for $\sigma_{\theta_i}(r)$. Test other conditions on the tuple after fetching it into the memory buffer.
  - **A8 (Conjunctive selection using composite index)**: Use an appropriate composite (multiple-key) index if available.
  - **A9 (Conjunctive selection by intersection of identifiers)**: Requires indices with record pointers. Use the corresponding index for each condition, and take the intersection of all obtained sets of record pointers. Then fetch records from the file. If some conditions do not have appropriate indices, apply the test in memory.
- **Disjunction**: $\sigma_{\theta_1 \vee \theta_2 \vee ... \vee \theta_n}(r)$
  - **A10 (Disjunctive selection by union of identifiers)**: Applicable if all conditions have available indices (otherwise use a linear scan). Use the corresponding index for each condition and take the union of all obtained sets of record pointers. Then fetch records from the file.
- **Negation**: $\sigma_{\neg \theta}(r)$
  - Use a linear scan on the file. If very few records satisfy $\neg \theta$ and an index is applicable to $\theta$, find satisfying records using the index and fetch them from the file.

### Bitmap Index Scan
- The bitmap index scan algorithm of PostgreSQL bridges the gap between a secondary index scan and a linear file scan when the number of matching records is not known before execution.
- It uses a bitmap with 1 bit per page in the relation.
- **Steps**:
  1. Index scan is used to find record IDs, and set the bit of the corresponding page in the bitmap.
  2. Linear file scan fetching only pages with the bit set to 1.
- **Performance**:
  - Similar to an index scan when only a few bits are set.
  - Similar to a linear file scan when most bits are set.
  - Never behaves very badly compared to the best alternative.

## Sorting
- We may build an index on the relation, and then use the index to read the relation in sorted order (this may lead to one disk block access for each tuple).
- For relations that fit in memory, techniques like quicksort can be used.
- For relations that don't fit in memory, **external sort-merge** is a good choice.

### External Sort-Merge
![Example: External Sorting Using Sort-Merge](../images/ch15_slides/slide_018.png)
- Let $M$ denote memory size (in pages).
1. **Create sorted runs**: Let $i = 0$ initially. Repeatedly do the following till the end of the relation:
   - Read $M$ blocks of relation into memory.
   - Sort the in-memory blocks.
   - Write sorted data to run $R_i$; increment $i$. Let the final value of $i$ be $N$.
2. **Merge the runs (N-way merge)**: Assuming $N < M$.
   - Use $N$ blocks of memory to buffer input runs, and 1 block to buffer output. Read the first block of each run into its buffer page.
   - Repeat:
     - Select the first record (in sort order) among all buffer pages.
     - Write the record to the output buffer. If the output buffer is full, write it to disk.
     - Delete the record from its input buffer page. If the buffer page becomes empty, read the next block (if any) of the run into the buffer.
   - Until all input buffer pages are empty.
- If $N \geq M$, several merge passes are required:
  - In each pass, contiguous groups of $M - 1$ runs are merged.
  - A pass reduces the number of runs by a factor of $M - 1$ and creates runs longer by the same factor.
  - Repeated passes are performed till all runs have been merged into one.
- **Cost Analysis**:
  - Instead of 1 block per run (which leads to too many seeks), use $b_b$ buffer blocks per run. Read/write $b_b$ blocks at a time.
  - Can merge $\lfloor M/b_b \rfloor - 1$ runs in one pass.
  - Total number of merge passes required: $\lceil \log_{\lfloor M/b_b \rfloor - 1}(b_r/M) \rceil$.
  - Block transfers:
    - Initial run creation as well as in each pass: $2b_r$
    - We ignore final write cost for all operations (output might be sent to the parent operation).
    - Total number of block transfers: $b_r ( 2 \lceil \log_{\lfloor M/b_b \rfloor - 1} (b_r / M) \rceil + 1)$
  - Seeks:
    - During run generation: $2 \lceil b_r / M \rceil$
    - During merge phase: $2 \lceil b_r / b_b \rceil$ per pass.
    - Total number of seeks: $2 \lceil b_r / M \rceil + \lceil b_r / b_b \rceil (2 \lceil \log_{\lfloor M/b_b \rfloor - 1}(b_r / M) \rceil - 1)$

## Join Operation
- Several algorithms to implement joins:
  - Nested-loop join
  - Block nested-loop join
  - Indexed nested-loop join
  - Merge-join
  - Hash-join
- Choice is based on cost estimates.

### Nested-Loop Join
- To compute the theta join $r \bowtie_\theta s$:
  ```text
  for each tuple tr in r do begin
      for each tuple ts in s do begin
          test pair (tr,ts) to see if they satisfy the join condition θ
          if they do, add tr • ts to the result.
      end
  end
  ```
- $r$ is the **outer relation** and $s$ the **inner relation**.
- Requires no indices and can be used with any kind of join condition.
- Expensive since it examines every pair of tuples in the two relations.
- Cost estimate (worst case, memory holds only one block of each relation):
  - $n_r \times b_s + b_r$ block transfers
  - $n_r + b_r$ seeks
- If the smaller relation fits entirely in memory, use that as the inner relation. This reduces the cost to $b_r + b_s$ block transfers and 2 seeks.

### Block Nested-Loop Join
- Variant in which every block of the inner relation is paired with every block of the outer relation.
  ```text
  for each block Br of r do begin
      for each block Bs of s do begin
          for each tuple tr in Br do begin
              for each tuple ts in Bs do begin
                  Check if (tr,ts) satisfy the join condition
                  if they do, add tr • ts to the result.
              end
          end
      end
  end
  ```

### Indexed Nested-Loop Join
- Index lookups can replace file scans if the join is an equi-join or natural join and an index is available on the inner relation’s join attribute.
- For each tuple $t_r$ in the outer relation $r$, use the index to look up tuples in $s$ that satisfy the join condition.
- **Cost**: $b_r (t_T + t_S) + n_r \times c$
  - Where $c$ is the cost of traversing the index and fetching all matching $s$ tuples for one tuple of $r$.
- If indices are available on join attributes of both relations, use the relation with fewer tuples as the outer relation.

### Merge-Join
1. Sort both relations on their join attribute.
2. Merge the sorted relations to join them (similar to the merge stage of sort-merge). Handles duplicate values in the join attribute (every pair with the same value must be matched).
- Can be used only for equi-joins and natural joins.
- **Cost**: $b_r + b_s$ block transfers + $\lceil b_r / b_b \rceil + \lceil b_s / b_b \rceil$ seeks (+ cost of sorting if unsorted).
- **Hybrid Merge-Join**: If one relation is sorted and the other has a secondary B+-tree index on the join attribute, merge the sorted relation with the leaf entries of the B+-tree.

### Hash-Join
- Applicable for equi-joins and natural joins.
- A hash function $h$ is used to partition tuples of both relations on their common join attributes.
  - Each tuple $t_r \in r$ is put in partition $r_i$ where $i = h(t_r[JoinAttrs])$.
  - Each tuple $t_s \in s$ is put in partition $s_i$ where $i = h(t_s[JoinAttrs])$.
- **Algorithm**:
  1. Partition $s$ (the **build input**) using $h$.
  2. Partition $r$ (the **probe input**) using $h$.
  3. For each $i$:
     - Load $s_i$ into memory and build an in-memory hash index on it (using a different hash function).
     - Read tuples in $r_i$ from disk one by one. For each tuple $t_r$, locate each matching tuple $t_s$ in $s_i$ using the in-memory hash index and output their concatenation.
- The value $n$ and hash function $h$ are chosen such that each $s_i$ fits in memory.
  - $n$ is typically $\lceil b_s / M \rceil \times f$ (fudge factor $f \approx 1.2$).
- **Recursive partitioning** is required if the number of partitions $n$ is greater than memory pages $M$.
- **Handling Overflows**:
  - Hash-table overflow occurs if $s_i$ does not fit in memory (due to many duplicates or a bad hash function).
  - Overflow resolution (build phase) or avoidance. Fallback: block nested loops join.
- **Cost**:
  - If no recursive partitioning: $3(b_r + b_s) + 4 \times n_h$ block transfers + $2(\lceil b_r / b_b \rceil + \lceil b_s / b_b \rceil)$ seeks.
  - It is best to choose the smaller relation as the build relation.

### Hybrid Hash-Join
- Useful when memory sizes are relatively large and the build input is bigger than memory.
- Main feature: Keep the first partition of the build relation in memory.
- Saves the cost of writing and reading the first partition to/from disk.

### Complex Joins
- **Conjunctive Condition** ($r \bowtie_{\theta_1 \wedge ... \wedge \theta_n} s$):
  - Use nested loops / block nested loops, or
  - Compute a simpler join $r \bowtie_{\theta_i} s$, then filter the intermediate result.
- **Disjunctive Condition** ($r \bowtie_{\theta_1 \vee ... \vee \theta_n} s$):
  - Use nested loops / block nested loops, or
  - Compute as the union of individual joins: $(r \bowtie_{\theta_1} s) \cup ... \cup (r \bowtie_{\theta_n} s)$.

### Joins over Spatial Data
- Indexed nested loops join with spatial indices (R-trees, quad-trees, k-d-B-trees).

## Other Operations
- **Duplicate elimination**: Implemented via hashing or sorting.
- **Projection**: Perform projection on each tuple, followed by duplicate elimination.
- **Aggregation**: Implemented similarly to duplicate elimination (sorting or hashing to bring tuples in the same group together, then applying aggregate functions).
  - Optimization: Partial aggregation during run generation.
- **Set Operations ($\cup, \cap, -$ )**: Use a variant of merge-join after sorting, or a variant of hash-join.
- **Outer Join**: Computed as a join followed by the addition of null-padded non-participating tuples, or by modifying join algorithms (e.g., modifying merge-join or hash-join).
- **Answering Keyword Queries**: Inverted indices mapping keywords to document IDs.

## Evaluation of Expressions
![Pipeline Stages](../images/ch15_slides/slide_054.png)
- Alternatives for evaluating an entire expression tree:
  1. **Materialization**: Evaluate one operation at a time. Store (materialize) intermediate results on disk.
     - Always applicable.
     - High cost of disk I/O for intermediate results.
     - Double buffering allows overlap of disk writes with computation.
  2. **Pipelining**: Evaluate several operations simultaneously, passing results of one operation directly to the next.
     - Cheaper than materialization (no need to write temporary relations to disk).
     - May not always be possible (e.g., sort and hash-join are blocking operations).
     - **Demand-driven (lazy) evaluation**: System repeatedly requests the next tuple from the top-level operation (pull model). Implemented via iterators with `open()`, `next()`, `close()`.
     - **Producer-driven (eager) pipelining**: Operators produce tuples eagerly and pass them up to parents via buffers (push model).
- **Blocking Operations**: Cannot generate any output until all input is consumed (e.g., sort, hash-join). 
  - They can be divided into suboperations (e.g., run generation and merge) to consume from/produce to a pipeline.
  - **Double-pipelined join**: Algorithm variant (like modified hybrid hash join) to generate results on the fly.
- **Pipelining for Continuous-Stream Data**: Data entering continuously (e.g., sensor networks). Results updated as streaming data enters. Aggregation on windows (e.g., tumbling windows). Punctuations are used to infer when window data is complete.

## Query Processing in Memory
- **Query compilation to machine code**: Overcomes interpretation overheads via JIT compilation (e.g., Java byte code, LLVM).
- **Column-oriented storage**: Allows vector operations.
- **Cache Conscious Algorithms**: Goal is to minimize cache misses.
  - Sorting: Use runs as large as the L3 cache.
  - Hash-join: Subpartition so the build subpartition + index fits in the L3 cache.
  - Lay out attributes to maximize cache usage.
  - Use multiple threads for parallel processing to hide cache miss stalls.
