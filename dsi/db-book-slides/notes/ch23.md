# Chapter 23: Parallel and Distributed Transaction Processing

## 1. Distributed Transactions
- **Local transactions**: Access/update data at only one database.
- **Global transactions**: Access/update data at more than one database.
- **Key issue**: How to ensure ACID properties for transactions in a system with global transactions spanning multiple databases.
- A transaction may access data at several sites.
  - Each site has a **local transaction manager**.
  - Each site has a **transaction coordinator**.
- Global transactions can be submitted to any transaction coordinator.
- **Transaction Coordinator** responsibilities:
  - Starting the execution of transactions that originate at the site.
  - Distributing subtransactions to appropriate sites for execution.
  - Coordinating the termination of each transaction that originates at the site.
  - Ensuring the transaction is committed at all sites or aborted at all sites.
- **Local Transaction Manager** responsibilities:
  - Maintaining a log for recovery purposes.
  - Coordinating the execution and commit/abort of the transactions executing at that site.

## 2. System Failure Modes
- Failures unique to distributed systems:
  - **Failure of a site**.
  - **Loss of messages** (handled by network transmission control protocols like TCP/IP).
  - **Failure of a communication link** (handled by network protocols, routing via alternative links).
  - **Network partition**: A network is split into two or more subsystems lacking connection between them (a subsystem may be a single node).
- Network partitioning and site failures are generally indistinguishable.

## 3. Commit Protocols
- Used to ensure atomicity across sites. A transaction executing at multiple sites must either commit at all sites or abort at all sites.
- Cannot have a transaction committed at one site and aborted at another.
- **Two-phase commit (2PC)**: widely used.
- **Three-phase commit (3PC)**: avoids some drawbacks of 2PC but is more complex.
- **Consensus protocols**: solve a more general problem, but can be used for atomic commit.
- Protocols generally assume a **fail-stop model**: failed sites simply stop working and do not cause other harm (e.g., sending incorrect messages).

### 3.1. Two-Phase Commit Protocol (2PC)
![Two-Phase Commit Protocol](../images/ch23_slides/slide_010.png)
- Initiated by the coordinator after the last step of the transaction is reached.
- Involves all local sites where the transaction executed. Let $T$ be a transaction initiated at site $S_i$, with coordinator $C_i$.
- **Phase 1: Obtaining a Decision**
  - Coordinator $C_i$ asks all participants to prepare to commit transaction $T$.
  - $C_i$ adds `<prepare T>` to its log and forces it to stable storage.
  - Sends `prepare T` messages to all sites executing $T$.
  - Upon receiving the message, the local transaction manager determines if it can commit:
    - If not, adds `<no T>` to the log and sends `abort T` message to $C_i$.
    - If yes, adds `<ready T>` to the log, forces all records for $T$ to stable storage, and sends `ready T` message to $C_i$. Transaction is now in **ready state**.
- **Phase 2: Recording the Decision**
  - $T$ can commit if $C_i$ receives `ready T` from *all* participating sites; otherwise, it must abort.
  - Coordinator adds a decision record (`<commit T>` or `<abort T>`) to the log and forces it to stable storage. The decision is now irrevocable.
  - Coordinator sends the decision message to each participant.
  - Participants take appropriate local action.

#### Handling Failures in 2PC
- **Site Failure**: When site $S_k$ recovers, it examines its log:
  - `<commit T>`: executes `redo(T)`.
  - `<abort T>`: executes `undo(T)`.
  - `<ready T>`: must consult $C_i$ to determine $T$'s fate. If $T$ committed, `redo(T)`; if aborted, `undo(T)`.
  - No control records for $T$: implies $S_k$ failed before responding to `prepare T`. Since $C_i$ couldn't receive a response, it must have aborted $T$. $S_k$ must execute `undo(T)`.
- **Coordinator Failure**: If coordinator fails while executing 2PC, participants must decide $T$'s fate:
  1. Active site has `<commit T>`: $T$ must commit.
  2. Active site has `<abort T>`: $T$ must abort.
  3. Some active site does not have `<ready T>`: $C_i$ couldn't have decided to commit. Can safely abort $T$.
  4. If all active sites have `<ready T>` but no decision record: active sites must wait for $C_i$ to recover (**Blocking problem**).
- **Network Partition**:
  - Coordinator and all participants in one partition: no effect.
  - Coordinator and participants in different partitions:
    - Sites without coordinator think coordinator failed and execute coordinator failure protocol. May result in waiting (blocking).
    - Coordinator thinks sites in other partition failed and follows normal protocol.

#### Recovery and Concurrency Control
- **In-doubt transactions**: Have a `<ready T>` but no commit/abort record. Recovering site must contact other sites, which can block recovery.
- **Solution**: Note lock information in the log (`<ready T, L>` where $L$ = list of locks). Reacquire locks on recovery, allowing normal transaction processing to resume while in-doubt transactions wait for resolution.

### 3.2. Avoiding Blocking During Consensus
- 2PC blocking is a serious concern.
- **Idea**: Involve multiple nodes in the decision process, so the failure of a few nodes does not cause blocking as long as a majority don't fail.
- **Distributed Consensus**: A set of $n$ nodes need to agree on a decision.
  - Inputs provided to all nodes, each node votes.
  - All nodes must "learn" the same value, even if some nodes fail or there are network partitions.
  - Protocol should not block if a majority remain alive and communicative (e.g., Paxos, Raft).
- **Using Consensus**: Coordinator initiates distributed consensus by sending its decision to a set of participants. If coordinator fails, a new coordinator is chosen and finds the decision without blocking as long as a majority are accessible.

### 3.3. Distributed Transactions via Persistent Messaging
![Persistent Messaging Implementation](../images/ch23_slides/slide_020.png)
- Single transaction spanning multiple sites can be inappropriate (e.g., across organizations, high latency).
- Carry out transactions by sending messages. Code must ensure atomicity/durability. Isolation not guaranteed (intermediate stages visible), requiring care to avoid inconsistent states.
- **Persistent messages**: Guaranteed to be delivered exactly once.
- Example: Funds transfer. Debit money and send message; destination site receives message and credits account. Avoids 2PC blocking.
- Error Handling: Requires manual/compensating logic (e.g., return money if destination account doesn't exist).
- Implementation often uses timestamps to avoid processing duplicate messages after long delays. Forms the basis of **workflows**.

## 4. Concurrency Control in Distributed Databases
- Assume commit protocols ensure global atomicity. Assume all replicas of an item are updated.
- **Single-Lock-Manager**: Lock manager runs on a single site.
  - Reads from any replica, writes to all replicas.
  - Advantages: Simple implementation and deadlock handling.
  - Disadvantages: Bottleneck and vulnerability to manager failure.
- **Distributed Lock Manager**: Lock managers at each site control local data.
  - Locking performed separately on each accessed site.
  - Advantages: Distributed work, robust to failures.
  - Disadvantages: Global deadlocks possible without local deadlocks. Requires cooperation for detection.

### Deadlock Handling
![Local and Global Wait-For Graphs](../images/ch23_slides/slide_028.png)
![Example Wait-For Graph for False Cycles](../images/ch23_slides/slide_029.png)
- **Centralized Deadlock Detection**: Global wait-for graph maintained at a single site.
  - Constructed from local wait-for graphs.
  - Can suffer from **false cycles** (e.g., due to network delays for delete/insert messages). False cycles cannot occur with Two-Phase Locking (2PL).
- **Distributed Deadlock Detection**: Sites exchange wait-for info. Expensive, not used in practice.
- **Leases**: Lock granted for a specific time period. Must be renewed. Prevents coordinator failures from blocking indefinitely. Depends on clock synchronization.

### Distributed Timestamp-Based Protocols
- **Distributed Timestamps**: Generate unique local timestamp (counter or clock), concatenate with site ID for global uniqueness.
- **Clock Synchronization**: Slower clocks disadvantage transactions. Keep synchronized via NTP or logical clocks (advance logical clock when receiving request with higher timestamp).
- **Distributed Timestamp Ordering**: Centralized TSO extended. Clocks should be synchronized.

### Distributed Validation
- Validation protocol extended to distributed systems.
- Start/validation/finish timestamps issued by participating nodes.
- 2PC needed to ensure atomic commit. Validation done first, writes performed only after 2PC decision.
- Optimistic concurrency control without read-validation is widely used (e.g., HBase `checkAndPut`).

## 5. Replication
- **Goal**: High availability and robustness. Replicate at data item or partition level.
- **Consistency**: Ideally, all replicas have the same value. Handled via **linearizability** (reads see most recent write).
- Node failure vs. network partition is indistinguishable. Protocols requiring all copies to be updated block on failure.
- **Asynchronous replication**: Commit after updating primary copy, update replicas asynchronously. Lower overhead, risks stale data or lost updates.

### Concurrency Control With Replicas
- **Primary Copy**: One replica chosen as primary. Concurrency control done there. Low overhead but vulnerable to primary node failure.
- **Majority Protocol**: Lock acquired if obtained at a majority of replicas. Resilient to failures (needs majority). High overhead, possibility of deadlocks.
- **Biased Protocol**: Shared lock on any replica, exclusive lock on all replicas. Reduces read overhead, but writes block if any replica unavailable.
- **Quorum Consensus**: Assign weights to sites. Choose read quorum $Q_R$ and write quorum $Q_W$ such that $Q_R + Q_W > S$ and $2 * Q_W > S$. Generalizes majority and biased protocols.

### Handling Failures
- Read-one-write-all-available is incorrect (network partition can cause concurrent updates).
- **Majority Protocol with Version Numbers**:
  - Replicas have version numbers.
  - Read: find replica with largest version number from a majority.
  - Write: find highest version $V$, set new version to $V+1$, write to majority.
  - Atomic commit using 2PC or consensus (Paxos).
  - Benefits: Consistency despite failures. No special reintegration needed. Drawback: High read overhead.
- **Reducing Read Cost**:
  - Primary copy with leases to handle primary failures.
  - **Chain replication**: Writes at head, passed along. Reads at tail (fully replicated).

### Reconfiguration and Reintegration
- When a node fails, reconfigure to remove it, assign tasks to others. Avoid multiple central servers during partition (use majority approach).
- **Site Reintegration**: Recovering site must catch up. Can lock all replicas at the site, update, then release (partition by partition).
- Provides higher availability than simple remote backup without the switchover time.

## 6. Extended Concurrency Control Protocols
- **Multiversion 2PL**: Read-only transactions use `startTS`.
  - In distributed setting, consistent timestamps are hard without a central coordinator.
  - **Google Spanner**: Uses atomic clocks/GPS to bound clock uncertainty ($t' - \epsilon \le t \le t' + \epsilon$). **Commit wait**: hold locks until guaranteed actual time has passed. Allows consistent snapshots and lock-free reads.
- **Distributed Snapshot Isolation**: Running SI separately can result in different serialization orders. Extensions exist.
- **Federated Databases**: Local serializability $\neq$ global serializability. Use tickets to force conflicts.

## 7. Replication With Weak Degrees of Consistency
- **CAP Theorem**: Consistency, Availability, Partition tolerance. Can have at most two.
  - In reality, partitions happen. Choose between Consistency and Availability.
  - Latency is also traded off for consistency (PACELC).
- Weak consistency allowed by setting $Q_R + Q_W \le S$. Good for fast local reads, but risks old versions and divergent replicas.
- **Eventual Consistency (BASE)**: Basically Available, Soft state, Eventual consistency. If no updates occur, eventually all copies become consistent.
- **Asynchronous Replication**:
  - **Master-slave**: updates at master, propagated to slaves (reads only).
  - **Multimaster**: updates anywhere, propagated. Requires persistent messaging or publish-subscribe (Kafka).
- **Detecting Inconsistency**:
  - Use **Vector Clocks (Version Vectors)**: Array of `[node, counter]` pairs.
  - Allows detecting concurrent incomparable updates. Reads return all incomparable versions, application must reconcile.
  - **Merkle Trees**: Efficiently find differences between replicas.
- **Reconciliation**: Application-specific (e.g., merging shopping carts). Better to track history of operations.
  - **Order Independent Operations**: If operations commute, they can be applied in any order for eventual consistency.
- **Weak Consistency Models**: Read-your-writes, Session consistency, Monotonic consistency.

## 8. Coordinator Selection
- **Backup Coordinators**: Maintain state to assume role if actual coordinator fails. Vulnerable to two-site failure.
- **Election Algorithms**: Use leases or fault-tolerant services (ZooKeeper/Chubby).
  - Candidates propose themselves with term numbers.
  - **Bully Algorithm**: Site with highest ID wins.
  - Split-brain avoided using term numbers (majority votes) or leases.

## 9. Distributed Consensus
- **Goal**: A decision-making protocol that is non-blocking if a majority of nodes are up. (e.g., 2PC commit decision).
- Abstracted as atomically appending a record to a fault-tolerant replicated log.

### Paxos Consensus Protocol
- **Proposers**, **Acceptors**, **Learners**.
- Ensures at most one value is chosen. If a majority accept a value, learners learn it.
- **Phase 1 (Prepare)**: Proposer selects proposal number $n$, sends to majority of acceptors. Acceptor responds if $n$ is greater than any previous prepare request, returning the highest-numbered proposal it has already accepted.
- **Phase 2 (Accept)**: If proposer gets majority responses, it sends accept request for $n$ with value $v$ ($v$ = highest accepted value from responses, or its own if none). Acceptors accept if they haven't responded to a higher prepare.
- Guarantees once a majority accepts a value, future majorities will force that same value to be chosen.

### The Raft Consensus Protocol
![Example of Raft Logs](../images/ch23_slides/slide_107.png)
- Log-based, heavily relies on a single **Leader**. Time divided into **terms**.
- **Leader Election**: Randomized retry. Candidates request votes with their log state. Nodes vote if candidate's log is at least as up-to-date as theirs.
- **Log Replication**: Leader sends `AppendEntries`. Followers check if previous log entry matches. If so, append new entries.
- Follower out of date $\rightarrow$ Leader backtracks until matching entry found, then overwrites follower's log.
- Ensures any elected leader has all committed log entries.

## 10. Fault-Tolerant Services using Replicated State Machines
- **Replicated State Machine**: Stored state, receives inputs, makes deterministic transitions.
- Replicated on multiple nodes. All replicas process the identical sequence of inputs from the replicated log (e.g., Paxos/Raft).
- Uses: Fault-tolerant lock manager, Key-value store (Spanner).
- **Two-Phase Commit using Consensus**: Record commit decisions using consensus instead of coordinator's local log. Avoids blocking (e.g., Spanner uses Paxos group leaders for 2PC).

## 11. Dynamo (Extra)
- Key-value store optimizing for High Availability and Low Latency over Consistency (PA/EL).
- Uses DHTs with consistent hashing. Replication at virtual node level.
- $Q_R + Q_W$ can be configured per instance.
- Vector clocks used to detect divergent versions. Application reconciles on `get()`.
