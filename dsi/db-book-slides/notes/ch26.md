# Chapter 26: Blockchain Databases

## 1. Overview
This chapter covers the fundamentals of blockchain databases, including properties, cryptographic hash functions, consensus mechanisms, data management, smart contracts, performance enhancements, and emerging applications.

## 2. History
Blockchain technology's development was driven initially by cryptocurrencies, but cryptocurrency is just one application of blockchain.

**Cryptocurrencies:**
- Purely online.
- Maintained by a decentralized distributed ledger.

**Bitcoin:**
- One of the first successful cryptocurrencies, and the best known.
- Published under the pseudonym Satoshi Nakomoto.
- Aims to be an anonymous, fully distributed, and decentralized currency.
- There are other blockchains that are more appropriate for blockchain-based enterprise data.

## 3. Types of Blockchain
The type of blockchain influences the choice of algorithm used by which nodes agree on the next block to be added to the blockchain.

- **Public Blockchain:**
  - Anyone can download the needed software and create a blockchain node.
  - No trust assumed among participating nodes.
- **Permissioned Blockchain:**
  - Permission to run a blockchain node is granted by a permissioning authority.
  - Some degree of relaxation of the assumptions of trustlessness and autonomy.

## 4. Blockchain Properties and Structure

**Structure:**
- **Linked list of blocks:** Each block contains a pointer to the previous block plus a hash of the previous block (except for the first block, called the genesis block).

**Properties:**
- **Decentralization:** Majority consensus with no central authority.
- **Tamper Resistance:** The inclusion of the hash of the previous block makes tampering difficult. Changing the contents of a block means changing all newer blocks as well. It relies on specific mathematical requirements for the hash function. Replication prevents replacement of the entire blockchain without gaining majority control.
- **Irrefutability:** Digital signatures using public-key encryption allow users to sign transactions, ensuring that users cannot deny submitting the transaction.
- **Anonymity:** Users can remain anonymous unless there is a way to tie the user's ID (public key) to a real-world entity.

**Node Types:**
- **Full node:** Maintains a copy of the blockchain and participates in the consensus process.
- **Light node:** Submits updates to the blockchain but does not participate in the consensus process.

**Forks:**
A fork occurs if a block is added to a block that is not the most recent one.
- **Accidental:** Consequence of the consensus algorithm. One fork survives; others are eventually orphaned.
- **Malicious:** Due to an attempt to damage the blockchain.
- **Consensus-based:** Agreed to by a majority of users.
  - *Hard fork:* Old version of blockchain software does not recognize new blocks as valid.
  - *Soft fork:* Old version of blockchain software recognizes new blocks as valid.

## 5. Cryptographic Hash Functions
Let $h$ denote a cryptographic hash function. Then $h$ must satisfy the following properties:
- **Collision resistant:** It is infeasible to find two distinct values $x$ and $y$ such that $h(x) = h(y)$.
- **Irreversible:** Given $h(x)$, it is infeasible to find $x$.

*Note:* By infeasible, we mean that there is strong mathematical evidence, if not an actual proof, that there is no approach to obtaining an answer that is better than guessing from the set of all possibilities.

## 6. Blockchain Transactions
The exact transaction model is specific to each blockchain.

**Bitcoin:**
- No account balances stored directly.
- A transaction specifies:
  - Input transactions (whose output are spent by this transaction).
  - A set of outputs, each specifying the recipient and the amount.
  - A digital signature from the user submitting the transaction.
- Additionally, a Bitcoin transaction may store a small amount of data on the blockchain and specify a slightly more complex transaction using the Bitcoin scripting language.

**Ethereum:**
- Maintains account balances, which are modified by transactions.
- Has a more sophisticated, Turing-complete scripting language.

## 7. Consensus
All nodes must agree on additions to the blockchain. In a decentralized system like a blockchain system, there is no central coordinator (unlike the case for 2PC and 3PC).

**Categorization of Consensus Algorithms:**
- **Proof of Work:** Node needs to solve a cryptographic puzzle in order to add a block.
  - To add a block $B$, a node needs to find a nonce, $n$, such that the value of the hash function $h$ applied to the concatenation of $n$ and $B$ ($n \parallel B$) is less than some specified value.
  - The function $h$ must have the *puzzle-friendliness* property: Given $k$ and an $n$-bit value $y$, it is infeasible to find $x$ such that $h(x \parallel k) = y$ in time significantly less than $2^n$.
  - *Forks in Proof of Work:* If more than one node solves the puzzle around the same time, two blocks could be added after the most recent block, resulting in a fork. Since nodes attempt to add to the most recent block of the longest chain, eventually blocks on shorter forks are orphaned.
- **Proof of Stake:** Node is chosen to add the next block based on the amount of currency held, with probability proportionate to stake.
- **Byzantine Consensus:** Node is chosen to add the next block based on a message-passing-based consensus algorithm.
  - *Byzantine failure:* A failed node can behave in an arbitrarily bad manner, including taking the exactly correct set of steps to sabotage the system. This contrasts with the *fail-stop* model of failure (e.g., 2PC, 3PC, Paxos, and Raft) where the only assumed type of failure is a crash.
  - Achieves consensus with Byzantine failure provided that at most $(n-1)/3$ nodes fail, where $n$ is the total number of nodes.
  - Modern blockchain Byzantine consensus algorithms are robust to the number of nodes changing, unlike traditional algorithms that assume $n$ does not change.
- **Other Approaches:** Proof of activity, proof of burn, proof of capacity, proof of elapsed time.

## 8. Sybil Attacks
A Sybil attack is an attempt to overwhelm the consensus algorithm by adding a large number of nodes.

**Protection Against Sybil Attack:**
- **Proof of work:** Hard for an attacker to control a majority of the computing power in the network, thus making it hard to dominate success in solving the cryptographic puzzle.
- **Proof of stake:** Costly to acquire a majority of all outstanding currency.
- **Byzantine consensus:** Vulnerable to attack unless there is a permissioning mechanism for new nodes (either a trusted permission-granting agent or a decentralized trust-based feature in the protocol itself).

## 9. Data Management in a Blockchain
Validating a transaction requires data look-up in the blockchain:
- **Bitcoin:** Look up input transactions to ensure that their output has not already been spent ("double-spend").
- **Ethereum:** Look up account balances.

**Data Structures:**
- **Merkle-tree:** Allows a node to store just the root-hash of the Merkle tree for verification purposes, rather than the entire blockchain. However, blockchain immutability means the tree structure can't be updated in place.
- **Merkle-Patricia-tree:** 
  - Patricia-tree structure allows key-based search.
  - Updates are performed by creating a new root that points to unchanged parts of the data structure.

## 10. Smart Contracts
Transaction execution is specified by code.

**Bitcoin:**
- Uses a relatively simple stack-based scripting language with instructions designed for funds-transfer.
- Includes the `multisig` instruction: $m$ of $n$ users must approve to enable escrow transactions.
- Infinite loops are not possible due to the limited power of the language.

**Ethereum:**
- Uses a Turing-complete scripting language based on the Ethereum Virtual Machine (EVM).
- *Solidity:* A high-level language compiled to EVM code.
- Greater expressive power but carries the risk of infinite loops. Needs a mechanism for terminating such loops despite the undecidability of the halting problem. A cost-per-instruction framework serves both to avoid infinite loops and to incentivize miners.

**Concept of "Gas" in Ethereum:**
- Each Ethereum instruction has a fixed cost, denominated in *gas*.
- Each smart contract sets its own *gas price* in Ether, defining the amount paid to the miner for one unit of gas.
- **Setting price wisely:**
  - *Too low:* Miners are disincented to include the transaction.
  - *Too high:* User overpays.
- **Limits:**
  - *Transaction gas limit:* Upper bound on transaction gas usage, set by the user.
  - *Block gas limit:* Upper bound on gas usage in a block, set by the system.
- Infinite loops are impossible since the transaction gas limit is reached eventually, at which point the transaction fails and terminates (though the miner keeps the payment received).

**Advanced Smart Contract Features:**
- **External input:** Messages from other contracts or input pertaining to the outside world from trusted sources called *oracles*.
- **Autonomy:** An Ethereum smart contract may run indefinitely by receiving Ether from external sources to fund its continued operation. Such contracts are called distributed autonomous organizations (DAOs).
- **Tokens:** A smart contract may be used to create a separate currency or token on top of the Ethereum blockchain (e.g., the ERC-20 standard).
- **Cross-chain transactions:** Smart contracts may be used in the implementation of cross-chain transactions, allowing transactions between separate blockchain systems.

## 11. Performance Enhancement
The consensus mechanism is an important factor in blockchain performance. Other ways to enhance performance include:
- **Sharding:** Parallelizing the mining of new blocks.
- **Off-chain transaction processing:** Creation of a separate channel for users who process transactions among themselves frequently.
  - The channel is funded with funds from the underlying blockchain.
  - Routine transactions avoid mining overhead.
  - Users can terminate the agreement to process transactions off-chain at any point, with current channel funds balances refunded on the underlying blockchain.
