# Chapter 14: Indexing

## 1. Basic Concepts
*   **Indexing Mechanisms**: Used to speed up access to desired data (e.g., an author catalog in a library).
*   **Search Key**: An attribute or set of attributes used to look up records in a file.
*   **Index File**: Consists of records (called index entries) of the form `[search-key, pointer]`. Index files are typically much smaller than the original file.
*   **Two Basic Kinds of Indices**:
    1.  **Ordered Indices**: Search keys are stored in sorted order.
    2.  **Hash Indices**: Search keys are distributed uniformly across "buckets" using a "hash function".

### Index Evaluation Metrics
*   **Access types supported efficiently**: e.g., records with a specified value in the attribute, or records with an attribute value falling in a specified range.
*   **Access time**
*   **Insertion time**
*   **Deletion time**
*   **Space overhead**

## 2. Ordered Indices
In an ordered index, index entries are stored sorted on the search key value.

*   **Clustering Index (Primary Index)**: In a sequentially ordered file, the index whose search key specifies the sequential order of the file. The search key is usually (but not necessarily) the primary key.
*   **Secondary Index (Non-clustering Index)**: An index whose search key specifies an order different from the sequential order of the file.
*   **Index-Sequential File**: A sequential file ordered on a search key, with a clustering index on the search key.

### Dense vs. Sparse Index Files
*   **Dense Index**: An index record appears for *every* search-key value in the file. Secondary indices must be dense.
*   **Sparse Index**: Contains index records for only *some* search-key values. Applicable when records are sequentially ordered on the search key.
    *   *To locate a record with search-key value $K$*: Find the index record with the largest search-key value $\le K$, then search the file sequentially starting from that pointer.
    *   *Trade-offs*: Less space and maintenance overhead, but generally slower than a dense index for locating records.
    *   *Good tradeoff*: For clustered indices, a sparse index with an entry for every block in the file.

### Multilevel Index
If an index does not fit in memory, access becomes expensive. 
*   **Solution**: Treat the index kept on disk as a sequential file and construct a sparse index on it.
    *   **Outer Index**: A sparse index of the basic index.
    *   **Inner Index**: The basic index file.
*   If the outer index is still too large, another level of index can be created. Indices at all levels must be updated on insertion or deletion.

## 3. B+-Tree Index Files
![Example of B+-Tree](../images/ch14_slides/slide_014.png)
![Example of B+-tree](../images/ch14_slides/slide_019.png)
A B+-tree is a rooted tree satisfying the following properties:
*   All paths from the root to a leaf are of the same length.
*   Each non-leaf/non-root node has between $\lceil n/2 \rceil$ and $n$ children.
*   A leaf node has between $\lceil (n-1)/2 \rceil$ and $n-1$ values.
*   *Special cases*: If the root is not a leaf, it has at least 2 children. If the root is a leaf, it can have between 0 and $n-1$ values.

### Node Structure
![B+-Tree Node Structure](../images/ch14_slides/slide_016.png)
*   A typical node contains search-key values $K_i$ and pointers $P_i$.
*   Search-keys are ordered: $K_1 < K_2 < K_3 < \dots < K_{n-1}$.
*   **Leaf Nodes**: $P_i$ points to a file record (or bucket) with search-key $K_i$. $P_n$ points to the next leaf node in search-key order.
*   **Non-Leaf Nodes**: Form a multi-level sparse index on the leaf nodes. Pointers route to subtrees based on ranges between keys.

### Observations and Queries
*   **Height**: With $K$ search-key values, the tree height is no more than $\lceil \log_{\lceil n/2 \rceil}(K) \rceil$. Searches are very efficient (e.g., only 4 nodes accessed for 1,000,000 keys with $n=100$).
*   **Queries**: Point queries traverse from root to leaf. Range queries find the lower bound leaf and follow the $P_n$ (next) pointers.
*   **Non-Unique Keys**: Typically handled by creating a composite key combining the non-unique search key with a primary key or record ID.

### Updates on B+-Trees
![B+-Tree  Insertion](../images/ch14_slides/slide_027.png)
![B+-Tree  Insertion](../images/ch14_slides/slide_028.png)
![Examples of B+-Tree Deletion](../images/ch14_slides/slide_030.png)
![Examples of B+-Tree Deletion (Cont.)](../images/ch14_slides/slide_031.png)
![Example of B+-tree Deletion (Cont.)](../images/ch14_slides/slide_032.png)
*   **Insertion**: 
    *   Find the appropriate leaf node. If there is room, insert the value and pointer.
    *   If full, **split** the node: distribute entries evenly between the original and a new node. Insert the new node's least key into the parent. Splits can cascade up to the root.
*   **Deletion**:
    *   Remove the entry from the leaf.
    *   If the node becomes under-full (fewer than $\lceil (n-1)/2 \rceil$ entries), attempt to **merge** with a sibling. 
    *   If merging exceeds node capacity, **redistribute** pointers evenly with the sibling and update the parent's separating key.
*   **Complexity**: Insertions and deletions take logarithmic time $O(\log_{\lceil n/2 \rceil}(K))$. 

### B+-Tree File Organization
![B-Tree Index File Example](../images/ch14_slides/slide_042.png)
*   Leaf nodes store the actual records instead of pointers. This keeps data records clustered despite updates.
*   **Secondary Indices**: Should use the search key of the primary B+-tree rather than physical record pointers. This prevents massive secondary index updates when records are moved due to splits/merges.

### Other Issues in Indexing
*   **Indexing Strings**: Uses variable fanout and prefix compression to save space in internal nodes.
*   **Bulk Loading**: Inserting entries one-by-one is inefficient (too much I/O). Instead, sort entries first and build the B+-tree bottom-up, layer by layer.
*   **In-Memory Indexing**: Optimize cache usage by maintaining small node sizes that fit within cache lines, minimizing cache misses during binary search inside nodes.

## 4. Hashing
![Example of Hash File Organization](../images/ch14_slides/slide_049.png)
![Example of Hash Index](../images/ch14_slides/slide_081.png)
### Static Hashing
*   A **bucket** is a unit of storage (typically a disk block).
*   A **hash function** maps search-key values to bucket addresses.
*   Buckets must be searched sequentially if multiple keys map to the same bucket.

### Handling Bucket Overflows
*   Overflows occur due to insufficient buckets or data skew.
*   **Overflow Chaining (Closed Addressing)**: Overflow buckets of a given bucket are chained together in a linked list. (Open addressing is not suitable for databases).

### Dynamic Hashing
Static hashing suffers when databases grow (overflows) or shrink (wasted space). Dynamic hashing allows the number of buckets to be modified.
*   **Periodic Rehashing**: Rebuilding the hash table with a new size when a threshold is met.
*   **Extendable Hashing**: Tailored for disk-based hashing; doubles the number of entries in the directory without immediately doubling all data buckets.
*   **Linear Hashing**: Performs rehashing in an incremental manner.

### Ordered Indexing vs. Hashing
*   **Hashing** is generally better for point queries (retrieving records with a specific key value).
*   **Ordered Indices (B+-Trees)** are strictly preferred for range queries. 
*   *In practice*, B+-trees are the standard (SQL Server supports only B+-trees, PostgreSQL discourages hash indices).

## 5. Multiple-Key Access
For queries filtering on multiple attributes (e.g., `dept_name = "Finance" and salary = 80000`).
*   **Composite Search Keys**: Search keys containing more than one attribute (e.g., `(dept_name, salary)`). Values are sorted lexicographically.
    *   Efficient for: `dept_name = "Finance" and salary < 80000`.
    *   Inefficient for: `dept_name < "Finance" and salary = 80000` (requires fetching many irrelevant records).
*   **Covering Indices**: Adding extra attributes to an index leaf level so that some queries can be answered entirely from the index without fetching actual records.

---

## 6. Write-Optimized Indices
Standard B+-trees suffer from heavy random I/O overhead on write-intensive workloads.
*   **Log-Structured Merge (LSM) Tree**:
    *   Records are first inserted into an in-memory tree ($L_0$).
    *   When full, it is merged via sequential I/O to a disk-based tree ($L_1$), which merges to $L_2$, etc.
    *   Deletions are handled using special "delete" entries (tombstones).
    *   *Benefits*: Extremely fast inserts (sequential I/O). *Drawback*: Queries must search multiple levels (mitigated by Bloom filters). 
    *   Used heavily in NoSQL/Big Data systems (Cassandra, BigTable, RocksDB).
*   **Buffer Tree**:
    *   Each internal node of a B+-tree has a buffer to batch inserts. When a buffer is full, inserts are pushed down in bulk.

---

## 7. Bitmap Indices
Designed for efficient querying on attributes that have a small number of distinct values (e.g., gender, country).
*   A **bitmap** is an array of bits (one bit per record). The bit is `1` if the record matches the value, and `0` otherwise.
*   Queries are answered using extremely fast bitwise operations (AND, OR, NOT).
*   Highly space-efficient for low-cardinality attributes.

## 8. Spatial and Temporal Indices
### Spatial Data
![Division of Space by Quadtrees](../images/ch14_slides/slide_072.png)
![Example R-Tree](../images/ch14_slides/slide_074.png)
Databases store geometric types (lines, polygons) and perform spatial queries (contains, overlaps, nearest neighbor).
*   **k-d Tree**: Partitions multi-dimensional space into two at each level, cycling through dimensions. (k-d-B tree is the disk-optimized variant).
*   **Quadtrees**: Each internal node divides its rectangular space into four equal quadrants.
*   **R-Trees**: An N-dimensional extension of B+-trees for indexing bounding boxes (rectangles/polygons). Bounding boxes of children are allowed to overlap.

### Indexing Temporal Data
*   **Temporal Data**: Data associated with a valid time interval (start time, end time). Currently valid data uses an end time of "infinity".
*   Indexed using a spatial index (like an R-tree) where the attribute is one dimension and time is another. 
*   Current tuples are typically stored in a separate index to avoid bounding box issues caused by "infinite" end times.
