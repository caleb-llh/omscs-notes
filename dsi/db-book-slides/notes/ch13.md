# Chapter 13: Data Storage Structures

*Based on Database System Concepts, 7th Ed. by Silberschatz, Korth and Sudarshan*

## 1. File Organization

The database is stored as a collection of files. Each file is a sequence of records, and a record is a sequence of fields.

**A Simple Approach:**
- Assume record size is fixed.
- Each file has records of one particular type only.
- Different files are used for different relations.
- This is the easiest case to implement.
- **Assumption:** Records are smaller than a disk block.

---

## 2. Fixed-Length Records

- **Basic Approach:** Store record $i$ starting from byte $n \times (i - 1)$, where $n$ is the size of each record.
  - Record access is simple, but records may cross block boundaries.
- **Modification:** Do not allow records to cross block boundaries.
- **Deletion of record $i$ (Alternatives):**
  1. Move records $i + 1, \dots, n$ to $i, \dots, n - 1$.
  2. Move record $n$ to $i$.
  3. Do not move records, but link all free records on a free list.

---

## 3. Variable-Length Records

Variable-length records arise in database systems in several ways:
- Storage of multiple record types in a file.
- Record types that allow repeating fields (used in some older data models).
- Record types that allow variable lengths for one or more fields (e.g., strings/varchar).

**Representation:**
- Attributes are stored in order.
- Variable-length attributes are represented by a fixed size (offset, length), with the actual data stored after all fixed-length attributes.
- Null values are represented by a null-value bitmap.

### Slotted Page Structure
Used for organizing variable-length records within a block.
![Variable-Length Records: Slotted Page Structure](../images/ch13_slides/slide_008.png)
- **Header contains:**
  - Number of record entries.
  - End of free space in the block.
  - Location and size of each record.
- Records can be moved around within a page to keep them contiguous with no empty space between them (the entry in the header must be updated).
- **Pointers:** Pointers should not point directly to the record; instead, they should point to the entry for the record in the header.

---

## 4. Storing Large Objects

Large objects (e.g., BLOB/CLOB types) require special handling because records must typically be smaller than pages.

**Alternatives:**
1. Store as files in standard file systems.
2. Store as files managed directly by the database.
3. Break into pieces and store in multiple tuples in a separate relation (e.g., PostgreSQL TOAST).

---

## 5. Organization of Records in Files

- **Heap:** Records can be placed anywhere in the file where there is free space.
- **Sequential:** Records are stored in sequential order, based on the value of the search key of each record.
- **Multitable Clustering:** Records of several different relations can be stored in the same file.
  - *Motivation:* Store related records on the same block to minimize I/O.
- **B+-tree:** Ordered storage that maintains order even with inserts and deletes (covered in Chapter 14).
- **Hashing:** A hash function is computed on the search key; the result specifies the block where the record should be placed (covered in Chapter 14).

---

## 6. Heap File Organization

- Records are placed anywhere in the file with free space and usually do not move once allocated.
- It is critical to efficiently find free space within the file.
- **Free-Space Map:**
  - An array with 1 entry per block. Each entry is a few bits to a byte, recording the fraction of the block that is free (e.g., 3 bits per block, where the value divided by 8 indicates the free fraction).
  - Can implement a second-level free-space map (e.g., each entry stores the maximum from 4 entries of the first-level map).
  - The map is written to disk periodically. It is acceptable to have occasionally wrong (old) values, as they will be detected and fixed.

---

## 7. Sequential File Organization

- Suitable for applications that require sequential processing of the entire file.
- Records are ordered by a search-key.
- **Deletion:** Handled using pointer chains.
- **Insertion:** Locate the correct position for the record.
  - If there is free space, insert it there.
  - If there is no free space, insert the record in an overflow block.
  - In either case, pointer chains must be updated.
- The file needs to be reorganized periodically to restore physical sequential order.

---

## 8. Multitable Clustering File Organization

Stores several relations in one file (e.g., a multitable clustering of `department` and `instructor`).
![Multitable Clustering File Organization](../images/ch13_slides/slide_014.png)
- **Pros:** Good for queries involving joins (e.g., `department` ⨝ `instructor`) and for queries involving one single department and its instructors.
- **Cons:** Bad for queries involving only one of the relations (e.g., only `department`).
- Results in variable size records.
- Pointer chains can be added to link records of a particular relation.

---

## 9. Partitioning

**Table partitioning:** Records in a relation can be partitioned into smaller relations that are stored separately.
- *Example:* A `transaction` relation may be partitioned by year (`transaction_2018`, `transaction_2019`, etc.).
- Queries written on the full relation must access records in all partitions unless the query has a specific selection (e.g., `year=2019`), in which case only one partition is needed.

**Benefits:**
- Reduces costs of operations such as free space management.
- Allows different partitions to be stored on different storage devices (e.g., current year on SSD, older years on magnetic disk).

---

## 10. Data Dictionary Storage

The **Data Dictionary** (or system catalog) stores metadata (data about data), including:
![Relational Representation of System Metadata](../images/ch13_slides/slide_018.png)
- **Information about relations:** Names of relations, names/types/lengths of attributes, names and definitions of views, and integrity constraints.
- **User and accounting information:** Including passwords.
- **Statistical and descriptive data:** e.g., Number of tuples in each relation.
- **Physical file organization information:** How the relation is stored (sequential, hash, etc.) and its physical location.
- **Information about indices.**

It is represented relationally on disk, but uses specialized data structures designed for efficient access in main memory.

---

## 11. Storage Access & Buffer Management

- **Blocks** are units of both storage allocation and data transfer.
- The database system seeks to minimize block transfers between the disk and memory by keeping as many blocks as possible in main memory.
- **Buffer:** A portion of main memory available to store copies of disk blocks.
- **Buffer Manager:** The subsystem responsible for allocating buffer space in main memory.

### How the Buffer Manager Works
When a program needs a block from disk:
1. If the block is already in the buffer, it returns the memory address.
2. If not, it allocates space in the buffer.
   - It may replace (throw out) another block to make space.
   - The replaced block is written back to disk *only* if it was modified since it was last written/fetched.
   - It reads the required block from disk into the buffer and returns the memory address.

### Buffer Concurrency and Pinning
- **Pinned Block:** A memory block not allowed to be written back to disk.
  - Pinning is done before reading/writing; unpinning is done when complete.
  - A pin count is kept; a block can only be evicted if its pin count is 0.
- **Shared and Exclusive Locks:**
  - Prevents concurrent operations from reading page contents while they are moved/reorganized.
  - Readers get a shared lock; updates require an exclusive lock.
  - Only one exclusive lock is allowed at a time. Shared locks cannot be held concurrently with an exclusive lock, but multiple shared locks are permitted.

---

## 12. Buffer-Replacement Policies

- **LRU (Least Recently Used):** Uses past patterns to predict future references. However, LRU can be bad for certain database queries (e.g., nested loop joins or sequential scans).
- **Mixed Strategy:** Queries have well-defined access patterns. The database can use hints from the query optimizer to choose a replacement strategy.
- **Toss-Immediate Strategy:** Frees the space occupied by a block as soon as the final tuple of that block has been processed.
- **MRU (Most Recently Used):** System pins the block currently being processed. Once processing is done, it is unpinned and becomes the most recently used block (making it the first candidate for eviction).
- **Heuristics:** Buffer manager can use statistical information (e.g., keeping frequently accessed data-dictionary blocks in memory).

### Ordering of Writes
- OS or buffer manager may reorder writes, which can lead to on-disk data structure corruption (e.g., broken linked lists).
- Careful ordering of writes is required to avoid these problems.

---

## 13. Optimization of Disk Block Access

- Buffer managers support forced output of blocks for recovery purposes.
- **Nonvolatile Write Buffers:** Speed up disk writes by writing blocks to NV-RAM or flash immediately. The physical disk writes can then be reordered to minimize disk arm movement.
- **Log Disk:** A disk devoted to writing a sequential log of block updates. Extremely fast since no seeks are required.
- **Journaling File Systems:** Write data in-order to NV-RAM or log disk to prevent corruption from reordering.

---

## 14. Column-Oriented Storage

Also known as **columnar representation**, this method stores each attribute of a relation separately rather than row-by-row.
![Columnar File Representation](../images/ch13_slides/slide_027.png)

**Benefits:**
- Reduced I/O if only specific attributes are accessed.
- Improved CPU cache performance.
- Improved compression.
- Better suited for vector processing on modern CPU architectures.

**Drawbacks:**
- High cost for tuple reconstruction from columns.
- High cost for tuple deletion and update.
- Cost of decompression.

**Usage:**
- Columnar representation is more efficient for **decision support** (analytics) applications.
- Traditional row-oriented representation is preferable for **transaction processing**.
- **Hybrid Stores:** Some databases support both (hybrid row/column stores).
- **File Formats:** ORC and Parquet are popular file formats with columnar storage inside the file, heavily used in big-data applications.

---

## 15. Storage Organization in Main-Memory Databases

- Can store records directly in memory without a traditional buffer manager.
- Column-oriented storage can be used in-memory to speed up decision support applications.
- Compression is often utilized to reduce memory requirements.
