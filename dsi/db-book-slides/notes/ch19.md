## 1. Failure Classification

Failures in a database system can be classified into several categories:
* **Transaction failure**: 
  * *Logical errors*: A transaction cannot complete due to some internal error condition.
  * *System errors*: The database system must terminate an active transaction due to an error condition (e.g., deadlock).
* **System crash**: A power failure or other hardware/software failure causes the system to crash.
  * *Fail-stop assumption*: Non-volatile storage contents are assumed to not be corrupted by a system crash. Database systems have numerous integrity checks to prevent disk data corruption.
* **Disk failure**: A head crash or similar disk failure destroys all or part of disk storage.
  * Destruction is assumed to be detectable (e.g., disk drives use checksums to detect failures).

---

## 2. Storage Structure

* **Volatile storage**: Does not survive system crashes (e.g., main memory, cache memory).
* **Nonvolatile storage**: Survives system crashes (e.g., disk, tape, flash memory, non-volatile RAM). It may still fail, losing data.
* **Stable storage**: A mythical form of storage that survives all failures. It is approximated by maintaining multiple copies on distinct nonvolatile media (often at remote sites to protect against disasters).

### Stable-Storage Implementation
To protect storage media from failure during data transfer (when updating copies):
1. Write the information onto the first physical block.
2. When the first write successfully completes, write the same information onto the second physical block.
3. The output is completed only after the second write successfully completes.

To recover from a failure during transfer:
* Maintain a record of in-progress disk writes on non-volatile storage. 
* Compare copies of only those blocks that may be inconsistent. If one has an error (bad checksum), overwrite it with the other.

### Data Access

![Block Storage Operations](../images/ch19_slides/slide_094.png)

* **Physical blocks**: Blocks residing on the disk.
* **Buffer blocks**: Blocks residing temporarily in main memory.
* **Block movements**:
  * `input(B)`: Transfers physical block B to main memory.
  * `output(B)`: Transfers buffer block B to the disk.
* **Transaction Work-Area**: Each transaction $T_i$ has a private work-area for local copies of data items.
  * `read(X)`: Assigns the value of data item X to a local variable.
  * `write(X)`: Assigns the value of the local variable to data item X in the buffer block.

## 3. Recovery and Atomicity

To ensure atomicity despite failures, the system outputs information describing the modifications to stable storage *before* modifying the database itself. 
* **Log-based recovery mechanisms** are most commonly used.
* **Shadow-copy and shadow-paging** are less used alternatives.

---

## 4. Log-Based Recovery

![Portion of the Database Log Corresponding to T0 and T1](../images/ch19_slides/slide_095.png)
![State of the Log and Database Corresponding to T0 and T1](../images/ch19_slides/slide_096.png)

A log is a sequence of log records kept on stable storage. It keeps information about update activities.
* `<Ti start>`: Written when transaction $T_i$ starts.
* `<Ti, X, V1, V2>`: Written before $T_i$ executes `write(X)`. $V_1$ is the old value, and $V_2$ is the new value.
* `<Ti commit>`: Written when $T_i$ finishes its last statement.

### Immediate vs. Deferred Database Modification

![Immediate DB Modification Recovery Example](../images/ch19_slides/slide_020.png)

* **Immediate Database Modification**: Allows updates of an uncommitted transaction to be made to the buffer (or disk) *before* the transaction commits. The update log record must be written before the database item is written.
* **Deferred Database Modification**: Performs updates to the buffer/disk only at the time of transaction commit.

### Transaction Commit
A transaction has committed when its commit log record is output to stable storage. All previous log records of the transaction must have been output already.

---

## 5. Concurrency Control and Recovery

With concurrent transactions, all share a single disk buffer and log. 
* Uncommitted updates must not be visible to other transactions.
* Strict two-phase locking (holding exclusive locks on updated items until the end of the transaction) ensures this isolation and makes recovery (undo) possible.

---

## 6. Undo and Redo Operations

* **`undo(Ti)`**: Restores the value of all data items updated by $T_i$ to their old values, going backwards from the last log record for $T_i$. A special compensation log record `<Ti, X, V>` is written for each restoration. Finally, `<Ti abort>` is written.
* **`redo(Ti)`**: Sets the value of all data items updated by $T_i$ to the new values, going forward from the first log record for $T_i$. No logging is done during redo.

### Recovering from Failure
* **Undo** transaction $T_i$ if the log contains `<Ti start>` but neither `<Ti commit>` nor `<Ti abort>`.
* **Redo** transaction $T_i$ if the log contains `<Ti start>` and either `<Ti commit>` or `<Ti abort>`.
* **Repeating History**: If a transaction was previously undone and a failure occurs, the recovery process first redoes the original actions (including the steps that restored old values) and then proceeds. This simplifies recovery greatly.

## 7. Checkpoints

![Example of Checkpoints](../images/ch19_slides/slide_023.png)


Processing the entire log during recovery is too time-consuming. **Checkpointing** streamlines recovery:
1. Output all log records currently in main memory to stable storage.
2. Output all modified buffer blocks to the disk.
3. Write a log record `<checkpoint L>` onto stable storage, where $L$ is a list of all active transactions.
4. Stop all updates while doing checkpointing.

**Recovery with Checkpoints**:
Scan backwards from the end of the log to find the most recent `<checkpoint L>`. Only transactions in $L$ or those that started *after* the checkpoint need to be redone or undone.

---

## 8. Basic Recovery Algorithm

![Recovery Algorithm](../images/ch19_slides/slide_024.png)

### Normal Operation
* **Logging**: Log start, updates, and commit.
* **Transaction Rollback**: Scan the log backwards. For each update, perform the undo, write a compensation log record, and finally write an abort log record.

### Failure Recovery (Two Phases)

![Example of Recovery](../images/ch19_slides/slide_029.png)

1. **Redo Phase**: Replay updates of *all* transactions (committed, aborted, or incomplete).
   * Find the last `<checkpoint L>` and set `undo-list = L`.
   * Scan forward from the checkpoint. Redo updates.
   * Add new transactions to the `undo-list`, and remove them if a commit or abort record is found.
2. **Undo Phase**: Undo all incomplete transactions.
   * Scan the log backwards from the end.
   * Undo updates for transactions in the `undo-list` and write compensation log records.
   * Write an abort record and remove the transaction from the `undo-list` when its start record is found.
   * Stop when the `undo-list` is empty.

## 9. Buffer Management

### Log Record Buffering
Log records are buffered in main memory and output to stable storage when the block is full or a **log force** operation is executed.
* **Write-Ahead Logging (WAL)**: Before a block of data in main memory is output to the database, all log records pertaining to data in that block must have been output to stable storage.

### Database Buffering
* **Force vs. No-Force**: The recovery algorithm supports a **no-force policy** (updated blocks need not be written to disk when a transaction commits). A force policy is more expensive.
* **Steal vs. No-Steal**: The algorithm supports a **steal policy** (blocks containing updates of uncommitted transactions can be written to disk).
* **Latches**: Short-duration exclusive locks acquired on a block before writing to ensure no updates are in progress during the output.

### Dual Paging Problem
Database buffers are generally implemented in virtual memory. When the OS evicts a modified page, it goes to swap space. If the database later decides to write that page to disk, it must be read from swap and written to the database (extra I/O). Ideally, the OS should pass control to the database to output directly to the database instead of swap space.

## 10. Fuzzy Checkpointing

To avoid long interruptions during checkpointing, updates are allowed to happen concurrently.
1. Temporarily stop all updates.
2. Write `<checkpoint L>` and force the log to stable storage. Note the list $M$ of modified buffer blocks.
3. Permit transactions to proceed.
4. Output to disk all modified blocks in $M$ (following WAL).
5. Store a pointer to the checkpoint record in a fixed position (`last_checkpoint`) on disk.

During recovery, scan from the checkpoint record pointed to by `last_checkpoint`.

---

## 11. Failure with Loss of Nonvolatile Storage

Dealt with by periodically dumping the entire content of the database to stable storage.
* **Fuzzy/Online Dump**: Similar to fuzzy checkpointing, allows transactions to be active during the dump.
* **Recovery**: Restore from the most recent dump, then consult the log to redo all transactions that committed after the dump.

---

## 12. Remote Backup Systems

Provide high availability by allowing transaction processing to continue if the primary site is destroyed.
* **Detection**: Use heart-beat messages over multiple communication links.
* **Transfer of Control**: Backup site performs recovery using its copy of the database and redo logs. It then becomes the new primary.
* **Hot-Spare**: Backup continually processes redo log records as they arrive, permitting very fast takeover.
* **Durability/Commit Strategies**:
  * *One-safe*: Commit as soon as written at primary (risk of lost updates).
  * *Two-very-safe*: Commit when written at both primary and backup (reduces availability if either fails).
  * *Two-safe*: Two-very-safe if both are active; falls back to one-safe if only primary is active.

## 13. Early Lock Release & Logical Undo

![Failure Recovery with Logical Undo](../images/ch19_slides/slide_054.png)
![Transaction Rollback: Another Example](../images/ch19_slides/slide_055.png)

For high-concurrency structures like B+-trees, locks are released early.
* **Logical Undo**: Restoring old values (physical undo) won't work because other transactions may have modified the structure. Instead, executing a compensating logical operation (e.g., executing a deletion to undo an insertion) is required.
* **Operation Logging**:
  * Log `<Ti, Oj, operation-begin>`.
  * Log physical redo and undo information during execution.
  * Log `<Ti, Oj, operation-end, U>` (where U is logical undo information) upon completion.
* **Rollback**:
  * If `operation-end` is found, roll back logically using U.
  * If `operation-end` is missing, use physical undo.
  * Redo always uses physical redo information.

## 14. ARIES Recovery Algorithm

ARIES (Algorithm for Recovery and Isolation Exploiting Semantics) is a state-of-the-art recovery method featuring several optimizations.

### ARIES Data Structures

![ARIES Data Structures](../images/ch19_slides/slide_065.png)

1. **Log Sequence Number (LSN)**: Identifies each log record. Stored in pages (`PageLSN`) to identify which updates have been applied.
2. **Physiological Redo**: Affected page is physically identified, but the action within the page can be logical. Reduces logging overhead.
3. **Dirty Page Table**: Tracks updated pages in the buffer (stores `PageLSN` and `RecLSN`). Avoids unnecessary redos during recovery.
4. **Fuzzy Checkpointing**: Records information about dirty pages and active transactions, but does *not* require dirty pages to be written out at checkpoint time.

### ARIES Recovery: 3 Passes

![Aries Recovery: 3 Passes](../images/ch19_slides/slide_068.png)
![Recovery Actions in ARIES](../images/ch19_slides/slide_074.png)

1. **Analysis Pass**: 
   * Starts from the last complete checkpoint.
   * Determines which transactions to undo (populates `undo-list`).
   * Determines which pages were dirty.
   * Sets `RedoLSN` (the minimum `RecLSN` of all dirty pages) to mark where redo should start.
2. **Redo Pass**: 
   * Repeats history by replaying every action not already reflected in the page on disk.
   * Scans forward from `RedoLSN`. 
   * Skips redo if the page is not in the Dirty Page Table, or if the log record's LSN is less than the page's `RecLSN` or `PageLSN`.
3. **Undo Pass**: 
   * Rolls back all incomplete transactions (those in `undo-list`).
   * Scans backwards, using `PrevLSN` and `UndoNextLSN` (for Compensation Log Records) to skip already undone records.

## 15. Shadow Paging (Alternative/Extra)

![Sample Page Table](../images/ch19_slides/slide_090.png)
![Example of Shadow Paging](../images/ch19_slides/slide_091.png)


Useful primarily for serially executing transactions.
* **Idea**: Maintain two page tables—the *current* page table and the *shadow* page table (stored on nonvolatile storage).
* **Execution**: All reads/writes use the current page table. When a page is written for the first time, a copy is made to an unused block, and the current page table points to this new block.
* **Commit**: Flush all modified pages to disk, output the current page table to disk, and update a fixed pointer to make it the new shadow page table.
* **Pros**: No log writing overhead, trivial recovery (no redo/undo needed, just use the shadow page table).
* **Cons**: Copying the page table is expensive, high commit overhead, disk fragmentation, garbage collection overhead, and very hard to extend for concurrent transactions.
