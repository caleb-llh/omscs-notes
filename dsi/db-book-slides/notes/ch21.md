# Chapter 21: Parallel and Distributed Storage

## Introduction
* **Hardware Trends:** Parallel machines have become common and affordable due to sharp drops in the prices of microprocessors, memory, and disks.
* **Growing Data Needs:** Data storage requirements are scaling massively:
  * Web-scale user data involving hundreds of millions of users and petabytes of data.
  * Transaction data collected and stored for analysis.
  * Multimedia objects such as images and videos.
* **Parallel Storage System Requirements:**
  * Storing large volumes of data.
  * Processing time-consuming decision-support queries.
  * Providing high throughput for transaction processing.
  * Meeting very high demands for scalability and availability.

## Parallel/Distributed Data Storage History
* **1980s/1990s:** Distributed database systems with tens of nodes.
* **2000s:**
  * **Distributed file systems (1000s of nodes):** Managed millions of large objects (100s of megabytes) like web logs, images, and videos. Typically create/append-only.
  * **Distributed data storage systems (1000s of nodes):** Handled billions to trillions of smaller objects (kilobytes to megabytes) such as social media posts, emails, and online purchases. Supported inserts, updates, and deletes.
  * Emergence of **key-value stores**.
* **2010s:** Distributed database systems scaling up to 1000s of nodes.

## I/O Parallelism
![Range Partitioning](../images/ch21_slides/slide_006.png)
I/O parallelism reduces the time required to retrieve relations from disks by partitioning the data across multiple disks and nodes. 

* **Horizontal Partitioning:** Tuples of a relation are divided among many nodes such that a subset of tuples resides on each node. By default, "partitioning" refers to horizontal partitioning.
  * *(Contrast with vertical partitioning, where columns are divided, e.g., splitting `r(A,B,C,D)` into `r1(A,B)` and `r2(A,C,D)`).*
* **Partitioning Techniques (for $n$ nodes):**
  * **Round-robin:** Send the $i^{th}$ tuple inserted in the relation to node $i \pmod n$.
  * **Hash partitioning:** Choose one or more partitioning attributes. Apply a hash function $h$ with a range of $0 \dots n-1$ to the attribute value. Send the tuple to the resulting node.
  * **Range partitioning:** Choose a partitioning attribute and a partitioning vector $[v_0, v_1, \dots, v_{n-2}]$. A tuple with attribute value $v$ goes to:
    * Node 0 if $v < v_0$
    * Node $i+1$ if $v_i \le v < v_{i+1}$
    * Node $n-1$ if $v \ge v_{n-2}$

## Comparison of Partitioning Techniques
Evaluated based on sequential scanning, point queries (e.g., `r.A = 25`), and range queries (e.g., `10 ≤ r.A < 25`).

* **Round-robin:**
  * Best for sequential scans of the entire relation. Data is evenly distributed, balancing retrieval work.
  * *Drawback:* All queries (point and range) must be processed at all nodes.
* **Hash partitioning:**
  * Good for sequential access (assuming a good hash function).
  * Excellent for point queries on the partitioning attribute; requires looking up only a single node, leaving others free.
  * *Drawback:* Inefficient for range queries, which must be processed at all nodes.
* **Range partitioning:**
  * Clusters data by attribute value.
  * Good for sequential access and point queries (requires accessing only one node).
  * Good for range queries on the partitioning attribute, as only a few nodes need to be accessed.
  * *Drawback:* Susceptible to **execution skew**. If a range query fetches many blocks from just one or a few nodes, the potential for parallel disk access across the cluster is wasted.

## Handling Small and Medium Relations
* **Small Relations:** Partitioning is counterproductive if the relation fits in one or a few disk blocks. Instead, assign the relation to a single node or replicate it across all nodes.
* **Medium Relations:** Choose the number of partitions based on the relation's size.
* **Large Relations:** Typically partitioned across all available nodes.

## Data Skew
Skew leads to imbalanced workloads where some nodes handle significantly more data or queries than others.

* **Data-Distribution Skew:** Some nodes have many tuples while others have few. Causes include:
  * **Attribute-value skew:** Many tuples share the same partitioning attribute value, forcing them into the same partition. (Can occur in both hash and range partitioning).
  * **Partition skew:** A badly chosen range-partition vector assigns too many tuples to certain partitions, even without attribute-value skew. (Less likely with hash partitioning).
* **Execution Skew:** Occurs even without data-distribution skew (e.g., most queries access recent dates in a date-partitioned relation).

### Handling Skew in Range-Partitioning
* **Balanced Partitioning Vectors:** Sort the relation by the partitioning attribute and pick boundaries such that each partition gets $1/n$ of the tuples. 
  * To reduce cost, this can be done using a random sample of tuples or **histograms** (e.g., equi-depth histograms that divide ranges to contain approximately equal numbers of tuples).
* **Virtual Node Partitioning:**
  * **Concept:** Create 10x to 20x as many *virtual nodes* as real nodes. Tuples are partitioned across virtual nodes using a partitioning vector or hashing.
  * **Mapping:** Virtual nodes are mapped to real nodes (e.g., using round-robin or a mapping table).
  * **Benefits:** If a normal partition would have been skewed, the load is spread over multiple virtual partitions. Skewed virtual partitions are distributed across different physical nodes, balancing the work. Also enables elastic storage (easy to move virtual nodes to new machines).

## Dynamic Repartitioning
A fixed partitioning vector cannot handle shifting data distributions over time, and full repartitioning is expensive.
* **Incremental Repartitioning:** Using the virtual node scheme (where virtual nodes are often called **tablets**).
  * Tablets that grow too large can be split (similar to B+-tree node splits).
  * Tablets can be moved from heavily loaded nodes to less loaded ones.

## Routing and Indexing
![Global Primary and Secondary Indices](../images/ch21_slides/slide_026.png)
* **Query Routing:**
  * Typically handled via a partition table stored at a master node and cached at routers.
  * **Consistent hashing / Distributed Hash Tables (DHT):** Alternative peer-to-peer routing schemes that eliminate the need for a master node.
* **Parallel Indexing:**
  * **Local index:** Built only on local data.
  * **Global index:** Built on all data and usually partitioned across nodes.
  * **Global primary index:** Data is partitioned on the index attribute.
  * **Global secondary index:** Data is partitioned on a non-index attribute. (Requires creating a secondary relation `ris` mapping the secondary key to the primary key, partitioned on the secondary key).

## Replication and Consistency
* **Goal:** High availability despite failures. Data (tablets) is typically replicated across 2 or 3 nodes.
* **Replica Location:**
  * *Within a data center:* Handles machine failures and reduces local latency.
  * *Across data centers:* Handles full data center failures (e.g., power loss, earthquakes) and provides lower latency to geographically distributed users.
* **Consistency:** Replicas must be kept consistent during updates.
  * **Master replica (primary copy) scheme:** Updates go to the master and replicate outwards.
  * **Update protocols:** Two-phase commit, persistent messaging (leading to *eventual consistency*), or consensus protocols (which don't require a designated master).

## Distributed File Systems (GFS / HDFS)
* **Architecture:**
  * **Master (NameNode):** Manages metadata, mapping filenames to Block IDs, and Block IDs to replica locations.
  * **Chunk servers (DataNodes):** Read and write large blocks (e.g., 64 MB).
* **Characteristics:** 
  * Replicates blocks (usually 3 copies) within a data center.
  * **Data coherency:** Write-once-read-many access. Clients can only append to files.
* **Limitations:** 
  * The central master can become a memory bottleneck, limiting the total number of files.
  * High overhead for small files/objects.
  * Weak consistency guarantees (blocks cached locally). 
  * Ideal for append-only data, often used as the storage layer for other systems (e.g., BigTable uses GFS).

## Data Storage Systems (Key-Value & Wide-Column Stores)
![Architecture of Key-Value Store](../images/ch21_slides/slide_038.png)
* **Sharding Limitations:** Manually sharding traditional SQL databases scales well but forces the application to manage routing and replication, breaking transparency.
* **Key-Value & Wide-Column Stores:**
  * **Examples:** Amazon S3/Dynamo (key-value), Google BigTable, Apache Cassandra, HBase (wide-column), MongoDB (document).
  * **API:** Standard `get`, `put`, `delete`, and `execute` operations.
  * **Features:** Flexible/no schema, multi-versioning, but often limited support for complex relational models, referential integrity, and full ACID transactions.
* **Architecture (e.g., BigTable):**
  * Vertically partitioned by attribute (columnar storage).
  * Records sorted by key.
  * Tables are split into tablets (100–200 MB), each managed by a single tablet server.
  * Master handles load balancing; GFS handles actual data and log storage.

## Transactions and Optimizations in Key-Value Stores
* **Transactions:** 
  * Most treat single-item updates as transactions.
  * Secondary indices are hard to maintain without full transactions (often maintained asynchronously).
  * Some systems (like Google Spanner) support full multi-item ACID transactions using two-phase commit and Paxos.
* **Index Structures:**
  * B+-trees and **LSM trees** (Log-Structured Merge-trees, heavily used in BigTable/HBase for write optimization) are ideal for range queries and appends.
* **Querying Optimizations:**
  * Lacking declarative query languages, applications often maintain **materialized views** to avoid run-time joins.
  * **Entity-groups:** Storing related data items together (e.g., a user and all their posts) makes joins incredibly cheap.
