## 1. Lock-Based Protocols

A **lock** is a mechanism to control concurrent access to a data item. Data items can be locked in two modes:
1. **Exclusive (X) mode**: Data item can be both read as well as written. X-lock is requested using the `lock-X` instruction.
2. **Shared (S) mode**: Data item can only be read. S-lock is requested using the `lock-S` instruction.

Lock requests are made to the concurrency-control manager. A transaction can proceed only after the request is granted.

* **Lock-compatibility matrix**: A transaction may be granted a lock on an item if the requested lock is compatible with locks already held on the item by other transactions.
  * Any number of transactions can hold shared locks on an item.
  * If any transaction holds an exclusive lock on the item, no other transaction may hold any lock on the item.
* **Locking Protocol**: A set of rules followed by all transactions while requesting and releasing locks. Locking protocols enforce serializability by restricting the set of possible schedules.

### Deadlock and Starvation
* **Deadlock**: A situation where a set of transactions are waiting for each other to release locks (e.g., $T_3$ waits for $T_4$ to release a lock, and $T_4$ waits for $T_3$). To handle a deadlock, one of the transactions must be rolled back and its locks released. The potential for deadlock exists in most locking protocols; deadlocks are a necessary evil.
* **Starvation**: Occurs when a concurrency control manager is badly designed. For example:
  * A transaction may wait indefinitely for an X-lock while a sequence of other transactions are continuously granted S-locks on the same item.
  * The same transaction is repeatedly rolled back due to deadlocks.
  * Concurrency control managers can be designed to prevent starvation.

### The Two-Phase Locking Protocol (2PL)
A protocol which ensures conflict-serializable schedules.
* **Phase 1: Growing Phase**: A transaction may obtain locks, but may not release locks.
* **Phase 2: Shrinking Phase**: A transaction may release locks, but may not obtain locks.
* The protocol assures serializability. It can be proved that transactions can be serialized in the order of their **lock points** (the point where a transaction acquired its final lock).
* Two-phase locking **does not** ensure freedom from deadlocks.
* **Extensions to basic 2PL** (to ensure recoverability and freedom from cascading roll-back):
  * **Strict two-phase locking**: A transaction must hold all its exclusive locks till it commits/aborts. Ensures recoverability and avoids cascading roll-backs.
  * **Rigorous two-phase locking**: A transaction must hold all locks till commit/abort. Transactions can be serialized in the order in which they commit. Most databases implement rigorous 2PL, but simply refer to it as two-phase locking.
* 2PL is not a necessary condition for serializability (there are conflict-serializable schedules that cannot be obtained using 2PL), but without extra information (like ordering of access to data), 2PL is necessary for conflict serializability.
* **Lock Conversions**: 2PL can allow lock conversions:
  * **Growing Phase**: can acquire lock-S, lock-X, or convert lock-S to lock-X (upgrade).
  * **Shrinking Phase**: can release lock-S, lock-X, or convert lock-X to lock-S (downgrade).

### Automatic Acquisition of Locks
Transactions can issue standard read/write instructions without explicit locking calls:
* **read(D)**: If $T_i$ has a lock on $D$, proceed. Else, wait until no other transaction has a lock-X on $D$, grant $T_i$ a lock-S on $D$, then read.
* **write(D)**: If $T_i$ has a lock-X on $D$, proceed. Else, wait until no other transaction has any lock on $D$. If $T_i$ has a lock-S on $D$, upgrade to lock-X, else grant $T_i$ a lock-X on $D$, then write.
* All locks are released after commit or abort.

### Implementation of Locking
* A lock manager can be implemented as a separate process. Transactions send lock/unlock requests as messages.
* The lock manager replies with lock grant messages (or roll-back messages in case of a deadlock).
* The lock manager maintains an in-memory data structure called a **lock table** to record granted locks and pending requests.
  * New requests are added to the end of the queue for the data item and granted if compatible.
  * Unlock requests delete the granted lock, and later requests are checked to see if they can now be granted.
  * If a transaction aborts, all waiting or granted requests of the transaction are deleted.

### Graph-Based Protocols

![Tree Protocol](../images/ch18_slides/slide_018.png)

An alternative to 2PL. Imposes a partial ordering (directed acyclic graph) on the set of all data items. If $d_i \rightarrow d_j$, any transaction accessing both must access $d_i$ before $d_j$.
* **Tree Protocol**:
  1. Only exclusive locks are allowed.
  2. The first lock by $T_i$ may be on any data item. Subsequently, a data $Q$ can be locked by $T_i$ only if the parent of $Q$ is currently locked by $T_i$.
  3. Data items may be unlocked at any time.
  4. A data item that has been locked and unlocked by $T_i$ cannot subsequently be relocked by $T_i$.
* **Advantages**: Ensures conflict serializability and freedom from deadlock. Unlocking may occur earlier than in 2PL (shorter waiting times, increased concurrency, no rollbacks required).
* **Drawbacks**: Does not guarantee recoverability or cascade freedom (needs commit dependencies). Transactions may have to lock data items they do not access (increased locking overhead, potential decrease in concurrency).

### Deadlock Handling

![Deadlock Detection](../images/ch18_slides/slide_024.png)

* **Deadlock Prevention**: Ensures the system never enters a deadlock state.
  * **Pre-declaration**: Require a transaction to lock all its data items before it begins.
  * **Graph-based protocol**: Impose partial ordering of data items.
  * **Wait-die scheme (non-preemptive)**: Older transaction may wait for younger one to release data item. Younger transactions never wait for older ones; they are rolled back instead.
  * **Wound-wait scheme (preemptive)**: Older transaction wounds (forces rollback of) younger transaction instead of waiting. Younger transactions may wait for older ones.
  * In both wait-die and wound-wait, rolled-back transactions restart with their original timestamp to avoid starvation.
  * **Timeout-Based Schemes**: A transaction waits for a lock only for a specified amount of time. If timeout occurs, transaction is rolled back. Simple to implement but may roll back unnecessarily in the absence of deadlock, and starvation is possible.
* **Deadlock Detection**:
  * Use a **Wait-for graph**: Vertices are transactions. An edge from $T_i \rightarrow T_j$ means $T_i$ is waiting for a lock held in conflicting mode by $T_j$.
  * Deadlock exists if and only if the wait-for graph has a cycle. Invoke a detection algorithm periodically.
* **Deadlock Recovery**:
  * Select a victim transaction to roll back that will incur minimum cost.
  * Rollback can be **total** (abort and restart) or **partial** (roll back only as far as necessary to release required locks).
  * To prevent starvation, ensure the oldest transaction in a deadlock set is never chosen as the victim.

## 2. Multiple Granularity

![Example of Granularity Hierarchy](../images/ch18_slides/slide_027.png)
![Compatibility Matrix with Intention Lock Modes](../images/ch18_slides/slide_029.png)


Allows data items to be of various sizes and defines a hierarchy of data granularities (e.g., `database` $\rightarrow$ `area` $\rightarrow$ `file` $\rightarrow$ `record`). Represented as a tree.
* When a transaction locks a node explicitly, it implicitly locks all its descendents in the same mode.
* **Fine granularity** (lower in tree): high concurrency, high locking overhead.
* **Coarse granularity** (higher in tree): low locking overhead, low concurrency.
* **Intention Lock Modes**:
  * **Intention-shared (IS)**: indicates explicit locking at a lower level with shared locks.
  * **Intention-exclusive (IX)**: indicates explicit locking at a lower level with exclusive or shared locks.
  * **Shared and intention-exclusive (SIX)**: subtree rooted by that node is locked explicitly in shared mode, and explicit locking is being done at a lower level with exclusive-mode locks.
* Intention locks allow a higher level node to be locked in S or X mode without checking all descendent nodes.

**Multiple Granularity Locking Scheme Rules for $T_i$ to lock node $Q$:**
1. Lock compatibility matrix must be observed.
2. Root of the tree must be locked first (in any mode).
3. Lock $Q$ in S or IS only if parent is locked in IX or IS.
4. Lock $Q$ in X, SIX, or IX only if parent is locked in IX or SIX.
5. Must be two-phase (no unlocks before all locks acquired).
6. Unlock $Q$ only if none of the children of $Q$ are currently locked by $T_i$.
* Locks are acquired root-to-leaf, and released leaf-to-root.
* **Lock granularity escalation**: if there are too many locks at a particular level, switch to a higher granularity S or X lock.

## 3. Insert/Delete Operations and Phantom Phenomenon

![Non-Serializable Execution Due to Phantom Phenomenon](../images/ch18_slides/slide_033.png)

* **Locking Rules**: An exclusive lock must be obtained on an item before it is deleted. A transaction that inserts a new tuple is automatically given an X-mode lock on it.
* **Phantom Phenomenon**: A conflict can occur between a transaction performing a predicate read/scan and another transaction that inserts/updates/deletes a tuple matching the predicate. E.g., $T_1$ reads the count of "Physics" instructors, $T_2$ inserts a new "Physics" instructor. Even with tuple locks, schedules can be non-serializable because the new tuple was not locked by the read.
* **Handling Phantoms**:
  * **Relation-level locking**: Associate a data item with the relation. Scan acquires a shared lock, insert/delete acquires an exclusive lock. (Results in very low concurrency).
  * **Index Locking**: Every relation must have $\geq 1$ index. Transactions access tuples through indices. A lookup locks all accessed index leaf nodes in S-mode (even if no tuple satisfies the condition). Insert/update/delete must update all indices and get X-locks on all affected index leaf nodes.
  * **Next-Key Locking**: Provides higher concurrency than locking the entire leaf node. Lock all values that satisfy the lookup, and also lock the next key value in the index.

## 4. Timestamp-Based Protocols

![Example of Schedule Under TSO](../images/ch18_slides/slide_042.png)
![Another Example Under TSO](../images/ch18_slides/slide_043.png)


Each transaction $T_i$ is issued a unique timestamp $TS(T_i)$ when it enters the system. Time-stamp order determines the serializability order.

* **Timestamp-Ordering Protocol (TSO)**: Maintains two timestamp values for each data item $Q$:
  * `W-timestamp(Q)`: largest timestamp of any transaction that successfully executed `write(Q)`.
  * `R-timestamp(Q)`: largest timestamp of any transaction that successfully executed `read(Q)`.
* **read(Q) rules**:
  * If $TS(T_i) < W\text{-timestamp}(Q)$, read is rejected, $T_i$ rolled back (needs an overwritten value).
  * If $TS(T_i) \geq W\text{-timestamp}(Q)$, read is executed, $R\text{-timestamp}(Q)$ is set to $\max(R\text{-timestamp}(Q), TS(T_i))$.
* **write(Q) rules**:
  * If $TS(T_i) < R\text{-timestamp}(Q)$, write is rejected, $T_i$ rolled back (value was needed previously).
  * If $TS(T_i) < W\text{-timestamp}(Q)$, write is rejected, $T_i$ rolled back (attempting to write obsolete value).
  * Otherwise, write executed, $W\text{-timestamp}(Q) = TS(T_i)$.
* **Correctness**: Guarantees serializability and freedom from deadlock (no transaction ever waits). However, schedules may not be cascade-free or recoverable.
* **Recoverability**: Achieved by structuring writes at the end of a transaction (atomic action), using a limited form of locking (wait for data to be committed), or using commit dependencies.
* **Thomas’ Write Rule**: A modified version of TSO. If $TS(T_i) < W\text{-timestamp}(Q)$, $T_i$ is attempting to write an obsolete value. Instead of rolling back $T_i$, the `write` operation is simply **ignored**. Allows some view-serializable schedules that are not conflict-serializable, providing greater potential concurrency.

## 5. Validation-Based Protocols (Optimistic Concurrency Control)

![Schedule Produced by Validation](../images/ch18_slides/slide_051.png)


Postpone writes to the end of the transaction. Keep track of data items read/written. Validation is performed at commit time to detect any out-of-serialization order reads/writes.
* **Phases of execution**:
  1. **Read and execution phase**: $T_i$ writes only to temporary local variables.
  2. **Validation phase**: $T_i$ performs validation test to check for serializability violations.
  3. **Write phase**: If validated, updates are applied to database; otherwise, $T_i$ is rolled back.
* **Timestamps**: `StartTS(Ti)`, `ValidationTS(Ti)` (which becomes the effective `TS(Ti)`), `FinishTS(Ti)`.
* **Validation Test for $T_j$**: For all $T_i$ with $TS(T_i) < TS(T_j)$, one of the following must hold:
  1. `finishTS(Ti) < startTS(Tj)` (no concurrent overlap)
  2. `startTS(Tj) < finishTS(Ti) < validationTS(Tj)` AND the set of data items written by $T_i$ does not intersect with the set of data items read by $T_j$.

## 6. Multiversion Schemes

![Snapshot Write: First Committer Wins](../images/ch18_slides/slide_063.png)


Keep old versions of data items to increase concurrency. Reads never have to wait.
* **Multiversion Timestamp Ordering**: Each version $Q_k$ has Content, W-timestamp, R-timestamp. Read returns version with largest W-timestamp $\leq TS(T_i)$. Write creates a new version unless it violates constraints (e.g., $TS(T_i) < R\text{-timestamp}$ of the version it would overwrite, in which case it rolls back).
* **Multiversion Two-Phase Locking**: Differentiates read-only and update transactions. Update transactions follow rigorous 2PL and create new versions with timestamps assigned at commit time. Read-only transactions are assigned a timestamp at start and read the appropriate version without obtaining any locks.
* **Snapshot Isolation (SI)**: Gives a logical "snapshot" of the database state to a transaction.

![Snapshot Read](../images/ch18_slides/slide_062.png)

  * Reads/writes performed in own snapshot. Concurrent updates not visible.
  * **First-committer-wins rule**: Commits only if no other concurrent transaction has already written data that it intends to write. (Variant: First-updater-wins).
  * **Benefits**: Reads never block, avoids dirty read, lost update, non-repeatable read.
  * **Anomalies**: Does not always give serializable executions. Can lead to **write skew** (where transactions modify different items based on previous states of items the other modified) and phantom phenomena.
  * **Serializable Snapshot Isolation (SSI)**: Extension of SI that tracks read-write conflicts to ensure serializability. Implemented in PostgreSQL (since 9.1).
  * **Workaround for SI Anomalies**: Use `SELECT ... FOR UPDATE` to lock data read by query.

## 7. Weak Levels of Concurrency

* **Degree-two consistency**: S-locks may be released/acquired at any time; X-locks held till end of transaction. Serializability not guaranteed.
* **Cursor stability**: For reads, tuple is locked, read, lock released immediately. X-locks held till end.
* **SQL Isolation Levels**:
  * **Serializable**: Default standard.
  * **Repeatable read**: Allows only committed records to be read, repeating a read returns the same value (read locks retained). Phantoms can still occur.
  * **Read committed**: Same as degree two consistency (often implemented as cursor-stability). The default in most DB systems.
  * **Read uncommitted**: Allows reading uncommitted data.
* **Concurrency across user interactions**: Often uses application-level concurrency control with version numbers (equivalent to optimistic concurrency control without validating the read set) to avoid long-duration locks across user interactions.

## 8. Advanced Topics in Concurrency Control

* **Online Index Creation**: Build index on a snapshot, track subsequent updates, apply updates in a catch-up phase, and lock the relation briefly at the end to finish catch-up.
* **Concurrency in Index Structures**:
  * Standard 2PL on index nodes leads to low concurrency. Exact values in internal B+-tree nodes are irrelevant as long as we reach the correct leaf.
  * **Crabbing Protocol**: Lock root in S-mode. Lock children, then release parent lock. Upgrade leaf to X-mode for update. If split/coalesce needed, lock parent in X-mode. Can cause excessive deadlocks.
  * **B-link tree locking**: Improves concurrency by releasing parent lock before acquiring child lock and dealing with changes that occurred between.
* **Main-Memory Databases**: Simplified index locking (short term lock on entire index). **Latch-free techniques** (using Compare-And-Swap / CAS) for data-structure updates can speed up operations further, though care is needed to avoid the ABA problem.
* **Concurrency Control with Operations**: Certain operations (e.g., increments) commute. We can introduce operation-specific locks (e.g., increment-mode lock) that don't conflict with each other, allowing reordering of operations and higher concurrency.
* **Real-Time Transaction Systems**: Transactions have deadlines (hard, firm, soft). Locking causes blocking, so optimistic concurrency control often performs well in real-time settings.
* **View Serializability**: A weaker form of serializability than conflict serializability. Two schedules are view equivalent if they have the same initial reads, same read-write dependencies, and same final writes. Checking view serializability is NP-complete. Schedules that are view serializable but not conflict serializable must contain "blind writes".
