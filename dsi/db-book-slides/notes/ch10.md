# Chapter 10: Big Data

## Motivation
- **Data Explosion:** Very large volumes of data are being collected, driven by the growth of the web, social media, and the Internet of Things (IoT).
- **Web Logs:** An early source of massive data. Analytics on web logs provide immense value for advertisements, website structuring, and personalized recommendations.
- **Big Data Characteristics (The 3 Vs):** Big Data is differentiated from the data handled by earlier generation databases by:
  - **Volume:** Much larger amounts of data stored.
  - **Velocity:** Much higher rates of data insertion.
  - **Variety:** Many types of data, moving beyond traditional relational data.

## Querying Big Data
- **Transaction Processing Systems:** Many applications that need extremely high scalability are willing to sacrifice ACID properties and other traditional database features to achieve it.
- **Query Processing Systems:** Must provide high scalability while also supporting non-relational data formats.

## Big Data Storage Systems
Several system architectures have emerged to store Big Data:
1. Distributed file systems
2. Sharding across multiple databases
3. Key-value storage systems
4. Parallel and distributed databases

### Distributed File Systems
- **Overview:** Stores data across a large collection of machines while providing a single file-system view.
- **Scale:** Highly scalable for data-intensive applications (e.g., clusters with 10K nodes, 100 million files, 10 PB of data).
- **Reliability:** Provides redundant storage on cheap, unreliable computers by replicating files to handle hardware failures. The system automatically detects and recovers from failures.
- **Examples:** Google File System (GFS), Hadoop Distributed File System (HDFS).

#### Hadoop Distributed File System (HDFS) Architecture
- **Namespace:** Uses a single namespace for the entire cluster.
- **Blocks:** Files are broken up into large blocks (typically 64 MB). Each block is replicated on multiple DataNodes.
- **NameNode:** 
  - Maps a filename to a list of Block IDs.
  - Maps each Block ID to the DataNodes containing a replica of the block.
- **DataNode:** Maps a Block ID to a physical location on disk.
- **Client Access:** The client finds the location of blocks from the NameNode, then accesses the data directly from the DataNode.
- **Data Coherency:** Follows a write-once-read-many access model. Clients can only append to existing files.
- **Trade-offs:** Excellent for millions of large files, but incurs very high overhead and poor performance when handling billions of smaller tuples.

### Sharding
- **Definition:** Partitioning data across multiple databases.
- **Mechanism:** Partitioning is usually done using specific attributes known as partitioning keys or shard keys (e.g., user ID). 
  - *Example:* Records with keys 1–100,000 on Database 1, 100,001–200,000 on Database 2, etc.
- **Positives:** Scales well and is relatively easy to implement.
- **Drawbacks:**
  - **Not Transparent:** The application must track which records are on which database and handle the routing of queries and cross-database operations.
  - **Load Balancing:** Moving part of the load from an overloaded database is difficult.
  - **Failures:** A larger number of databases increases the chance of failure, meaning the application often has to manage replicas to ensure availability.

### Key-Value Storage Systems
- **Overview:** Store massive numbers (billions or more) of small (KB–MB) records.
- **Mechanism:** Records are partitioned and replicated across multiple machines. The system automatically routes queries to the appropriate machine and ensures updates are applied to all replicas for consistency.

#### Types of Key-Value Stores
- **Uninterpreted Bytes:** Store raw bytes with an associated key (e.g., Amazon S3, Amazon Dynamo).
- **Wide-Table:** Can have arbitrarily many attribute names with an associated key, allowing some operations (like filtering) to execute on the storage node (e.g., Google BigTable, Apache Cassandra, HBase, DynamoDB).
- **Document Stores:** Store semi-structured data, typically JSON (e.g., MongoDB, CouchDB).
- **Versioning:** Some stores support multiple versions of data using timestamps or version numbers.

#### Supported Operations
- `put(key, value)`: Stores a value with an associated key.
- `get(key)`: Retrieves the value associated with the specified key.
- `delete(key)`: Removes the key and its value.
- *Advanced:* Some systems support range queries on keys, and document stores support querying non-key attributes.
- *Limitations (NoSQL):* Key-value stores are not full databases. They have limited or no support for transactional updates, requiring applications to manage query processing. Stripping these features makes it easier to build highly scalable storage.

### Parallel and Distributed Databases
- **History:** Developed in the 1980s, long before the Big Data era.
- **Scale:** Originally designed for smaller clusters (tens to hundreds of machines), lacking easy scalability.
- **Failure Handling:** Use replication to ensure data availability. However, if a machine fails, they typically restart the entire query. Frequent restarts at a very large scale make this impractical, whereas modern MapReduce systems can work around failures mid-query.

## Replication and Consistency
- **Availability:** Essential for distributed systems. If parts of the system fail, it must continue to run. Achieved via replication (if one node fails, another copy is available).
- **Consistency:** All live replicas must have the same value, and every read must return the latest version. Often implemented using majority protocols (e.g., out of 3 replicas, reads/writes must access 2).
- **Network Partitions:** Occur when a network breaks into multiple isolated parts, with active systems unable to communicate.
- **Brewer’s CAP Theorem:** In the presence of network partitions, a system cannot guarantee both availability and consistency simultaneously.
  - Traditional databases typically choose **consistency**.
  - Most web applications choose **availability** (except for critical functions like order processing).

## The MapReduce Paradigm
- **Overview:** A platform for reliable, scalable parallel computing that abstracts the complexities of distributed environments from the programmer.
- **Operation:** The programmer provides the core logic via `map()` and `reduce()` functions. The system handles parallelization, coordination, and failure recovery.
- **Scale:** Runs on clusters of 1,000s to 10,000s of machines (e.g., Google MapReduce, Hadoop).
- **Data Access:** Storage is typically handled by distributed file systems or key-value stores.

### Programming Model
Inspired by functional programming languages (like Lisp):
- **Input:** A set of key/value pairs.
- **User Functions:**
  - `map(k, v) -> list(k1, v1)`
  - `reduce(k1, list(v1)) -> v2`
- **Output:** A set of `(k1, v2)` pairs.
- *Example (Hadoop):* The system breaks files into lines and calls the `map` function with the line's content as the value and the line number as the key.

### Example 1: Word Count
![Pseudo-code of Word Count](../images/ch10_slides/slide_018.png)
- **Goal:** Count occurrences of each word in a large document collection.
- **Map:** Parses the document to find words, emitting `(word, 1)`.
- **Shuffle:** Partitions the `(word, count)` pairs across workers based on the word.
- **Reduce:** Locally adds up the counts for each word and outputs `(word, total_count)`.

```java
// Pseudo-code
map(String record):
    for each word in record
        emit(word, 1);

reduce(String key, List value_list):
    String word = key
    int count = 0;
    for each value in value_list:
        count = count + value
    Output(word, count);
```

### Example 2: Log Processing
- **Goal:** Count file accesses in a specific directory within a date range from a massive log file.
- **Map:** Tokenizes the log record, checks if the date is within the range and the path matches the directory, and emits `(filename, 1)`.
- **Reduce:** Sums up the counts for each filename.

### Hadoop MapReduce
- **Hadoop:** A widely used open-source Java implementation of MapReduce.
- **I/O:** Parallel input/output is managed using HDFS. It supports various input formats (Text/CSV, Avro, ORC, Parquet) and key-value stores.
- **Types:** Uses generic interfaces with typed arguments (e.g., `LongWritable`, `Text`, `IntWritable`).
- **Job Setup:** Requires configuring the Mapper and Reducer classes, output key/value types, input format, and input/output paths.

## MapReduce vs. Databases
- **MapReduce:** Widely used for complex parallel processing (e.g., PageRank, index building, log analysis). It allows procedural code and unstructured data. However, it is cumbersome for writing simple queries.
- **Databases (SQL):** Many computations are easier to express in SQL. 
- **Convergence:** SQL queries can now be translated into MapReduce infrastructure for execution (e.g., Apache Hive, Pig Latin, Microsoft SCOPE). Current execution engines support relational operations (joins, aggregations) natively.

## Beyond MapReduce: Algebraic Operations
![Word Count in Spark](../images/ch10_slides/slide_035.png)
- **Current Execution Engines:** Natively support algebraic operators and allow users to create custom operators forming execution trees (DAGs). Examples include Apache Tez and Apache Spark.
- **Apache Spark:**
  - **RDD (Resilient Distributed Dataset):** An abstraction for a collection of records stored across multiple machines.
  - **Lazy Evaluation:** Operations on RDDs are executed lazily. An operator tree is built and optimized, and execution only occurs when an action (like `saveAsTextFile()` or `collect()`) is called.
  - **API:** Spark heavily utilizes Java 8 Lambda expressions for concise function definitions.
  - **DataFrames and DataSets:** Allows dynamic type specification. The `Row` type can infer attributes from files (like Parquet). Operations such as `filter`, `join`, `groupBy`, and `agg` execute in parallel.

## Streaming Data
- **Definition:** Data that arrives in a continuous fashion (data-in-motion), in contrast to data-at-rest. Applications include stock trades, e-commerce clicks, IoT sensors, network monitoring, and social media feeds.
- **Querying Streams:** Useful for monitoring, alerts, and automated actions.
  - **Windowing:** Breaks the stream into finite windows (time-based or tuple-based).
    - *Tumbling window:* Fixed, non-overlapping (e.g., hourly).
    - *Hopping window:* Overlapping (e.g., hourly window computed every 20 mins).
    - *Sliding window:* Based around each incoming tuple.
    - *Session window:* Groups tuples by user sessions.
  - **Continuous Queries:** Output partial results based on the stream seen so far.
  - **Algebraic Operators:** Consume tuples, maintain state, and output tuples.
  - **Pattern Matching (CEP):** Complex Event Processing systems detect specific patterns and trigger actions.
- **Architectures:**
  - Many streaming systems run purely in-memory.
  - **Lambda Architecture:** Splits the incoming stream—one path goes to the streaming system for real-time processing, the other to a database for permanent storage.
- **Publish-Subscribe Systems:**
  - A convenient abstraction where tuples are published to a "topic" and consumers subscribe to it.
  - Parallel pub-sub systems (like **Apache Kafka**) partition topic data across multiple machines.

## Graph Databases
- **Graph Data Model:** A general model where entities are nodes and relationships are edges.
- **Representation:** Can be modeled as relations (`node(ID, label, data)`, `edge(fromID, toID, label, data)`), but graph databases (e.g., Neo4J) provide dedicated graph views and specialized query languages (e.g., Cypher) for efficient edge traversal.

*Neo4J Query Example:*
```cypher
match (i:instructor)<-[:advisor]-(s:student)
where i.dept_name = 'Comp. Sci.'
return i.ID as ID, i.name as name, collect(s.name) as advisees
```

- **Parallel Graph Processing:**
  - Needed for massive graphs (billions of nodes, trillions of edges) like web graphs or social networks.
  - **Bulk Synchronous Processing (BSP):** A framework with much lower per-iteration overhead than MapReduce, making it ideal for the multiple iterations required in graph computations.
  - **BSP Operation:** Vertices are partitioned across machines. In each "superstep", nodes process received messages, update their state, and send new messages to neighbors. Computation ends when all nodes vote to halt.
  - **Examples:** Google's Pregel, Apache Giraph, Spark GraphX.
