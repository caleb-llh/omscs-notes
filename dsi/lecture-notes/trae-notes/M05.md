# Module 05: Buffer Manager and Cache Replacement Policies

## 1. The Buffer Manager

The **Buffer Manager** serves as a critical bridge between fast, expensive, volatile memory (DRAM) and slow, cheap, persistent storage (SSD/Disk).

* **DRAM:** ~50 ns latency, ~$10 per GB.
* **SSD:** ~50,000 ns latency (1000x slower), ~$0.1 per GB.

To optimize database performance, the Buffer Manager caches frequently accessed disk pages in DRAM. Architecturally, it sits between the database execution engine (e.g., BuzzDB) and the Storage Manager (which strictly handles low-level file I/O).

### Basic Architecture

> **Intuition:** Why build a custom Buffer Manager instead of letting the OS handle it with its own file cache? Databases know their specific access patterns (like sequential scans vs. random index lookups) much better than the OS does. The OS might blindly cache everything, but the database can make intelligent decisions about what to keep and what to evict.

```cpp
class BufferManager {
private:
    StorageManager storage_manager;
    
    // LRU list maintains the temporal order of page usage
    std::list<std::pair<PageID, std::unique_ptr<SlottedPage>>> lruList;
    
    // Hash map for O(1) lookup of a page's location in the list
    std::unordered_map<PageID, typename std::list<std::pair<PageID, std::unique_ptr<SlottedPage>>>::iterator> pageMap;

public:
    // Fetches a page by ID, applying the underlying caching policy
    std::unique_ptr<SlottedPage> &getPage(int page_id);
};
```

* **`lruList`**: Stores the currently loaded pages in a specific order (e.g., Most Recently Used to Least Recently Used).
* **`pageMap`**: A hash map connecting a `PageID` to its exact iterator in the `lruList`, enabling constant-time access without scanning the list.

### Core Operations

* **`getPage(PageID)`**: 
  Checks if the page exists in memory via `pageMap`. If it is a cache miss, it uses `StorageManager` to fetch it from disk. Finally, it calls `touch()` to update the page's recency status.
* **`touch(iterator)`**: 
  Updates a page's position to reflect recent access. In an LRU implementation, `std::list::splice` is used to efficiently detach the node and reattach it at the front of the list without reallocating memory.
* **`evict()`**: 
  When the buffer reaches maximum capacity, it removes a chosen page (typically from the back of the list). Crucially, it calls `storage_manager.flush()` to ensure any in-memory modifications are written safely to disk before the page object is destroyed.

**Modularity Benefit:** The main execution engine interacts *exclusively* with the Buffer Manager for all page requests, completely abstracting away disk I/O and caching mechanics.

## 2. Cache Replacement Policies

Because DRAM capacity is limited, the Buffer Manager must decide which existing page to evict to make room for a new page.

### Policy vs. Mechanism
> **Tradeoff:** Separating policy from mechanism adds a slight overhead due to virtual function calls and abstraction layers, but it drastically improves the maintainability and testability of the database system.

* **Policy (What):** The logical rule determining *which* page to evict (e.g., LRU, FIFO).
* **Mechanism (How):** The physical implementation of the eviction (e.g., flushing to disk, updating maps, freeing memory).

### The Policy Interface
By defining a generic `Policy` interface, a database system can seamlessly swap out different eviction strategies.

```cpp
class Policy {
public:
    virtual void touch(PageID page_id) = 0;
    virtual PageID evict() = 0;
    virtual ~Policy() = default;
};
```

* **FIFO (First-In-First-Out):** Evicts the oldest loaded page based strictly on arrival time.
  * *Drawback:* Blind to access frequency. May evict "hot" (frequently accessed) pages simply because they were loaded early on.
* **LRU (Least Recently Used):** Evicts pages that have gone unaccessed for the longest period. Generally performs well for typical database workloads.

## 3. Buffer Pool Flooding

**Sequential Scans** occur when a query requires reading every page in a table (e.g., filtering on an unindexed column).

**Buffer Pool Flooding** is a performance-degrading phenomenon where a massive sequential scan loads thousands of "read-once" pages into the buffer pool, displacing valuable cached data.
> **Common Confusion:** It's easy to assume that because a page is being read *right now*, it must be important. In a sequential scan, the opposite is true: once read, that page is likely never needed again in the near future. Standard LRU fails here because it treats the most recent read as the most valuable.

* **Under FIFO:** The massive influx of new pages pushes out older, frequently accessed hot pages.
* **Under LRU:** The read-once pages are marked as "most recently used", causing the exact same issue: hot pages are pushed down and evicted to store cold data that will never be accessed again.

---

## 4. The TwoQ (2Q) Policy

The **TwoQ (2 Queue)** policy elegantly solves Buffer Pool Flooding by segregating pages into two distinct queues:
1. **FIFO Queue:** A holding area for new, potentially read-once pages (e.g., from sequential scans).
2. **LRU Queue:** A persistent area for frequently accessed hot pages.

### TwoQ Logic: `touch(PageID)`
> **Intuition:** The TwoQ policy acts like a nightclub bouncer. The FIFO queue is the "waiting line" outside. Only if a page is requested a *second* time (proving it's actually popular) does the bouncer let it into the VIP area (the LRU queue).

When a page is requested:
1. **Cache Miss (Not in memory):** Trigger eviction if full. Load the new page and insert it into the **FIFO** queue.
2. **Cache Hit in FIFO Queue:** If accessed a *second* time, the page has proven it is not a read-once scan page. It is removed from FIFO and promoted to the front of the **LRU** queue.
3. **Cache Hit in LRU Queue:** The page is simply moved to the front of the LRU queue, reinforcing its "most recently used" status.

### TwoQ Logic: `evict()`
When memory is full and eviction is required:
1. **Prioritize FIFO Eviction:** The policy aggressively attempts to evict from the front of the FIFO queue first. This flushes out read-once sequential scan pages, protecting the hot pages.
2. **Fallback to LRU Eviction:** If the FIFO queue is entirely empty, it falls back to evicting the least recently used page from the back of the LRU queue.

### Other Advanced Policies
* **LFU (Least Frequently Used):** Retains pages with the highest access counts. 
  * *Drawback:* Fails to adapt to shifting access patterns. A page that was extremely hot yesterday but unused today will remain stuck in memory.
* **ARC (Adaptive Replacement Cache):** Dynamically and continuously balances between recency (LRU) and frequency (LFU) for optimal performance. 
  * *Drawback:* Patented (historically) and carries a highly complex implementation overhead.
