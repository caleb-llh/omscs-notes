# Module 03: Storage Management

> **Overview:** This module delves into how databases manage the flow of data between memory and disk, handling memory safety with modern C++, and the serialization processes required to persist data structures durably.

---

## 1. Storage Technologies and the Data Lifecycle

A primary responsibility of a Database Management System (DBMS) is to orchestrate data across the storage hierarchy, balancing blazing-fast execution speeds with ironclad durability.

### Volatile vs. Persistent Storage Architecture

| Feature | Volatile Storage (DRAM) | Persistent Storage (Disk/SSD) |
| :--- | :--- | :--- |
| **Speed** | Nanoseconds (Extremely Fast) | Milliseconds to Microseconds (Slow) |
| **Role in DB** | Caching "Hot Data" (Buffer Pool) | Long-term durable storage |
| **Volatility** | Loses all data on power loss/crash | Retains data permanently |
| **Cost / Capacity** | Expensive / Limited Capacity | Cheap / Massive Capacity |

### The Data Lifecycle and Paging
Databases do not read and write single bytes to disk; they operate on blocks called **Pages**.
1. **Stage One (DRAM Caching):** When data is requested, the DBMS fetches the relevant page from Disk into DRAM. This "hot data" can now be queried or mutated rapidly.
2. **Stage Two (Disk Persistence):** When data is modified in DRAM (a "dirty page"), the DBMS must eventually flush (write) these changes back to Disk to guarantee durability before a transaction is fully committed.

## 2. File I/O and Performance Profiling in C++

### Safe File I/O Operations
Writing database files or logs requires robust I/O handling:
- **`std::ifstream` & `std::ofstream`:** Standard C++ streams used for reading and writing file data.
- **Error Handling:** A DBMS must rigorously verify file availability and permissions. Unhandled I/O failures lead to data corruption. Developers should utilize `std::cerr` for error logging to isolate issues without crashing the main application.

### Query Performance Profiling
Benchmarking query execution time is essential for optimizing indexing and storage layouts.
- **C++ `<chrono>` Library:** Use `std::chrono::high_resolution_clock` to precisely measure the microsecond-level elapsed time of database operations, enabling accurate comparative profiling.

## 3. Generalizing Data Structures: Tuples and Fields

To be useful, BuzzDB must support diverse data types (e.g., Integers, Floats, Strings), requiring flexible `Tuple` and `Field` classes.

### The Flexible `Field` Class
A single `Field` instance must adapt to hold an `INT`, `FLOAT`, or `STRING`.

> **Intuition:** Think of the `Field` class as a protective wrapper or "box" around raw bytes. The `FieldType` enum is the label on the box telling the database how to safely interpret the bytes inside (e.g., as a number vs. text).

- **Type Tracking (Enums):** Use an enumeration (`enum FieldType { INT, FLOAT, STRING }`) to explicitly track what data the field currently holds.
- **Memory Optimization (Unions):** A `union` allows different data types to share the exact same memory location.
  ```cpp
  union Data {
      int i;
      float f;
      char* s;
  };
  ```
  The compiler allocates memory equal to the largest member, drastically reducing the memory footprint compared to a `struct`.
- **Constructor Overloading:** Define multiple constructors (`Field(int)`, `Field(float)`, `Field(std::string)`) for seamless initialization.

### Dynamic String Memory and Destructors
Strings have variable lengths, requiring dynamic memory allocation on the **Heap**:
```cpp
// Allocating exactly enough space for the string + null terminator
data.s = new char[str.length() + 1]; 
```
If raw pointers (`new`) are used, the class must implement a **Destructor** (`~Field()`) containing `delete[] data.s;` to free the memory and prevent leaks when the `Field` object is destroyed.

## 4. Modern C++: Smart Pointers and Memory Safety

### The Perils of Raw Pointers
Manual memory management in C/C++ is a notorious source of fatal bugs:
1. **Memory Leaks:** Forgetting to call `delete`, causing memory exhaustion over time.
2. **Dangling Pointers:** Dereferencing a pointer after its memory has been freed (Undefined Behavior).
3. **Double-Free Errors:** Attempting to `delete` the same memory address twice, causing immediate application crashes.
4. **Ownership Ambiguity:** Confusion over which object or function is responsible for cleaning up the memory.

### The Solution: `std::unique_ptr`
Modern C++ (C++11+) resolves these issues using Smart Pointers, specifically `std::unique_ptr`:
- **Deterministic Destruction (RAII):** Memory is automatically freed the moment the `unique_ptr` falls out of scope.
- **Prevents Dangling & Double-Frees:** Enforces strict, single ownership. Calling `.reset()` safely deletes the payload and sets the pointer to `nullptr`.
- **Explicit Transfers:** Ownership cannot be copied; it must be explicitly moved using `std::move()`, clarifying system architecture.

*Refactoring tip:* By changing the raw `char* s` to a `std::unique_ptr<char[]> s`, the `Field` class destructor is entirely relieved of manual `delete[]` responsibilities.

## 5. Copy Semantics: Heap vs. Stack Allocation

Understanding memory regions is critical for database performance.

| Feature | Stack Allocation | Heap Allocation |
| :--- | :--- | :--- |
| **Speed** | Extremely Fast (pointer increment) | Slower (OS-level allocation) |
| **Lifetime** | Scope-bound (auto-destroyed) | Programmer-managed (or Smart Pointers) |
| **Size Constraints** | Very Limited (megabytes) | Massive (gigabytes) |
| **Use Case** | Local variables, primitives | Large arrays, strings, database pages |

### Deep Copies and Move Semantics
When an object containing heap-allocated data (like a String `Field`) is copied:

> **Common Confusion:** A "shallow copy" just duplicates the pointer, meaning two objects now point to the exact same memory address on the heap. When both objects are destroyed, they both try to `delete` that same address, causing a fatal "double-free" crash. A "deep copy" safely duplicates the underlying data itself.

- **Deep Copy Requirement:** You must implement a **Copy Constructor** and **Copy Assignment Operator** to allocate *new* heap memory and copy the actual string bytes. A "shallow copy" (copying just the pointer) leads to double-free errors.
- **Move Semantics:** Because `std::unique_ptr` explicitly forbids copying, objects holding them must implement **Move Constructors** to transfer ownership via `std::move()`, providing massive performance gains by avoiding unnecessary deep copies.

## 6. Disk Serialization and Deserialization

To satisfy the **Durability** property of ACID, in-memory data must be converted into a binary format suitable for disk storage.

### The `Page` Class
A **Page** is the fundamental unit of I/O between DRAM and Disk.
- It encapsulates a vector of `Tuple` objects and tracks its `used_size` (in bytes).
- Methods like `addTuple()` enforce capacity limits, rejecting inserts if they exceed the `PAGE_SIZE` (e.g., 4KB or 8KB).

### Serialization (Memory $\rightarrow$ Disk)
Serialization translates complex, pointer-rich in-memory structures into a flat, contiguous binary byte-stream.
- **Decoupled Architecture:** Best practice delegates serialization logic to the respective classes: `Field::serialize()`, `Tuple::serialize()`, and `Page::write()`.
- **Binary Format Layout:** A page writes its header (number of tuples), followed by each tuple's header (field count), followed by each field's metadata (type, length) and raw byte data.

### Deserialization (Disk $\rightarrow$ Memory)
Deserialization reverses the process, reading binary data to perfectly reconstruct the C++ objects in DRAM.
- Reads metadata (field type, string length) *first* to dynamically allocate the exact necessary heap memory before reading the payload.
- **Static vs. Instance Methods:** 
  - **Static Method:** `Page::deserialize("data.db")` acts as a factory, reading the file and returning a newly instantiated `Page` object without requiring an existing instance.
  - **Instance Method:** `pageInstance.write("data.db")` operates on an existing object's state.

### Ensuring Data Consistency
When a tuple is deleted from a Page in memory (removed from the `std::vector`), the database state becomes inconsistent with the disk.
- **The Synchronization Imperative:** If the database crashes before the page is re-serialized, the deleted tuple will "reappear" upon reboot (a violation of Durability). Any structural modification to a page (Insert, Update, Delete) must eventually be followed by a `write(filename)` flush to maintain strict DRAM-Disk consistency.
