# Module 08: Thread-Safe Hash Index

## 1. Parallel Index Construction
With modern multi-core CPUs, parallelizing index construction offers a significant performance boost by distributing the scanning and insertion workload across multiple threads.

> **Intuition:** Imagine you have a massive stack of books to index. Instead of doing it alone, you hire 4 friends, split the stack into 5 equal piles, and everyone works simultaneously.

### Page Assignment Strategy
To parallelize efficiently, we divide the total number of database pages (`num_pages`) by the number of available threads (`num_threads`). Each thread is assigned a specific, non-overlapping range of pages to process.

```cpp
void parallelProcessPages(size_t num_threads = 5) {
    auto num_pages = buffer_manager.getNumPages();
    size_t pages_per_thread = num_pages / num_threads;
    std::vector<std::thread> threads;
    
    for (size_t i = 0; i < num_threads; i++) {
        size_t start_page = i * pages_per_thread;
        // Ensure the last thread picks up any remaining pages (due to integer division)
        size_t end_page = (i == num_threads - 1) ? num_pages : (start_page + pages_per_thread);
        
        // Emplace back constructs the thread and starts execution
        threads.emplace_back(&BuzzDB::processPageRange, this, start_page, end_page);
    }
    
    // Wait for all threads to complete their work
    for (auto& t : threads) {
        if (t.joinable()) t.join();
    }
}
```

## 2. Thread Safety and Race Conditions
While parallel construction improves speed, it introduces a critical challenge: concurrent operations on the shared index (the Hash Table) by multiple threads can lead to an inconsistent or corrupted state.

### The Race Condition (Lost Update Problem)
When two or more threads attempt to write to the exact same slot in a hash table simultaneously, their operations can interleave in unpredictable ways.

> **Mental Model:** A race condition is like two people trying to write their names on the exact same line of a sign-up sheet at the same time—they end up scribbling over each other and one (or both) names are lost.
- **Example Scenario:**
  1. **Thread 1** hashes `key 15` and probes slot 5.
  2. **Thread 2** hashes `key 25` and also probes slot 5.
  3. **Both threads** check and see that slot 5 is empty.
  4. **Thread 1** stores `key 15` in slot 5.
  5. **Thread 2** stores `key 25` in slot 5, incorrectly overwriting Thread 1's data. `key 15` is now lost.

## 3. Concurrency Control with Locks
To prevent race conditions, we must synchronize thread access using locks. There are several granularities of locking, each with different trade-offs between safety, performance, and memory overhead.

### A. Global Mutex (`std::mutex`)
A single, global `std::mutex` "serializes" access to the entire shared index structure. Only one thread can operate on the hash table at any given time.
- **`std::lock_guard`**: An RAII wrapper that automatically acquires the lock on creation and releases it when it goes out of scope (e.g., when the function returns or throws).

```cpp
class HashIndex {
private:
    mutable std::mutex indexMutex; // Protects the entire hash table
    
public:
    void insertOrUpdate(int key, int value) {
        std::lock_guard<std::mutex> guard(indexMutex);
        // Perform thread-safe update on the index
        // No other thread can read or write ANY slot right now
    }
};
```
- **Limitation (Severe Bottleneck):** Using a single lock destroys the benefits of parallelism. Threads must wait in line even if they want to operate on completely different, non-overlapping slots.

> **Tradeoff:** A global mutex is extremely easy to implement and perfectly safe, but completely destroys performance. It's like putting a single padlock on the entire library because someone is reading one book.

### B. Fine-Grained Locking (Mutex per Slot)
To restore parallelism, we apply fine-grained locking: using a separate lock for *each individual slot* rather than one for the entire table.

- **Implementation Details:**
  Because `std::mutex` is non-copyable and non-movable, we cannot store it directly in a standard `std::vector`. Instead, we use `std::unique_ptr<std::mutex>`, which is movable.

```cpp
// A vector of pointers to mutexes, one for each slot in the hash table
std::vector<std::unique_ptr<std::mutex>> mutexes;

void insertOrUpdate(int key, int value) {
    size_t index = hashFunction(key); 
    bool inserted = false;
    
    do {
        // Lock ONLY the mutex for this specific slot
        std::lock_guard<std::mutex> lock(*mutexes[index]);
        
        if (slot_is_empty_or_matches_key) { 
            // perform insert/update
            inserted = true;
        } else {
            // Collision! Must probe the next slot.
            // The lock for the current slot is automatically released here.
            index = getNextProbeIndex(index);
        }
    } while (!inserted);
}
```

- **Benefits:**
  - **High Parallelism:** Threads can modify different slots simultaneously without blocking each other.
  - **Reduced Contention:** Threads only clash if they map to the exact same slot.
- **Limitations:**
  - **Memory Overhead:** Storing a mutex for every single slot consumes significant memory.
  - **Acquisition Overhead:** Continuously locking and unlocking as a thread probes through a dense table can become computationally expensive.

> **Tradeoff:** Fine-grained locking maximizes throughput by only locking the specific slot being modified, but the memory overhead of having a lock per slot can be massive for large tables.

### C. Shared Mutex (Read-Write Locks)
Even with fine-grained locking, standard mutexes block multiple threads from *reading* the same slot concurrently. A **Shared Mutex** (`std::shared_mutex`) solves this by allowing multiple concurrent readers, while ensuring exclusive access for writers.

- **Exclusive Write Lock (`std::unique_lock<std::shared_mutex>`)**
  - Used for `insert` or `update`. 
  - Blocks all other readers and writers from accessing the slot.
- **Shared Read Lock (`std::shared_lock<std::shared_mutex>`)**
  - Used for lookups (`getValue`). 
  - Allows multiple readers to access the slot concurrently, provided no thread is currently writing.

> **Intuition:** A shared mutex is like a museum exhibit. Any number of people can look at it (read lock), but if someone needs to clean or repair it (write lock), they must close the exhibit, wait for everyone to leave, and block anyone else from entering until they are done.

```cpp
mutable std::vector<std::unique_ptr<std::shared_mutex>> mutexes;

void insertOrUpdate(int key, int value) {
    size_t index = hashFunction(key);
    // Acquire EXCLUSIVE lock for writing
    std::unique_lock<std::shared_mutex> lock(*mutexes[index]);
    // Insert or update data...
}

int getValue(int key) const {
    size_t index = hashFunction(key);
    // Acquire SHARED lock for reading
    std::shared_lock<std::shared_mutex> lock(*mutexes[index]);
    // Read data safely (other threads can also read this slot simultaneously)
    return slot_value;
}
```

## 4. Simulation Framework and Performance Comparison
A simulation framework models a hash table under different concurrency control protocols to deterministically compare their efficiency. 

### Protocols Modeled
1. **`GLOBAL_MUTEX`**: One single lock for the entire table.
2. **`MUTEX_PER_SLOT`**: One exclusive lock per slot (Fine-grained).
3. **`SHARED_MUTEX_PER_SLOT`**: One read-write lock per slot (Fine-grained + Shared).

### Results Analysis
Comparing the total logical time steps taken to process a mixed read/write workload trace reveals massive efficiency gains:

| Protocol | Approx. Time Steps | Characteristics |
| :--- | :--- | :--- |
| **Global Mutex** | ~30 steps | **Slowest.** Highly serialized; threads constantly blocked. |
| **Mutex Per Slot** | ~21 steps | **Faster.** Allows concurrent access to distinct slots. Blocks on concurrent reads of the same slot. |
| **Shared Mutex Per Slot** | ~15 steps | **Fastest.** Maximizes concurrency by allowing distinct slot access *and* simultaneous reads of the same slot. |
