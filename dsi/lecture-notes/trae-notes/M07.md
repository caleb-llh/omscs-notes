# Module 07: Indexing in C++ and Hash Tables

## 1. Indexing in Database Systems
Indexing provides a mechanism to quickly look up data without scanning every row in a database table, functioning much like a book index that points directly to page numbers for specific topics.

> **Intuition:** Just like you wouldn't read a 1000-page book cover-to-cover to find mentions of a specific word, a database uses an index to jump directly to the relevant data blocks, avoiding expensive full table scans.

### C++ Indexing Structures
Standard C++ offers two primary associative containers that can serve as foundational concepts for database indexes:

- **`std::map` (Ordered Map)**
  - **Ordering:** Keys are maintained in a strict weak ordering.
  - **Implementation:** Typically a Self-Balancing Binary Search Tree (e.g., Red-Black Tree).
  - **Time Complexity:** $O(\log N)$ for search, insertion, and deletion (Average and Worst Case).
  - **Best For:** Range queries and ordered traversals.
- **`std::unordered_map` (Unordered Map)**
  - **Ordering:** Keys are not sorted; elements are organized into buckets based on hashes.
  - **Implementation:** Hash Table with separate chaining (typically).
  - **Time Complexity:** $O(1)$ Average Case, $O(N)$ Worst Case (in the event of severe hash collisions).
  - **Best For:** Point queries (exact match lookups).

> **Tradeoff:** `std::map` gives you ordering and range queries at the cost of $O(\log N)$ lookups, while `std::unordered_map` offers blazing fast $O(1)$ point lookups but completely abandons any sense of order.

### Basic HashIndex in BuzzDB
A database point-query index can wrap an unordered map for quick in-memory lookups:

```cpp
class HashIndex {
private:
    // Maps a key (e.g., primary key) to a value (e.g., tuple ID or file offset)
    std::unordered_map<int, int> hash_index;
public:
    void insertOrUpdate(int key, int value) { 
        hash_index[key] = value; 
    }
    
    int getValue(int key) const {
        auto it = hash_index.find(key);
        return it != hash_index.end() ? it->second : -1;
    }
};
```
*Note: During the database scanning phase, tuples are read, their key-value pairs extracted, and then inserted into the `HashIndex`.*

## 2. Hash Table Fundamentals
Think of a hash table as a cabinet of drawers. Each drawer represents a "slot" (or bucket) and holds a piece of data (key-value pair).

> **Mental Model:** Imagine a magical filing cabinet where a math equation (the hash function) tells you exactly which drawer holds your document, instantly, no matter how many documents are inside.

### Hash Functions
A hash function is a deterministic algorithm that maps keys of arbitrary or variable size to a fixed-size integer, which corresponds to a slot in the hash table.
- **Simple Example:** `HASH(KEY) = KEY % TABLE_SIZE`
- **Purpose:** Enables direct memory access to the storage slot, ideally achieving $O(1)$ retrieval.
- **Ideal Properties:** Uniform distribution (minimizes collisions), deterministic (same input yields same output), and fast to compute.

---

## 3. Collision Handling (Open Addressing)
When two different keys hash to the exact same slot, a **collision** occurs. Open addressing resolves collisions by probing (searching) for the next available slot within the array itself.

### A. Linear Probing
- **Mechanism:** Move to the next adjacent slot sequentially until an empty one is found.
- **Formula:** `INDEX = (HASH(KEY) + K) % TABLE_SIZE` (where $K$ is the probe step, starting at $0$).
- **Insertion & Retrieval:** Uses linear probing to find an empty slot (for insertion) or locate the target key/empty slot (for retrieval).
- **Operation Complexity:**
  - *Sparse Table:* $O(1)$ for Insert and Find.
  - *Dense Table / High Collisions:* Approaches $O(N)$.
- **Limitation (Primary Clustering):** Contiguous blocks of occupied slots form. As clusters grow, the probability of a new key hitting the cluster and expanding it increases, drastically degrading performance.

> **Common Confusion:** Why use Linear Probing if clustering is so bad? Linear probing exhibits excellent cache locality. Since modern CPUs fetch data in cache lines, probing adjacent memory slots is incredibly fast in practice compared to jumping around memory.

### B. Quadratic Probing
- **Mechanism:** The probe sequence follows a quadratic progression, spacing out the search sequence.
- **Formula:** `INDEX = (HASH(KEY) + K^2) % TABLE_SIZE` ($K = 0, 1, 2, 3...$).
- **Benefit:** Mitigates primary clustering by spreading keys further apart across the table.
- **Limitation (Secondary Clustering):** Keys that hash to the exact same initial slot will follow the exact same probe sequence, leading to milder but still present clustering.

### C. Double Hashing
- **Mechanism:** Uses a secondary hash function to determine the step size for the probe sequence.
- **Formula:** `INDEX = (HASH1(KEY) + K * HASH2(KEY)) % TABLE_SIZE`.
  - *Example 1:* `HASH1(KEY) = KEY % TABLE_SIZE` (Initial slot)
  - *Example 2:* `HASH2(KEY) = 1 + KEY % (TABLE_SIZE - 1)` (Step size)
- **Benefit:** Highly resistant to both primary and secondary clustering. Keys hashing to the same initial slot will have completely different step sizes, generating unique probe sequences.

## 4. Key Deletion and Position Tracking

### The Deletion Problem in Open Addressing
If a key is physically removed from its slot, it leaves a "hole" that breaks the continuous probe sequence. Subsequent searches for colliding keys placed after the deleted key will hit the empty slot and erroneously return "Not Found."

### Solution 1: Rehashing (Naive)
- **Approach:** Re-insert all remaining keys into a completely new hash table. 
- **Drawback:** Computationally prohibitive ($O(N)$) for every deletion.

### Solution 2: Lazy Deletion (Tombstones)
- **Approach:** Mark a hash entry as deleted (a "tombstone") without physically removing its data or leaving a true empty slot.
- **Mechanism:** Searches safely pass over "deleted" entries to continue probing. Insertions can reuse these deleted slots.

> **Intuition:** Think of tombstones as "Out of Order" signs on a broken elevator. You know an elevator used to be there, but you just skip it and keep looking for a working one.
- **Implementation (Exists Flag):**
```cpp
struct HashEntry {
    int key;
    int value;
    bool exists; // true = active, false = deleted (tombstone)
    
    HashEntry(int k, int v) : key(k), value(v), exists(true) {}
};
```

### Position Tracking in Static Hash Tables
In embedded or low-level systems, position tracking allows monitoring the exact final physical location of each entry within a fixed-size array.

```cpp
class StaticHashIndex {
private:
    static const size_t CAPACITY = 100;
    HashEntry hashTable[CAPACITY]; // Contiguous static array
public:
    // ... insertion logic ...
};
```
*Note: When a key is inserted after resolving collisions, its final settled index is explicitly recorded or implicitly defined by its position in the array, making memory access highly predictable and cache-friendly.*
