# Module 13: Query Parsing, Interpretation, and Compilation

## 1. Query Parsing

**Query parsing** is the critical first step in query execution, translating a raw, unstructured query string into a structured, internal representation. Historically, simpler database systems relied on hard-coded operator frameworks for this translation.

Consider the following query variants, demonstrating increasing complexity:
- **Filtering only:** `"{1} WHERE {1} > 2 AND {1} < 6"`
- **Filtering & Aggregation:** `"SUM{1} WHERE {1} > 2 AND {1} < 6"`
- **Filtering, Aggregation & Grouping:** `"SUM{1} GROUP BY {2} WHERE {1} > 2 AND {1} < 6"`

### 1.1 Parsing with Regular Expressions (Regex)

Database systems frequently use regex to parse query strings. The parsing engine typically extracts:
1. **Selection (`SELECT`)**: The specific columns to retrieve.
2. **Aggregation (e.g., `SUM`)**: The presence of aggregate functions and their target columns.
3. **Grouping (`GROUP BY`)**: The column(s) defining the grouping boundaries.
4. **Filtering (`WHERE`)**: The conditional logic, including target columns and bounding values.

**Example: Regex for `SUM` Detection**
- **Query String**: `SUM{3}`
- **Regex Pattern**: `SUM\{(\d+)\}`
  - `SUM`: Matches the literal string.
  - `\{ \}`: Escapes the curly braces.
  - `(\d+)`: Capturing group extracting one or more digits (the column index).

```cpp
// Conceptual C++ example of Regex-based parsing
QueryComponents parseQuery(const std::string &query) {
    QueryComponents components;
    std::regex selectRegex("\\{(\\d+)\\}(, \\{(\\d+)\\})?");
    std::smatch selectMatches;
    std::string::const_iterator queryStart(query.cbegin());
    
    while (std::regex_search(queryStart, query.cend(), selectMatches, selectRegex)) {
        // Extract matches and populate components...
    }
    return components;
}
```

### 1.2 Query Components Structure

The parsed query is materialized into a structured data object, often a struct like `QueryComponents`. This acts as the blueprint for the execution plan.

| Component Type | Data Type | Description |
| :--- | :--- | :--- |
| `selectAttributes` | `std::vector<int>` | Indices of columns selected in the query. |
| `sumOperation` | `bool` | Flag indicating the presence of a `SUM` operation. |
| `sumAttributeIndex` | `int` | Column index targeted by the `SUM` operation. |
| `groupBy` | `bool` | Flag indicating the presence of a `GROUP BY` clause. |
| `groupByAttributeIndex` | `int` | Column index used for grouping. |
| `whereCondition` | `bool` | Flag indicating the presence of a `WHERE` clause. |
| `whereAttributeIndex` | `int` | Column index targeted by the filter. |
| `lowerBound` / `upperBound`| `int` | The lower and upper bounds for the filter condition. |

### 1.3 Building the Execution Plan

The parsed `QueryComponents` are mapped to a directed acyclic graph (DAG) of physical operators. For the query `"SUM{1} GROUP BY {2} WHERE {1} > 2 and {1} < 6"`, the pipeline is constructed bottom-up:

1. **Scan Operator**: Iterates through the table via the buffer manager, retrieving all tuples.
2. **Select Operator**: Applies the `WHERE` predicate (Column 1 $\in (2, 6)$).
3. **Hash Aggregation Operator**: Computes `SUM` on Column 1, grouped by Column 2.

```cpp
// Conceptual Execution Pipeline Construction
void executeQuery(const QueryComponents &components, BufferManager &bm) {
    ScanOperator scanOp(bm);
    Operator *rootOp = &scanOp; 

    std::optional<SelectOperator> selectOpBuffer;
    std::optional<HashAggregationOperator> hashAggOpBuffer;

    // 1. Inject WHERE Filter
    if (components.whereAttributeIndex != -1) {
        selectOpBuffer.emplace(*rootOp, makeComplexPredicate(components));
        rootOp = &*selectOpBuffer;
    }

    // 2. Inject Grouping/Aggregation
    if (components.sumOperation || components.groupBy) {
        hashAggOpBuffer.emplace(*rootOp, components.groupByAttributeIndex, prepareAggregation(components));
        rootOp = &*hashAggOpBuffer;
    }

    // 3. Execute Pipeline (Volcano Model)
    rootOp->open();
    while (rootOp->next()) {
        printTupleFields(rootOp->getOutput());
    }
    rootOp->close();
}
```

## 2. Query Interpretation (The Volcano Model)

**Query Interpretation** is the classical execution paradigm where queries run through a generalized, polymorphic operator framework at runtime. 

**The Lifecycle:**
1. **Parsing**: Extract intent.
2. **Plan Generation**: Construct the operator tree.
3. **Execution**: Pass tuples up the tree via standard interfaces (e.g., `open()`, `next()`, `close()`).

### 2.1 The CPU Overhead of Interpretation

> **Common Confusion:** Why are virtual function calls considered so slow here? It's not just the cost of the call itself. Virtual dispatch prevents the CPU from predicting the execution path effectively, breaking instruction pipelining and preventing compiler optimizations like inlining.

While highly flexible, interpreted execution suffers from severe **CPU overhead** known as the "interpretation tax":
- **Virtual Function Calls**: Deep operator trees require millions of dynamic dispatches (e.g., repeatedly calling `Operator::next()`).
- **Tuple Deserialization**: Generic extraction logic is used for every row, regardless of schema.
- **Memory Thrashing**: Frequent dynamic allocation/deallocation for temporary objects (e.g., `std::unique_ptr<Field>`).
- **Branching Penalties**: Highly generic code leads to branch mispredictions and pipeline stalls.
- **Lack of Specialization**: The engine cannot optimize for the exact constants or types of a specific query.

## 3. Query Compilation (Code Generation)

> **Intuition:** If Interpretation is a flexible, general-purpose factory that requires constant re-tooling between steps, Query Compilation is like building a custom, specialized assembly line for *one specific product* (the query). It takes time to build the line, but once running, it's incredibly fast.

To eliminate the "interpretation tax", modern high-performance DBMSs utilize **Query Compilation** (or Just-In-Time (JIT) Code Generation).

**The Modern Lifecycle:**
`SQL String` $\rightarrow$ `Parsing` $\rightarrow$ **`C/C++ Code Generation`** $\rightarrow$ **`Compilation to Machine Code`** $\rightarrow$ `Execution`

Instead of pushing data through a generic operator tree, the DBMS generates highly optimized, hard-coded logic tailored *exactly* to the specific query.

### 3.1 Anatomy of Generated Code

Query compilation fuses operators together (pipelining), removing intermediate materialization and virtual calls.

**1. Direct Scanning**
Generated code bypasses abstract iterators, interacting directly with raw page buffers and slots.
```cpp
// Hard-coded loop unrolling and direct memory access
void compiledQuery(BufferManager &bm) {
    for (int pageIdx = 0; pageIdx < bm.getNumPages(); ++pageIdx) {
        auto &page = bm.getPage(pageIdx);
        Slot *slots = reinterpret_cast<Slot *>(page.data);
        
        for (int slotIdx = 0; slotIdx < MAX_SLOTS; ++slotIdx) {
            if (!slots[slotIdx].empty) {
                // Inline tuple processing...
            }
        }
    }
}
```

**2. Hard-Coded Field Extraction**
Deserialization logic jumps directly to the byte offsets of the required columns, ignoring unused data.
```cpp
// Extracting only the 4th attribute directly from the byte array
const char *tuple_data = page_buffer + slots[slotIdx].offset;
int current_col = 0; 
int target_col = 4;
int char_offset = 0;

// Skip to target column
while (current_col < target_col) {
    if (tuple_data[char_offset++] == ' ') current_col++;
}

// Parse integer inline
int fieldValue = std::atoi(tuple_data + char_offset);
```

**3. Inlined Aggregation & Filtering**
`WHERE` clauses and hash maps are baked directly into the loop, operating on raw primitives.
```cpp
// Inlined predicate and aggregation state
static std::unordered_map<int, int> groupSums;

if (fieldValue > 2 && fieldValue < 6) {       // Fused SelectOperator
    groupSums[fieldValue] += fieldValue;      // Fused HashAggOperator
}
```

### 3.2 Trade-offs of Query Compilation

> **Tradeoff:** This is a classic setup-time vs. execution-time tradeoff. OLTP systems (many quick, simple queries) often prefer Interpretation to avoid compilation latency, while OLAP systems (few complex, long-running queries) heavily benefit from Compilation.

| Aspect | Query Compilation |
| :--- | :--- |
| **Advantages** | **1. Blistering Execution Speed:** Often 10x-30x faster by removing virtual calls, allocations, and generic branches.<br>**2. Data Locality:** Fused loops keep data in CPU registers longer. |
| **Drawbacks** | **1. Compilation Latency:** Invoking LLVM/Clang/GCC takes time. For ultra-short queries (OLTP), compile time might exceed execution time.<br>**2. Rigidity:** Code is hard-wired. Changing a parameter (e.g., `WHERE x > 10` to `WHERE x > 20`) requires full recompilation (unless parameterized). |
