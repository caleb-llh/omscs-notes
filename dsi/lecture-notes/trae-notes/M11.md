# Module 11: Modular Query Execution and Operators

This module covers the architecture of query execution engines in relational databases, focusing on how complex SQL queries are translated into a composable pipeline of discrete operators.

---

## 1. Modular Query Execution (The Volcano Model)

### 1.1 Limitations of Hard-Coded Queries
Historically, or in naive implementations, queries are written as monolithic functions (e.g., a single loop that scans, filters, and groups data). This approach has severe drawbacks:

> **Intuition:** Hard-coding queries is like building a custom machine that can only make one specific type of sandwich. If you want a different sandwich, you have to build a whole new machine.

- **Tight Coupling**: Scanning logic is intertwined with filtering and aggregation.
- **Poor Extensibility**: Supporting a new query type requires writing a completely new function.
- **Maintenance Nightmare**: Code duplication leads to higher bug rates and difficult optimizations.

### 1.2 Operators as "Lego Blocks"
Modern database systems use **Modular Query Execution** (often based on the Volcano/Iterator model). Queries are compiled into a Directed Acyclic Graph (DAG) of discrete **Operators** (e.g., `Scan`, `Select`, `Join`, `Aggregate`).

> **Tradeoff:** The Volcano model provides immense flexibility and composability, but it introduces overhead. Calling `next()` for every single tuple (virtual function calls) can be slow compared to a tight, hard-coded loop. This is why modern systems sometimes use vectorized execution (passing batches of tuples) to amortize this cost.

- **Composability**: Operators act like Lego blocks. They share a common interface, allowing the output stream of one operator to seamlessly become the input stream of the next.
- **Pipelining**: Tuples flow through the operator tree (typically from bottom to top), minimizing memory overhead by processing data in small chunks (or one tuple at a time) rather than materializing entire intermediate tables.

## 2. The Abstract Operator Class

In object-oriented database implementations (like C++ or Java), the composability of operators is achieved via inheritance and polymorphism.

### 2.1 The `Operator` Interface
An abstract base class defines the standard lifecycle and data-retrieval interface for *all* operators.

```cpp
class Operator {
public:
    virtual ~Operator() = default;
    
    // Initializes the operator (e.g., opens files, allocates memory, resets pointers)
    virtual void open() = 0;
    
    // Advances to the next tuple. Returns true if a tuple is available, false if EOF.
    virtual bool next() = 0;
    
    // Returns the current tuple produced by the operator.
    virtual std::vector<std::unique_ptr<Field>> getOutput() = 0;
    
    // Cleans up resources (e.g., closes files, frees memory).
    virtual void close() = 0;
};
```

### 2.2 Operator Classification
Specific operators inherit from `Operator` and override its pure virtual functions. They are categorized by their inputs:
- **0-ary Operators (Source)**: No input operators. They read directly from disk or memory (e.g., `ScanOperator`).
- **Unary Operators**: Take exactly **one** child operator as input (e.g., `SelectOperator`, `SortOperator`, `HashAggregationOperator`).
- **Binary Operators**: Take **two** child operators as input (e.g., `JoinOperator`).

## 3. The Scan Operator

The **Scan Operator** acts as the data source (leaf node) in a query plan. It reads tuples from a table's physical pages on disk via the **Buffer Manager**.

> **Common Confusion:** The Scan Operator doesn't read directly from the disk. It asks the Buffer Manager for pages. The Buffer Manager handles the disk I/O, ensuring that if the page is already in memory, it doesn't need to be fetched again.

### 3.1 Lifecycle Implementation
- **`open()`**: Initializes the scan. It requests the first page from the Buffer Manager, resets slot indices, and calls a helper `loadNextTuple()` to prepare the first tuple.
- **`next()`**: Sequentially advances through the slots on the current page.
  - If the current page is exhausted, it requests the next page from the Buffer Manager.
  - Returns `true` if a new tuple is successfully loaded into the operator's state (`currentTuple`); returns `false` if all pages are exhausted.
- **`getOutput()`**: Returns the `currentTuple` to the parent operator.
- **`close()`**: Resets internal pointers and explicitly unpins/releases pages back to the Buffer Manager.

## 4. The Select Operator and Predicates

The **Select Operator** acts as a filter (a Unary Operator). It consumes a stream of tuples from its child operator and yields only those that satisfy a specific logical condition (a Predicate).

### 4.1 Predicates
A **Predicate** encapsulates the filtering logic (e.g., `salary > 50000`). It consists of:
- **Left Operand**: Typically a reference to a column.
- **Right Operand**: A constant value or another column reference.
- **Predicate Type**: The comparison operator (`EQ` =, `NEQ` !=, `GT` >, `LT` <, `GE` >=, `LE` <=).

#### Operand Resolution (Direct vs. Indirect)
To maintain flexibility, operands evaluate dynamically:
- **Direct (Constant)**: A hardcoded literal value (e.g., `50000`).
- **Indirect (Field Reference)**: An index pointing to a specific column in the incoming tuple (e.g., `TUPLE[2]` meaning the 3rd column).

### 4.2 Select Operator Implementation
```cpp
class SelectOperator : public UnaryOperator {
private:
    Predicate predicate; 
    std::vector<std::unique_ptr<Field>> currentOutput; 
};
```
- **`next()` Execution Loop**: 
  1. Calls `input->next()` on its child operator.
  2. If the child returns a tuple, it evaluates `predicate.checkPredicate(tuple)`.
  3. If the predicate evaluates to `true`, the operator performs a **deep copy** of the tuple into `currentOutput` and returns `true`.
  4. If `false`, it loops back to step 1 until a matching tuple is found or the child returns `false` (EOF).

### 4.3 Memory Management: Deep vs. Shallow Copy
When passing tuples up the operator pipeline, memory isolation is critical.

> **Intuition:** Think of shallow copy as giving someone a link to a Google Doc (if the original changes, they see the changes), while a deep copy is like giving them a printed PDF (it remains exactly as it was when copied).
> 
> **Tradeoff:** Deep copying ensures safety and memory isolation between operators, but it is computationally expensive and increases memory pressure, especially when filtering millions of rows.

- **Shallow Copy**: Copying only pointers. If the child operator overwrites its internal buffer to read the next tuple, the parent operator's reference becomes corrupted.
- **Deep Copy**: Allocating new memory and cloning the actual data. 
- **`duplicateFields()`**: A crucial helper method used by the Select Operator. When a tuple passes the predicate, `duplicateFields()` invokes `.clone()` on each `Field` to create a safe, independent copy before yielding it to the parent.

### 4.4 Example: Operator Composition
```cpp
// 1. Initialize the source
ScanOperator scanOperator(buffer_manager, table_id);

// 2. Define the condition: Column[0] > 1000
Predicate predicate(Predicate::Operand(0), // Indirect: Column 0
                    Predicate::Operand(std::make_unique<Field>(1000)), // Direct: 1000
                    PredicateType::GT);

// 3. Chain the operators
SelectOperator selectOperator(scanOperator, std::move(predicate));

// 4. Execute the pipeline
selectOperator.open();
while (selectOperator.next()) {
    auto tuple = selectOperator.getOutput();
    // Process matching tuple...
}
selectOperator.close();
```
