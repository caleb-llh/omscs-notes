# Module 14: Row vs Columnar Storage, Compression, and Vectorized Execution

## 1. Physical Data Layout: Row vs. Columnar Storage

> **Intuition:** Think of Row storage as reading a book page by page—great if you want the whole story of one character. Columnar storage is like having an index of just the verbs used in the book—perfect if you only want to count action words, without reading the full text.

The physical arrangement of data on disk dictates the I/O efficiency of a database, heavily influencing query performance based on the workload's access patterns.

### 1.1 Architectural Comparison

> **Common Confusion:** Does Columnar storage mean we lose the relationship between attributes in a row? No. The relationships are maintained through implicit row offsets (indices). The $n$-th value in the `Temperature` column belongs to the same logical record as the $n$-th value in the `Timestamp` column.

| Feature | Row Storage (N-ary Storage Model / NSM) | Columnar Storage (Decomposition Storage Model / DSM) |
| :--- | :--- | :--- |
| **Data Layout** | Contiguous storage of an entire record (all attributes grouped together). | Contiguous storage of a single attribute across many records (columns stored in separate files/regions). |
| **Primary Workload** | **OLTP (Online Transaction Processing):** Write-heavy, point lookups. | **OLAP (Online Analytical Processing):** Read-heavy, aggregations, scans. |
| **Access Efficiency** | Optimal for reading/writing entire individual records (e.g., fetching a user profile). | Optimal for scanning specific attributes across millions of rows (e.g., computing an average). |
| **Compression** | Poor. Heterogeneous data types (strings, ints, dates) are interleaved. | Excellent. Homogeneous data types are contiguous, enabling specialized compression. |

### 1.2 Execution Mechanics: A Case Study

**Dataset:** Weather readings with 4 columns: `[Timestamp, Temperature, Humidity, Windspeed]`.
**Query:** `SELECT AVG(Temperature) FROM Weather WHERE Timestamp BETWEEN 5 AND 75;`

**The Row Storage Approach:**
- **Execution:** The engine must load entire rows (including `Humidity` and `Windspeed`) from disk into memory, check the `Timestamp`, and extract the `Temperature`.
- **Bottleneck:** Massive I/O waste. It reads unneeded columns, saturating disk bandwidth.

**The Columnar Storage Approach:**
1. **Filter Phase:** Sequentially scan *only* the `Timestamp` column. Generate a list of row offsets (indices) where `5 <= Timestamp <= 75`.
2. **Aggregate Phase:** Use the collected offsets to read *only* the required values from the `Temperature` column. Compute the average.
- **Advantage:** Total bypass of irrelevant columns (`Humidity`, `Windspeed`), drastically minimizing disk I/O.

**Illustrative Performance Impact:**
- **Row Storage:** 112.1 ms (Reads 3,907 pages)
- **Columnar Storage:** 3.6 ms (Reads 962 pages: 489 for filter + 473 for aggregate)

## 2. Columnar Compression Techniques

> **Intuition:** Columnar data compresses exceptionally well because adjacent values are of the exact same data type and often similar in value. It’s much easier to compress a list of 1,000 dates than a mixed list of names, dates, and account balances.

Because columnar storage groups identical data types sequentially, it exhibits high data redundancy and low entropy. This makes it highly receptive to lightweight, algorithmic compression.

### 2.1 Common Compression Algorithms

| Algorithm | Best Suited For | Mechanism |
| :--- | :--- | :--- |
| **Delta Encoding** | Sequential/Incrementing Numeric Data (e.g., Timestamps, IDs). | Stores the difference (delta) from the preceding value instead of the absolute value. <br>*Example:* `[100, 102, 105] -> [100, +2, +3]`. |
| **Bit-Packing** | Numeric Data with a Narrow Domain (e.g., Ages, Temperatures). | Subtracts the domain minimum to shrink the range, then packs values using the absolute minimum required bits. <br>*Example:* Storing temperatures ($0-60^\circ C$) requires only 6 bits per value instead of 32. |
| **Huffman Encoding** | Categorical Data with Skewed Frequencies. | Assigns variable-length binary codes based on frequency. Common values get short codes; rare values get long codes. |
| **Dictionary Encoding** | Categorical/String Data with Low Cardinality (e.g., States, Statuses). | Maps strings to dense integer IDs (e.g., 1-byte). A separate dictionary maps the IDs back to the original strings. |

### 2.2 The Performance Multiplier of Compression

> **Tradeoff:** Compression introduces a CPU vs. I/O tradeoff. We spend extra CPU cycles to decompress data on the fly, but we save massive amounts of disk I/O time. Since disk access is typically orders of magnitude slower than CPU processing, this tradeoff heavily favors compression.

While decompression costs CPU cycles, the reduction in disk I/O heavily outweighs this overhead in modern systems (where disk bandwidth is the primary bottleneck).

**Illustrative Query Time (Weather Dataset):**
- **Row Storage:** 17.57 ms
- **Uncompressed Columnar:** 5.13 ms
- **Compressed Columnar:** **4.08 ms** *(Delta Encoding for Timestamps + Bit-Packing for Temperatures)*

## 3. Vectorized Execution (SIMD)

> **Mental Model:** Tuple-at-a-time (Volcano) processing is like carrying groceries from the car one item at a time. Vectorized execution (SIMD) is like carrying a whole bag of groceries at once. You make fewer trips (instructions) and get the job done much faster.

Traditional DBMSs process queries using **Tuple-at-a-Time** execution (the Volcano model). This approach suffers from high function call overhead, poor cache locality, and pipeline stalls due to branching. 

Modern analytical engines (e.g., DuckDB, ClickHouse) utilize **Vector-at-a-Time Processing** powered by **SIMD**.

### 3.1 What is SIMD?

**SIMD (Single Instruction, Multiple Data)** is a hardware-level capability allowing a CPU to execute a single operation on a "vector" (batch) of data simultaneously, rather than processing scalar values one by one.

**Database Applications of SIMD:**
- **Filtering:** Rapidly evaluating predicates to generate bitmasks.
- **Aggregations:** Computing parallel sums/averages.
- **Compression:** High-speed vectorized bit-unpacking.
- **Hash Joins:** Concurrently hashing multiple keys.

### 3.2 The Advantages of SIMD Execution

> **Common Confusion:** Is Vectorized Execution the same as Multithreading? No. Multithreading uses multiple CPU cores to do different tasks at the same time. SIMD uses a single CPU core to apply one instruction to multiple pieces of data simultaneously. They can be used together for massive performance gains.

1. **Instruction-Level Parallelism:** Processing $N$ data points requires only $N/W$ instructions ($W = \text{vector width}$, e.g., 4 or 8).
2. **Cache Alignment:** Columnar arrays load perfectly into wide SIMD registers (e.g., 256-bit AVX registers), maximizing L1/L2 cache efficiency.
3. **Branchless Execution:** SIMD replaces expensive `if/else` branches with logical bitmask operations, virtually eliminating CPU pipeline stalls and branch mispredictions.

### 3.3 SIMD Intrinsics & Naming Conventions

SIMD instructions (like Intel AVX or ARM NEON) use specialized intrinsics. 
**Example:** `vaddq_f32` (ARM NEON)
- `v`: Vector instruction.
- `add`: Operation type (Addition).
- `q`: Vector width (Quad-word; 128-bit register holding four 32-bit values).
- `f32`: Data type (32-bit float).

### 3.4 The Evolution of SIMD

- **1960s-1970s:** Pioneered in supercomputers (e.g., ILLIAC IV) for scientific computing.
- **1980s-1990s:** Adapted for multimedia and graphics (e.g., Intel MMX in 1996 for pixel manipulation).
- **2000s:** Standardized in consumer CPUs (Intel SSE/AVX, ARM NEON).
- **2010s-Present:** Became the backbone of big data analytics and columnar query engines (e.g., Apache Arrow, modern OLAP databases).
