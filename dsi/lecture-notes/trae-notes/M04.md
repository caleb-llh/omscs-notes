# Module 04: Slotted Pages and Database File Management

## 1. Slotted Pages

### Limitations of the Basic Page Class
The simple page class structure suffers from several significant limitations:
* **Linear Scan for Insertion:** Locating space for a new tuple requires sequentially scanning the page.
* **Wasted Space (Internal Fragmentation):** Poor management of variable-length tuples results in unused, fragmented memory.
* **Compaction Overhead:** Consolidating free space requires periodic, computationally expensive page "compaction" (moving tuples around).

### The Slotted Page Design
> **Intuition:** Think of a slotted page like a book's table of contents (the slots) and the chapters (the tuples). Instead of flipping through every page to find a chapter, you look at the table of contents to jump straight to it.

To mitigate these issues, modern databases employ a **Slotted Page** architecture.
* **Slots:** Entries in a page's "header" section that track the exact location of tuples within the page.
* **Direct Access:** Enables O(1) logical access to any tuple via its slot index.

```cpp
struct Slot {
    uint16_t offset; // Offset of the tuple within the page
    uint16_t length; // Length of the tuple data
};

class SlottedPage {
    std::unique_ptr<char[]> page_data;
    std::vector<Slot> slots;
    size_t free_space_offset;
    // ...
};
```

#### Anatomy of a Slotted Page
1. **Metadata & Status:** Tracks the page's overall health and slot count.
2. **Slot Array:** Each slot stores the `offset` and `length` of a specific tuple.
3. **Free Space Offset:** A pointer to the start of the next contiguous block of available memory.
4. **Variable-Length Tuples:** Tuple data can grow backwards (from the end of the page) or forwards. Slots decouple logical ordering from physical placement.

#### Managing Tuples
> **Tradeoff:** Slotted pages trade a small amount of space (the slot array metadata) to gain O(1) tuple access and simplified space management.

* **Insertion (`addTuple`):** 
  Verifies available contiguous free space. If space permits, it copies the tuple data, creates a new slot with the current `free_space_offset` and `length`, and updates the offset.
  ```cpp
  bool addTuple(const char *tupleData, size_t length) {
      if (free_space_offset + length > PAGE_SIZE) return false; // Out of space
      slots.push_back({free_space_offset, length}); // Update slot array
      free_space_offset += length;                  // Advance free space pointer
      return true;
  }
  ```
* **Deletion:** 
  Logically marks a tuple as deleted by updating its slot (e.g., `slots[index].empty = true`). This instantly reclaims logical space for future use without requiring immediate physical reorganization.
  > **Common Confusion:** Logical deletion does not immediately free up physical disk space or even memory in the `page_data` buffer. It only marks the slot as available. The physical space is only reclaimed later during a compaction phase or if a new tuple exactly fits the old space.
* **Update:** 
  If the updated tuple fits in its current location, it is updated in-place. Otherwise, it is moved to a new location within the page, and its corresponding slot's `offset` and `length` are updated.

#### Key Benefits
* **Maximized Utilization:** Variable-length tuples are tightly packed, minimizing internal fragmentation.
* **Simplified Compaction:** Tuples can be physically moved to defragment the page without changing their logical IDs; only the slot offsets require updating.

## 2. Database File Management

While a single `SlottedPage` allows in-memory operations, scaling a database requires managing an on-disk database file spanning multiple pages.

### File Operations with `std::fstream`
C++ handles file I/O using `std::ifstream` (read), `std::ofstream` (write), and `std::fstream` (read/write).
```cpp
// Open file with read/write permissions
file.open(database_filename, std::ios::in | std::ios::out);

// Calculate total pages by seeking to the end of the file
file.seekg(0, std::ios::end);
num_pages = file.tellg() / PAGE_SIZE;
```

### Extending the Database File
When all existing pages are full, the database dynamically extends the file by appending a newly initialized `SlottedPage`.
```cpp
void extendDatabaseFile() {
    auto empty_page = std::make_unique<SlottedPage>();
    file.seekp(0, std::ios::end); // Seek to physical end of file
    file.write(empty_page->page_data.get(), PAGE_SIZE);
    file.flush(); // Force OS to write to disk
    num_pages++;
}
```

### Data Lifecycle: Insertion, Loading, and Flushing
> **Intuition:** A database is essentially a very specialized file manager. It cannot trust the Operating System to manage when data is saved to disk (because a power loss could corrupt the database), so it must explicitly control the loading and flushing of pages.

* **Inserting:** The system scans existing pages for free space. If `try_to_insert` fails across all pages, it triggers `extendDatabaseFile()` and retries.
* **Loading Pages:** During startup, the system iterates through the file, deserializing raw `PAGE_SIZE` byte chunks from disk into in-memory `SlottedPage` objects.
* **Flushing to Disk:** C++ uses buffered I/O (storing data temporarily in DRAM). Explicitly calling `flush()` bypasses the buffer, immediately writing data to persistent storage to prevent data loss.
  ```cpp
  void SlottedPage::flush(std::fstream &file, uint16_t page_id) const {
      size_t page_offset = page_id * PAGE_SIZE;
      file.seekp(page_offset, std::ios::beg);
      file.write(page_data.get(), PAGE_SIZE);
      file.flush(); // Critical for persistence
  }
  ```

## 3. Index Construction

An index (e.g., a B-Tree) organizes records to bypass full sequential scans for fast O(log n) retrieval. Building an index from an existing on-disk file requires a full sequential scan:

1. **Iterate** over all pages in the database file.
2. **Access** the raw page data buffer.
3. **Cast** the buffer to a `Slot` array to interpret the metadata.
4. **Scan Slots:** For every non-empty slot, use the `offset` to locate the tuple data.
5. **Deserialize & Index:** Convert the raw bytes into a `Tuple` object, extract the index key, and insert it into the index structure.

```cpp
void BuzzDB::scanTableToBuildIndex() {
    for (size_t page_itr = 0; page_itr < num_pages; page_itr++) {
        char *page_buffer = pages[page_itr]->page_data.get();
```

## 4. Casting in C++

C++ enforces strict type safety but provides four casting operators for necessary conversions: `static_cast`, `reinterpret_cast`, `dynamic_cast`, and `const_cast`.

* **`static_cast`**: Safely converts between naturally compatible types (e.g., `float` to `int` or upcasting/downcasting in class hierarchies).
  ```cpp
  float floatKey = 123.45f;
  int intKey = static_cast<int>(floatKey); 
  ```
* **`reinterpret_cast`**: Forcibly reinterprets the underlying bit pattern of a pointer into a completely different, unrelated pointer type. **Crucial in databases** for mapping structured metadata (like a `Slot` array) directly onto raw byte buffers.
  ```cpp
  char *pageData = getPageData(); 
  Slot *slots = reinterpret_cast<Slot*>(pageData); // Treat raw bytes as Slot structs
  ```

## 5. Streams in C++

The **Stream Abstraction** provides a unified interface for sequential I/O, hiding the complexity of the underlying data source or destination (File, Memory, Console, Network).

* **`std::fstream`**: Manages persistent File I/O operations.
* **`std::stringstream`** (`<sstream>`): Treats in-memory strings as I/O streams. Highly useful for **serialization and deserialization** of tuples.
  ```cpp
  std::istringstream iss(tuple_data); // Wrap raw string in an input stream
  auto loadedTuple = Tuple::deserialize(iss); // Consume stream to build object
  ```

## 6. Storage Management & RAII

For robust architecture, file I/O and page management should be abstracted into a dedicated **Storage Manager**, responsible for:
* **Lifecycle Management:** Constructors and Destructors.
* **`load()`**: Fetching a page from disk to memory.
* **`flush()`**: Persisting memory changes to disk.
* **`extend()`**: Growing the database file.

### RAII (Resource Acquisition Is Initialization)
> **Common Confusion:** Despite the name containing "Initialization", the most important part of RAII is actually the *destruction*. RAII ensures that when an object goes out of scope, its destructor deterministically cleans up resources. This is entirely different from Garbage Collection (like in Java or Python), which cleans up memory non-deterministically.

RAII is a fundamental C++ paradigm ensuring resource safety by tying resource lifecycles to object lifecycles.
* **Acquisition:** Resources (memory, file locks, network sockets) are acquired in the **Constructor**.
* **Release:** Resources are automatically freed in the **Destructor** when the object goes out of scope.

**Common RAII Examples:**
1. **Smart Pointers (`std::unique_ptr`)**: Automatically deallocates heap memory when the pointer goes out of scope, preventing memory leaks.
2. **File Handles**: A `StorageManager` constructor opens `std::fstream`, and its destructor calls `.close()`. Even if an exception is thrown, the file handle is safely released, preventing resource starvation.
