## 1. CPU History and Multi-Threading

### The Evolution of CPUs
> **Intuition:** For decades, software automatically got faster every year because CPU clock speeds increased. When the "Thermal Wall" hit, the free lunch was over. Software engineers suddenly had to rewrite applications to run concurrently on multiple cores to see performance gains.

* **1970s–1980s:** Early CPUs operated at a few Megahertz (MHz).
* **1990s:** Clock speeds rapidly increased from hundreds of MHz to over 1 GHz.
* **Early 2000s:** Top-end CPUs pushed past 3 GHz.
* **Mid 2000s:** Speeds peaked around ~3.8 GHz as engineers hit the **Thermal Wall**. Clock speed (the rate of instruction execution) could no longer increase without causing severe hardware overheating.
* **2005 Onwards:** To circumvent the thermal wall, manufacturers introduced **Multi-Core CPUs** (e.g., 2-core processors, then the 4-core AMD Phenom X4 in 2006). 
* **Today:** Modern architectures support up to 64+ cores (e.g., AMD Threadripper).

Instead of relying on a single core executing instructions faster (and hotter), multi-core CPUs execute multiple instruction streams (threads) in parallel.

### Multi-Threading in C++
A **thread** is a sequential execution of instructions. Multi-threading allows programs to perform concurrent operations.

```cpp
#include <iostream>
#include <thread>
#include <vector>

int bankBalance = 1000; 

void performTransactions() {
    for (int i = 0; i < 10000; ++i) {
        bankBalance += 10; // Deposit
        bankBalance -= 10; // Withdrawal
    }
}

int main() {
    std::vector<std::thread> threads;
    for (int i = 0; i < 8; ++i) {
        threads.emplace_back(performTransactions); // Start 8 parallel threads
    }
    for (auto &thread : threads) {
        thread.join(); // Block main thread until all worker threads finish
    }
    return 0;
}
```

### The Need for Synchronization
Running the above code often results in an inaccurate final balance (e.g., `$910` or `$1020` instead of `$1000`). This is caused by a **Race Condition**.

At the hardware assembly level, a seemingly simple operation like `bankBalance += 10` is actually **non-atomic** (it requires multiple steps):
1. `MOV EAX, [bankBalance]` (LOAD value from memory into register)
2. `ADD EAX, 10` (ADD 10 to register)
3. `MOV [bankBalance], EAX` (STORE register value back to memory)

**The Race:** If Thread A and Thread B both LOAD the balance ($1000) simultaneously, both ADD 10, and both STORE $1010. One thread's transaction is completely overwritten and lost.
> **Common Confusion:** A single line of C++ code (like `bankBalance += 10`) is almost never a single atomic hardware instruction. It's usually a combination of load, modify, and store instructions. A context switch can happen *between* any of these micro-steps, causing a race condition.

## 2. Mutual Exclusion and Locking

### `std::mutex`
A **mutex (Mutual Exclusion)** acts as a lock to protect shared variables (the "critical section") from concurrent access.

```cpp
std::mutex bankMutex;

void performTransactions() {
    for (int i = 0; i < 10000; ++i) {
        bankMutex.lock();   // CRITICAL SECTION STARTS
        bankBalance += 10;  
        bankBalance -= 10;  
        bankMutex.unlock(); // CRITICAL SECTION ENDS
    }
}
```
* **Critical Section:** The code execution between `lock()` and `unlock()`. Only one thread can enter this block at a time, strictly preventing data races.
* **Hardware Level:** Mutexes rely on atomic hardware instructions, such as `LOCK CMPXCHG` (Compare and Exchange), to guarantee safe locking.

### Fine-Grained Locking
> **Tradeoff:** Fine-grained locking increases concurrency (good for performance) but dramatically increases the complexity of the code and the risk of Deadlocks (bad for reliability). Managing multiple locks correctly is notoriously difficult.

Using a single global mutex for an entire database (or banking system) creates a massive bottleneck, effectively reducing the program to single-threaded performance. 
**Solution:** Use **Fine-Grained Locking**. By assigning a separate mutex to each individual account (or database page), non-conflicting transactions on different accounts can execute entirely in parallel.

### `std::lock_guard` and RAII
Manual `lock()` and `unlock()` calls are error-prone. If a thread throws an exception or returns early before unlocking, it causes a **Deadlock (Thread Starvation)**, permanently freezing other threads waiting for that lock.

C++ resolves this via `std::lock_guard`, applying the **RAII (Resource Acquisition Is Initialization)** principle:
```cpp
void performTransactions(int account) {
    // Lock is acquired upon object creation.
    // Lock is automatically released when 'lock' goes out of scope.
    std::lock_guard<std::mutex> lock(bankAccountMutexes[account]);
    bankAccounts[account] += 10; 
}
```

**Common RAII Examples in C++:**
* `std::lock_guard`: Safely manages Mutex locks.
* `std::unique_ptr`: Safely manages dynamic heap memory.
* `std::fstream`: Safely manages file handles.

## 3. Database Configuration Tuning

Databases expose numerous configuration parameters (e.g., `PAGE_SIZE`, `MAX_SLOTS`, `BUFFER_POOL_SIZE`).
* **The Challenge:** Finding the "sweet spot" between cost and performance is complex, particularly in cloud environments.
* **Immutability:** Some parameters (like `PAGE_SIZE`) are baked into the disk format and are generally immutable after creation. Others (like `BUFFER_POOL_SIZE`) are mutable and can be adjusted at runtime.

### Workload Characteristics
> **Intuition:** You wouldn't use a sports car to haul gravel, and you wouldn't use a dump truck for a drag race. Similarly, OLTP databases are tuned for millions of tiny, fast transactions, while OLAP databases are tuned for a few massive, complex queries.

Tuning heavily depends on the application's workload profile:
* **OLTP (Online Transaction Processing):** CPU- or I/O-bound. Database size is typically slightly larger than DRAM. Characterized by high concurrency and short, rapid transactions (e.g., e-commerce checkouts).
* **OLAP (Online Analytical Processing):** I/O- or DRAM-bound. Database size vastly exceeds DRAM (Data Warehouses). Characterized by complex, long-running read queries (e.g., business reporting).
* **WEB (Web Applications):** Mostly CPU-bound. Database often fits within DRAM. Dominated by simple, read-heavy queries.

*Note: Modern database systems are increasingly utilizing Machine Learning (like Reinforcement Learning) to autonomously tune configurations based on live state, action spaces, and reward metrics (e.g., maximizing throughput).*

## 4. Database System Debugging

* **Origin of "Bug":** The term was popularized by computer pioneer Grace Hopper after a literal moth was discovered causing a hardware malfunction in an early computer.
* **Database Manifestations:** Bugs in databases are particularly severe, leading to data corruption, silent performance degradation, or catastrophic system crashes.

### Debugging with GDB (GNU Debugger)
GDB allows developers to inspect a program's internal state during execution or analyze a core dump after a crash.
* **`run`**: Starts the program execution.
* **`break <location>`**: Sets a breakpoint to pause execution at a specific line or function.
* **`next`**: Steps over to the next line of code.
* **`continue`**: Resumes execution until the next breakpoint is hit.
* **`print <var>`**: Evaluates and displays the value of a variable.
* **`info locals`**: Dumps all local variables in the current stack frame.
* **`backtrace` (`bt`)**: Displays the call stack, showing the exact function call path that led to the current state.

### Print Statements & Operator Overloading
Strategic `print` statements remain highly effective. Overloading the `<<` operator allows developers to easily log the state of complex custom classes.
```cpp
std::ostream &operator<<(std::ostream &os, const Person &person) {
    os << "Person[name=" << person.name << ", age=" << person.age << "]";
    return os;
}
```

### Core Debugging Principles
1. **Stress Testing:** Force the system into edge-cases rapidly. (e.g., Setting `MAX_PAGES_IN_MEMORY = 3` forces the buffer pool to evict pages constantly, instantly exposing eviction-related bugs).
2. **Modular Design:** Enforce strict separation of concerns (e.g., decoupling metadata management from raw data storage). Clear interfaces isolate bugs.
3. **Literate Programming:** Championed by Donald Knuth. Code must be written to be understood by humans first. Comprehensive documentation is an integral part of the codebase, not an afterthought.
4. **Robustness:** Design systems to gracefully handle and recover from failures (e.g., catching a `DiskIOException` and retrying, rather than allowing the entire database process to crash).
