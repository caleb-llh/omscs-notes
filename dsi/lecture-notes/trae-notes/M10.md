# Module 10: Advanced Indexing Structures

This module explores specialized indexing structures that address the limitations of traditional B+Trees when dealing with specific data types such as strings, text documents, multi-dimensional spatial data, and predictable data distributions.

---

## 1. Tries and Patricia Tries (String Indexing)

### 1.1 Limitations of B+Trees for String Keys
While B+Trees excel at range queries, they struggle with string-based **prefix queries** (e.g., auto-completing "Samsung Galaxy").

> **Intuition:** Think of a B+Tree like a phone book—great for finding a specific name or a range of names, but terrible if you want to find everyone whose name contains a specific sequence of letters without looking at every entry.

- **Redundant Key Storage**: Shared prefixes are repeated across multiple nodes, wasting space.
- **Space Overhead**: Storing full, long strings in each node consumes significant memory.
- **Inefficient Prefix Search**: Prefix matching requires traversing and comparing full strings rather than isolated characters.

### 1.2 The Trie (Prefix Tree)
A **Trie** solves string indexing by storing strings character-by-character.
- **Structure**: A tree where the root represents an empty string, and edges represent characters. A path from the root to a node represents a prefix or a full word.
- **Advantages**: Eliminates redundant key storage (shared prefixes are stored exactly once) and accelerates prefix lookups.

### 1.3 Patricia Trie (Radix Tree)
A **Patricia Trie** is a space-optimized variant of the standard Trie.

> **Tradeoff:** Path compression saves memory and lookup time by collapsing single-child chains, but makes the insertion and splitting logic significantly more complex than a standard Trie.

- **Path Compression**: It merges sequences of single-child nodes into a single node with a string label. This collapses "chains" where no branching occurs, drastically reducing memory overhead.
- **Insertion Algorithm**: 
  1. Recursively find the longest common prefix between the existing key and the new key.
  2. If a mismatch occurs, **split** the existing node at the divergence point.
  3. Terminate when the entire new word is inserted.

### 1.4 Complexity Comparison: Patricia Trie vs. B+Tree
| Metric | Patricia Trie | B+Tree |
| :--- | :--- | :--- |
| **Search / Insert Time** | $\mathcal{O}(L)$ | $\mathcal{O}(\log_b N)$ |
| **Space Complexity** | $\mathcal{O}(N \times L)$ | $\mathcal{O}(N)$ |
| **Optimal Use Case** | Fast prefix / wildcard queries | Fast range / equality queries |
| **Memory Efficiency** | Highly efficient for keys with shared prefixes; poor for dissimilar keys | Consistently efficient (stores multiple keys per block) |

> **Common Confusion:** It's easy to confuse the space complexity of a B+Tree and a Patricia Trie. While a Patricia Trie is more space-efficient than a standard Trie, a B+Tree generally has lower space overhead ($\mathcal{O}(N)$) because it groups multiple keys into a single block, whereas a Patricia Trie creates a node structure tied to the length of the keys ($\mathcal{O}(N \times L)$).

> **Note:** $L$ = average key length, $N$ = total number of keys, $b$ = branching factor.

## 2. Inverted Index (Text & Search)

The **Inverted Index** is the foundational data structure for full-text search engines (e.g., Elasticsearch, Google), mapping words (terms) to the documents or positions where they appear.

### 2.1 Core Concepts

> **Intuition:** An inverted index is exactly like the index at the back of a textbook. Instead of reading the whole book to find a topic, you look up the word in the index, which tells you exactly which pages (or Document IDs) contain it.

- **Document Search**: Maps a term to a list of `DocID`s.
- **Proximity Search**: Maps a term to specific positions within a document, enabling phrase queries (e.g., "Apple" within 3 words of "Pie").
- **Underlying Structure**: Typically implemented as a Hash Table or B+Tree of terms, pointing to a "Postings List".
  ```cpp
  // Example C++ representation: Term -> DocID -> List of Positions
  std::unordered_map<std::string, std::unordered_map<int, std::vector<int>>> inverted_index;
  ```

### 2.2 Core Operations
- **`addDocument(docID, content)`**: Tokenizes content, normalizes (e.g., lowercase, stemming), and maps each term to the `docID` and its positional offset.
- **`getDocuments(word)`**: Normalizes the query and performs an $\mathcal{O}(1)$ lookup to return matching `docID`s.
- **`proximitySearch(word1, word2, k)`**: Intersects the postings lists of two words, filtering for instances where `|pos1 - pos2| <= k`.

### 2.3 Challenges & Web-Scale Architecture

> **Tradeoff:** Storing positional data enables powerful phrase and proximity searches, but massively inflates the size of the index. This requires aggressive compression techniques to keep storage costs manageable.

- **Storage Overhead**: Postings lists grow massively. **Compression** (e.g., Delta Encoding, Variable Byte Encoding) is mandatory to minimize disk I/O.
- **Distributed Search (Web-Scale)**:
  - **Sharding**: The index is partitioned across clusters. **Term-partitioning** (words distributed across servers) or **Document-partitioning** (documents distributed across servers).
  - **Replication**: Shards are duplicated for high availability.
  - **Ranking**: Post-retrieval, algorithms like **TF-IDF**, **PageRank**, or ML-based Learning-to-Rank (LTR) sort the results by relevance.

## 3. R-Tree (Multi-Dimensional Indexing)

### 3.1 Limitations of B+Trees
B+Trees are strictly 1-dimensional. They cannot efficiently answer multi-dimensional queries like "Find all restaurants within 5 miles of my $(x, y)$ location."

### 3.2 R-Tree Architecture
An **R-Tree** is a balanced search tree that clusters multi-dimensional data based on spatial proximity using **Minimum Bounding Rectangles (MBRs)**.

> **Intuition:** Imagine trying to group items on a map. An R-Tree draws a big box around all items in a state, smaller boxes around items in a city, and even smaller boxes around items in a neighborhood. To find a specific restaurant, you only check the boxes that overlap your search area.

- **Data Types**:
  - **Point**: Exact coordinate in space (e.g., `lat, long`).
  - **Rectangle (MBR)**: Defined by min/max coordinates across all dimensions.
- **Node Structure**:
  - **Leaf Nodes**: Contain actual spatial objects (points or polygons).
  - **Inner Nodes**: Contain child pointers and the MBR that perfectly encapsulates all child MBRs.
  - **Root Node**: The top-level MBR encompassing the entire dataset.

### 3.3 Core Operations
- **Insertion**: Traverses down the tree, choosing the child node that requires the **least enlargement** of its MBR to accommodate the new point.
- **Node Splitting (SEEDS Algorithm)**: When a node overflows, it must be split. A quadratic algorithm picks the two "seed" points that are farthest apart to form the basis of two new nodes, minimizing overlap.
- **Queries**:
  - **Range/Window Query**: Recursively checks if the query bounding box intersects with node MBRs.
  - **K-Nearest Neighbor (k-NN)**: Uses a priority queue ordered by distance to the MBRs to efficiently find the $k$ closest points.

## 4. ND R-Tree (High-Dimensional Indexing)

While standard R-Trees work well for 2D or 3D data, **N-Dimensional (ND) R-Trees** extend the concept to high-dimensional spaces (e.g., 512-D vectors for image embeddings).

> **Common Confusion:** The "Curse of Dimensionality" isn't just about things getting slower; it's a mathematical phenomenon where in high dimensions, the concept of "distance" breaks down because almost all points become nearly equidistant from one another. This renders bounding boxes (MBRs) almost useless as they all end up overlapping.

- **Structure**: Uses $N$-dimensional points and $N$-dimensional Hyper-rectangles.
- **The Curse of Dimensionality**: As dimensions increase, MBRs tend to overlap heavily, and empty space grows exponentially. This degrades search performance to nearly $\mathcal{O}(N)$ (linear scan).
- **Applications**: 3D collision detection, computer vision, vector search for ML embeddings.

## 5. Learned Indexes (ML-Driven Indexing)

Traditional indexes (B+Trees, Hash Tables) are generic and do not leverage the underlying data distribution. 

### 5.1 The Key Idea
A **Learned Index** replaces tree traversals with a Machine Learning model. It treats index lookup as a **regression problem**: predicting the physical array index (position) of a key based on its value.

> **Intuition:** Instead of navigating a map (a tree) to find an address, a Learned Index is like having a mathematical formula where you plug in the address and it calculates exactly where the house should be.

- **Advantages**: Faster lookups (computations instead of memory fetches), massively reduced memory footprint (no pointers or internal nodes).
- **Limitations**: Only provides *approximate* positions (requiring local search), struggles with highly volatile (frequent inserts) or randomly skewed data.

### 5.2 Learned Index via Linear Regression
Uses a **Recursive Model Index (RMI)**—a hierarchy of simple models:
- **Architecture**: A Root Model routes the key to a specific Sub-Model, which then predicts the final position.
- **Training**: Fits a linear equation ($y = mx + b$) where $x$ is the key, $y$ is the predicted position, $m$ is the slope, and $b$ is the intercept.
- **Search Process**:
  1. Root model calculates an approximate bin.
  2. Sub-model calculates the predicted position.
  3. **Neighborhood Search**: Because predictions have a known error bound, a local binary or exponential search is performed around the predicted index to find the exact key.

### 5.3 Learned Index via Neural Networks
Simple regression fails on **non-linear** data distributions (e.g., highly clustered geographical data).
- **Approach**: Uses Neural Networks with hidden layers and non-linear activation functions (e.g., ReLU, Sigmoid) to model complex CDFs (Cumulative Distribution Functions).
- **Training**: Involves Forward Passes, Loss Calculation, and Backpropagation.
- **Trade-offs**: Highly accurate for complex patterns but incurs higher latency for inference (computational cost) and larger memory overhead for storing network weights compared to simple regression.
