# Module 09: Range Queries and B+Tree Indexes

## 1. Range Query vs Point Query
Database queries generally fall into two categories when interacting with an index:
- **Point Query:** Searches for tuples where a column is equal to a single specific value (e.g., `SELECT * FROM products WHERE price = 30`).
- **Range Query:** Searches for tuples where a column falls within a range of values (e.g., `SELECT * FROM products WHERE price BETWEEN 10 AND 20`).

### The Hash Table Limitation
Hash tables are inherently unordered. While a point query on a hash table enjoys an $O(1)$ average complexity, a range query is highly inefficient. Because keys are pseudo-randomly scattered based on their hash, finding a range of values requires a full table scan ($O(N)$), defeating the purpose of an index.

> **Intuition:** A hash table is like a bucket of completely scrambled scrabble tiles. If you want to find the exact tile "Q", you can pull it out instantly if you know its spot. But if you want to find all tiles from "A" to "C", you have to dig through the entire bucket.

## 2. Ordered Index: The B+Tree Data Structure
To efficiently execute both point and range queries, databases employ ordered indexes, with the **B+Tree (Balanced Tree)** being the industry standard.

### Core B+Tree Characteristics
- **Node Hierarchy:**
  - **Root Node:** The top-level entry point of the tree.
  - **Inner (Internal) Nodes:** Contain only keys and pointers (page offsets) to child nodes. They act as "signposts" guiding the search.
  - **Leaf Nodes:** Contain the actual data (keys and their associated values, or pointers to table rows).
- **Structural Properties:**
  - **Node Capacity:** An inner node with $K$ children contains exactly $K-1$ keys. A leaf node with $K$ keys contains $K$ values.
  - **High Fan-Out:** The maximum number of children an inner node can have is large (often hundreds). This keeps the tree exceptionally shallow.
  - **Self-Balancing:** The tree dynamically balances itself during insertions and deletions, ensuring all leaf nodes remain at the exact same depth (uniform height).
- **Leaf Sibling Pointers:** Every leaf node maintains a pointer to its adjacent (next) leaf node, forming a singly or doubly linked list of strictly sorted data. This is the "plus" in B+Tree and is critical for fast range queries.

> **Mental Model:** A B+Tree is like a train system. The inner nodes are the signposts guiding you down to the right station (leaf node). Once you arrive, the leaf sibling pointers are the train tracks that let you smoothly ride through all the adjacent stations in perfect order.

### Fast Range Queries Using B+Trees
1. **Vertical Traversal ($O(\log N)$):** Traverse down from the root, following the appropriate child pointers until reaching the leaf node that contains the `lowerBound` of the query.
2. **Horizontal Traversal ($O(K)$):** Iterate sequentially through the sorted keys in the leaf node. If the end of the node is reached, follow the sibling pointer directly to the next leaf node. Continue collecting values until a key exceeds the `upperBound`.

## 3. Implementing an In-Memory B+Tree in C++

### Leveraging C++ Templates
B+Trees are typically implemented using templates to support generic key and value types safely and efficiently.
- **Type Safety:** The compiler enforces correct types at compile time.
- **Reusability:** A single `BPlusTree<Key, Value>` class can map `int -> int` (Employee ID to Salary), `std::string -> int` (Product Name to Price), or even use complex structs as composite keys.

> **Tradeoff:** C++ templates provide zero-overhead abstractions and immense flexibility, but they can significantly increase compile times and produce cryptic error messages if type constraints are violated.

### Node Structure Definition
```cpp
template <typename Key, typename Value> 
class BPlusTree {
private:
    struct Node {
        std::vector<Key> keys;
        std::vector<Value> values;                   // Only used in Leaf Nodes
        std::vector<std::shared_ptr<Node>> children; // Only used in Inner Nodes
        std::shared_ptr<Node> next = nullptr;        // Sibling pointer for Leaf Nodes
        bool isLeaf;
        
        explicit Node(bool leaf) : isLeaf(leaf) {}
    };
    
    size_t maxKeys; // Order (or degree) of the tree
    std::shared_ptr<Node> root;
    
    // ... helper methods ...
};
```

### Insertion and Node Splitting Algorithm
1. **Recursive Descent:** Traverse the tree to find the correct leaf node for insertion. Maintain a `path` stack of visited nodes to allow backtracking.
2. **Binary Search:** Within a node, use `std::lower_bound` to find the precise insertion index among the sorted keys in $O(\log(\text{maxKeys}))$ time.
3. **Insertion:** Insert the key (and value) into the leaf node.
4. **Node Splitting (If capacity `maxKeys` is exceeded):**
   - **Leaf Split:** Create a new leaf node. Move the upper half of the keys and values to the new node. Link the original node's `next` pointer to the new node.
   - **Inner Node Split:** Create a new inner node. Move the upper half of the keys and child pointers. The median key is strictly pushed *up* to the parent.
5. **Backtracking:** Pop nodes from the `path` stack to insert the median key and new child pointer into the parent node. If the parent also overflows, split it and propagate upward. If the root splits, create a new root, increasing the tree's overall height by 1.

> **Common Confusion:** Unlike Binary Search Trees which grow downwards from the leaves, B+Trees grow *upwards* from the root. A new root is only created when the old root splits in half.

## 4. On-Disk B+Tree

### The Necessity of On-Disk Structures
- **Capacity Constraints:** Databases frequently index tables that vastly exceed available DRAM.
- **Durability (Persistence):** Index structures must survive system reboots. Rebuilding a massive index on every startup is unacceptable.

### Adaptation for Disk Storage
In-memory constructs like `std::vector` or `std::shared_ptr` allocate dynamically on the heap and cannot be written directly to disk. Nodes must be redesigned using fixed-size static arrays and file offsets (Page IDs).

> **Intuition:** Think of pointers as street directions ("turn left, go two blocks"). This works when you're in the city (RAM). But if you pack up the city and move it (save to disk and load later), those directions are useless. Page IDs are like GPS coordinates—they remain valid no matter where you load the data.

```cpp
struct DiskNode {
    bool isLeaf;
    uint16_t keyCount;
    uint32_t nextLeafPageId;             // Offset for the next leaf (0 if none)
    
    Key keys[MAX_KEYS];                  // Fixed-size array for keys
    uint32_t children[MAX_KEYS + 1];     // Page IDs for child nodes (replaces pointers)
    Value values[MAX_KEYS];              // Used only if isLeaf == true
};
```
*Note: A `DiskNode` is serialized to a raw byte stream (e.g., `std::vector<uint8_t>`) before being flushed to a disk page.*

### Page Alignment and Massive Fan-Out
Disk I/O operates in fixed-size blocks called **Pages** (commonly 4 KB, 8 KB, or 16 KB). The node capacity (`MAX_KEYS`) is deliberately calculated so that one serialized `DiskNode` perfectly fills exactly one page.

- **Example Calculation:** For a 4 KB (4096 bytes) page with 32-bit integer keys and values, the node can hold approximately $M \approx 500$ keys.
- **The Power of Fan-Out:** With a fan-out of 500:
  - Level 1 (Root): 1 node
  - Level 2: 500 nodes
  - Level 3: 250,000 nodes
  - Level 4 (Leaves): 125,000,000 nodes
  - A B+Tree of just **4 levels** can index over **60 Billion keys** ($\sim 0.5$ TB of data).
  - *Result:* Finding any tuple among 60 billion requires a maximum of **4 disk reads**.

### Minimizing Disk I/O
- **Buffer Pool Caching:** The Database Buffer Manager caches frequently accessed pages in DRAM. Upper-level inner nodes (especially the Root) are almost always cached, drastically reducing physical disk reads.
- **Performance Impact:** In practice, traversing a 4-level tree often requires only 1 or 2 actual physical disk I/Os, as the top levels are already in memory.
