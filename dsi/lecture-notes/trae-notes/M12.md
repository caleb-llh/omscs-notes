## 1. Complex Predicates (Logical Trees)

### 1.1 The Need for Complex Predicates
Real-world SQL queries rarely rely on a single condition. They require compound logic combining multiple criteria (e.g., `WHERE (salary > 1000 AND age < 30) OR (title = 'Manager')`). 

### 1.2 The `IPredicate` Interface
To evaluate deeply nested conditions without hardcoding specific rules, the system employs the Composite Design Pattern via an abstract `IPredicate` interface.

```cpp
class IPredicate {
public:
    virtual ~IPredicate() = default;
    
    // Evaluates the predicate against a given tuple.
    // Returns true if the tuple satisfies the condition.
    virtual bool check(const std::vector<std::unique_ptr<Field>> &tupleFields) const = 0;
};
```

### 1.3 Implementations and Evaluation

> **Intuition:** Evaluating a complex predicate is like evaluating a mathematical expression with parentheses. You build a tree where the leaves are the simple checks (e.g., age > 30) and the branches are the logical operators (AND, OR) that combine them.

- **`SimplePredicate` (Leaf Nodes)**: Implements `IPredicate` to perform basic relational comparisons (`>`, `<`, `=`, `!=`) between two operands (Direct values or Indirect column references).
- **`ComplexPredicate` (Inner Nodes)**: Implements `IPredicate` to manage logical groupings. It contains a collection (`std::vector<std::unique_ptr<IPredicate>>`) of child predicates and a logical operator (`AND` or `OR`).

#### Recursive Evaluation Strategy
- **`AND` Logic**: The `check()` method iterates through all child predicates. **Short-circuiting** is used: if *any* child returns `false`, it immediately returns `false`. It returns `true` only if all children pass.
- **`OR` Logic**: Iterates through all child predicates. Short-circuits by returning `true` if *any* child returns `true`. Returns `false` only if all children fail.

By nesting `ComplexPredicate`s and `SimplePredicate`s, an execution engine can dynamically build and evaluate an Abstract Syntax Tree (AST) representing any `WHERE` clause.

## 2. Hash Aggregation Operator

The **Hash Aggregation Operator** handles queries requiring grouping and summarization (e.g., `GROUP BY`, `SUM()`, `COUNT()`).

```sql
SELECT Category_ID, SUM(Profit), COUNT(*) 
FROM Sales_Data 
GROUP BY Category_ID;
```

### 2.1 Operator Architecture
Because aggregation requires analyzing multiple rows before producing a single output row, it is a **Blocking Operator** (it cannot stream tuples immediately).

> **Common Confusion:** A "Blocking Operator" doesn't mean the database is frozen or deadlocked. It simply means this specific step in the pipeline must consume all of its input before it can produce its first row of output. You can't know the final SUM until you've seen every number.

```cpp
class HashAggregationOperator : public UnaryOperator {
private:
    std::vector<size_t> group_by_attrs;         // Column indices used for the GROUP BY key
    std::vector<AggrFunc> aggr_funcs;           // Aggregation operations (e.g., SUM, MIN, MAX)
    std::vector<Tuple> output_tuples;           // Materialized results
    size_t output_iterator;                     // Tracks progress during next()
};
```

### 2.2 Execution Logic

> **Tradeoff:** Hash Aggregation is generally faster than sorting the data first (Sort-Based Aggregation), but it requires enough memory to hold the entire hash table. If the number of unique groups exceeds available memory, it will "spill" to disk, severely degrading performance.

- **`open()` (The Blocking Phase)**:
  - Iterates through the *entire* input stream (calling `child->next()`).
  - Constructs an in-memory **Hash Table**.
  - **Key**: The values of the `group_by_attrs` columns.
  - **Value**: The running aggregates (e.g., current sum, current count).
- **Custom Hashing (`FieldVectorHasher`)**: Because a group key can span multiple columns (e.g., `GROUP BY City, State`), a custom hasher is required to bitwise combine (`^=`, `<<`, `>>`) the hash values of individual fields into a single, uniform hash key.
- **`updateAggregate()`**: When a tuple maps to an existing hash key, this helper function applies the aggregation math (e.g., `old_sum + new_value`) while strictly enforcing data type consistency.
- **`next()` / `getOutput()` (The Streaming Phase)**:
  - Once `open()` completes, the hash table is fully populated.
  - `next()` iterates over the hash table entries (or the materialized `output_tuples` vector), yielding one aggregated group per call until exhausted.

## 3. The Relational Operator Framework vs. Unix Pipelines

The architectural philosophy of modular query execution draws heavily from the Unix command-line pipeline (both conceptualized in the 1970s).

> **Intuition:** The Volcano model in databases and the Unix pipeline are fundamentally the same idea: take a stream of data, pass it through a series of single-purpose filters, and get a result. `SELECT * FROM users WHERE age > 30` is conceptually `cat users | grep "age > 30"`.

| Concept | Unix OS | Relational Database |
| :--- | :--- | :--- |
| **Philosophy** | "Do one thing and do it well." | Operators are highly specialized. |
| **Data Stream** | Standard Text (stdin / stdout) | Standard Tuples (`getOutput()`) |
| **Composability** | `cat data.txt \| grep "Error" \| sort` | `Scan -> Select -> Sort` |
| **Extensibility** | Easy to write new bash tools. | Easy to subclass `Operator`. |
| **Pipelining** | Data flows concurrently between tools. | Tuples flow upward via Iterator model. |

## 4. DDL Execution and Index Creation

SQL is divided into **DML** (Data Manipulation Language: `SELECT`, `INSERT`, `UPDATE`) and **DDL** (Data Definition Language: `CREATE`, `ALTER`, `DROP`). Just as DML uses operators to manipulate data, DDL uses specialized operators to manipulate the database schema and structures.

### 4.1 Create Index Executor (`CreateIndexOperator`)
When a user executes `CREATE INDEX idx_name ON table(column);`, the system invokes a dedicated operator.

> **Tradeoff:** Creating an index speeds up future queries, but the `CREATE INDEX` operation itself is expensive. It requires a full table scan and a massive number of insertions into the new index structure, which can lock the table or consume significant resources on a live system.

- **Purpose**: Populates a newly instantiated index structure (e.g., a Hash Index or B+Tree) with existing data from a table.
- **`open()` Phase**:
  - Consumes tuples from a child `ScanOperator` attached to the target table.
  - Extracts the **Key** (the column(s) being indexed) and the **Value** (typically the `TupleID` or Primary Key).
  - Invokes `index.insertOrUpdate(key, value)` to populate the index structure.
- **`next()` Phase**: Because index creation is fully completed during `open()`, calling `next()` immediately returns `false` (no tuples are yielded).
- **`getIndex()`**: A specialized method that returns a reference to the fully built index, allowing the Database Catalog to register it for future query optimization.
