# A Relational Model of Data for Large Shared Data Banks

**Author**: E. F. Codd (IBM Research Laboratory, San Jose, California)  
**Published**: Communications of the ACM, June 1970 (Volume 13 / Number 6)

---

## 1. Introduction and Motivation

> **Context:** Before 1970, databases were heavily tied to their physical storage formats (like trees or network graphs). If the physical layout changed (e.g., adding an index or moving a file), all the application code querying that data had to be rewritten. Codd's paper revolutionized this by introducing *data independence*.

Future users of large data banks must be protected from having to know how the data is organized in the machine (the internal representation). 
Activities of users at terminals and most application programs should remain unaffected when the internal representation of data is changed, or even when some aspects of the external representation are changed. Changes in data representation are often needed due to changes in query, update, and report traffic, and the natural growth in the types of stored information.

Existing noninferential, formatted data systems (like those based on tree-structured files or network models) provide inadequate data independence. This paper proposes a model based on **n-ary relations**, introduces a **normal form** for data base relations, and discusses a **universal data sublanguage**.

### 1.2 Data Dependencies in Present Systems
Present systems (circa 1970) clutter the user's model with representational properties. Three principal kinds of data dependencies need to be removed:
1. **Ordering Dependence**: Many systems require or permit data elements to be stored in at least one total ordering (often closely associated with hardware addresses). Application programs that rely on this stored ordering will fail if the ordering is changed. A clear distinction must be made between the order of presentation and stored ordering.
2. **Indexing Dependence**: Indices are redundant components used to improve query/update response time (while slowing down insertions/deletions). Application logic should remain invariant as indices are created and destroyed to adapt to traffic patterns. Some systems (like IDS) expose indexing chains to application programs, causing failures if those chains are later removed.
3. **Access Path Dependence**: Systems providing tree-structured or network models force applications to depend on the structure of trees or networks. If the tree structure changes (e.g., from "Projects subordinate to Parts" to "Parts subordinate to Projects"), previously written programs will fail because they attempt to reference nonexistent paths or files.

## 2. A Relational View of Data

> **Mental Model:** Think of a relation as a simple table. The "domains" are the column types, and the "n-tuples" are the rows. Unlike arrays in programming languages, the order of the rows does not matter, and every row must be unique (which naturally forms a mathematical set).

The relational view of data avoids superimposing any additional structure for machine representation purposes, thus yielding maximal data independence.

### Mathematical Foundations
- Given sets $S_1, S_2, \dots, S_n$, $R$ is a **relation** on these $n$ sets if it is a set of $n$-tuples where the first element is from $S_1$, the second from $S_2$, etc. 
- $S_j$ is the $j$-th **domain** of $R$.
- $R$ has **degree $n$**. (Degree 1 = unary, 2 = binary, 3 = ternary, $n$ = $n$-ary).

### Array Representation Properties
An array representing an $n$-ary relation $R$ has the following properties:
1. Each row represents an $n$-tuple of $R$.
2. The ordering of rows is immaterial.
3. All rows are distinct.
4. The ordering of columns is significant (corresponds to the ordering of domains).
5. Each column is labeled by the name of the corresponding domain.

### Relationships (Domain-Unordered Relations)
Because users shouldn't have to remember column ordering, Codd proposes using **relationships** (domain-unordered relations). Domains must be uniquely identifiable within a relation. If two or more domains are identical (e.g., `part` as a subassembly and `part` as a superassembly), the domain name is qualified by a **role name** (e.g., `sub.part`, `super.part`).

### Key Terminology
- **Active Domain**: The set of values represented in the data bank at any instant.
- **Primary Key**: A domain (or combination of domains) whose values uniquely identify each element ($n$-tuple) of a relation. It is **nonredundant** if no participating domain is superfluous.
- **Foreign Key**: A domain (or combination) that is not the primary key of its relation, but its elements are values of the primary key of some relation.
- **Simple / Nonsimple Domains**: A simple domain contains atomic (nondecomposable) values. A nonsimple domain contains relations as elements (e.g., repeating groups).

## 3. Normal Form

> **Intuition:** Normalization is the process of flattening nested data structures. Instead of having a list of items embedded inside a single customer record (which creates complex, nested, pointer-heavy structures), normalization extracts the nested list into a separate table linked by a foreign key. This creates a simple, predictable, flat, 2D tabular structure.

Relations with nonsimple domains (e.g., a repeating group inside a record) complicate data representation. They can be eliminated through **normalization**.

### Normalization Procedure
Starting at the top of a tree of nested relations:
1. Take the primary key of the parent relation.
2. Expand each immediately subordinate relation by inserting this primary key.
3. The new primary key of the subordinate relation consists of its old primary key augmented by the parent's primary key.
4. Strike out the nonsimple domains from the parent relation.
5. Repeat for each subtree.

### Advantages of Normal Form
- Simplifies array representation (a two-dimensional column-homogeneous array).
- Devoid of pointers (address-valued or displacement-valued).
- Avoids dependence on hash addressing schemes.
- Contains no indices or ordering lists.
- Simplifies data naming (e.g., `Relation.domain`).

## 4. Linguistic Aspects (Universal Data Sublanguage)

The relational model allows for a universal data sublanguage based on an applied **first-order predicate calculus**.
- **Descriptive Ability**: Users specify *what* data to retrieve, not *how* to compute it. Any qualification expression must have the descriptive power of well-formed formulas of applied predicate calculus.
- **Symmetric Exploitation**: In a relation, any combination of arguments can be used as "knowns" and the remaining as "unknowns." Tree and network models lack this symmetry, requiring users to coin many path names or use awkward nested binary expressions.
- **Expressible vs. Named Relations**: The **named set** are relations users can identify by a simple name. The **expressible set** includes all relations that can be designated by expressions in the data language (using logical connectives, quantifiers, etc.).

## 5. Operations on Relations

Since relations are sets, standard set operations apply. In addition, specific relational operations are used to derive relations:

1. **Permutation**: Interchanging columns.
2. **Projection**: Selecting certain columns and removing any duplicated rows. (Selection operator $\pi$).
3. **Join**: Combining two binary relations that have a domain in common into a ternary relation without loss of information. 
    - **Natural Join**: Denoted $R * S$. Joins elements where the common domain values match.
    - Ambiguity occurs if a joining element has multiple relatives in both relations.
    - **Cyclic and Linear 3-Joins** can be defined for multiple relations.
4. **Composition**: Taking a join of $R$ and $S$ and then projecting out the joining domain. 
    - > **Common Confusion:** The "Connection Trap" is a classic pitfall. Just because you can join `Suppliers -> Parts` and `Parts -> Projects`, it doesn't mean a specific Supplier supplies a Part *specifically* for that Project. Path-following can lead to logically false associations.
    - **Connection Trap**: Assuming that path-following (composing) through an intermediate entity correctly associates the start and end entities. This is only true if the target relation is exactly the natural composition of the other two for all time.
5. **Restriction**: A generalization of function restriction. $R$ restricted by $S$ (where domains match) is the maximal subset of $R$ whose projection matches the corresponding projection of $S$.

## 6. Redundancy and Consistency

### Redundancy in the Named Set
- **Derivability**: A relation is derivable from a set of relations if there exists a sequence of operations (projection, natural join, tie, restriction) that yields it for all time.
- **Strong Redundancy**: A set of relations contains a relation that has a projection derivable from other projections in the set (characterized by an equation). Maintained for user convenience (e.g., retaining old access paths for legacy programs).
- **Weak Redundancy**: A relation's projection is not derivable, but is at all times a projection of some join of other projections (e.g., due to business constraints). Not removable by the administrator.

### Consistency
Consistency is a property of the instantaneous state of the data bank. A state is consistent if it satisfies a set of constraint statements (derived from redundancies). 
- If a user introduces an inconsistency, the system cannot easily determine if it's an error of omission or commission without interrogating the environment.
- **Checking Approaches**: Can be done on every update (slows down operations) or as a periodic batch operation (better if non-transitory inconsistencies are rare).

## 7. Summary
The relational model protects users from disruptive changes in data representation. Normal form provides a clean, pointer-free basis. Relational operations (projection, join, composition, restriction) and concepts of redundancy allow for rigorous management of data consistency in large shared data banks.
