# What Goes Around Comes Around... And Around...

**Authors:** Michael Stonebraker, Andrew Pavlo (MIT, Carnegie Mellon University)
**Journal:** SIGMOD Record, June 2024

## 1. Introduction
Revisiting the classic 2005 paper, the authors examine the last 20 years of data modeling and query language trends. Despite repeated efforts to replace the Relational Model (RM) and SQL (such as the NoSQL movement, MapReduce, and specialized databases), the RM remains dominant. Instead of being replaced, SQL has continuously absorbed the best ideas from competing approaches. While data models have remained largely stable, significant architectural advancements have occurred in DBMS implementations driven by shifting hardware and cloud computing.

> **Intuition:** Good ideas rarely replace standard ones; instead, the standard absorbs the good ideas. SQL and the Relational Model are the "Borg" of data management—they assimilate competing paradigms.

## 2. Data Models & Query Languages

### 2.1 MapReduce Systems
- **History:** Google created MapReduce (MR) in 2003 for batch processing; Yahoo cloned it as Hadoop (HDFS).
- **Outcome:** The MR paradigm was overly restrictive, lacked schema, and suffered poor performance compared to parallel RDBMSs. Google abandoned MR for BigTable/Spanner. Hadoop vendors struggled as enterprises realized its limitations.
- **Legacy:** Brought about a revival of shared-disk architectures with disaggregated storage. Successors like Spark and Flink ultimately added SQL interfaces, proving the necessity of high-level declarative languages.

> **Common Confusion:** People often thought MapReduce was faster because it scaled to thousands of nodes. However, node-for-node, a parallel RDBMS was vastly more efficient due to indexing, schema awareness, and declarative optimization.

### 2.2 Key/Value Stores
- **Concept:** Simplest model `(key, value)`, where value is an opaque blob.
- **Outcome:** Useful for caching (Memcached, Redis) but dangerous for complex applications lacking joins and secondary indexes.
- **Legacy:** Many evolved into Document Databases. Notably, embedded KV stores are now used as underlying storage engines for full RDBMSs (e.g., RocksDB in MySQL, WiredTiger in MongoDB).

### 2.3 Document Databases (NoSQL)
- **Concept:** Stores data as hierarchical JSON documents. Initially marketed as "NoSQL" (SQL is too slow) and "BASE" (ACID transactions are unnecessary).
- **Outcome:** Essentially a repeat of 1990s Object-Oriented and XML databases. Denormalization causes data duplication and update anomalies. 
- **Legacy:** Almost all major NoSQL systems (MongoDB, DynamoDB, Cassandra) eventually added SQL-like query languages and ACID transactions. Meanwhile, the SQL standard added native JSON support, making the two approaches functionally indistinguishable.

> **Tradeoff:** NoSQL offers rapid prototyping by eliminating upfront schema design, but it pushes the complexity of data integrity and schema evolution into the application code, creating massive technical debt over time.

### 2.4 Column-Family Databases
- **Concept:** Reduces document nesting to a single level (e.g., Google BigTable, Cassandra, HBase).
- **Outcome:** Remained a niche market. Many adopted SQL frontends (Cassandra CQL, HBase Phoenix).

### 2.5 Text Search Engines
- **Concept:** Uses inverted indexes to support full-text search (Elasticsearch, Solr, Lucene).
- **Outcome:** Good for text but lack robust transactional recovery. Modern RDBMSs have added comparable full-text search, though integration can be clunky. Often deployed in a "polystore" architecture alongside an operational RDBMS.

### 2.6 Array Databases
- **Concept:** Multi-dimensional arrays for scientific, geospatial, or genomics data (SciDB, Rasdaman, TileDB).
- **Outcome:** Highly niche. RDBMSs have absorbed this via the SQL/MDA (Multi-Dimensional Arrays) standard, challenging the need for standalone array systems.

### 2.7 Vector Databases
- **Concept:** Stores single-dimension embeddings generated by ML models for Approximate Nearest Neighbor (ANN) similarity search (Pinecone, Milvus).
- **Outcome:** A current massive fad. Unlike document DBs which took years, major RDBMSs added vector indexes (e.g., pgVector) within months. Specialized vector databases will likely be absorbed into mainstream RDBMSs as a simple feature.

> **Mental Model:** A vector database is just a regular database with a specialized index (like an HNSW index) for calculating distance. It does not require a completely new database architecture.

### 2.8 Graph Databases
- **Concept:** Uses nodes and edges (Property Graphs or RDF). Used for operational (Neo4j) or analytical (Tigergraph) workloads.
- **Outcome:** RDBMSs simulate graphs easily using two tables (Nodes, Edges). Studies show RDBMSs outperforming native graph DBMSs. SQL:2023 introduced SQL/PGQ (Property Graph Queries), closing the query language gap.

## 3. System Architectures

### 3.1 Columnar Systems
- Revolutionized the OLAP (Data Warehouse) market.
- Storing data by columns (instead of rows) drastically improves compression and enables vectorized execution (processing columns via SIMD instructions). 

### 3.2 Cloud Databases
- The shift to the cloud separated compute and storage using network-attached object stores (e.g., Amazon S3).
- **Serverless computing:** Compute nodes can scale elastically per-query without reshuffling data (e.g., Snowflake). This marks a successful return to the "shared-disk" architecture.

> **Mental Model:** Think of cloud databases like a rental car service. Storage (the garage) is cheap and permanent, but compute (the car) is rented only when you need to drive (run a query).

### 3.3 Data Lakes / Lakehouses
- Instead of monolithic DBMSs hoarding data in proprietary formats, applications dump raw files into a cloud object store (Data Lake).
- **Open Formats:** Uses open-source columnar formats like Parquet, ORC, and Arrow.
- **Lakehouses:** Adds transactional middleware (Delta Lake, Iceberg, Hudi) and caching/metadata services to bring warehouse-like governance and SQL processing to the Data Lake.

### 3.4 NewSQL Systems
- Attempted to combine NoSQL horizontal scalability with SQL/ACID guarantees for OLTP workloads (e.g., VoltDB, NuoDB).
- **Outcome:** Adoption was slow because organizations are highly risk-averse with operational data. Evolved into modern Distributed SQL databases (CockroachDB, TiDB, Spanner).

### 3.5 Hardware Accelerators
- Utilizing FPGAs or GPUs to accelerate queries. 
- **Outcome:** Historically not cost-effective for enterprises. Only viable for massive cloud vendors (e.g., AWS Redshift AQUA) who can amortize custom hardware R&D costs across massive scale.

### 3.6 Blockchain Databases
- Decentralized, log-structured ledgers using BFT protocols.
- **Outcome:** An inefficient technology looking for a use case. Legitimate businesses with trust run distributed DBMSs 5 orders of magnitude faster. Even crypto exchanges run on standard RDBMSs.

## 4. Parting Comments & Future Outlook

- **Marketing vs. Engineering:** Never underestimate good marketing for bad products. Inferior products often gain traction, buying them time to fix technical debt (e.g., MongoDB, MySQL).
- **Not Invented Here:** Beware of open-source DBMSs pushed by large tech companies; they are often built by engineers lacking database expertise looking for promotions.
- **Out-of-Box Experience:** Essential for adoption (e.g., DuckDB's success). DBMSs need more "self-driving" auto-tuning capabilities.
- **ORMs:** Useful for prototyping, but developers must still know how to write raw SQL to optimize performance.
- **AI/ML Impact:** 
  - Natural Language to SQL (LLMs) is useful for analytical exploration but won't replace SQL in programmatic OLTP.
  - ML-optimized DBMS internals (learned indexes, query optimizers) are promising but don't replace high-quality systems engineering.
- **Standardization:** The community should stop rewriting standard components (parsers, buffer pools) and embrace open-source reusable components (Apache Calcite, Arrow, Velox) for a POSIX-like DBMS standard.
