## Lesson 1: Introduction to CUDA Programming

**Course Learning Objectives:**
- Write kernel code for Vector Addition.
- Explain basic CUDA programming terminologies.
- Understand the Vector Addition CUDA code example.

### 1.1 CUDA Code Example: Vector Addition

CUDA programs consist of both host code (executed on the CPU) and kernel code (executed on the GPU). The CPU sets up the environment, allocates memory, reads data, and invokes the kernel. The GPU executes the kernel, enabling parallel processing.

**Kernel Code:**
```c
__global__ void vectorAdd(const float *A, const float *B, float *C, int numElements) {
    int i = blockDim.x * blockIdx.x + threadIdx.x;
    if (i < numElements) {
        C[i] = A[i] + B[i] + 0.0f;
    }
}
```

**Host Code:**
```c
int main(void) {
    // Allocate the device input vector A
    float *d_A = NULL;
    err = cudaMalloc((void **)&d_A, size);

    // Copy the host input vectors A and B in host memory to the device input vectors in device memory
    printf("Copy input data from host memory to the CUDA device \n");
    err = cudaMemcpy(d_A, h_A, size, cudaMemcpyHostToDevice);

    // Launch the Vector Add CUDA Kernel
    vectorAdd<<<blocksPerGrid, threadsPerBlock>>>(d_A, d_B, d_C, numElements);

    // Copy the device result vector in device memory to the host result vector in host memory
    printf("Copy output data from the CUDA device to the host memory\n");
    err = cudaMemcpy(h_C, d_C, size, cudaMemcpyDeviceToHost);
}
```

When calling the kernel, arguments are passed using angle brackets (`<<<blocksPerGrid, threadsPerBlock>>>`) to define the execution configuration. Data variables (`d_A`, `d_B`, `d_C`) and constants (`numElements`) are also passed.

### 1.2 SPMD (Single Program, Multiple Data)

GPUs execute code concurrently following the SPMD paradigm. 
[![image](https://lowyx.com/assets/posts/gatech/gpu/m3l1_spmd.png)](https://lowyx.com/assets/posts/gatech/gpu/m3l1_spmd.png)

If multiple threads run the exact same instructions without distinction, they might all print the same message without any specific ordering. To perform useful work, each thread must operate on different data elements.

### 1.3 Thread Identifiers (`threadIdx.x`)

[![image](https://lowyx.com/assets/posts/gatech/gpu/m3l1_threadidx.png)](https://lowyx.com/assets/posts/gatech/gpu/m3l1_threadidx.png)

To assign different tasks to different threads, CUDA provides built-in variables like `threadIdx.x` (representing the x-axis coordinate). These unique identifiers allow each thread to operate on different elements, enabling parallel processing within a single program.

**Vector Add with Thread IDs (Simplified):**
```c
void vectorAdd(/* arguments */) {
    int idx = threadIdx.x; 
    c[idx] = a[idx] + b[idx];
}
```
[![image](https://lowyx.com/assets/posts/gatech/gpu/m3l1_threadidx_vectoradd.png)](https://lowyx.com/assets/posts/gatech/gpu/m3l1_threadidx_vectoradd.png)

In vector addition, `threadIdx.x` ensures each thread accesses a distinct pair of elements (`a[idx]` and `b[idx]`), significantly enhancing parallelism.

### 1.4 Execution Hierarchy

CUDA execution is hierarchical, extending beyond the microarchitecture concept of warps (a hardware-level group of threads executed together). 

- **CUDA Block:** A group of threads that execute concurrently. 
- Threads within the same block share a specific memory access scope.
- Due to varying memory scopes, data is divided among blocks.
- For simplicity, assume each block executes on one Streaming Multiprocessor (SM).
- **Execution Order:** There is no guaranteed order of execution among CUDA blocks.

### 1.5 Data Indexing

- **Thread Index:** `threadIdx.x`, `threadIdx.y`, `threadIdx.z`
- **Block Index:** `blockIdx.x`, `blockIdx.y`, `blockIdx.z`
- **Block Dimension:** `blockDim.x`

**Example of Indexing:**
```c
void vectorAdd(/* arguments */) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    c[idx] = a[idx] + b[idx];
}
```
[![image](https://lowyx.com/assets/posts/gatech/gpu/m3l1_data_index.png)](https://lowyx.com/assets/posts/gatech/gpu/m3l1_data_index.png)

Imagine dividing 16 vector elements into 4 blocks, each containing 4 elements. Indexes can be 1D, 2D, or 3D, easily matching physical dimensions (like images or 3D objects). To compute a globally unique index (`idx`), use the formula: `idx = blockIdx.x * blockDim.x + threadIdx.x`.

### 1.6 Memory Spaces

[![image](https://lowyx.com/assets/posts/gatech/gpu/m3l1_memory_space.png)](https://lowyx.com/assets/posts/gatech/gpu/m3l1_memory_space.png)

- **Local Memory:** Accessible only by a single thread.
- **Shared Memory (`__shared__`):** On-chip scratchpad memory managed by software. Faster than global memory but visible only within a single CUDA block. Explicit communication is needed to share data between SMs.
- **Global Memory:** Off-chip memory accessible by all threads across all blocks in a kernel.
- **Constant & Texture Memory:** Small, read-only memory primarily used in 3D graphics (e.g., storing the value of pi or 2D textures). Rarely used in general-purpose CUDA programming.

### 1.7 Shared Memory Example

[![image](https://lowyx.com/assets/posts/gatech/gpu/m3l1_sharedmemory.png)](https://lowyx.com/assets/posts/gatech/gpu/m3l1_sharedmemory.png)
*(The green dot represents on-chip storage)*

```c
__global__ void vectorAdd(int* a, int* b, int* c) {
    __shared__ int sharedMemory[N]; 
    
    // Each thread loads an element from global memory into shared memory
    int idx = threadIdx.x;
    sharedMemory[idx] = a[idx] + b[idx];
    
    // Wait for all threads in the block to finish loading
    __syncthreads();
    
    // Perform addition using data from shared memory
    c[idx] = sharedMemory[idx];
}
```

### 1.8 Execution Ordering and Synchronization

- **Threads:** Execute in an undefined order. A print statement might output thread IDs in any sequence (e.g., 4, 3, 2, 1 or 1, 3, 4, 2).
[![image](https://lowyx.com/assets/posts/gatech/gpu/m3l1_execution_order_threads.png)](https://lowyx.com/assets/posts/gatech/gpu/m3l1_execution_order_threads.png)

- **Blocks:** Also execute in any sequence (ascending, descending, or concurrently).
[![image](https://lowyx.com/assets/posts/gatech/gpu/m3l1_execution_order_blocks.png)](https://lowyx.com/assets/posts/gatech/gpu/m3l1_execution_order_blocks.png)

**Thread Synchronization (`__syncthreads()`):**
Since threads progress at different speeds, `__syncthreads()` is used to block all threads in a block until everyone reaches that point. Inter-block synchronization is generally achieved by launching separate kernels.

```c
__global__ void Kernel(){
    // work-1
    __syncthreads(); // synchronization
    // work-2
}
```

**Bulk Synchronous Parallel (BSP) Pattern:**
A typical computation pattern using shared memory:
1. Load data from global to shared memory.
2. `__syncthreads()`
3. Compute using shared memory.
4. `__syncthreads()`
5. Store results back to global memory.

[![image](https://lowyx.com/assets/posts/gatech/gpu/m3l1_usage_with_thread_sync.png)](https://lowyx.com/assets/posts/gatech/gpu/m3l1_usage_with_thread_sync.png)

### 1.9 Kernel Launch Details

[![image](https://lowyx.com/assets/posts/gatech/gpu/m3l1_kernel_launch.png)](https://lowyx.com/assets/posts/gatech/gpu/m3l1_kernel_launch.png)

Kernel launches define the grid and block dimensions:
- **Grid:** Consists of multiple blocks.
- **Block:** Consists of multiple threads.
- Total threads = `gridDim` × `blockDim`.

```c
int main() {
    // ...
    sortKernel<<<1, 1>>>(d_data, dataSize); // 1 block, 1 thread
    addKernel<<<gridDim, blockDim>>>(d_data, d_data, d_result, dataSize); 
    storeKernel<<<1, 1>>>(d_result, dataSize);
    // ...
}
```
*Note: Different kernels can use varying block/thread configurations based on the task (e.g., sorting vs. parallel addition).*

## Lesson 2: Occupancy

**Course Learning Objectives:**
- Explain the concept of occupancy.
- Determine how many CUDA blocks can run on one Streaming Multiprocessor (SM).

### 2.1 Hardware Constraints on SMs

[![image](https://lowyx.com/assets/posts/gatech/gpu/m3l2_howmanycuda.png)](https://lowyx.com/assets/posts/gatech/gpu/m3l2_howmanycuda.png)

While it's simple to assume one block per SM, multiple blocks actually coexist on a single SM. The maximum number of concurrent blocks is determined by hardware limits and kernel requirements.

### 2.2 Calculating Occupancy

Occupancy is constrained by three primary factors:
1. Number of registers used per thread.
2. Amount of shared memory allocated per block.
3. Total number of threads.

**Example Scenario:**
- **Hardware Limits:** 256 max threads, 64 KB register file, 32 KB shared memory per SM.
- **Kernel Requirements:** 32 threads/block, 2 KB shared memory/block, 64 registers/thread.

Let's calculate the block limits based on each constraint:
- **Threads:** 256 max threads / 32 threads per block = **8 blocks**
- **Registers:** 64 KB (1024 registers of 64 bytes) -> `(64 * 1024) / (64 * 32) = 32` blocks.
- **Shared Memory:** 32 KB / 2 KB per block = **16 blocks**

The final occupancy is the minimum of all constraints: **8 CUDA blocks per SM**.

### 2.3 Variables Determining Occupancy

- **Threads Per Block:** Set by the host during kernel launch (`<<<numBlocks, threadsPerBlock>>>`).
- **Registers Per Block:** Determined by the compiler based on the kernel code's complexity (unlike CPUs with fixed ISA registers).
- **Shared Memory Size:** Determined dynamically at launch or statically in code (e.g., `__shared__ int sharedMemory[1000];` uses 4,000 bytes).

### 2.4 Why Does Occupancy Matter?

Higher occupancy implies greater parallelism and better hardware utilization, which generally leads to improved performance. 

[![image](https://lowyx.com/assets/posts/gatech/gpu/m3l2_occupancy.png)](https://lowyx.com/assets/posts/gatech/gpu/m3l2_occupancy.png)

- **Case A:** 1 block/SM × 6 threads/block × 4 SMs = 24 total threads.
- **Case B:** 2 blocks/SM × 4 threads/block × 4 SMs = 32 total threads.
*Case B achieves higher utilization despite having fewer threads per block.*

### 3.1 Managing Global Memory

[![image](https://lowyx.com/assets/posts/gatech/gpu/m3l3_managing_global_mem.png)](https://lowyx.com/assets/posts/gatech/gpu/m3l3_managing_global_mem.png)
[![image](https://lowyx.com/assets/posts/gatech/gpu/m3l3_hostcode.png)](https://lowyx.com/assets/posts/gatech/gpu/m3l3_hostcode.png)

Because CPU and GPU memory are physically separate (connected via an I/O interface like PCIe), the host must explicitly manage device memory.

- `cudaMalloc`: Allocates memory on the GPU.
- `cudaMemcpy`: Transfers data between CPU and GPU (`cudaMemcpyHostToDevice` or `cudaMemcpyDeviceToHost`).
*(Note: Modern CUDA supports Unified Memory, eliminating the need for explicit copies, which is covered in later lectures.)*

## Lesson 4: Stencil Operation with CUDA

**Course Learning Objectives:**
- Write a stencil code utilizing CUDA shared memory and synchronization.

### 4.1 Recap: Stencil Operations

[![image](https://lowyx.com/assets/posts/gatech/gpu/m3l4_stencil.png)](https://lowyx.com/assets/posts/gatech/gpu/m3l4_stencil.png)

Stencil operations (e.g., averaging an element with its North, South, East, and West neighbors) are common in HPC. 
- **Data Decomposition:** Each CUDA block processes a specific geographic zone of the data.
- **Data Reuse:** Because neighbor elements overlap, a single element is read multiple times. This high reuse makes stencil operations perfect candidates for shared memory caching.

### 4.2 Using Shared Memory for Stencils

The operation follows the 3-stage BSP pattern:
1. Load data from global memory into shared memory.
2. Synchronize (`__syncthreads()`).
3. Compute the stencil operation.
4. Synchronize again (if necessary).
5. Write results back to global memory.

### 4.3 Handling Boundaries (Halo Regions)

[![image](https://lowyx.com/assets/posts/gatech/gpu/m3l4_stencil_boundaries.png)](https://lowyx.com/assets/posts/gatech/gpu/m3l4_stencil_boundaries.png)

Because shared memory is strictly per-block, computing elements at the edge of a block's assigned zone requires data from neighboring zones. 
- **Solution:** Each block must load both its assigned "inner" elements AND the necessary "boundary" elements (halo region) into shared memory. 
- This is analogous to explicit boundary communication in MPI programming.

```c
// Load data into shared memory
__shared__ float sharedInput[sharedDim][sharedDim];
int sharedX = threadIdx.x + filterSize / 2;
int sharedY = threadIdx.y + filterSize / 2;
```

### 4.4 Using Conditional Logic (If-Else) for Boundaries

CUDA kernels use standard `if-else` statements to check if a thread falls within the valid data range. If it does, it loads the actual data; if it falls outside the global image boundaries, it can pad with zeros.

**Loading Data with Boundary Checks:**
```c
if (x >= 0 && x < width && y >= 0 && y < height) {
    sharedInput[sharedY][sharedX] = input[y * width + x];
} else {
    // Handle boundary conditions by padding with zeros
    sharedInput[sharedY][sharedX] = 0.0f; 
}
```

**Performing Computations (Inner Elements Only):**
To load the extra boundary data, a block must launch more threads than the number of actual output elements it computes. Only the threads mapping to the "inner" color zone execute the math.

```c
// Apply the filter to the pixel and its neighbors using shared memory
for (int i = 0; i < filterSize; i++) {
    for (int j = 0; j < filterSize; j++) {
        result += sharedInput[threadIdx.y + i][threadIdx.x + j] * filter[i][j];
    }
}
```
*(This example uses a convolutional filter approach to simplify the code and reduce complex if-else branching during computation.)*
