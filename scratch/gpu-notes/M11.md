## Lesson 1: Live-Variable Analysis

### Learning Objectives
- Understand the concept of Liveness Analysis.
- Explore its application in register allocation.
- Identify data-flow equations and their role in the analysis.

### Overview of Live-Variable (Liveness) Analysis
Liveness analysis is a backward data-flow analysis technique used to determine which variables are "live" (i.e., hold values that may be needed in the future) at various points in a program.
- **Primary Use Case:** Register allocation. By reserving registers exclusively for live variables, compilers minimize register spilling and optimize program performance.

### Data-Flow Equations
[![image](https://lowyx.com/assets/posts/gatech/gpu/m11l1_live.png)](https://lowyx.com/assets/posts/gatech/gpu/m11l1_live.png)

Key components of the data-flow equations:
- **`defB`**: Variables defined in basic block `B` before any use.
- **`useB`**: Variables whose values may be used in block `B` before any definition.
- **Boundary Condition (`IN[EXIT]`)**: Specifies that no variables are live upon exiting the program.
- **`IN[B] = useB ∪ (OUT[B] - defB)`**: A variable is live coming into a block if it is either used before being redefined in that block, or it is live coming out of the block and not redefined within it.
- **`OUT[B] = ∪ IN[Successors]`**: A variable is live coming out of a block if and only if it is live coming into one of its successors.

Unlike reaching-definition analysis (which moves forward), liveness analysis proceeds **backward**.

### Iterative Algorithm
[![image](https://lowyx.com/assets/posts/gatech/gpu/m11l1_algo.png)](https://lowyx.com/assets/posts/gatech/gpu/m11l1_algo.png)

1. **Initialization:** Set `IN[EXIT] = 0` and initialize all other `IN` values to `0`.
2. **Iteration:** Loop through each basic block until no values change:
   - Calculate `OUT[B]` by taking the union of the `IN` values of all successors of `B`.
   - Calculate `IN[B] = useB ∪ (OUT[B] - defB)`.

### Example of Live-Variable Analysis
[![image](https://lowyx.com/assets/posts/gatech/gpu/m11l1_live_eg.png)](https://lowyx.com/assets/posts/gatech/gpu/m11l1_live_eg.png)

*(The example traces the algorithm backward from the exit node across multiple passes.)*
1. **Identify `def` and `use` sets** for each basic block (e.g., reading values = `use`, writing values = `def`).
2. **Pass 1 (Backward):** Compute `OUT` and `IN` for each block starting from the exit block (B4) back to the entry block (B1).
3. **Subsequent Passes:** Repeat the process. The iteration halts when the computed `IN` and `OUT` values match the previous pass (e.g., stopping after the third pass when it yields the same results as the second).

### Register Allocation
[![image](https://lowyx.com/assets/posts/gatech/gpu/m11l1_live_analysis.png)](https://lowyx.com/assets/posts/gatech/gpu/m11l1_live_analysis.png)

Liveness analysis directly informs register allocation:
- **Rule:** Only live variables need to reside in registers.
- **Reuse:** Once a variable is no longer live (dead), its register can be repurposed for other variables.
- **Spilling/Filling:** Since hardware typically lacks enough physical registers for all live variables, compilers must temporarily store (spill) values to memory/stack and load (fill) them back when needed. Note: PTX assumes an infinite register pool to simplify its code generation, so stack operations are usually omitted in PTX code.

### Summary: Reaching Definitions vs. Live Variables
[![image](https://lowyx.com/assets/posts/gatech/gpu/m11l1_summary.png)](https://lowyx.com/assets/posts/gatech/gpu/m11l1_summary.png)

| Feature | Reaching Definitions | Live Variables |
|---------|----------------------|----------------|
| **Domain** | Set of definitions | Set of variables |
| **Direction** | Forward | Backward |
| **Transfer Function** | `genB ∪ (x - killB)` | `useB ∪ (x - defB)` |
| **Boundary** | Initialize `OUT[ENTRY]` | Initialize `IN[EXIT]` |
| **Meet Operation** | Union (`∪`) | Union (`∪`) |

## Lesson 2: Static Single-Assignment (SSA)

### Learning Objectives
- Understand the SSA form.
- Learn the basics of converting code to SSA.
- Understand how to merge values from different paths using Phi (Φ) functions.

### What is SSA?
[![image](https://lowyx.com/assets/posts/gatech/gpu/m11l2_ssa.png)](https://lowyx.com/assets/posts/gatech/gpu/m11l2_ssa.png)

Static Single-Assignment (SSA) is an intermediate representation (IR) used for compiler optimization. It improves upon traditional def-use chains.
- **Key Property:** Each variable is assigned a value exactly once (a unique definition point).
- **Benefit:** Simplifies analysis and optimizations by eliminating the need to track multiple definitions of the same variable. For example, variables `a`, `b`, and `c` are versioned as `a1, a2`, `b1`, and `c1, c2` whenever redefined.

### Control Flow Graphs and Phi (Φ) Functions
[![image](https://lowyx.com/assets/posts/gatech/gpu/m11l2_ssa2.png)](https://lowyx.com/assets/posts/gatech/gpu/m11l2_ssa2.png)
[![image](https://lowyx.com/assets/posts/gatech/gpu/m11l2_phi_func.png)](https://lowyx.com/assets/posts/gatech/gpu/m11l2_phi_func.png)

**Challenge:** If a variable (e.g., `b`) is defined differently across multiple conditional paths, which version should a subsequent block use?

**Solution: The Φ Function**
- Merges values from different converging paths.
- Added at joint points when a variable has multiple predecessors.
- In hardware (ISA level), Φ functions can be implemented using moves, selects, or conditional moves.
- **Usage:** Each definition gets a new version, and the usage always references the latest merged version.

### SSA Conversion Example
[![image](https://lowyx.com/assets/posts/gatech/gpu/m11l2_ssa_eg.png)](https://lowyx.com/assets/posts/gatech/gpu/m11l2_ssa_eg.png)

When converting to SSA:
1. Version every definition (e.g., `a1`, `a2`, `b1`, `b2`).
2. Insert Φ functions at block entries where multiple paths converge, combining the possible incoming versions (e.g., `a3 = Φ(a1, a2)`).

### When to Insert a Φ Function?
[![image](https://lowyx.com/assets/posts/gatech/gpu/m11l2_phi_func2.png)](https://lowyx.com/assets/posts/gatech/gpu/m11l2_phi_func2.png)

To avoid generating excessive and unnecessary Φ functions, we use the **Path-Convergence Criterion**. We only insert Φ functions if multiple values actually exist on converging paths.

#### Path-Convergence Criterion
[![image](https://lowyx.com/assets/posts/gatech/gpu/m11l2_path_converge.png)](https://lowyx.com/assets/posts/gatech/gpu/m11l2_path_converge.png)

A Φ function is needed for variable `a` at node `z` if all the following are true:
1. Block `x` contains a definition of `a`.
2. Block `y` (`y ≠ x`) also contains a definition of `a`.
3. There is a non-empty path from `x` to `z`.
4. There is a non-empty path from `y` to `z`.
5. These paths do not share any common nodes other than `z` (and potentially nodes prior to the paths).

#### Applying the Criterion
[![image](https://lowyx.com/assets/posts/gatech/gpu/m11l2_path_converge2.png)](https://lowyx.com/assets/posts/gatech/gpu/m11l2_path_converge2.png)
[![image](https://lowyx.com/assets/posts/gatech/gpu/m11l2_path_converge3.png)](https://lowyx.com/assets/posts/gatech/gpu/m11l2_path_converge3.png)

- If paths converge but lack conflicting definitions of a variable, the Φ function for that variable can be safely omitted.
- Common paths leading into a join node dictate whether merging is necessary.

### Φ Functions in LLVM
[![image](https://lowyx.com/assets/posts/gatech/gpu/m11l2_llvm.png)](https://lowyx.com/assets/posts/gatech/gpu/m11l2_llvm.png)

In LLVM IR, the Φ function explicitly exists (`phi`) and acts as a standard SSA definition. During compilation to machine code, LLVM converts `phi` instructions back into conditional moves, branch logic, or standard register allocations depending on the target ISA.

## Lesson 3: Examples of Compiler Optimizations

### Learning Objectives
- Understand fundamental compiler optimization concepts.
- Explore specific techniques: Loop Unrolling, Function Inlining, and more.

### 1. Loop Unrolling
[![image](https://lowyx.com/assets/posts/gatech/gpu/m11l3_loop.png)](https://lowyx.com/assets/posts/gatech/gpu/m11l3_loop.png)
Expands a loop to execute multiple iterations sequentially within a single loop body.
- **Benefits:** Better instruction scheduling, increased vectorization opportunities, and fewer branch evaluations.
- **Implementation:** Unrolls the loop by a factor (e.g., 4). An epilogue loop handles any remaining iterations if the loop count isn't a multiple of the factor.

### 2. Function Inlining
[![image](https://lowyx.com/assets/posts/gatech/gpu/m11l3_funcinline.png)](https://lowyx.com/assets/posts/gatech/gpu/m11l3_funcinline.png)
Replaces function calls with the actual function body code.
- **Benefits:** Eliminates stack operation overhead and exposes further global optimization opportunities (inter-procedural analysis).
- **Drawbacks:** Can significantly increase binary code size due to duplication. Must be used judiciously.

### 3. Dead Code Elimination (DCE)
[![image](https://lowyx.com/assets/posts/gatech/gpu/m11l3_dce.png)](https://lowyx.com/assets/posts/gatech/gpu/m11l3_dce.png)
Identifies and removes instructions that do not affect the program's final output (e.g., variables computed but never used).
- **Benefits:** Reduces code size and improves execution speed.

### 4. Constant Propagation
[![image](https://lowyx.com/assets/posts/gatech/gpu/m11l3_cp.png)](https://lowyx.com/assets/posts/gatech/gpu/m11l3_cp.png)
Replaces variables with their known constant values at compile time.
- **Benefits:** Eliminates unnecessary variable access and often triggers subsequent optimizations (e.g., replacing `c = 5.0 * 3.0` with `c = 15.0`).

### 5. Strength Reduction
[![image](https://lowyx.com/assets/posts/gatech/gpu/m11l3_sr.png)](https://lowyx.com/assets/posts/gatech/gpu/m11l3_sr.png)
Replaces computationally expensive operations with cheaper equivalents.
- **Examples:**
  - Division by 2 → Right bit-shift.
  - Exponentiation (square) → Multiplication.

### 6. Code Motion: Loop-Invariant Instructions
[![image](https://lowyx.com/assets/posts/gatech/gpu/m11l3_cm.png)](https://lowyx.com/assets/posts/gatech/gpu/m11l3_cm.png)
Relocates instructions that do not depend on the loop's iteration (loop-invariant) to outside the loop.
- **Benefits:** The statement executes only once instead of on every iteration, reducing dynamic instruction count.
- **Loop Induction Variables:** Variables (like `i`) used to control loop iterations. Detecting these (e.g., `add.u32 r1, r1, 1` in PTX) is crucial as they often unlock further optimizations.

## Lesson 4: Divergence Analysis

### Learning Objective
- Describe static code analysis techniques used to detect warp divergence.

### Review: Divergent Branches
[![image](https://lowyx.com/assets/posts/gatech/gpu/m11l4_db.png)](https://lowyx.com/assets/posts/gatech/gpu/m11l4_db.png)
In SIMT architecture, divergent branches occur when threads within the same warp take different execution paths. 
- The hardware manages this using a SIMT stack.
- **Compiler's Role:** The compiler must identify divergent branches at compile-time to insert necessary reconvergence points (immediate post-dominators) so the warp can safely synchronize after the branch.

### Divergence Analysis and Vectorization
The concept of divergence analysis originates from traditional compiler vectorization tests (converting loops to vector code). To vectorize, the compiler must ensure all instructions execute in lock-step. GPUs inherited and adapted these algorithms. While simple `if-else` divergence is easy to detect, complex control flow with synchronization is significantly harder.

### Divergent Branches: Thread Dependency
[![image](https://lowyx.com/assets/posts/gatech/gpu/m11l4_td.png)](https://lowyx.com/assets/posts/gatech/gpu/m11l4_td.png)
A branch is divergent if its condition is dependent on the Thread ID. 
- Formally: At program point `p`, if a variable may evaluate to different values for different threads, it is thread-dependent.
- Examples: 
  - Direct dependency: `if (threadIdx.x > 5)`
  - Indirect dependency: `c = threadIdx.x; if (c > 5)`

### How to Check Thread Dependency?
[![image](https://lowyx.com/assets/posts/gatech/gpu/m11l4_check.png)](https://lowyx.com/assets/posts/gatech/gpu/m11l4_check.png)

1. **Construct a Def-Use Chain:** Track definitions and usages of Thread IDs.
2. **Data-Flow Analysis:** Use iterative searching (similar to reaching definitions) to check if a branch condition can be traced back to a Thread ID definition.
3. **Memory Dependency:** What if the branch depends on a value loaded from memory?
   - If the memory location is uniform (constant across threads), the loaded value is uniform, meaning no divergence.
   - If the memory location depends on the Thread ID (e.g., an array index), the loaded value varies, causing divergence.

**Challenge:** Overly conservative divergence analysis might flag non-divergent branches (e.g., uniformly iterating loops) as divergent. The compiler algorithm must carefully trim down false positives to avoid unnecessary performance overhead.
