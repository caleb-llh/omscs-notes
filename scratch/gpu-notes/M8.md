## Module 8 Lesson 1: GPU Cycle Level Simulation (Part 1)

**Course Learning Objectives:**
* Describe cycle-level performance modeling for CPUs and GPUs
* Explain queue-based performance modeling
* Describe the basic simulation code structures for CPUs and GPUs
* Get ready for the architecture modeling programming project

### Performance Modeling Techniques
Several methods exist for evaluating processor performance:
* **Cycle-level simulation**: Highly detailed, modeling events cycle by cycle.
* **Event-driven simulation**: Driven by events rather than a global clock.
* **Analytical model**: Uses mathematical formulas to estimate performance based on first-order design parameters.
* **Sampling-based techniques**: Simulates representative portions of execution.
* **Database statistical and ML modeling**: Builds models based on collected data and statistics.
* **FPGA-based emulation**: Hardware-accelerated modeling.

### Cycle-Level Simulation Fundamentals
A cycle-level simulator maintains a global clock. In each cycle, microarchitectural events (e.g., instruction fetch, decode) are modeled. Simulators can also feature multiple clock domains (e.g., processor clock, memory clock, NoC clock).

#### Execution-Driven vs. Trace-Driven Simulation
* **Execution-Driven**: Instructions are executed dynamically during the simulation.
  * *Execute-at-Fetch*: Instructions execute as soon as they are fetched.
  * *Execute-at-Execute*: Instructions execute at the simulated execution stage.
  * *Pros*: No need to store traces; naturally captures runtime-dependent behavior (e.g., locks, barriers).
* **Trace-Driven**: Replays pre-recorded instruction traces.
  * *Pros*: Simpler, lighter, and easier to develop. Useful for isolating specific subsystems (e.g., memory-only or cache-only simulation).
  * *Cons*: Cannot accurately model dynamic behaviors like lock contention.

### Queue-Based Modeling
[![image](https://lowyx.com/assets/posts/gatech/gpu/m8l1_queue.png)](https://lowyx.com/assets/posts/gatech/gpu/m8l1_queue.png)

Pipeline stages are frequently modeled using queues. Instructions move between queues (acting as pipeline buffers) in a FIFO manner.
* **Scheduler**: An exception to FIFO; it selects instructions from a pool of ready candidates based on dependencies and resources.
* **Parameterization**: 
  * **Queue depth** models pipeline stage latency.
  * **Instructions transferred per cycle** models pipeline width (e.g., issue/execution bandwidth).
  * **Instruction latencies** (e.g., 1 cycle for ADD, 3 for MUL) are provided as parameters, often derived from literature or detailed RTL/CACTI models. They don't require circuit-level simulation during architecture modeling.

### CPU & GPU Modeling Mechanics

#### 5-Stage CPU Processor Modeling
[![image](https://lowyx.com/assets/posts/gatech/gpu/m8l1_cpu_processor.png)](https://lowyx.com/assets/posts/gatech/gpu/m8l1_cpu_processor.png)

Simulators like MacSim use hierarchical modules. The main function initializes parameters and loops through `run_a_cycle()` until completion. Inside `macsim::run_a_cycle()`, cycles are incremented, and it cascades to CPU, memory, and NoC cycle runs.

[![image](https://lowyx.com/assets/posts/gatech/gpu/m8l1_example.png)](https://lowyx.com/assets/posts/gatech/gpu/m8l1_example.png)

* **Instruction Tracking**: An `op` data structure represents each instruction, tracking its progress through the pipeline (fetch, decode, schedule, execute, write-back, retire).
* **Done Cycle**: The scheduler calculates when an instruction will finish (`schedule_time + instruction_latency`). For variable latencies (e.g., cache misses), cache models dynamically determine the delay.
* **Scheduler Role**: Enforces resource constraints (e.g., FPUs, load/store queues, ports) to ensure resources are available for the entire multi-cycle latency before issuing instructions.

#### GPU Cycle-Level Modeling
GPU simulation shares CPU concepts but centers on **warps** instead of individual threads to capture SIMT execution.
* Fetch, decode, schedule, and execution are modeled per warp.
* Schedulers issue instructions from the heads of active warps (in-order within a warp, out-of-order across warps).
* **Major Differences**: Must handle divergent warps, SIMT stacks, coalesced memory, and the Warp/Thread Block/Kernel hierarchy.

#### End of Simulation
[![image](https://lowyx.com/assets/posts/gatech/gpu/m8l1_end.png)](https://lowyx.com/assets/posts/gatech/gpu/m8l1_end.png)

The simulator tracks the completion of individual threads. When all threads in a CUDA block finish, the block retires. When all blocks finish, the kernel ends, and when all kernels end, the application terminates.

## Module 8 Lesson 2: GPU Cycle Level Simulation (Part 2)

**Course Learning Objectives:**
* Describe advanced GPU cycle-level modeling techniques such as divergent warps, coalesced memory
* Introduce several open source GPGPU simulators

### Advanced GPU Modeling Unit
Because the modeling unit is a warp, not all threads in it may be active simultaneously. The simulator must maintain **mask bits** to track thread activity and accurately model resource usage.

#### Divergent Branches
[![image](https://lowyx.com/assets/posts/gatech/gpu/m8l2_divergent.png)](https://lowyx.com/assets/posts/gatech/gpu/m8l2_divergent.png)

When threads within a warp take different paths, the SIMT stack handles divergence.
* **Execution-Driven**: Can faithfully implement and simulate the SIMT stack dynamically.
* **Trace-Driven**: Relies heavily on how traces were captured. The trace must encode the mask bits for each basic block path (e.g., BB #1 has `1111`, BB #2 has `1100`, BB #3 has `0011`, merging back at BB #4 as `1111`) to properly simulate reconvergence. Changing divergence mechanisms is challenging without new traces.

#### Memory Coalescing Modeling
[![image](https://lowyx.com/assets/posts/gatech/gpu/m8l2_memory_coalescing.png)](https://lowyx.com/assets/posts/gatech/gpu/m8l2_memory_coalescing.png)

Merging memory requests is critical for accurately modeling memory transactions and bandwidth.
* **Coalesced**: Contiguous memory accesses by a warp merge into a single cache line request.
* **Uncoalesced**: Scattered accesses generate multiple independent cache line requests.
* **Trace-Driven Implications**: Traces can pre-coalesce requests to save space (e.g., saving just the base address and size), but this bakes in a specific cache line size. Changing line sizes requires generating new traces. Saving individual addresses offers flexibility but inflates trace size.

#### Cache Hierarchy & Sectored Caches
[![image](https://lowyx.com/assets/posts/gatech/gpu/m8l2_cache_hierarchy.png)](https://lowyx.com/assets/posts/gatech/gpu/m8l2_cache_hierarchy.png)

After coalescing, requests flow through TLBs, L1, and L2 caches depending on the architecture.

[![image](https://lowyx.com/assets/posts/gatech/gpu/m8l2_sector_cache.png)](https://lowyx.com/assets/posts/gatech/gpu/m8l2_sector_cache.png)

Modern GPUs heavily utilize **sectored caches**, fetching only necessary chunks (sectors) of a cache block rather than the whole line (e.g., a 16-byte sector of a 64-byte line).
* *Pros*: Significantly reduces memory bandwidth for uncoalesced accesses.
* *Cons*: Reduces spatial locality.

### GPU Simulators
[![image](https://lowyx.com/assets/posts/gatech/gpu/m8l2_gpu_sim.png)](https://lowyx.com/assets/posts/gatech/gpu/m8l2_gpu_sim.png)

Several open-source simulators exist:
* **GPGPU-Sim**: Execution-driven, highly popular, models NVIDIA PTX/SASS.
* **Accel-Sim**: Trace-driven (from GPGPU-Sim authors), targets NVIDIA and accelerators.
* **MGPU-Sim**: Execution-driven, models AMD GPUs, supports multi-GPU setups.
* **MacSim**: Trace-driven, models NVIDIA/Intel GPUs and heterogeneous computing.
* **Gem5-GPGPU-Sim**: Combines Gem5 (CPU) and GPGPU-Sim for full heterogeneous execution-driven simulation (supports AMD/NVIDIA).

## Module 8 Lesson 3: Analytical Models of GPUs

**Course Learning Objectives:**
* CPU and GPU cycle level simulation techniques are reviewed.
* Analytical model provides the first order of processor design parameters or application performance analysis.
* CPI computation was reviewed.
* Roofline was introduced.
* Compute bounded or memory bandwidth bounded is the most critical factor.

Analytical models provide rapid, first-order performance insights without full program execution, simplifying the vast design space.

### First-Order GPU Architecture Design
Imagine designing an accelerator for a vector dot product (`sum += x[i] * y[i]`) aiming for 1 Tera-operations per second (1T FMA/sec).
* **Compute Needs**: 1T FMA/sec. At 2 GHz, this requires 500 FMA units.
* **Memory Needs**: 2 bytes read per FMA = 2 TB/sec bandwidth.

[![image](https://lowyx.com/assets/posts/gatech/gpu/m8l3_arch1.png)](https://lowyx.com/assets/posts/gatech/gpu/m8l3_arch1.png)

* **SM Configuration Options**:
  * 16 SMs × 1 warp/cycle (assuming warp width = 32)
  * 8 SMs × 2 warps/cycle
  * Both yield ~500 FMA units. Fewer, larger SMs allow larger shared caches, whereas more, smaller SMs split resources finer.

[![image](https://lowyx.com/assets/posts/gatech/gpu/m8l3_arch2.png)](https://lowyx.com/assets/posts/gatech/gpu/m8l3_arch2.png)

#### Multithreading Hardware Constraints (W_width and W_depth)
To hide memory latency, GPUs rely on massive multithreading.
* **W_width**: Threads executing per cycle (e.g., 32). Dictated by ALU count and scheduler width.
* **W_depth**: Max unique warps schedulable during a stall cycle. Dictated by register file size and PC capacity.

[![image](https://lowyx.com/assets/posts/gatech/gpu/m8l3_arch3.png)](https://lowyx.com/assets/posts/gatech/gpu/m8l3_arch3.png)

*Finding W_depth:* If memory latency is 200 cycles, and an application has 1 compute per 1 memory instruction, `W_depth` needs to be 100 warps (200 / 2) to hide the stall fully. If it does 4 computes per memory instruction, `W_depth` only needs to be 40 warps (200 / 5).

#### Sub-core Architecture
[![image](https://lowyx.com/assets/posts/gatech/gpu/m8l3_subcore.png)](https://lowyx.com/assets/posts/gatech/gpu/m8l3_subcore.png)

Modern SMs are partitioned into sub-cores. Each sub-core has its own PC, decoder, and warp scheduler, but they share the SM's I-cache and larger shared caches.

### Roofline Model
[![image](https://lowyx.com/assets/posts/gatech/gpu/m8l3_roffline.png)](https://lowyx.com/assets/posts/gatech/gpu/m8l3_roffline.png)

A visual tool determining if an application is compute-bound or memory-bound.
* **X-Axis**: Arithmetic Intensity (FLOPs per byte accessed).
* **Y-Axis**: Performance (FLOPs/sec).
* *Example*: `sum += x[i] * y[i]` requires 1 FLOP per 2 bytes (Intensity 0.5) → **Memory-bound** (Blue region).
* *Example*: `sum += x[i]*x[i]*y[i]*y[i]` requires 4 FLOPs per 2 bytes (Intensity 2.0) → **Compute-bound** (Yellow region).

### CPI (Cycle per Instruction) Computation
Average CPI models sustainable performance plus penalties from events (assumed serialized):
`Average CPI = CPI_steady_state + sum(Frequency_event * CPI_event)`

*Example*: 5-stage in-order CPU (`CPI_steady` = 1). Branch mispredict penalty is 3 (2% frequency), Cache miss penalty is 5 (5% frequency).
`Average CPI = 1 + (0.02 * 3) + (0.05 * 5)`

#### CPI for Multi-threading
For multithreading, ideal CPI is scaled by `W_depth`:
`CPI_MT = (CPI_single / W_depth) + Resource_Contentions`
Resource contentions include MSHRs, busy ALUs, and DRAM bandwidth limits.

#### Interval-Based Modeling
[![image](https://lowyx.com/assets/posts/gatech/gpu/m8l3_interval_based.png)](https://lowyx.com/assets/posts/gatech/gpu/m8l3_interval_based.png)

Extends CPI by defining execution in "intervals" between long-latency miss events. It accounts for pipeline drain and refill times rather than abrupt stalls.
* **GPU Adaptation**: To work for GPUs, interval models must account for **branch divergence** (serialized execution paths) and **memory divergence** (varying latencies from uncoalesced accesses). Advanced models also incorporate sub-core architectures and sectored caches.

## Module 8 Lesson 4: Accelerating GPU Simulation

**Course Learning Objectives:**
* Describe techniques to accelerate simulation speed
* Identify challenges in cycle-level simulation
* Explore techniques for accelerating simulation
* Describe sampling based techniques

### Challenges of Cycle Level Simulation
Cycle-level simulation is incredibly slow. Simulating 1 second of real machine time (at 1 KIPS) can take 28 hours. Simulating complex ML workloads would take the equivalent of a century of real-world time.

### Accelerating Simulations
We can either make the simulator faster or reduce the workload being simulated.

#### 1. Making the Simulator Faster
* **Parallelizing the Simulator**: Assigning cores to threads.
  * *Challenge*: Serializing shared memory and communication structures bottlenecks scaling.
  [![image](https://lowyx.com/assets/posts/gatech/gpu/m8l4_psim.png)](https://lowyx.com/assets/posts/gatech/gpu/m8l4_psim.png)
* **Event-Driven Simulation**: Skipping idle cycles and processing a queue of events. Highly effective for long-latency operations (e.g., NVM storage).
  [![image](https://lowyx.com/assets/posts/gatech/gpu/m8l4_esim.png)](https://lowyx.com/assets/posts/gatech/gpu/m8l4_esim.png)
* **Simplifying Models**: Abstracting non-critical components. For example, assuming a fixed memory latency to focus on core pipeline design, or simplifying the pipeline to focus on memory behavior (e.g., z-sim).

#### 2. Sampling Techniques
[![image](https://lowyx.com/assets/posts/gatech/gpu/m8l4_sample.png)](https://lowyx.com/assets/posts/gatech/gpu/m8l4_sample.png)

Simulating representative fractions of execution.
* **Phase Detection (SimPoint)**: Identifying repeating high/low IPC phases and simulating only representative slices. Requires handling state warm-up (caches, predictors).
* **GPU-Specific Sampling**: Because GPU threads are short-lived, sampling is done at the hierarchy level:
  * *Block-level*: Simulating 100 blocks instead of thousands.
  * *Kernel-level*: Simulating 1-2 kernels instead of tens (highly effective for repetitive ML training loops).
  * *Warp-level*: Reducing the number of simulated warps.

#### 3. Reducing Workloads
* **Reduce Iterations**: Running 1 ML training epoch instead of 1000.
* **Reduce Input Size**: Traversing a 1-million node graph instead of 1-billion.
* **Kernel Focus**: Isolating the 1 or 2 kernels that consume 90% of execution time.

#### 4. Data-Driven Modeling
[![image](https://lowyx.com/assets/posts/gatech/gpu/m8l4_ddm.png)](https://lowyx.com/assets/posts/gatech/gpu/m8l4_ddm.png)

Using ML or statistics to build predictive performance equations.
1. Run application to collect features (instruction count, memory accesses, divergence metrics) via hardware counters or fast simulation.
2. Fit data to an analytical model. Example:
   `Cycles = C1*(Insts)^e1 + C2*(FP_Insts)^e2 + C3*(Mem_Insts)^e3`
3. Use the trained model to rapidly predict performance based on collected features.
