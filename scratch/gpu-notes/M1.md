### What is a GPU?

While Graphics Processing Units (GPUs) initially gained prominence for rendering 3D graphics, they have since evolved into highly versatile parallel processors. Today, they are the backbone of machine learning (ML) acceleration and high-performance computing (HPC).

The key distinction between CPUs and GPUs lies in their design goals:
* **CPUs (Central Processing Units):** Tailored for single-threaded applications aiming for minimum latency (maximum speed per task). They dedicate significant hardware to control logic and precise exceptions, which are crucial for operating system (OS) stability and debugging. CPUs act as the **host** system.
* **GPUs:** Excel at maximizing throughput via massive parallelism. They handle thousands of threads simultaneously. They do not prioritize precise exceptions, relying instead on the host CPU for OS and I/O operations, functioning purely as an **accelerator**.

### GPU Instruction Set Architecture (ISA)

The Instruction Set Architecture (ISA) defines the hardware-software interface.
* **CPU ISAs** (e.g., x86, ARM) are typically public and open, ensuring broad software compatibility across different hardware platforms.
* **GPU ISAs** operate in an accelerator mode and are often closed. A driver translates generic code into the specific hardware ISA. To provide a stable programming target, NVIDIA introduced **PTX** (Parallel Thread Execution), a virtual, public ISA.

| Feature | CPU | GPU |
| :--- | :--- | :--- |
| **Target Application** | Latency-sensitive applications | Throughput-sensitive applications |
| **Support Precise Exceptions?** | Yes | No |
| **System Role** | Host | Accelerator |
| **ISA** | Public / Open | Open / Closed |
| **Programming Model** | SISD / SIMD | SPMD |

### Parallel Execution Models

To understand modern processing, it helps to distinguish between different execution models:
* **SISD (Single Instruction, Single Data):** Sequential processing typical of early single-core CPUs.
* **SIMD (Single Instruction, Multiple Data):** 
  * *Analogy:* A group of chefs in a kitchen, all performing the identical chopping motion (instruction) on different vegetables (data) at exactly the same time.
  * *Strengths:* Excellent for data-parallel tasks with repetitive operations on independent data elements (e.g., image processing, vector calculations).
  * *Limitations:* Requires data with a consistent structure and struggles with branching/conditional logic due to lockstep execution.
* **SPMD (Single Program, Multiple Data):**
  * *Analogy:* A team of artists, each working on a different section of the same painting (program) using their own techniques and pace (data).
  * *Strengths:* More flexible than SIMD. It can handle diverse tasks with branching and conditional logic. It is widely used for complex workflows and distributed computing.
  * *Limitations:* Can incur overhead due to thread management and communication needs.

While CPU programming primarily centers around single-threaded (SISD) or single-data operations, GPU programming relies heavily on the **SPMD** model to emphasize parallelism.

**Learning Objective:** Describe CPU design and techniques used to improve CPU performance.

[![image](https://lowyx.com/assets/posts/gatech/gpu/m1l2_cpupipeline.png)](https://lowyx.com/assets/posts/gatech/gpu/m1l2_cpupipeline.png)

### The 5-Stage CPU Pipeline

The foundation of CPU design revolves around a five-stage pipeline:
1. **Fetch (Front-End):** Instructions are fetched from the Instruction Cache (I-cache).
2. **Decode:** The instruction is translated. (For example, a single complex x86 instruction may generate multiple simpler micro-operations or "uops"). Registers are read after decoding.
3. **Schedule / Rename:** The scheduler selects which instructions to execute. 
   * *In-order processors* schedule strictly based on program order.
   * *Out-of-order processors* select any ready instruction, bypassing stalled ones to maximize hardware utilization.
4. **Execute:** The execution unit performs the actual mathematical computation or memory access.
5. **Write-Back:** The result is written back to the register file.

### Increasing Execution Parallelism

#### 1. Instruction Level Parallelism (ILP)
Superscalar processors enhance CPU performance by fetching, decoding, and executing more than one instruction per cycle, effectively achieving an Instructions Per Cycle (IPC) greater than 1. This increases **Instruction Level Parallelism (ILP)**.

[![image](https://lowyx.com/assets/posts/gatech/gpu/m1l2_ilp.png)](https://lowyx.com/assets/posts/gatech/gpu/m1l2_ilp.png)

How many instructions can run simultaneously if a machine has two execution units?
* **Independent Instructions:** Can be executed concurrently, fully utilizing both units (improving ILP).
* **Dependent Instructions:** If Instruction #2 requires the result of Instruction #1, they must execute sequentially, limiting ILP.
* *Out-of-order execution* helps improve ILP by dynamically finding independent instructions to execute while others wait on dependencies.

#### 2. Clock Frequency & Caches
* **Deeper Pipelines:** Breaking the pipeline into smaller, faster stages allows for higher clock frequencies. However, this requires highly accurate branch prediction to avoid costly pipeline flushes.
* **Larger Caches:** Reduces cache misses, significantly cutting down expensive memory access times.

#### 3. Multi-threading
[![image](https://lowyx.com/assets/posts/gatech/gpu/m1l2_multi_thread.png)](https://lowyx.com/assets/posts/gatech/gpu/m1l2_multi_thread.png)

Multi-threading increases parallelism by maintaining the context of multiple threads simultaneously. If one thread stalls (e.g., waiting for memory), the CPU quickly switches to another thread, exposing more instructions that might be ready to execute. This requires minimal additional hardware resources and is a foundational concept heavily utilized in high-performance GPUs.

#### 4. Multiprocessors (Multi-core)
[![image](https://lowyx.com/assets/posts/gatech/gpu/m1l2_cpu_gpu.png)](https://lowyx.com/assets/posts/gatech/gpu/m1l2_cpu_gpu.png)

Scaling the total number of cores in a system is a straightforward and powerful way to increase overall throughput. This technique is ubiquitous in both CPUs and GPUs today.

### Amdahl’s Law

Amdahl's Law quantifies the theoretical performance boost achievable by parallelizing a task across multiple processors. The formula is:

$$ \text{Speedup} = \frac{1}{S + \frac{P}{N}} $$

Where:
* **P** = Parallelizable fraction of the code
* **S** = Serial (non-parallelizable) fraction of the code ($S = 1 - P$)
* **N** = Number of processors

[![image](https://lowyx.com/assets/posts/gatech/gpu/m1l3_amdahllaw.png)](https://lowyx.com/assets/posts/gatech/gpu/m1l3_amdahllaw.png)

**Implications:** When serial sections are minimal, performance scales almost linearly with the number of processors. However, if even a small serial fraction exists (e.g., 10%), it becomes a rigid bottleneck, severely capping the maximum possible speedup regardless of how many processors you add. Writing effective parallel programs requires minimizing serial sections.

### Task vs. Data Decomposition

When parallelizing a workload, you must decide how to divide the work:

1. **Task Decomposition:** 
   * Different cores execute different operations (e.g., Core A calculates the sum, Core B calculates the min/max).
   * The same data array must be broadcasted/sent to both cores.
   * [![image](https://lowyx.com/assets/posts/gatech/gpu/m1l3_taskdecompose.png)](https://lowyx.com/assets/posts/gatech/gpu/m1l3_taskdecompose.png)

2. **Data Decomposition:**
   * Cores perform the exact same operation, but on different segments of the data.
   * A final reduction operation is often needed to combine the results.
   * [![image](https://lowyx.com/assets/posts/gatech/gpu/m1l3_datadecompose.png)](https://lowyx.com/assets/posts/gatech/gpu/m1l3_datadecompose.png)

### Flynn’s Classical Taxonomy

[![image](https://lowyx.com/assets/posts/gatech/gpu/m1l3_flynn.png)](https://lowyx.com/assets/posts/gatech/gpu/m1l3_flynn.png)

* **SISD:** Single Instruction, Single Data
* **SIMD / SIMT:** Single Instruction, Multiple Data / Threads
* **MISD:** Multiple Instruction, Single Data
* **MIMD:** Multiple Instruction, Multiple Data

**CPU vs. GPU Execution:**
* CPUs can be SISD, SIMD (via vector processing units), and MIMD (via multi-core processing).
* GPUs are typically **SIMT (Single Instruction, Multiple Threads)** architectures, leveraging many ALUs.

### The SPMD / SIMT Relationship
* **SPMD (Single Program, Multiple Data)** is a software programming style. All threads run the *same* program, but work on *different* data, effectively utilizing Data Decomposition.
* **SIMT (Single Instruction, Multiple Threads)** is the hardware execution model that efficiently runs SPMD programs on the GPU.

#### A Simple CUDA Example
In a CUDA program, the code executing on the GPU is called a *kernel*. The snippet below demonstrates SPMD programming. Every thread executes the exact same `vector_sum` function, but uses its unique thread ID to calculate the correct index, thus operating on different data in parallel.

```cpp
__global__ void vector_sum(float* A, float* sum) { 
    // Differentiate work by thread ID
    int index = threadIdx.x; 
    sum[index] += A[index]; 
} 
```

## Module 1 Lesson 4: Introduction to GPU Architecture

**Learning Objectives:**
* Gain a high-level understanding of GPU architecture.
* Describe key terms including "Streaming Multiprocessors" (SM), "Warp", and "Wave-front".

### GPU Architecture Overview

[![image](https://lowyx.com/assets/posts/gatech/gpu/m1l4_gpuarch.png)](https://lowyx.com/assets/posts/gatech/gpu/m1l4_gpuarch.png)

A GPU is composed of numerous cores that work in harmony to handle complex tasks.
* **Streaming Multiprocessors (SM):** The equivalent of a "core" in CPU terms, referred to as an SM (NVIDIA) or SIMT multiprocessor. An SM contains an instruction cache, decoder, shared memory, and multiple execution units.
* **Stream Processors (SP) / SIMT Lanes:** These are the actual Arithmetic Logic Units (ALUs) inside the SM. While marketing materials often call these "GPU cores", in this course, we strictly refer to them as SIMT lanes or Stream Processors to avoid confusion with CPU cores.

### The GPU Execution Pipeline

[![image](https://lowyx.com/assets/posts/gatech/gpu/m1l4_gpupipeline.png)](https://lowyx.com/assets/posts/gatech/gpu/m1l4_gpupipeline.png)

1. **Fetch:** Work items are fetched. Massive register files are used to maintain the state of thousands of threads simultaneously. 
2. **Decode & Read:** Instructions are decoded and necessary register values are read.
3. **Schedule / Scoreboarding:** Schedulers (e.g., round-robin or greedy schedulers that factor in cache misses or branch predictions) select ready execution units.
4. **Execute & Write-Back:** Selected units are executed, and results are written back.

### Execution Unit: Warps & Wave-fronts

In this course, **Warp** (NVIDIA terminology) and **Wave-front** (AMD terminology) are used interchangeably. 
* A warp is the fundamental unit of execution on a GPU, consisting of a group of threads. 
* A single instruction is fetched per warp, and that instruction is executed simultaneously across all threads in the warp (SIMT execution). 
* Historically, the **warp size** has remained constant at **32 threads**.

[![image](https://lowyx.com/assets/posts/gatech/gpu/m1l4_gpuwarp.png)](https://lowyx.com/assets/posts/gatech/gpu/m1l4_gpuwarp.png)

**How Warp Scheduling Works:**
Programmers specify a large number of threads for a kernel. The hardware groups these threads into warps. When the source operands for a given instruction are ready, the entire warp executes across the SIMT lanes. If one warp stalls (e.g., waiting on memory), the hardware scheduler instantly swaps it out and executes a different, ready warp. 

[![image](https://lowyx.com/assets/posts/gatech/gpu/m1l4_gpuwarp2.png)](https://lowyx.com/assets/posts/gatech/gpu/m1l4_gpuwarp2.png)
*(For example, if 12 threads are spawned and the warp size is 4, the hardware executes them as three distinct warps of 4 threads, one warp at a time).*

## Module 1 Lesson 5: Historical Trends of GPU Architectures

**Learning Objectives:**
* Describe the evolution of GPUs and traditional 3D graphics pipelines.

### The Traditional 3D Graphics Pipeline

[![image](https://lowyx.com/assets/posts/gatech/gpu/m1l5_trad3dpipeline.png)](https://lowyx.com/assets/posts/gatech/gpu/m1l5_trad3dpipeline.png)

* **Early Pipelined GPUs:** Initially, GPUs were strictly fixed-function hardware designed to process 3D primitives through distinct stages: Geometry Processing $\rightarrow$ Vertex Processing $\rightarrow$ Pixel Processing.
* **Programmable Shaders:** Over time, these fixed-function units became programmable (Vertex and Pixel Shaders).
* **Unified Architecture & GPGPU:** Eventually, discrete vertex and pixel units were replaced by a unified, programmable shader architecture (e.g., NVIDIA's Tesla architecture). This marked the dawn of **GPGPU** (General Purpose computing on GPU), allowing developers to write generic code (CUDA) for the GPU.
* **Modern Expansion:** Today, the "GPGPU" moniker is largely redundant, as GPUs are inherently general-purpose accelerators utilized across diverse fields, particularly Machine Learning.

### Programmable GPU Architecture Evolution

To support increasingly complex workloads, programmable GPU architectures have continuously evolved:
* **Memory Hierarchies:** Addition of L1 and L2 caches to lower latency.
* **Precision Variability:** Expanded from standard FP32 to **FP64 (Double Precision)** for strict high-performance computing (HPC) scientific applications.
* **Specialized Operations:** Integration of atomic and fast integer operations to support diverse computing algorithms.
* **High Bandwidth Memory (HBM):** Adopted to provide unprecedented data transfer rates, feeding the massive parallel compute engines.
* **Machine Learning Optimizations:** 
  * Adoption of smaller, faster floating-point formats (e.g., **FP16**) to increase parallelism for ML training and inference.
  * Integration of **Tensor Cores** for accelerated matrix multiplication.
  * Integration of **Transformer Cores** specifically tuned for modern ML workloads like Large Language Models (LLMs).

### Case Study: NVIDIA H100 (2023)

The NVIDIA H100 represents the cutting edge of modern GPU architecture, featuring:
* Support for a wide spectrum of precisions: FP64, FP32, FP16, FP8, and INT8.
* Next-generation Tensor Cores and a newly introduced **Transformer Engine** to meet the immense computational demands of modern ML applications.
* Massive increases in register file capacity, Stream Multiprocessors (SMs), and floating-point execution units.
* Advanced data-movement mechanisms like the Tensor Memory Accelerator (TMA).
* Utilization of the **NVIDIA NVLink** switch system to tightly interconnect multiple GPUs, drastically increasing system-level parallelism.
