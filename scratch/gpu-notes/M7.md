## Lesson 1: GPU Virtual Memory

Virtual memory is an essential component of modern programmable GPUs, enabling complex memory systems like the Unified Virtual Address Space.

### 1. Address Translation Fundamentals
In a CPU system, the OS manages page allocations. In a GPU system, the CPU and GPU driver historically collaborate to manage pages via functions like `cudaMalloc` (allocation) and `cudaMemcpy` (transfer). 

When programmers write code using **Virtual Addresses (VA)**, these must be mapped to **Physical Addresses (PA)**. Key terms include:
* **VPN (Virtual Page Number)**: Mapped to the **PFN (Physical Frame Number)**.
* **Page Offset (PO)**: Remains unchanged during translation. 
* Standard page sizes are typically **4 KB** or **2 MB**.

[![image](https://lowyx.com/assets/posts/gatech/gpu/m7l1_translation.png)](https://lowyx.com/assets/posts/gatech/gpu/m7l1_translation.png)

### 2. TLB and Page Tables
* **Translation Look-aside Buffer (TLB)**: A cache that stores recently used address translations to accelerate memory accesses.
* **Page Table Entry (PTE)**: Stores the mapping from VPN to PFN. Since PTEs reside in memory, accessing them directly is slow; the TLB mitigates this.
* **TLB Miss**: Requires a slower page table access to fetch the translation.
* **Page Fault**: Occurs when a physical page has not yet been allocated, prompting the OS to allocate one.

#### Multi-Level Address Translation
Modern architectures (x86, ARM, GPUs) use a **4-level address translation** hierarchy. Without levels, a 48-bit VPN space would require trillions of table entries stored in memory. By dividing the index across 4 levels, the system only needs to store active routing tables, drastically reducing memory overhead to thousands of entries.
* **The "Page Walk"**: A translation must traverse through the 4 levels (L4 → L3 → L2 → L1) to find the final PTE. This requires at least four memory accesses. 
* **Page Table Walker (PTW)**: A hardware unit that performs this traversal.

[![image](https://lowyx.com/assets/posts/gatech/gpu/m7l1_fourleveltlb.png)](https://lowyx.com/assets/posts/gatech/gpu/m7l1_fourleveltlb.png)

### 3. GPU-Specific Virtual Memory Characteristics
Early GPUs lacked virtual memory or used basic 1-to-1 mappings. Modern GPUs use translation mechanisms similar to CPUs, but with a critical addition: **Address Coalescing**.
* Typically, **L1 cache** accesses use virtual addresses, while **L2 cache** accesses use physical addresses.

[![image](https://lowyx.com/assets/posts/gatech/gpu/m7l1_gpu_vm.png)](https://lowyx.com/assets/posts/gatech/gpu/m7l1_gpu_vm.png)

#### Memory Coalescing & TLB Accesses
When memory accesses within a warp are **coalesced**, multiple threads accessing the same page generate only a single TLB request. 
* **Uncoalesced Accesses**: If threads access disparate pages, the hardware generates separate TLB accesses for each distinct page. For a warp of 32 threads, a single uncoalesced memory instruction could generate up to 32 separate TLB requests.

[![image](https://lowyx.com/assets/posts/gatech/gpu/m7l1_memcoalsece.png)](https://lowyx.com/assets/posts/gatech/gpu/m7l1_memcoalsece.png)

### 4. Challenges and Optimizations in GPU Address Translation

**The Main Challenge: Scalability**
Uncoalesced accesses can trigger a massive spike in TLB misses. A high-bandwidth Page Table Walker (PTW) shared across multiple Streaming Multiprocessors (SMs) is often required to handle this load.

[![image](https://lowyx.com/assets/posts/gatech/gpu/m7l1_challenges.png)](https://lowyx.com/assets/posts/gatech/gpu/m7l1_challenges.png)

**Techniques to Reduce Translation Costs:**
1. **Segment Mapping**: Assigns contiguous virtual address spaces to specific programs. Translation simply involves appending a program ID to the upper bits, significantly reducing cost.
2. **Multi-level TLB Hierarchies**: Adds L1/L2 TLBs to catch more translations before triggering a page walk.
3. **Large Pages (e.g., 2 MB instead of 4 KB)**:
   * *Pros*: Reduces the number of VPN bits and TLB entries required, improving hit rates.
   * *Cons*: Increases **memory fragmentation**. Allocating a small array might waste nearly 2 MB of space.

[![image](https://lowyx.com/assets/posts/gatech/gpu/m7l1_solutions.png)](https://lowyx.com/assets/posts/gatech/gpu/m7l1_solutions.png)
[![image](https://lowyx.com/assets/posts/gatech/gpu/m7l1_largepages.png)](https://lowyx.com/assets/posts/gatech/gpu/m7l1_largepages.png)

## Lesson 2: GPU Virtual Memory & UVA

This section explores how memory spaces are unified between the CPU and GPU, moving away from explicit manual management.

### 1. The Legacy "Copy-Then-Execute" Model
Historically, programmers managed global memory explicitly:
* Allocate memory on the GPU (`cudaMalloc`).
* Manually transfer data from CPU to GPU (`cudaMemcpy`) before kernel execution.
* *Pros*: Maximizes PCI-E bandwidth efficiency via bulk transfers.
* *Cons*: High programming complexity; developers must manually orchestrate all memory movement.

[![image](https://lowyx.com/assets/posts/gatech/gpu/m7l2_cudahost.png)](https://lowyx.com/assets/posts/gatech/gpu/m7l2_cudahost.png)

### 2. Unified Virtual Address Space (UVA)
UVA (or Shared Virtual Memory - SVM) places the CPU and GPU in the same logical address space. 
* Programmers use `cudaMallocManaged` to allocate memory accessible by both processors.
* The system relies on **dynamic, on-demand page allocation** instead of explicit manual copies.

[![image](https://lowyx.com/assets/posts/gatech/gpu/m7l2_uva.png)](https://lowyx.com/assets/posts/gatech/gpu/m7l2_uva.png)

### 3. On-Demand Memory and Page Faults
In discrete GPUs, the CPU and GPU still have physically separate memories. UVA requires the system to handle data migration dynamically.
* **Page Fault Handling**: When the GPU accesses an unmapped UVA page, it triggers a page fault. The request is routed to the CPU's OS and GPU driver, which allocate the page and migrate the data. This round-trip over PCI-E can cause latency in the tens of milliseconds.

[![image](https://lowyx.com/assets/posts/gatech/gpu/m7l2_page_fault_handling.png)](https://lowyx.com/assets/posts/gatech/gpu/m7l2_page_fault_handling.png)

**The Role of the IOMMU:**
* The **Input-Output Memory Management Unit (IOMMU)** bridges peripheral devices and the MMU, enabling Direct Memory Access (DMA) using virtual addresses. 
* Both the CPU and GPU have IOMMUs. Under UVA, the CPU actively collaborates with the GPU's IOMMU to manage memory.

### 4. Overcoming On-Demand Overhead
The overhead of retrieving page mappings via the CPU's IOMMU and interrupt handlers is severe. Several techniques mitigate this:

[![image](https://lowyx.com/assets/posts/gatech/gpu/m7l2_challenge_ondemand.png)](https://lowyx.com/assets/posts/gatech/gpu/m7l2_challenge_ondemand.png)

#### Memory and Page Prefetching
Instead of waiting for a fault, the system predicts and fetches data in advance.
* **Memory Prefetching**: Fetching sequential memory addresses (e.g., array indices in a vector addition).
* **Page Prefetching**: Fetching sequential pages. However, since GPU thread blocks execute concurrently and out-of-order, sequential page prediction is often inaccurate.

[![image](https://lowyx.com/assets/posts/gatech/gpu/m7l2_pretech.png)](https://lowyx.com/assets/posts/gatech/gpu/m7l2_pretech.png)
[![image](https://lowyx.com/assets/posts/gatech/gpu/m7l2_preteching.png)](https://lowyx.com/assets/posts/gatech/gpu/m7l2_preteching.png)

#### Tree-Based Neighborhood Prefetching
To handle the out-of-order execution of thread blocks, NVIDIA uses a tree-based strategy:
* A 2 MB chunk is divided into two 1 MB sections, which are further subdivided into 64 KB nodes.
* A page fault triggers the fetch of an entire 64 KB node.
* If multiple 64 KB nodes fault, the system dynamically scales up the prefetch size to the 1 MB parent node. This captures spatial locality while preventing excessive unnecessary fetches.

[![image](https://lowyx.com/assets/posts/gatech/gpu/m7l2_treebase.png)](https://lowyx.com/assets/posts/gatech/gpu/m7l2_treebase.png)

#### GPU Memory Oversubscription
Allocating more virtual memory than the physical GPU memory capacity leads to frequent page evictions. Prefetching algorithms must carefully balance bringing new pages in against evicting useful pages, making oversubscription a major performance bottleneck.

## Lesson 3: GPU Warp Scheduling

When multiple warps are ready to execute in a Streaming Multiprocessor (SM), the **Warp Scheduler** decides which warp proceeds.

[![image](https://lowyx.com/assets/posts/gatech/gpu/m7l3_pipeline.png)](https://lowyx.com/assets/posts/gatech/gpu/m7l3_pipeline.png)

### 1. CPU vs. GPU Scheduling
* **CPU Instruction Scheduler**: Analyzes a pool of instructions and schedules based on policies like "oldest first" or "critical instruction first" (e.g., prioritizing loads or instructions with many dependencies to unblock future work).
* **GPU Warp Scheduler**: Uses an **in-order** execution model per warp but interleaves instructions from multiple ready warps. The overall instruction stream appears out-of-order.

[![image](https://lowyx.com/assets/posts/gatech/gpu/m7l3_instruction.png)](https://lowyx.com/assets/posts/gatech/gpu/m7l3_instruction.png)
[![image](https://lowyx.com/assets/posts/gatech/gpu/m7l3_gpu_schedule.png)](https://lowyx.com/assets/posts/gatech/gpu/m7l3_gpu_schedule.png)

### 2. Core Warp Scheduling Policies: RR vs. GTO
* **Round-Robin (RR)**: Cycles evenly through all active warps. 
  * *Drawback*: If all warps hit a memory instruction simultaneously, they will all stall at the same time waiting on cache misses. This prevents latency hiding.
* **Greedy-Then-Oldest (GTO)**: Runs the oldest warp continuously until it hits a long-latency event (like a cache miss, branch, or tensor operation), then switches to the next oldest warp.
  * *Advantage*: Staggers memory requests, allowing the processor to hide the memory latency of the first warp while executing instructions from the second.

[![image](https://lowyx.com/assets/posts/gatech/gpu/m7l3_rr_gto.png)](https://lowyx.com/assets/posts/gatech/gpu/m7l3_rr_gto.png)

### 3. Two-Level Scheduling
Probing all warps every cycle to check readiness consumes immense power. 
* **Solution**: Divide warps into **Active** and **Pending** queues. The scheduler only evaluates and schedules from the smaller active pool, significantly improving energy efficiency.

[![image](https://lowyx.com/assets/posts/gatech/gpu/m7l3_two_lvl.png)](https://lowyx.com/assets/posts/gatech/gpu/m7l3_two_lvl.png)

### 4. Impact on Cache and Working Set Size
Scheduling decisions directly affect L1 cache performance. 
* **Round-Robin Issue**: If the cache capacity is smaller than the combined working set of all warps, RR causes **thrashing**. By the time warp 1 runs again, its data has been evicted by warps 2, 3, and 4.
* **GTO Advantage**: By letting one warp run to completion (or stall), its working set remains in the cache, yielding primarily compulsory misses rather than thrashing.

**Working Set Size Formula**: 
If each warp requires $SS\_W$ cache, and $N$ warps run concurrently:
* Under RR, the working set is $SS\_W \times N$.
* Under a limited scheduler with $SW$ active warps, the working set drops to $SS\_W \times SW$.

[![image](https://lowyx.com/assets/posts/gatech/gpu/m7l3_cache_behavior.png)](https://lowyx.com/assets/posts/gatech/gpu/m7l3_cache_behavior.png)

### 5. Advanced Scheduling Policies

#### Cache-Conscious Wavefront Scheduling (Rogers 2012)
This policy artificially limits the number of actively scheduled warps to fit within the cache capacity. 
* It selects a subset of warps (e.g., 1-3) to run. Only when they finish does it schedule warp 4. 
* *Trade-off*: Decreases cache thrashing but restricts warp-level parallelism. It also requires careful handling to prevent deadlocks if warps rely on thread synchronization.

[![image](https://lowyx.com/assets/posts/gatech/gpu/m7l3_cache_conscious.png)](https://lowyx.com/assets/posts/gatech/gpu/m7l3_cache_conscious.png)

#### Other Schedulers
* **Prefetching-Aware Scheduler**: Integrates with the two-level scheduler to fetch data from non-consecutive warps, enhancing memory bank-level parallelism.
* **CTA-Aware Scheduling**: Prioritizes scheduling based on Cooperative Thread Array (CTA) boundaries to improve resource utilization.
